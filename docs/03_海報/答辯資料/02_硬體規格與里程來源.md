# 硬體規格與里程來源（海報 ④ 層的展開）

> 海報上只寫「LDS-01 雷射雷達 │ 輪子編碼器 │ OpenCR + Dynamixel 馬達」。
> 最容易被追問的是：**「你怎麼知道輪子轉了幾度、走了多遠？」**

---

## 一、TurtleBot3 Burger 硬體一覽

| 部位 | 型號 | 關鍵規格 |
|---|---|---|
| 主控電腦 | Raspberry Pi（3B+ / 4） | 跑 ROS Noetic、gmapping、move_base、我們的 `map_server.py` |
| 嵌入式控制板 | **OpenCR 1.0** | STM32F746（ARM Cortex-M7, 216 MHz），板載 IMU，負責讀馬達、算里程、驅動輪子 |
| 驅動馬達 | **Dynamixel XL430-W250-T ×2** | 智慧型伺服馬達，內建**磁性絕對編碼器**、減速機、控制器；TTL、Protocol 2.0 |
| 雷射雷達 | **LDS-01**（HLS-LFCD2） | 360°、5 Hz（300 rpm）、360 束（1°/束）、量測範圍 0.12–3.5 m |
| 輪子 | — | 半徑 **0.033 m**（直徑 66 mm），左右輪距 **0.160 m** |
| 車體 | — | 138 × 178 × 192 mm，約 1 kg，最大線速度 0.22 m/s、角速度 2.84 rad/s |
| 電池 | LiPo 11.1 V 1800 mAh | 約 2.5 小時 |

**注意用詞**：Burger 上**沒有獨立的編碼器零件**。編碼器是 Dynamixel 馬達內部的一部分。海報寫「輪子編碼器」不精確。

## 二、「轉了幾度、走了多遠」的完整鏈路

```
Dynamixel XL430 內建磁性編碼器（12-bit，4096 ticks / 輸出軸一圈）
        │  Present_Position（ticks）
        │  TTL, Dynamixel Protocol 2.0
        ▼
OpenCR 1.0  ── 韌體 turtlebot3_core.ino ──
        │  tick → 弧度 → 距離 → 差速運動學 → 位姿積分
        │  USB 序列（rosserial 協定）
        ▼
Raspberry Pi ── rosserial_python / serial_node.py（節點名 turtlebot3_core）
        │
        ├─ /odom          nav_msgs/Odometry      累積位姿 + 速度
        ├─ /joint_states  sensor_msgs/JointState 左右輪角度（弧度）← 「轉了幾度」看這裡
        └─ TF: odom → base_footprint
```

**關鍵觀念**：ROS 端沒有任何一個套件在算里程，`rosserial` 只是**傳聲筒**。真正的換算發生在 OpenCR 的韌體裡。

## 三、換算公式（Burger 參數，能寫在白板上）

```
編碼器解析度   4096 ticks / 圈
TICK2RAD      = 2π / 4096 = 0.001533981 rad/tick   (= 0.0879°/tick)
WHEEL_RADIUS  = 0.033 m
WHEEL_SEPARATION = 0.160 m

單輪轉角  θ  = ticks × TICK2RAD
單輪距離  s  = θ × WHEEL_RADIUS
車體位移  Δs = (s_left + s_right) / 2
車體轉角  Δφ = (s_right − s_left) / WHEEL_SEPARATION

位姿積分  x ← x + Δs·cos(φ)
          y ← y + Δs·sin(φ)
          φ ← φ + Δφ
```

**好記的數字**：

- 1 tick ≈ **0.0506 mm**（0.033 × 0.001534）
- 輪子轉一整圈 = 4096 ticks = **0.207 m**（2π × 0.033）
- 原地轉 360°：兩輪各走 π × 0.160 ≈ 0.503 m ≈ 9930 ticks

## 四、一個容易被抓的細節：θ 可能不是編碼器算的

TurtleBot3 官方韌體的 `calcOdometry()` 裡，**前進距離取自編碼器，但車體朝向 θ 是從 OpenCR 板載 IMU 的姿態四元數取出來的**，編碼器差值只用來算位移。這樣做是因為差速輪打滑時，用兩輪差算出來的轉角誤差比 IMU 大。

這會依韌體版本而異，**現場想確認就做這個實驗**：

```bash
rostopic echo /odom/pose/pose/orientation     # 一邊看
# 把機器人抬起來原地空轉輪子 → yaw 有變 = 編碼器有參與
# 把機器人整台平移旋轉（輪子不轉）→ yaw 有變 = IMU 有參與
```

## 五、LiDAR 那條線（順帶，常一起被問）

| 項目 | 值 | 怎麼證明 |
|---|---|---|
| 掃描頻率 | 約 5 Hz | `test/test_lidar_freq.py` 實測平均 Hz |
| 有效距離 | 驅動宣告 0.12–3.5 m | `test/test_lidar_range.py` 印出 `range_min/range_max`，並統計實際量到的最遠有效值 |
| 光束數 | 360（1°/束） | 同上工具印出 `len(msg.ranges)` |
| 超出範圍 | 回傳 `inf` | `map_server.py` 第 338 行用 `rmin <= r <= rmax` 過濾，同時排除 inf/nan |

> **這兩支工具是加分項**：代表你們不是照抄規格書，而是實測驗證過。被問「你怎麼知道是 3.5 公尺」→ 「我們寫了工具實測，把目標物往後移，看正前方距離何時跳成 inf」。

## 六、里程的先天問題（先講先贏）

`/odom` 是**純推算（dead reckoning）**：打滑、輪徑製造誤差、地面不平都會累積，走越久偏越多，而且**永遠不會自己修正**。

所以：

1. gmapping 用雷射掃描匹配算出 `map → odom` 這條 TF，把累積誤差吸收掉。
2. 覆蓋路徑的路點一律用 **`map` 座標系**（`map_server.py` 第 204 行取 `map_data['frame_id']`），不是 `odom`——這樣就算 odom 漂了，目標點在地圖上還是同一個地方。
3. 網頁上的行走軌跡是直接畫 `/odom` 的位置（`odom_callback`），所以**軌跡本身會有漂移**，它是「機器人自認為走過的路」，不是絕對真值。這點被問到要老實說。
