# 預想問答（口試前看這份）

> 答法原則：**先給一句結論，再給一個理由或數字，然後停**。
> 不確定的就說「這部分我們沒有實測」——比硬掰安全太多，評審通常追問一句就過。

---

## A. 定位問題（你到底做了什麼）

**Q1. 這個題目有現成的套件，為什麼要自己寫？**
ROS 生態裡有導航（move_base）、有 SLAM（gmapping），但**沒有現成、可直接用的完全覆蓋路徑規劃**。move_base 只回答「從 A 走到 B」，不回答「怎麼走才能不重複地走遍整個房間」。那條全覆蓋路線、以及把它逐點餵給 move_base 的排程、容錯、中止機制，都是我們寫的。

**Q2. 那你的貢獻具體是什麼？三句話。**
①用 PCA 讓掃描線自動對齊房間長軸，不受地圖朝向影響；②把演算法與 ROS 完全解耦（`coverage_planner.py` 不 import rospy，可獨立測試）；③做了一套免安裝、手機就能看的即時網頁監控，七個圖層可切換。

**Q3. 你的東西跟掃地機器人有什麼不同？**
原理同一類，但商用掃地機是封閉系統。我們這套是開放、模組化的：換演算法不用改 UI，換 UI 不用改演算法，可以拿來教學或當研究基底。

## B. PCA 相關（主打賣點，一定會被問）

**Q4. 為什麼需要 PCA？不能直接沿地圖 x 軸掃嗎？**
可以，但效果差。地圖座標系的方向是**機器人開機當下的朝向**決定的，跟牆面完全無關。房間一旦跟地圖軸有夾角，掃描線末端就被牆切成階梯狀鋸齒，轉彎次數暴增、邊角容易漏。PCA 讓環境自己決定方向。

**Q5. PCA 具體怎麼算？**
取所有可走格的座標，去中心化後算 2×2 共變異數矩陣，做特徵分解。最大特徵值的特徵向量就是自由空間變異最大的方向 = 房間長軸，當掃描方向；正交的那個是短軸，當換行方向。（推導見 [04_演算法數學細節.md](04_演算法數學細節.md)）

**Q6. 房間是正方形，PCA 不就沒有主軸了？**
對，正方形的兩個特徵值幾乎相等，主軸方向會不穩定。但**正方形的兩個方向本來就等價**，掃哪一個方向效率一樣，所以不影響結果。真正會出問題的是 L 形那種非凸空間（見 Q7）。

**Q7. 如果房間是 L 形呢？**
會退化。PCA 算的是全體點的平均方向，對 L 形的某一支不是最佳，可能出現長距離空跑。標準解法是先做 boustrophedon cell decomposition 把空間切成多個凸胞元，各自規劃後再用 TSP 排順序——這是我們列的第一項未來工作，目前的系統定位在單一凸空間。

**Q8. 特徵向量差一個負號也是合法解，會不會每次規劃方向都跳？**
會，所以我們有固定符號：`if axis_a[0] < 0: axis_a = -axis_a`。沒有這兩行的話每次重新規劃路徑起點會左右亂跳。

## C. 覆蓋與路徑

**Q9. 為什麼掃描間距是 0.18 m？**
機器人覆蓋寬度約等於車寬 0.20 m，取 0.18 是刻意留 **10% 重疊**。若剛好取 0.20，定位一有誤差相鄰兩條線之間就會留一條沒掃到的縫。

**Q10. 怎麼證明真的「完全」覆蓋？**
**老實說：我們目前沒有量化覆蓋率的機制。** 現在的證據是視覺上的——網頁上把規劃路徑與實際行走軌跡疊在地圖上，可以看出有沒有漏。量化覆蓋率指標是我們寫在未來工作裡的項目。

**Q11. 路點順序是最佳的嗎？**
不是。我們用的是固定的 S 形順序（一條掃完接著回頭走下一條），沒有做全域最佳化。牛耕式的 S 形本身在單一凸空間裡已經接近最優，但多區域情況需要 TSP，這是未來工作。

**Q12. 一條掃描線只有兩個路點，中間不會撞到東西嗎？**
兩點之間交給 move_base 走，它有自己的 local costmap 和 DWA 即時避障，會閃開途中的新障礙。我們的責任是保證**路點本身**落在安全區（膨脹過的可走格）。

**Q13. 為什麼路點少比較好？**
每個路點是一次 action goal，有送出、等待、判定的成本。路點少 → 動作連續、不會走走停停。

## D. 安全邊距 / 膨脹（最容易被抓的一題）

**Q14. 你的膨脹半徑是多少？**
要先問是哪一個，系統裡有**三個獨立的膨脹**：
① 規劃用安全邊距 `MARGIN = 0.10 m`（5×5 核）——**真的影響路徑**；
② 網頁顯示的侵蝕／膨脹圖層，固定 3×3 核跑 2 次——**純視覺參考，不影響規劃**；
③ move_base 自己的 costmap inflation（預設 1.0 m）——與前兩者完全獨立。

**Q15. 為什麼是膨脹障礙，不是縮小機器人？**
數學上等價（Minkowski 和），但膨脹障礙只要對地圖做一次形態學運算就好，之後所有規劃都能把機器人當成點來算，程式簡單很多。

**Q16. 未知區域（−1）算可走嗎？**
不算。判斷式是 `free = (data == 0) & ~safe`，只有明確是空地的格才可走。這是保守設計：地圖還沒建到的地方不會被排進路徑。

## E. ROS 與系統整合

**Q17. 為什麼用 action 不用 topic 送目標？**
導航是「需要時間、要回報進度、可能失敗、要能取消」的任務，這正是 action 的設計場景。用 topic 送目標的話，你不知道到了沒、也沒辦法取消。

**Q18. move_base 走到一半到不了怎麼辦？**
`run_coverage()` 檢查 action 的狀態碼，不是 `SUCCEEDED` 就記一筆 warning（`路點 i/N 跳過`）然後**繼續下一點**，不會整個任務卡死。代價是那一小塊可能沒覆蓋到——這是我們選的取捨：寧可漏一點也要跑完全程。

**Q19. 「停止」按鈕怎麼做到即時？**
覆蓋執行在獨立執行緒，每 0.5 秒檢查一次共享的 `cov_status['state']`，發現不是 `running` 就 `cancel_all_goals()` 並退出。所以最慢 0.5 秒生效。

**Q20. 多執行緒共用資料不會出問題嗎？**
用了四把 `threading.Lock`（`map_lock`、`robot_lock`、`cov_lock`、`scan_lock`）分別保護地圖、機器人狀態、覆蓋狀態、雷射資料。ROS callback 執行緒寫、Flask 執行緒讀，都要先拿鎖。

**Q21. 為什麼網頁不用 rosbridge / roslibjs？**
那需要前端額外載入函式庫、也多一個節點。我們直接在節點裡跑 Flask，把資料轉成 PNG 和 JSON，前端純 HTML+Canvas，**手機開瀏覽器就能用，不用裝任何東西**。代價是輪詢（1 Hz / 雷射 5 Hz）而非推播。

**Q22. gmapping 為什麼不用 Cartographer？**
gmapping 是 TurtleBot3 官方預設，2D 雷射 + 差速輪的標準組合，資源需求小、Raspberry Pi 跑得動。Cartographer 精度較好但參數多、CPU 吃重。我們的重點在覆蓋規劃，SLAM 取穩定可用即可。

**Q23. 那個在 `test/` 的 `boustrophedon.py` 是什麼？**
早期的獨立規劃節點，會發布 `/coverage_path` 給 RViz 看。後來規劃改由 `map_server.py` 直接呼叫 `coverage_planner`，它就變成純檢視工具，所以移到 `test/`、不隨 launch 啟動，避免重複規劃。

## F. 硬體

**Q24. 怎麼知道輪子轉了幾度、走了多遠？**
編碼器在 Dynamixel XL430 馬達裡（12-bit 磁性絕對編碼器，4096 ticks/圈，0.0879°/tick）。OpenCR 控制板讀 `Present_Position`，用輪半徑 0.033 m 換算成距離、輪距 0.160 m 換算成轉角，積分成位姿後透過 rosserial 傳上來變 `/odom`。**ROS 端沒有任何套件在算里程，只是傳聲筒。**（細節見 [02](02_硬體規格與里程來源.md)）

**Q25. odom 會漂移吧？**
會，它是純推算，打滑和輪徑誤差會累積且不會自我修正。所以 gmapping 用雷射匹配算出 `map→odom` 這條 TF 把誤差吸收掉，而且我們的路點一律用 `map` 座標系而非 `odom`。網頁上的行走軌跡是直接畫 odom，所以那條軌跡本身是有漂移的。

**Q26. LiDAR 只有 3.5 公尺，會不會不夠？**
對這個題目夠。覆蓋規劃吃的是 gmapping 建好的 `/map`，不是即時雷射；3.5 m 對室內單一房間的建圖足夠。我們有寫 `test/test_lidar_range.py` 實測驗證這個上限。

## G. 開放性問題

**Q27. 這個系統的極限在哪？**
三個：①非凸空間會退化（無區域分解）；②沒有量化覆蓋率；③要先有一份建好的地圖才能規劃，不能邊探索邊覆蓋。三個都在未來工作裡。

**Q28. 如果再給你三個月，你會先做什麼？**
先做**區域分解 + TSP 排序**，因為它一次解掉「非凸空間退化」和「路點順序非最佳」兩個問題，價值最高。其次是覆蓋率指標，因為沒有量化就沒辦法證明改善。
