## 1. 專案是什麼？要解決什麼問題

**目標**：讓一台 TurtleBot3 Burger 機器人，在一個封閉空間（例如一個房間）裡，**走遍每一個角落**——也就是「完全覆蓋路徑規劃」(Complete Coverage Path Planning, **CCPP**)。

這類問題的日常例子就是**掃地機器人**：它不是要從 A 點走到 B 點（那是一般導航），而是要**把整塊地面都掃過一遍**，而且最好不要重複、不要漏掉。

本專案採用的覆蓋策略是**牛耕式 (Boustrophedon)**——名稱來自古希臘「牛犁田」的走法：一條線走到底，轉個彎，再平行走回來，像耕田時牛來回的路線一樣（也就是英文寫字機常見的「S 形來回」）。

```
→ → → → → → →
              ↓
← ← ← ← ← ← ←
↓
→ → → → → → →
```

**整個系統還附帶一個網頁介面**，可以即時看到：地圖、機器人位置、走過的軌跡、規劃出來的覆蓋路徑，並用按鈕一鍵「開始 / 停止」任務。

## 2. 背景知識速成

要看懂這個專案，需要先認識幾個 ROS / 機器人領域的名詞：

| 名詞 | 一句話解釋 |
|------|-----------|
| **ROS (Noetic)** | 機器人作業系統。本質是一套「讓很多程式（節點）彼此傳訊息」的框架。 |
| **節點 (Node)** | 一個獨立執行的程式。本專案有 `map_server`、`boustrophedon_planner`、`move_base` 等節點。 |
| **話題 (Topic)** | 節點之間傳訊息的「頻道」。發布者 publish、訂閱者 subscribe。 |
| **`/map`** | 一張地圖，型別是 `OccupancyGrid`（佔據網格）。 |
| **`/odom`** | 里程計，機器人自己估計的位置，型別 `Odometry`。 |
| **SLAM / gmapping** | 邊走邊建地圖 + 同時定位的技術。本專案用 gmapping 產生 `/map`。 |
| **OccupancyGrid** | 把空間切成一格一格，每格存一個值：`0`=空地、`100`=障礙、`-1`=還沒探索過。 |
| **move_base** | ROS 的導航堆疊，負責「給它一個目標點，它自己避障走過去」。 |
| **DWA** | move_base 用的局部路徑規劃器（Dynamic Window Approach），負責即時避障。 |
| **TF** | 座標轉換系統，記錄各座標系（map、odom、機器人）之間的關係。 |

**佔據網格長怎樣？** 想像一張方格紙覆蓋在房間地板上，每一格記錄那塊地是「空的、有牆、還沒看過」。整張地圖就是一個二維陣列。

### 2.1 ROS 的核心觀念：節點 + 話題 + 訊息

ROS 最關鍵的一個想法是：**不要把整個機器人寫成一支大程式，而是拆成許多小程式（節點），它們彼此之間靠「傳訊息」溝通。**

- **節點 (Node)**：一支獨立執行的程式，各做各的事。本專案啟動後，`rosnode list` 會看到 `map_server`、`boustrophedon_planner`、`move_base`、`gmapping`… 同時在跑。每個節點啟動時都會先「報到」，例如 `map_server.py` 的第一行：
  ```python
  rospy.init_node('map_server')   # 跟 ROS 系統註冊「我叫 map_server」
  ```
- **話題 (Topic)**：節點之間的「廣播頻道」，每個頻道有名字（如 `/map`、`/odom`）和固定的訊息型別。
- **訊息 (Message)**：在話題上流動的資料，型別是事先定好的結構，例如 `OccupancyGrid`（地圖）、`Odometry`（位置）、`Path`（路徑）。

打個比方：話題像 **YouTube 頻道**，發布者是「上傳影片的人」，訂閱者是「按了訂閱的人」。**發布者和訂閱者彼此不認識、不需要知道對方是誰**——只要約好頻道名稱和影片格式（訊息型別）就能溝通。這種「解耦」是 ROS 能輕鬆組合不同模組的關鍵。

### 2.2 Publish（發布）—— 用 `boustrophedon.py` 當例子

「發布」就是把一則訊息丟到某個話題上，誰想看誰自己訂閱，發布者不管。

本專案的 `boustrophedon.py`（規劃節點）就是一個發布者：它算出覆蓋路徑後，發布到 `/coverage_path` 話題給 RViz 顯示。流程分兩步：

**第 1 步：開張一個發布者**（`boustrophedon.py:65`）

```python
_pub = rospy.Publisher('/coverage_path', Path, queue_size=1, latch=True)
#                       └ 話題名稱        └ 訊息型別  └ 佇列長度   └ 鎖存
```

- `'/coverage_path'`：要發布到哪個頻道。
- `Path`：這個頻道只能流動 `nav_msgs/Path` 型別的訊息（一串帶姿態的路點）。
- `queue_size=1`：來不及送出的訊息最多排隊 1 則，多的丟掉（路徑只要最新版，舊的沒意義）。
- `latch=True`：**鎖存**。最後一則訊息會被「留住」，之後才上線的訂閱者（例如晚一點才打開的 RViz）也能立刻收到上一次的路徑，不必空等下一次重算。

**第 2 步：把訊息送出去**（`boustrophedon.py:53-58`）

```python
path                 = Path()                 # 建一個空的 Path 訊息
path.header.stamp    = rospy.Time.now()        # 蓋上時間戳
path.header.frame_id = msg.header.frame_id or 'map'   # 標明座標系
path.poses           = [_make_pose(x, y, ...) for x, y in pts]   # 填入路點

_pub.publish(path)   # ← 真正發布出去
```

`_pub.publish(path)` 這一行就是「按下上傳鍵」。執行後，所有訂閱 `/coverage_path` 的節點都會收到這份路徑。注意 `boustrophedon.py` 完全不知道、也不在乎是誰在看——它只負責把路徑廣播出去。

> 你可以在終端機用 `rostopic echo /coverage_path` 親眼看到這些被發布的路點資料。

### 2.3 Subscribe（訂閱）—— 用 `map_server.py` 當例子

「訂閱」就是跟 ROS 說：「這個話題只要一有新訊息，就幫我呼叫某個函式來處理。」這個被呼叫的函式叫 **回呼函式 (callback)**。

`map_server.py` 在啟動時一口氣訂閱了兩個話題（`map_server.py:358-359`）：

```python
rospy.Subscriber('/map',  OccupancyGrid, map_callback,  queue_size=1)
rospy.Subscriber('/odom', Odometry,      odom_callback, queue_size=10)
#                 └ 話題    └ 訊息型別      └ 收到訊息要呼叫誰   └ 佇列長度
```

意思是：

- 只要 `/map` 一有新地圖，ROS 就自動呼叫 `map_callback(msg)`，把地圖塞進參數 `msg`。
- 只要 `/odom` 一有新位置，就自動呼叫 `odom_callback(msg)`。
- `/odom` 更新得很快，`queue_size=10` 允許多排幾則避免漏掉；`/map` 又大又慢，只留最新 1 則就好。

回呼函式長這樣（以 `boustrophedon.py:32` 的 `map_callback` 為例，`map_server.py` 的同名函式概念相同）：

```python
def map_callback(msg):           # msg 就是收到的那則 OccupancyGrid 訊息
    res  = msg.info.resolution   # 從訊息裡取出解析度
    w, h = msg.info.width, msg.info.height
    data = np.array(msg.data).reshape((h, w))   # 取出地圖陣列來用
    ...
```

**訂閱者完全不需要知道是誰在發布 `/map`**（其實是 gmapping）——它只認話題名稱和型別。哪天把 gmapping 換成別的建圖工具，只要對方一樣發布 `/map`，這支訂閱程式一行都不用改。這就是 pub/sub 解耦的威力。

最後，訂閱完要讓程式「掛在那裡」持續等訊息，否則 `main()` 跑完就結束了：

```python
rospy.spin()   # 卡住主執行緒，把 CPU 交給 ROS 去觸發各個回呼
```

### 2.4 串起來看：本專案的 pub/sub 關係

把上面兩節合起來，就能看出資料怎麼在節點間流動：

```
  gmapping ──publish──▶ /map ──┬──subscribe──▶ map_server.py    （轉成網頁圖層）
                                └──subscribe──▶ boustrophedon.py （算路徑）
                                                      │
                                                      └─publish──▶ /coverage_path ──subscribe──▶ RViz
  機器人底層 ──publish──▶ /odom ──subscribe──▶ map_server.py    （記錄軌跡）
```

幾個值得注意的重點：

1. **一個話題可以有多個訂閱者**：`/map` 同時被 `map_server.py` 和 `boustrophedon.py` 訂閱，gmapping 發布一次，兩邊都收到。
2. **同一個節點可以同時是發布者又是訂閱者**：`boustrophedon.py` 訂閱 `/map`、發布 `/coverage_path`——它在資料流中間做加工。
3. **發布/訂閱是非同步的**：gmapping 什麼時候發布、發布幾次，訂閱端無法控制；所以 `boustrophedon.py` 才需要「5 秒節流」（見 §4-B）來避免被太頻繁的 `/map` 更新逼到瘋狂重算。

> ⚠️ 補充：並不是所有 ROS 溝通都走 pub/sub。本專案把目標點丟給 `move_base` 用的是另一種機制 **Action**（適合「有開始、要等結果、可中途取消」的長時間任務），會在 §4-C 和 §8 再談。pub/sub 適合「持續廣播的資料流」，Action 適合「一次性的任務委派」。

### 2.5 move_base 與 DWA 是什麼（它們不是同一層的東西）

這兩個名詞常被混在一起，但其實是「**外包公司 vs 公司裡的某個部門**」的關係：

- **move_base** = 整套導航的**總管 / 框架**。你丟一個目標點給它，它負責「想辦法把機器人安全開過去」這整件事。
- **DWA** = move_base **內部**負責「即時避障、決定下一步馬達怎麼轉」的那個小元件（局部規劃器）。

換句話說，**DWA 是 move_base 裡面的一個零件**，不是平行的兩個東西。

#### move_base：導航的協調者

move_base 是 ROS 的**導航堆疊 (navigation stack)**。它本身不做演算法，而是把好幾個元件串起來一起工作。你只要給它一個目標座標，它內部會同時運作這四塊：

| 內部元件 | 工作 |
|---------|------|
| **Global planner**（全域規劃器） | 看整張地圖，規劃一條「從現在位置到目標」的大致路線（像 Google Map 先畫好整條路線） |
| **Local planner**（局部規劃器） | **就是 DWA**。盯著眼前幾秒，即時決定速度/轉向來貼著全域路線走、同時閃避突然出現的障礙 |
| **Global costmap**（全域成本地圖） | 整張地圖的「障礙 + 膨脹層」，給全域規劃器用 |
| **Local costmap**（局部成本地圖） | 機器人周圍一小塊的即時障礙圖（吃 LiDAR），給 DWA 用 |
| **Recovery behaviors**（脫困行為） | 卡住時的補救動作：原地旋轉、清除 costmap 等 |

這在 `start.launch` 看得非常具體 —— 啟動**一個** `move_base` 節點，然後往裡面塞一堆參數檔：

```xml
<node pkg="move_base" type="move_base" name="move_base" ...>
    <param name="base_local_planner" value="dwa_local_planner/DWAPlannerROS" />  <!-- 指定局部規劃器用 DWA -->
    ... global_costmap_params.yaml      <!-- 全域 costmap 設定 -->
    ... local_costmap_params.yaml       <!-- 局部 costmap 設定 -->
    ... move_base_params.yaml           <!-- move_base 本體(goal tolerance 等) -->
    ... dwa_local_planner_params.yaml   <!-- DWA 的速度/加速度上限 -->
</node>
```

注意那行 `base_local_planner = dwa_local_planner/DWAPlannerROS` —— **這就是「告訴 move_base：你的局部規劃器部門，請用 DWA 來當」**。理論上可以換成別的（例如 TEB、EBand），move_base 框架本身不變，只是換掉裡面那個零件。

#### DWA：即時避障的演算法

DWA = **Dynamic Window Approach（動態視窗法）**，是一種**局部路徑規劃 + 避障演算法**。它的運作方式：

1. 在「機器人當前速度 + 馬達加速度上限」能達到的範圍內（這個範圍就叫「**動態視窗**」），取樣出一堆「可能的下一步速度組合」（線速度 v、角速度 ω）。
2. 模擬每個組合「如果這樣走，接下來一小段會到哪」。
3. 用評分函式打分：**離障礙夠遠嗎？**、**有朝全域路線前進嗎？**、**速度夠快嗎？**
4. 選分數最高的那組，輸出成 `/cmd_vel`（速度指令）發給馬達。
5. 每幾十毫秒重複一次 —— 所以它能即時對「突然走進來的人 / 動態障礙」反應。

`dwa_local_planner_params_<model>.yaml` 裡的「速度上限、加速度上限」就是在限制上面第 1 步那個動態視窗有多大。

#### 在本專案裡怎麼串起來

`map_server.py` 扮演「**派工的人**」，它只跟 move_base 打交道（透過 §8 會講的 Action 機制），**完全碰不到也不需要知道 DWA**：

```python
# map_server.py:182 — 連上 move_base
client = actionlib.SimpleActionClient('move_base', MoveBaseAction)

# map_server.py:212-219 — 把一個覆蓋路點包成目標，丟給 move_base
goal = MoveBaseGoal()
goal.target_pose.pose.position.x = x
goal.target_pose.pose.position.y = y
client.send_goal(goal)        # ← 「這個點，你想辦法開過去」
```

完整的分工鏈：

```
map_server.py ──「去 (x,y) 這個點」──▶ move_base
                                         │
                  ┌──────────────────────┼───────────────────────┐
                  ▼                       ▼                        ▼
          Global planner            DWA(local planner)      Recovery
          畫整條大路線      ───▶   即時算速度、閃障礙   ───▶  卡住就脫困
                                         │
                                         ▼ /cmd_vel(速度指令)
                                       馬達轉動
                                         │
                                         ▼ 到了 → 回報 SUCCEEDED
                          map_server 收到結果 ──▶ 送下一個路點
```

所以本專案只說「去這個點」，**至於走哪條路、怎麼避開那面牆、要不要減速轉彎，全是 move_base（內部交給 DWA）自己搞定的**。這也是為什麼 `map_server.py:231` 的失敗容錯只需要看 move_base 回傳的狀態碼（`SUCCEEDED` / 失敗），根本不用管底下避障的細節。

> **記憶口訣：**
> - 問「**要不要去、去哪、到了沒**」→ 那是 **move_base** 的層級（`map_server` 在這層下指令）。
> - 問「**這一瞬間馬達該轉多快、往哪閃**」→ 那是 **DWA** 的層級。

## 3. 系統總覽（資料如何流動）

```
        ┌─────────────────────────────────────────────────────┐
        │                    實體 TurtleBot3                    │
        │              (LiDAR 360° 掃描 + 馬達)                 │
        └───────────────┬─────────────────────┬────────────────┘
                        │ /scan               │ /odom
                        ▼                     │
            ┌───────────────────────┐         │
            │   gmapping (SLAM)      │         │
            │  邊走邊建圖 + 定位      │         │
            └───────┬───────────────┘         │
                    │ /map (OccupancyGrid)    │
                    │ + TF (map→odom)         │
        ┌───────────┼─────────────────────────┼───────────────┐
        │           ▼                         ▼               │
        │  ┌─────────────────┐      ┌──────────────────┐      │
        │  │ boustrophedon.py │      │   map_server.py   │      │
        │  │  (Module B)      │      │   (Module A)      │      │
        │  │ 算路徑→/coverage │      │ 地圖圖層 + 網頁    │      │
        │  │   _path (RViz)   │      │ + 派送任務        │      │
        │  └─────────────────┘      └────────┬─────────┘      │
        │           ▲                         │ 目標點         │
        │           │  共用核心                ▼               │
        │   ┌───────────────────┐    ┌──────────────────┐    │
        │   │coverage_planner.py │    │     move_base     │    │
        │   │ (純演算法，無 ROS) │    │  導航 + DWA 避障   │    │
        │   └───────────────────┘    └────────┬─────────┘    │
        └─────────────────────────────────────┼──────────────┘
                                               │ /cmd_vel
                                               ▼
                                          馬達轉動
```

**一句話流程**：LiDAR 掃描 → gmapping 建出 `/map` → 規劃模組把 `/map` 變成一串覆蓋路點 → `map_server` 把路點一個個丟給 `move_base` → `move_base` 開著機器人避障走過去 → 網頁即時顯示全部過程。

## 4. 模組逐一拆解

本專案的程式碼分成「三支腳本 + 一個網頁 + 一個 launch」，刻意把**演算法**和**ROS 接線**拆開，這是很好的工程習慣。

### A. `coverage_planner.py` — 純演算法核心（無 ROS 依賴）

這是整個專案最值得學習的設計：**把核心演算法抽出來，完全不依賴 ROS**。

- 只用 `numpy` 和 `scipy`，輸入輸出都是普通陣列和座標。
- 因為不依賴 ROS，所以可以**單獨測試**、可以**被多個節點共用**（`boustrophedon.py` 和 `map_server.py` 都 import 它）。
- 提供兩個函式：
  - `apply_safety_margin(data, margin, resolution)`：把障礙物「膨脹」一圈安全距離，避免機器人貼著牆走。
  - `boustrophedon(free, res, ox, oy)`：在可走區域上計算牛耕路點。
- 兩個關鍵參數：
  - `SPACING = 0.25`（掃描線間距，公尺）—— 比機器人直徑小，確保相鄰掃線重疊不漏掃。
  - `MARGIN = 0.15`（安全邊距，公尺）—— 約等於機器人半徑。

### B. `boustrophedon.py` — 路徑規劃節點（Module B）

- 訂閱 `/map`，每隔 `REPLAN_INTERVAL = 5.0` 秒重新規劃一次。
- 呼叫 `coverage_planner` 算出路點，包成 `nav_msgs/Path`，發布到 `/coverage_path`。
- **這個節點的路徑只給 RViz 顯示用**，不負責驅動機器人。
- 注意它有「節流」設計：5 秒內重複收到 `/map` 就跳過，避免地圖一直更新時瘋狂重算。

### C. `map_server.py` — 地圖伺服器 + 任務執行（Module A，核心樞紐）

這支是最複雜的，身兼多職：

1. **訂閱 `/map`**（`map_callback`）：把佔據網格轉成三種 PNG 圖層（原始 / 侵蝕 / 膨脹），並裁切掉周圍空白。
2. **訂閱 `/odom`**（`odom_callback`）：記錄機器人位置與軌跡（每 0.1 m 記一點，最多存 10000 點）。
3. **Flask 網頁伺服器**：開在 8080 埠，提供 `/map.png`、`/robot_state`、`/coverage/start` 等 API。
4. **任務執行緒**（`run_coverage`）：把覆蓋路點一個一個送給 `move_base`，並監控到達狀態，可隨時被停止。

### D. `web/index.html` — 前端網頁

- 用 HTML5 Canvas **多圖層疊加**：原始地圖打底，侵蝕/膨脹層著色半透明疊上，再畫覆蓋路徑、行走軌跡、機器人位置。
- 每秒輪詢一次後端（`setInterval(refresh, 1000)`），重新抓圖和狀態。
- 有趣的前端技巧：`colorize()` 把灰階地圖即時轉成彩色障礙圖層（空地透明、障礙著色），讓多層地圖能疊在一起看。
- 圖層可以用按鈕一鍵開關。

### E. `start.launch` — 一鍵啟動

把上面所有東西串起來：設環境變數 → 啟動硬體驅動 → 啟動 gmapping → 啟動 move_base（沿用 turtlebot3_navigation 的標準參數）→ 啟動兩支自製節點。

### F. `test/test_lidar_freq.py` — 小工具

測量 `/scan` 光達訊息的頻率，用來確認感測器是否正常運作。

## 5. 核心演算法：牛耕式 + PCA 對齊

這是本專案最精彩的部分，分兩步看。

### 5.1 為什麼需要 PCA？

牛耕式最簡單的做法是「沿著 X 軸來回掃」。但問題來了：**SLAM 建出來的地圖，房間的牆壁往往不是正對著 X/Y 軸的**，而是歪斜一個角度（因為機器人開機那一刻的朝向決定了地圖座標方向）。

如果牆是斜的、掃描線是正的，覆蓋路徑就會變成**鋸齒/階梯狀**，效率很差、轉彎超多：

```
   牆是斜的，但掃描線是水平的 → 每條線長度都不同，邊緣全是碎階梯
   ╱──────────╱
  ╱  →→→→→→  ╱
 ╱  →→→→→→  ╱
╱──────────╱
```

**解法：用 PCA（主成分分析）找出房間自己的方向。**

### 5.2 PCA 怎麼做到的（`boustrophedon.py:49-62`）

1. 取出所有「可走格子」的世界座標，得到一堆點。
2. 計算這堆點的**共變異數矩陣**，求**特徵值/特徵向量**（`np.linalg.eigh`）。
3. 最大特徵值對應的向量 = 空間的**長軸**（沿這個方向掃，掃描線最長、轉彎最少）。
4. 最小特徵值對應的向量 = **短軸**（每掃完一條線，就沿短軸前進一個 `spacing`）。

這樣不管地圖怎麼歪，掃描線都會自動**和牆壁平行**。

### 5.3 牛耕路點怎麼生成（`boustrophedon.py:64-84`）

1. 把每個可走點投影到長軸 (`proj_a`) 和短軸 (`proj_b`)。
2. 沿短軸從一端走到另一端，每隔 `spacing` 取一條「掃描線」。
3. 每條掃描線上，找出最遠的兩個端點，連成一條線段。
4. 用一個布林旗標 `l2r` 控制方向**交替**：這條左到右，下條就右到左——這正是「牛耕」來回的精髓。

```python
if l2r:
    waypoints += [起點, 終點]
else:
    waypoints += [終點, 起點]   # 反向
l2r = not l2r                    # 下一條反過來
```

> **第一條掃描線從邊界內縮 `spacing/2`**（`b = b_min + spacing/2`），讓兩端對稱，覆蓋更均勻。

## 6. 地圖三種圖層：原始 / 侵蝕 / 膨脹

`map_server.py` 的 `map_callback` 會產生三種地圖，這是形態學（morphology）影像處理的應用：

| 圖層 | 端點 | 做法 | 用途 |
|------|------|------|------|
| **原始** | `/map.png` | 佔據網格直接轉灰階 | 真實地圖，**沒有形態學處理** |
| **侵蝕** | `/map_eroded.png` | `binary_erosion` 縮小障礙 | 確認「機器人中心」可安全到達的範圍 |
| **膨脹** | `/map_dilated.png` | `binary_dilation` 放大障礙 | 顯示安全緩衝區（牆變胖，路徑遠離牆） |

**灰階對應**：白 (255) = 空地、黑 (0) = 障礙、灰 (128) = 未知。

> ⚠️ 注意區分兩種「膨脹」：
> - 顯示用的膨脹（`MORPH_ITER = 3` 次）只是給人看的。
> - **路徑規劃實際用的安全邊距**是 `apply_safety_margin()`，用 `MARGIN = 0.15 m` 換算成格數做膨脹——這才是真正影響機器人走法的那一個。

### 動態裁切（`_crop`）

地圖周圍常有一大片「未知區」(`-1`)。`_crop` 會找出「已知格子」的最小外接矩形，加上 `CROP_PAD = 10` 格邊距後裁切，**減少網頁傳輸量、去掉多餘空白**。

> 補充：`map_callback` 裡那行 `print(f"地圖尺寸: {msg.info.width} x {msg.info.height}")` 印的是**裁切前的原始尺寸**（直接來自 `/map` 訊息），不是裁切後的大小。

## 7. 座標系與轉換

專案涉及三種座標：

| 座標系 | 說明 | 單位 |
|--------|------|------|
| **世界座標** (map frame) | gmapping 的全域座標，路徑規劃的基準 | 公尺 |
| **網格座標** (grid) | OccupancyGrid 的行列索引 | 格 |
| **圖片像素** (裁切後) | 網頁 Canvas 上的像素位置 | 像素 |

**世界 → 像素的轉換**（`world_to_px`，`map_server.py:244-247`）：

```python
px = (wx - origin_x) / resolution - c0          # 先換成格，再扣掉裁切左邊界
py = crop_h - ((wy - origin_y) / resolution - r0)  # Y 軸要翻轉（影像 Y 向下，世界 Y 向上）
```

兩個重點：
1. `(世界座標 - 原點) / 解析度` = 格座標。
2. **Y 軸要翻轉**：影像座標原點在左上、Y 向下；世界座標 Y 向上。`_to_png` 裡的 `np.flipud` 也是為了這件事。

## 8. 併發與執行緒安全

`map_server.py` 同時跑著好幾條執行緒，必須小心資料競爭：

- **ROS 回呼執行緒**：`map_callback`、`odom_callback` 不斷更新共享資料。
- **Flask 執行緒**：處理網頁請求時要讀共享資料。
- **任務執行緒**：`run_coverage` 在背景把路點送給 move_base。

解法是**三把鎖**：

```python
map_lock   = threading.Lock()   # 保護地圖資料
robot_lock = threading.Lock()   # 保護機器人位置/軌跡
cov_lock   = threading.Lock()   # 保護覆蓋任務狀態
```

每次讀寫共享資料都用 `with xxx_lock:` 包起來，確保 Flask 讀取時不會讀到寫到一半的資料。

**任務執行緒的停止機制**也很值得學：`run_coverage` 不是用「強制 kill」，而是在迴圈裡**定期檢查** `cov_status['state']`，發現變成非 `running` 就主動 `cancel_all_goals()` 並退出——這叫**合作式取消** (cooperative cancellation)，安全又乾淨。

```python
while not rospy.is_shutdown():
    with cov_lock:
        if cov_status['state'] != 'running':
            client.cancel_all_goals()
            return                       # 優雅退出
    if client.wait_for_result(rospy.Duration(0.5)):
        break                            # 每 0.5 秒檢查一次
```

**失敗容錯**：若某個路點 move_base 到不了（狀態非 `SUCCEEDED`），不會卡死，而是記錄警告後**跳過、繼續下一點**，確保任務不中斷。

## 9. 如何啟動與操作

### 前置安裝

```bash
pip3 install flask Pillow      # numpy 已隨 ROS 安裝
```

### 啟動（在機器人或連線的電腦上）

```bash
# 預設 Burger 型號
roslaunch turtlebot3_ccpp start.launch

# 換成 Waffle
roslaunch turtlebot3_ccpp start.launch model:=waffle

# 換埠號
roslaunch turtlebot3_ccpp start.launch port:=9000
```

### 操作流程

1. 啟動後，先**遙控機器人在房間裡走一圈**，讓 gmapping 把地圖建得夠完整。
2. 瀏覽器打開 `http://<機器人IP>:8080`。
3. 觀察地圖、機器人位置、規劃出來的覆蓋路徑（紫色）。
4. 點 **▶ 開始覆蓋**，機器人就會依路點自動走遍全場。
5. 隨時可點 **■ 停止**。

### 單獨看某張地圖

```
http://<IP>:8080/map.png           ← 原始（未經形態學處理）
http://<IP>:8080/map_eroded.png    ← 侵蝕
http://<IP>:8080/map_dilated.png   ← 膨脹
```

## 10. 常見問題與除錯

| 症狀 | 可能原因 | 排查方向 |
|------|---------|---------|
| 網頁顯示「等待地圖...」 | `/map` 還沒發布 | 確認 gmapping 有啟動、`rostopic echo /map` 有資料 |
| 「無可走路徑，地圖可能不完整」 | 地圖太空或全是障礙 | 先遙控機器人多建一點圖 |
| 「move_base 未啟動」 | move_base 沒起來 | 看 launch 輸出、`rosnode list` 確認 |
| 覆蓋路徑是鋸齒狀 | PCA 沒對齊（理論上不該發生） | 檢查可走格數量是否太少 |
| 機器人撞牆 | 安全邊距太小 | 調大 `coverage_planner.py` 的 `MARGIN` |
| 漏掃 | 掃描線太疏 | 調小 `SPACING`（但會變慢） |
| 路點到不了一直跳過 | 邊距太大把路堵死，或定位漂移 | 調 `MARGIN`、檢查 TF |
| 光達沒資料 | 感測器/連線問題 | 跑 `test/test_lidar_freq.py` 看頻率 |

### 好用的除錯指令

```bash
rostopic list                    # 看有哪些話題
rostopic echo /map --noarr       # 看地圖 metadata（不印整個陣列）
rostopic hz /scan                # 看光達頻率
rosnode list                     # 看有哪些節點在跑
rqt_graph                        # 視覺化節點與話題關係
```

## 11. 可延伸的練習

如果想在這個專案上繼續學習，可以嘗試：

1. **加一個「完全不裁切」的 `/map_full.png` 端點**，比較裁切前後的差異。
2. **把規劃結果也存成檔案**（用 `map_saver` 或自己寫），離線分析覆蓋率。
3. **計算覆蓋率指標**：走完後統計「實際走過的格 / 應覆蓋的格」。
4. **換覆蓋策略**：試試螺旋式 (spiral) 或基於 frontier 的探索（專案 README 的里程碑 v0.2.0 就規劃了 frontier 自主探索）。
5. **優化路點順序**：目前是固定 S 形，可研究如何減少總路程（接近 TSP 問題）。
6. **加上即時覆蓋率顯示**到網頁上。
