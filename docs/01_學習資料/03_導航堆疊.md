> **本章目標**：搞懂 `move_base` 是什麼、它內部怎麼運作、為什麼本專案完全不自己寫避障。

> **全域 / 局部兩層規劃**、**Action 通訊機制**。

## 3.1 先講問題：從「路點清單」到「輪子真的轉」

第 08~12 章的演算法會算出一串路點：

```python
[(0.15, 0.20), (3.80, 0.20), (3.80, 0.38), (0.15, 0.38), ...]
```

這只是**數學上的理想直線**。要讓機器人真的走過去，中間隔了一大堆現實問題：

| 問題 | 舉例 |
|---|---|
| 兩點之間可能有東西 | cell 換行的轉場線可能穿過牆角 |
| 有臨時障礙 | 有人把椅子搬過來、有人走過去 |
| 機器人有物理限制 | 不能瞬間從 0 加速到 0.22 m/s、不能橫移 |
| 定位有誤差 | 以為走到 (3.8, 0.2) 其實在 (3.75, 0.23) |
| 可能根本到不了 | 那個點被新出現的障礙包住了 |

### 直覺做法：自己寫一個「開過去」的函式

```python
def goto(target_x, target_y):
    while distance_to(target) > 0.05:
        angle = atan2(target_y - my_y, target_x - my_x)
        publish_cmd_vel(v=0.15, w=(angle - my_yaw) * 2.0)
```

### 這樣寫會撞到什麼牆

```
   目標 ●
        ╲
         ╲      ┌─────────┐
          ╲     │  障礙物 │
           ╲    └─────────┘
            ╲        ↑
             ●───────┘  機器人直直往目標開 → 撞上去
```

1. **完全不會避障** —— 它只知道目標方向，不知道中間有什麼
2. **不知道繞路** —— 就算加了「碰到東西就停」，它也不知道該往左還是往右繞
3. **會撞角** —— 機器人有實體寬度，路徑中心線沒撞到不代表車身沒撞到
4. **卡死不會恢復** —— 卡在牆角就永遠出不來

寫一個堪用的避障導航，本身就是好幾個月的工程。**所以本專案完全不寫，直接用 `move_base`。**

> 💡 **設計決策**：專題的核心貢獻是「覆蓋路徑規劃演算法」，不是「導航」。
> 導航是已經被解決得很好的問題，重造輪子只會讓專案品質變差。
> 把力氣花在自己的貢獻上，剩下的用最成熟的現成方案 —— 這是工程判斷，不是偷懶。

## 3.2 move_base 是什麼：導航的「協調者」

`move_base` **本身不是演算法**，它是一個把好幾個演算法組裝起來的框架。

```
              ┌──────────────────────────────────────────┐
              │              move_base                   │
              │                                          │
  目標點 ────→│  ┌──────────────┐    ┌────────────────┐ │
 (Action)     │  │ 全域規劃器   │    │  全域 costmap  │ │
              │  │ global       │←───│  （整張地圖）  │ │←── /map
              │  │ planner      │    └────────────────┘ │
              │  └──────┬───────┘                       │
              │         │ 一條完整路徑                  │
              │         ↓                               │
              │  ┌──────────────┐    ┌────────────────┐ │
              │  │ 局部規劃器   │    │  局部 costmap  │ │←── /scan
              │  │ DWA          │←───│ （身邊 3x3 m） │ │
              │  └──────┬───────┘    └────────────────┘ │
              │         │                               │
              │  ┌──────┴───────┐                       │
              │  │ 恢復行為     │  卡住時：原地轉圈、   │
              │  │ recovery     │  清空 costmap、後退   │
              │  └──────────────┘                       │
              └────────────────────┬─────────────────────┘
                                   ↓
                              /cmd_vel（速度指令）
```

**兩層規劃是核心設計：**

| | 全域規劃器 | 局部規劃器（DWA） |
|---|---|---|
| 看多遠 | 整張地圖 | 身邊 3×3 公尺 |
| 用什麼資料 | `/map`（SLAM 的靜態地圖） | `/scan`（即時雷射） |
| 多久算一次 | 收到新目標時（約 1 Hz） | **每秒 20 次** |
| 產出 | 一條完整路徑 | 一組速度指令 `(v, w)` |
| 演算法 | Dijkstra / A* | DWA |
| 負責 | 「大方向怎麼走」 | 「這 0.05 秒往哪動」 |

> 💡 **為什麼要分兩層？** 全域規劃算一次要幾百毫秒，太慢，無法應付突然衝出來的人；
> 局部規劃只看身邊、算得飛快，但看不到全局，會走進死巷。
> **兩層各補對方的短板**：全域負責不走冤枉路，局部負責即時不撞。
>
> ⚠ 這個「全域規劃慢但正確、局部規劃快但短視」的分層思維，
> 和第 11 章「先做 cell 分解、再在 cell 內蛇行」是同一種思路 ——
> **把難問題切成不同時間尺度的子問題**。

## 3.3 costmap：把地圖變成「成本」

`move_base` 不直接用 `OccupancyGrid`，而是先轉成 **costmap（成本地圖）**。

### 為什麼要多這一層

`OccupancyGrid` 只有「有障礙 / 沒障礙」，但實際上：

```
   離牆 5 公分：技術上可以走，但很危險，會擦撞
   離牆 30 公分：安全
   離牆 2 公尺：非常安全
```

costmap 給每一格一個 **0~254 的成本值**，讓規劃器「盡量不要貼著牆走」：

```
   ████  = 254   致命（障礙本體）
   ▓▓▓▓  = 253   內切半徑內（機器人中心進來一定撞）
   ▒▒▒▒  = 100~252  膨脹區（可以走但成本高，指數遞減）
   ░░░░  = 0     自由
```

```
   ┌────────────────────────────────┐
   │░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░│
   │░░░░░░░▒▒▒▒▒▒▒▒▒▒▒▒░░░░░░░░░░░░░│
   │░░░░░░▒▒▓▓▓▓▓▓▓▓▓▓▒▒░░░░░░░░░░░░│
   │░░░░░░▒▒▓███████▓▓▒▒░░░░░░░░░░░░│  ← 障礙物 + 膨脹層
   │░░░░░░▒▒▓▓▓▓▓▓▓▓▓▓▒▒░░░░░░░░░░░░│
   │░░░░░░░▒▒▒▒▒▒▒▒▒▒▒▒░░░░░░░░░░░░░│
   └────────────────────────────────┘
```

規劃器找「總成本最低」的路徑，自然就會走中間而不是貼著牆。

> ★ **這個「膨脹」和本專案 `coverage_planner.py:19` 的 `apply_safety_margin` 是同一個概念，
> 但完全獨立的兩套實作**：
>
> | | 本專案的安全邊距 | costmap 的膨脹層 |
> |---|---|---|
> | 誰做的 | 我們自己寫（`binary_dilation`） | `move_base` 內建 |
> | 給誰用 | 覆蓋規劃決定「哪裡可以生路點」 | 導航決定「怎麼走過去」 |
> | 值的型態 | 布林（能走 / 不能走） | 0~254 連續成本 |
> | 參數 | `MARGIN = 0.10 m` | `inflation_radius`（在 yaml 裡） |
>
> **兩者都要有**：我們要確保「路點本身」不會太靠牆（否則 `move_base` 根本到不了），
> `move_base` 要確保「走過去的過程」不擦撞。少任何一個都會出問題。

### 兩張 costmap

```xml
<!-- launch/start.launch:40-46 -->
<!-- 全域地圖（static_map: true → 訂閱 /map，即 SLAM 輸出）-->
<rosparam file="$(find turtlebot3_navigation)/param/global_costmap_params.yaml" command="load" />

<!-- 局部地圖（跟隨機器人移動的小範圍感知）-->
<rosparam file="$(find turtlebot3_navigation)/param/local_costmap_params.yaml" command="load" />
```

- **全域 costmap**：整張地圖，基於 `/map`，更新慢
- **局部 costmap**：一個跟著機器人跑的小視窗（約 3×3 m），基於即時 `/scan`，更新快
  —— 這就是為什麼它能看到 SLAM 地圖上沒有的臨時障礙（走動的人）

## 3.4 DWA：局部規劃器怎麼決定下一步

**DWA = Dynamic Window Approach（動態視窗法）**。名字裡的「動態視窗」指的是
「**在物理上做得到的速度範圍**」。

### 演算法四步

```
① 算出「動態視窗」：從當前速度出發，0.1 秒內物理上能達到的所有 (v, w) 組合
      當前 v=0.10, 最大加速度 a=0.5 m/s²
      → 0.1 秒後 v 只能在 0.05 ~ 0.15 之間
      （這就是「動態視窗」——不是所有速度都能選，受加速度限制）

② 在這個視窗裡採樣一堆候選 (v, w)
      (0.05, -0.5) (0.05, 0.0) (0.05, +0.5)
      (0.10, -0.5) (0.10, 0.0) (0.10, +0.5)
      (0.15, -0.5) (0.15, 0.0) (0.15, +0.5)  ...

③ 每個候選都模擬「如果保持這個速度開 2 秒，會畫出什麼弧線」
                    ╱─── 候選 A
      機器人 ●─────────── 候選 B
                    ╲─── 候選 C

④ 幫每條弧線打分，選最高分的那組速度送出去
      分數 = w1×(離全域路徑多近) + w2×(離障礙多遠) + w3×(前進多快)
```

每秒重複 20 次。這就是為什麼機器人能「一邊往目標走、一邊繞開突然出現的東西」。

### 為什麼 DWA 適合 TurtleBot3

TurtleBot3 是**差速輪**：只能前進/後退 + 原地旋轉，**不能橫移**。
所以它的運動只有 `(v, w)` 兩個自由度，DWA 的搜尋空間是二維的，非常小，算得飛快。

（如果是麥克納姆輪的全向底盤，多一個橫移自由度，搜尋空間變三維，就要換別的規劃器。）

### 速度上限從哪來

```xml
<!-- launch/start.launch:52-54 -->
<!-- DWA 局部路徑規劃器參數（速度、加速度上限）-->
<rosparam file="$(find turtlebot3_navigation)/param/dwa_local_planner_params_$(arg model).yaml"
          command="load" />
```

`$(arg model)` 會展開成 `burger` 或 `waffle`，載入對應型號的參數檔。
Burger 的規格是最大線速度 **0.22 m/s**、最大角速度 **2.84 rad/s**。

> ⚠ 本專案的**手動遙控**另外設了更保守的上限：
> ```python
> # scripts/map_server.py:56-57
> V_MAX = 0.18   # 手動遙控線速度上限（m/s），Burger 規格 0.22
> W_MAX = 1.50   # 手動遙控角速度上限（rad/s），Burger 規格 2.84
> ```
> 這是**兩套獨立的限速**：自動導航時由 DWA 的 yaml 管，手動遙控時由這兩個常數管。
> 手動壓得更低是因為人在網頁上操作有延遲，開太快容易撞。詳見第 16 章。

## 3.5 ★ Action：適合「耗時任務」的通訊機制

第 01 章提過 ROS 有三種通訊方式。「走到某個點」不適合用 Topic 或 Service：

| | 為什麼不行 |
|---|---|
| **Topic** | 單向廣播，發出去就沒了。你不知道到了沒、成功沒 |
| **Service** | 一問一答但**同步阻塞**。呼叫方會卡住 30 秒不能做別的事，也無法中途取消 |
| **Action** | ✅ 非同步、可查進度、**可中途取消**、有明確的成功/失敗狀態碼 |

### Action 的三種訊息

```
   Client                                    Server (move_base)
     │                                              │
     │──── Goal（目標）：走到 (3.2, 1.5) ─────────→│
     │                                              │ 開始規劃、開始移動
     │←─── Feedback（進度）：現在在 (1.1, 0.8) ────│
     │←─── Feedback ───────────────────────────────│
     │                                              │
     │←─── Result（結果）：SUCCEEDED ──────────────│
     │                                              │
     │──── Cancel（取消）───────────────────────→ │  ← 隨時可以叫停 ★
```

### 本專案怎麼用（第 13 章會完整拆解，這裡先看骨架）

```python
# scripts/map_server.py:294-298
client = actionlib.SimpleActionClient('move_base', MoveBaseAction)
if not client.wait_for_server(rospy.Duration(5.0)):
    with cov_lock:
        cov_status.update(state='error', msg='move_base 未啟動（等待 5 秒逾時）')
    return
```

★ `wait_for_server` 一定要設**逾時**。如果 `move_base` 沒啟動（沒裝、當掉、還在初始化），
不設逾時就會**永遠卡住**，而且這是在背景執行緒裡，網頁完全看不出問題在哪，
只會顯示「執行中」但機器人一動也不動。

設了逾時之後，5 秒沒等到就把狀態改成 `error` 並附上訊息，網頁上直接看得到原因。

### 送一個目標

```python
# scripts/map_server.py:323-330
goal = MoveBaseGoal()
goal.target_pose.header.frame_id    = fid          # 'map'
goal.target_pose.header.stamp       = rospy.Time.now()
goal.target_pose.pose.position.x    = x
goal.target_pose.pose.position.y    = y
goal.target_pose.pose.orientation.z = qz           # 朝向（四元數）
goal.target_pose.pose.orientation.w = qw
client.send_goal(goal)
```

★ **`frame_id` 一定要填 `'map'`**。同樣的座標 (3.2, 1.5)，
在 `map` 座標系和 `odom` 座標系是**不同的地方**（差一個 SLAM 修正量）。
填錯的話機器人會走到偏掉的位置，而且隨著漂移越來越偏。

### 等待與取消

```python
# scripts/map_server.py:332-339
while not rospy.is_shutdown():
    with cov_lock:
        if cov_status['state'] != 'running':
            client.cancel_all_goals()      # ★ 使用者按了停止 → 立刻取消
            return
    if client.wait_for_result(rospy.Duration(0.5)):
        break                              # 到了（或失敗了）
```

★ 這個「**每 0.5 秒醒來檢查一次停止訊號**」的寫法是關鍵。
如果直接寫 `client.wait_for_result()`（無限等待），使用者按下網頁的「結束」按鈕後，
程式要等到機器人走完這一點才會反應 —— 可能是 30 秒。
切成 0.5 秒一段，反應延遲就壓在半秒內。

### 失敗容錯

```python
# scripts/map_server.py:341-345
if client.get_state() != GoalStatus.SUCCEEDED:
    rospy.logwarn(f'[coverage] 路點 {i+1}/{n} 跳過（move_base 狀態碼 {client.get_state()}）')
    with cov_lock:
        cov_status['msg'] = f'路點 {i+1}/{n} 跳過（無法到達）'
    # ★ 注意：沒有 return，繼續跑下一個路點
```

★ **到不了就跳過，不中止整趟任務。**

覆蓋任務有幾百個路點，其中一兩個因為臨時障礙到不了是很正常的。
因為一個點失敗就把整趟停掉，實用性太差。
本專案的選擇是「記錄下來、告訴使用者、繼續走」。

> ⚠ 代價是**覆蓋率會悄悄下降**。網頁最後仍會顯示「完成」，
> 但實際上跳過的那幾格沒被覆蓋到。`cov_status['msg']` 是唯一的線索。
> 這是第 19 章「假完成」的成因之一。

### 常見狀態碼

| `GoalStatus` | 意思 | 什麼時候發生 |
|---|---|---|
| `SUCCEEDED` | 成功到達 | 正常 |
| `ABORTED` | 規劃器放棄了 | 目標被障礙包住、恢復行為全試過還是卡住 |
| `PREEMPTED` | 被取消 | 我們呼叫了 `cancel_all_goals()` |
| `REJECTED` | 目標無效 | 目標在地圖外、`frame_id` 錯誤 |

## 3.6 本專案的分工全圖

```
   ┌──────────────────────────────────────────────────────┐
   │  我們寫的（coverage_planner.py + map_server.py）     │
   │                                                      │
   │  「走遍整個房間」的路線怎麼算    ← 專題的核心貢獻    │
   │  一次送一個路點給 move_base                          │
   │  進度追蹤、停止、失敗記錄                            │
   └──────────────────────┬───────────────────────────────┘
                          │ Action（一個路點一個目標）
                          ↓
   ┌──────────────────────────────────────────────────────┐
   │  現成的（move_base）                                 │
   │                                                      │
   │  「從 A 到 B 怎麼走不撞」                            │
   │  全域路徑規劃 + DWA 局部避障 + 卡住時的恢復行為      │
   └──────────────────────────────────────────────────────┘
```

**一句話總結分工**：
> 我們決定**去哪些點、依什麼順序**；`move_base` 決定**怎麼走過去**。

## 3.7 ⚠ 這個分工留下的縫隙

界線切得很乾淨，但也留下三個已知問題（第 19、23 章詳談）：

**① 規劃器不知道路徑會不會被 move_base 拒絕**

覆蓋規劃只確保路點落在「膨脹後的自由格」上，但 `move_base` 用的是自己的 costmap，
兩者的膨脹半徑不一定一致。可能規劃器覺得可以，`move_base` 卻回 `ABORTED`。

**② cell 之間的轉場沒有避障規劃**

`coverage_planner` 產生的路點只是一串座標，**兩點之間是不是通的它不管**，
完全交給 `move_base` 去繞。所以：
- 好處：不用自己寫避障
- 壞處：**路徑長度的估算會嚴重失真**。規劃器以為兩點距離 0.5 m，
  實際 `move_base` 可能要繞 4 m

（第 22 章的實測就量到「斜置 30° 場地有 30 段轉場穿牆」——
這些段落全都要靠 `move_base` 繞路。）

**③ 失敗被吞掉了**

上面講的「跳過繼續」讓覆蓋率悄悄下降，而網頁上仍顯示「完成」。

## 3.8 本章重點回顧

1. **`move_base` 不是演算法，是把好幾個演算法組裝起來的框架**：
   全域規劃器 + 局部規劃器 + 兩張 costmap + 恢復行為。
2. **兩層規劃**：全域看整張地圖、算得慢、負責不走冤枉路；
   局部（DWA）只看身邊 3×3 m、每秒算 20 次、負責即時不撞。
3. **costmap 把「有無障礙」變成 0~254 的成本**，讓規劃器自動避開貼牆的路。
   它的膨脹層和本專案的 `apply_safety_margin` 是**兩套獨立實作，都要有**。
4. **DWA 在「物理上做得到的速度範圍」裡採樣、模擬弧線、打分、選最好的**。
5. ★ **耗時任務用 Action**：可查進度、**可中途取消**、有明確狀態碼。
   `wait_for_server` 一定要設逾時；等待要切成小段以便及時響應停止。
6. ★ **分工原則：我們決定去哪些點，`move_base` 決定怎麼走過去。**
   ⚠ 代價是規劃器對「實際路徑長度」和「路點可達性」都是盲的。

## 3.9 自我檢核題

**Q1. 為什麼 `move_base` 要分全域規劃器和局部規劃器兩層？只用一個不行嗎？**

<details>
<summary>參考答案</summary>

因為兩種需求在時間尺度上互相衝突：

- **只用全域規劃**：算一次要幾百毫秒。有人突然走到機器人前面，它來不及反應就撞上去了。
  而且它用的是 SLAM 的靜態地圖，**根本看不到臨時障礙**。
- **只用局部規劃**：DWA 只看身邊 3×3 公尺，算得飛快，但它**看不到全局**。
  走進一個死巷子它才發現，然後在裡面反覆掙扎出不來（局部極小值問題）。

分兩層之後：全域規劃給出「大方向」（保證不走進死巷），
局部規劃在這個大方向上做即時微調（保證不撞到突發障礙）。**互補對方的短板。**

> 這個「把難題切成不同時間尺度的子問題」的思路，
> 和本專案「先 cell 分解（全域結構）、再 cell 內蛇行（局部細節）」是同一種設計哲學。
</details>

**Q2. 本專案的 `apply_safety_margin` 和 costmap 的膨脹層，功能看起來一樣。
為什麼還要自己寫一份？只靠 costmap 不行嗎？**

<details>
<summary>參考答案</summary>

**不行，因為兩者作用在不同的階段、解決不同的問題。**

- **costmap 的膨脹層**作用在「**怎麼走過去**」：`move_base` 規劃路徑時避開貼牆的區域。
  但它管不到「路點本身該生在哪裡」——路點是我們給它的。
- **`apply_safety_margin`** 作用在「**路點該生在哪裡**」：
  如果不做，覆蓋演算法會在離牆 2 公分的地方生一個路點。
  這個點在 costmap 上是「致命」等級（機器人中心進去一定撞），
  `move_base` 會直接回 `ABORTED` —— **這個路點永遠到不了**。

所以兩者是串聯關係：
我們先確保**目標點合法**，`move_base` 再確保**過程安全**。

⚠ 附帶一提，兩者的膨脹半徑如果不一致會出問題：
我們用 `MARGIN = 0.10 m`，costmap 的 `inflation_radius` 如果設得更大，
就會出現「我們覺得可以的點，`move_base` 覺得太危險」的落差。這是 3.7 提到的縫隙 ①。
</details>

**Q3. `client.wait_for_result(rospy.Duration(0.5))` 為什麼要設 0.5 秒？
直接寫 `client.wait_for_result()` 一直等到走完不是更簡單？**

<details>
<summary>參考答案</summary>

因為**要能及時響應使用者按下的「結束」按鈕**。

網頁按停止 → Flask 路由把 `cov_status['state']` 改成 `'stopped'`（`map_server.py:500-506`）。
但真正在跑的是背景執行緒 `run_coverage`，它必須**主動去檢查**這個狀態才會知道。

如果寫 `wait_for_result()`（無限等待），執行緒會卡在那裡直到機器人走完當前這一點。
一個路點可能要走 10~30 秒，使用者按了停止卻要等半分鐘機器人才停 —— 體感上像當機。

切成 0.5 秒一段之後，迴圈每半秒醒來一次檢查狀態，反應延遲壓在 0.5 秒內：

```python
while not rospy.is_shutdown():
    with cov_lock:
        if cov_status['state'] != 'running':
            client.cancel_all_goals()      # 取消當前目標
            return                          # 結束整個執行緒
    if client.wait_for_result(rospy.Duration(0.5)):
        break
```

這是一個通用的併發模式：**長時間等待要切成可中斷的小段**。
</details>

**Q4. 某個路點 `move_base` 回傳 `ABORTED`，本專案怎麼處理？這個選擇有什麼代價？**

<details>
<summary>參考答案</summary>

**處理方式**（`map_server.py:341-345`）：印一則 warning、把訊息寫進 `cov_status['msg']`
讓網頁看得到，然後**繼續跑下一個路點**（沒有 `return`）。

**為什麼這樣選**：覆蓋任務動輒幾百個路點，其中一兩個因為臨時障礙、
定位誤差、或那個點剛好落在 costmap 的膨脹區而到不了，是完全正常的。
因為一個點失敗就把整趟停掉，實用性太差。

**代價有兩個**：
1. **覆蓋率悄悄下降**：跳過的那一格附近沒被覆蓋，但沒有任何地方統計這件事。
2. **最後仍顯示「完成」**：`cov_status` 最終會變成 `'done'`，
   網頁上看起來一切正常。`cov_status['msg']` 裡的「路點 N 跳過」是**唯一的線索**，
   而且會被後面的失敗覆寫掉，只留最後一則。

這是第 19 章「假完成」現象的成因之一。
改進方向：累積一個 `skipped` 計數，完成時一併回報，甚至對跳過的區域安排第二輪。
</details>

**Q5. 為什麼送目標時 `frame_id` 必須填 `'map'` 而不是 `'odom'`？**

<details>
<summary>參考答案</summary>

因為**同一組座標數值，在兩個座標系裡是不同的實際位置**。

第 02 章講過，`map → odom` 這段 TF 就是 SLAM 算出來的「里程計漂了多少」的修正量。
剛開機時它是零，兩個座標系重合；但走了五分鐘之後可能差了 20 公分甚至更多。

覆蓋路徑是從 `/map`（`OccupancyGrid`）算出來的，這些座標**天生就是 map 座標系**：

```python
# scripts/map_server.py:302
fid = map_data.get('frame_id', 'map')     # 從 /map 訊息的 header 拿，不是寫死的
```

填成 `'odom'` 的話，`move_base` 會把這些數字當成 odom 座標去解讀，
機器人會走到偏掉的位置，而且**偏差隨時間越來越大** —— 一開始還看起來正常，
跑久了整條覆蓋路徑就歪出房間了。這種 bug 特別難查，因為它一開始不會發作。
</details>
