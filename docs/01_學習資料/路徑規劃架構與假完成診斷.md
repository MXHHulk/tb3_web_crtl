# 牛耕式覆蓋路徑規劃架構與「假完成」診斷

本文件說明 CCPP 專案從地圖到路徑執行的完整資料流，並針對「明明還有空間沒走到，卻顯示『完成 ✓』」的現象，逐項對應到原始碼定位原因與修正方向。

> 對應檔案：`scripts/map_server.py`、`scripts/coverage_planner.py`、`web/index.html`

---

## 1. 整體架構

```
ROS (/map, /odom, /scan)
        │  訂閱
        ▼
┌─────────────────────────────────────────────┐
│  map_server.py  (Module A，ROS 節點 + Flask) │
│                                              │
│  map_callback   ── 收 OccupancyGrid          │
│     ├ 產生 原始/侵蝕/膨脹 PNG（顯示用）       │
│     └ 存 map_data（規劃用的原始 0/100/-1）   │
│                                              │
│  /coverage/start ── 觸發規劃 + 執行          │
│     ├ apply_safety_margin()  ← 膨脹障礙      │
│     ├ boustrophedon()        ← 算路點        │
│     └ run_coverage() 執行緒  ← 送 move_base  │
└─────────────────────────────────────────────┘
        │  HTTP                    │  actionlib
        ▼                          ▼
   web/index.html             move_base（導航）
   （畫地圖/路徑/狀態）
```

核心分兩個檔：

| 檔案 | 職責 |
| --- | --- |
| `coverage_planner.py` | 純演算法、無 ROS 依賴。提供 `apply_safety_margin`（膨脹障礙）與 `boustrophedon`（算牛耕路點）。 |
| `map_server.py` | ROS 節點，訂閱 topic、跑 Flask 網頁、呼叫上面演算法、用 move_base 執行。 |

> ⚠️ **注意**：`test/boustrophedon.py` 為另一個獨立檔案（已移入 `test/`，不隨 launch 啟動），`map_server.py` 實際 `import` 的是 `coverage_planner` 裡的版本（見 `map_server.py:12`），因此改 `boustrophedon.py` 不會影響機器人行為。舊版架構文件提到的「路徑規劃模組 `boustrophedon.py`」應理解為 `coverage_planner.py`。

## 2. 一次覆蓋規劃的完整流程

按網頁「開始」→ `POST /coverage/start`（`map_server.py:345`）：

1. **取地圖**：拿最新 `map_data['data']`（`0`=自由, `100`=障礙, `-1`=未知）。
2. **膨脹障礙**（`map_server.py:360`）：`apply_safety_margin` 把障礙外擴一圈安全邊距，得到 `safe_obs`。
3. **算可走格**（`map_server.py:361`）：
   ```python
   free = (raw['data'] == 0) & ~safe_obs
   ```
   **只有「已知且為自由」且「不在膨脹障礙內」的格子才算可走。**
4. **算路點**（`map_server.py:363`）：`boustrophedon(free, ...)` 回傳一串 `(wx, wy)`。
5. **執行**：開 `run_coverage` 執行緒，照順序把每個路點丟給 move_base。
6. **報完成**（`map_server.py:248-250`）：清單跑完就 `state='done'` → 前端顯示「完成 ✓」（`index.html:306`）。

---

## 3. `boustrophedon` 怎麼算路點（關鍵）

`coverage_planner.py:29-84` 的作法：

1. 把所有 `free=True` 的格子轉成世界座標點雲。
2. **用 PCA 找一條全域主軸**：長軸 `axis_a`（掃描方向）、短軸 `axis_b`（換行方向）。
3. 沿短軸每隔 `SPACING=0.18m` 切一條掃描帶，對每一帶：
   ```python
   mask    = |proj_b - b| < spacing/2   # 落在這條帶裡的自由格
   p_start = ... a_vals.min() ...       # 帶內投影最小的點
   p_end   = ... a_vals.max() ...       # 帶內投影最大的點
   ```
   **只取這一帶裡最左、最右兩個端點，連成一條直線。**

這個「整張圖單一主軸、每帶只連 min→max」的設計，就是「沒走完卻顯示完成」的主要根源。

## 4. 為什麼「還有空間沒走到，卻顯示完成」

### 原因 1：「完成」只代表路點清單跑完，不代表覆蓋率達標 ★最直接
`run_coverage` 設 `done` 的條件（`map_server.py:248-250`）只是「最後一個路點送完了」，**從未計算實際覆蓋率**。前端 `完成 ✓` 也只是 `state==='done'`（`index.html:306`）。只要 `boustrophedon` 一開始就沒幫某塊區域生路點，那塊永遠不會被走，但清單照樣跑完 → 顯示完成。

### 原因 2：單一全域 PCA 直線掃描，無法處理凹形 / 多房間 ★最常見幾何問題
每條掃描帶只取「最小端點→最大端點」連一條直線（`coverage_planner.py:75-76`）：

- **凹形 / L 形空間**：若某帶的自由格中間被牆隔成兩段，演算法仍只連 min→max 一條直線，**橫跨中間的牆**。中段牆讓 move_base 走不過（被當失敗跳過，`map_server.py:243`），牆另一側的空間雖有端點卻到不了 → 沒被覆蓋。
- **轉角藏的區域**：主軸是全域單一方向，對非矩形房間，掃描線端點對不上實際邊界凹凸，凹角被直線「截彎取直」跳過。

> 正規牛耕覆蓋需要 **Boustrophedon Cellular Decomposition**：在連通性改變的臨界點把空間切成多個子區塊，每塊各自掃。目前這版是「整張圖一條主軸掃到底」，所以非凸空間必留死角。

### 原因 3：未知格（-1）被排除，不會被覆蓋
`free = (raw['data'] == 0) & ...`（`map_server.py:361`）只收**已知自由**格。地圖上灰色未知區（`-1`）一律不規劃。

> 本系統做的是「**覆蓋已知地圖**」，**不是探索（exploration）**——不會主動前往未知區。若看到「沒探索到的空間」是灰色未知區，那是設計上就排除的，不是 bug。

### 原因 4：安全膨脹把窄通道封死，後面整塊被孤立
`~safe_obs` 會把貼牆自由格挖掉。若窄通道被膨脹封死，通道後方房間就算是自由格也跟主區域斷開。`boustrophedon` 不檢查連通性會照樣給端點，但 move_base 過不去 → 失敗跳過 → 那塊沒覆蓋。（與「窄出口被封死」是同一機制的延伸。）

## 5. 排查順序

| 步驟 | 觀察 | 指向原因 |
| --- | --- | --- |
| 1 | 沒走到區域的**顏色**：灰色(未知) | 原因 3 |
| 1 | 沒走到區域的**顏色**：白色(已知自由) | 原因 2 或 4 |
| 2 | console 是否大量 `[coverage] 路點 i/n 跳過（move_base 狀態碼 …）`（`map_server.py:244`） | 路點存在但走不到 → 原因 2 / 4 |
| 3 | 白色區是否**完全沒有藍線**經過 | `boustrophedon` 沒生路點 → 原因 2 截彎取直 |
| 3 | 有藍線但機器人沒跟上 | 執行端跳過 → 原因 4 |

---

## 6. 修正方向

1. **加真正的連通分量分解**（根治原因 2、4）：
   先用 `scipy.ndimage.label` 把 `free` 切成各連通區塊，對每塊分別跑 `boustrophedon`，並用機器人所在區塊過濾掉到不了的孤島。
2. **把「完成」改成有覆蓋率依據**（根治原因 1 的假完成）：
   記錄實際走過 / 可走格的比例，覆蓋率未達門檻就不顯示「完成 ✓」，並回報未覆蓋區塊。
3. **（可選）診斷輸出**：規劃時印出連通區塊數、每塊面積、生成 / 跳過的路點數，用實際數字確認當次屬於哪個原因。
