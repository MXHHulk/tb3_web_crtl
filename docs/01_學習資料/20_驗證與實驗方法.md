# 第 20 章　驗證與實驗方法

> **本章目標**：介紹 `test/` 底下的六隻工具，
> 以及「怎麼證明這個系統真的能運作」的完整方法論。
>
> ★ 一個專題的可信度，不在於它跑起來很順，而在於**你能不能拿出可重現的證據**。

---

## 20.1 ① 問題：怎麼證明它有效？

「我按下開始，機器人跑完了一圈，看起來很順」—— **這不是證據。**

問題：
- **不可重現**：下次跑結果可能不同（地圖不同、起點不同）
- **無法量化**：「很順」是幾 % 的覆蓋率？
- **無法比較**：改了參數之後有沒有變好？
- **無法歸因**：出問題時不知道是演算法、執行層、還是硬體的錯

---

## 20.2 ④ 三層驗證策略

```
   ┌─────────────────────────────────────────────────────┐
   │ 第 3 層：實機驗證                                   │
   │   真實場地、真實機器人、真實 SLAM                   │
   │   ✅ 最有說服力    ❌ 慢、不可重現、無法歸因        │
   └─────────────────────────────────────────────────────┘
                            ↑
   ┌─────────────────────────────────────────────────────┐
   │ 第 2 層：ROS 元件量測                               │
   │   test/test_lidar_*.py、test/map_recorder.py         │
   │   test/boustrophedon.py（RViz 檢視）                │
   │   ✅ 驗證硬體與 ROS 假設    ❌ 仍需要實機           │
   └─────────────────────────────────────────────────────┘
                            ↑
   ┌─────────────────────────────────────────────────────┐
   │ 第 1 層：★ 演算法離線測試                           │
   │   test/coverage_bench.py                            │
   │   ✅ 秒級、完全可重現、可歸因、可自動化             │
   │   ❌ 假設地圖是完美的（沒有 SLAM 雜訊）             │
   └─────────────────────────────────────────────────────┘
```

★ **由下往上做**：先在第 1 層確認演算法是對的，
再上第 2 層確認硬體假設，最後才上第 3 層。

**理由**：第 1 層一次跑 12 種場地只要幾秒，第 3 層跑一次要半小時。
把能在第 1 層抓到的問題留到第 3 層，等於用 500 倍的成本去除同一個蟲。


**驗證的假設**：LDS-01 的規格是 300 rpm = **5 Hz**。

**為什麼重要**：如果實測只有 2 Hz，代表 USB 頻寬、CPU 負載、或驅動有問題 ——
SLAM 的品質會直接受影響，但**症狀會表現成「地圖歪掉」而不是「雷射變慢」**。

> —— 附一段可以直接執行的程式碼，比截圖一個終端機指令有說服力。

### ② `test/test_lidar_range.py` — 量測光達實際有效距離 ★

這是設計得最好的一隻工具。它的思路值得學：

```python
# test/test_lidar_range.py 的 docstring
原理：/scan (sensor_msgs/LaserScan) 有兩種資訊
  1. 驅動「宣告」的上下限 range_min / range_max —— 規格書寫的值
  2. 「實際」量到的 ranges[] —— 超出有效距離的光束會回傳 inf（無效）
本工具把兩者一起印出，並統計每個視窗內「實際量到的最遠有效距離」，
那個數值就是真正的有效距離證據。
```

★ **「宣告值 vs 實測值」的對照，本身就是論證結構。**

```python
# test/test_lidar_range.py：有效讀數的判定
valid = np.isfinite(ranges) & (ranges >= msg.range_min) & (ranges <= msg.range_max)
```

輸出：

```
—— 驅動宣告值（規格）——
  range_min = 0.120 m
  range_max = 3.500 m   ← 驅動聲稱的最大有效距離
  光束數    = 360
—— 實際量測 ——
  正前方(0°)           : 2.847 m
  本視窗最遠有效距離   : 2.983 m
  歷來最遠有效距離     : 3.021 m   ← 有效距離的證據
  有效光束 / 總光束     : 271/360（inf 無效 89 束）
```

★ **配套的實驗方法也寫在 docstring 裡**：

> 建議搭配實驗：把機器人正對一面牆，逐步把牆/目標物往後移，
> 觀察「正前方距離」何時從有限值跳成 `inf` —— 跳掉的那一刻就是有效上限。

**為什麼這個數字重要**：宣告 3.5 m、實測約 3 m 的差距，
直接決定「房間要走多久才建得完整」——
房間比 3 m 寬時，機器人得走到中間才看得到對面，
否則就會留下未知區 → 第 19 章的假完成成因一。

```python
# test/map_server_raw.py 的 docstring
```

## 20.5 第 3 層：實機驗證的標準流程

```
   ① 場地佈置
      - 長方形，長寬比 ≥ 2:1（λ₁/λ₂ > 4，讓 PCA 有意義）★
      - 至少放一個障礙物（才看得到 cell 分解）
      - 記錄尺寸

   ② 建圖
      - 手動遙控繞完整（★ 走進房間中央，不要只繞邊緣）
      - 確認 /map.png 沒有大片灰色未知區

   ③ 規劃前檢查
      - /map_margin.png：通道有沒有被封死
      - 網頁「規劃資訊」：λ₁/λ₂ 是多少（< 1.5 就是退化）

   ④ 按下開始，記錄
      - 螢幕錄影（網頁畫面）
      - 記下：n_runs / n_cells / n_critical / axis_deg / ratio / total
      - 終端機輸出（有沒有「路點 N 跳過」）
```

## 20.6 ★ 怎麼量「覆蓋率」

這是最容易被質疑的數字。三種量法，可信度由低到高：

### 方法 A：目視（❌ 不要在報告裡用）

「看起來都走過了」—— 不可量化、不可重現。

### 方法 B：離線幾何量測（本專案第 21~23 章用的）

```python
# test/coverage_bench.py
covered |= (dx*dx + dy*dy) <= COV_RADIUS ** 2
return float(covered.mean())
```

**定義**：可走格中心離**任一掃描線**的距離 ≤ 0.10 m 的比例。

★ **要在報告裡明確寫出這個定義**，因為：
- 分母是**膨脹後的可走格**，不是房間面積（第 18 章 18.9 Q2）
- 只算**掃描線**，不算轉場線（轉場時機器人也在移動，但那不是有計畫的覆蓋）
- 假設路徑被**完美執行**（沒有定位誤差、沒有路點失敗）

**優點**：完全可重現、秒級、可比較。
**限制**：是「規劃的覆蓋率」，不是「實際的覆蓋率」。

### 方法 C：實機軌跡回放（最有說服力）

```
   ① 執行時記錄實際軌跡（robot_path 已經在記，每 0.1 m 一點）
   ② 把軌跡點取出來（/robot_state 的 path 欄位）
   ③ 用和方法 B 相同的公式，但用「實際軌跡」取代「規劃路徑」
   ④ 得到「實際覆蓋率」
```

★ **這個工具目前還沒寫**，但資料已經全部具備了
（`robot_path` 有記錄，`/robot_state` 有輸出）。

**大約 30 行就能做出來**，而且它會產生本專案最有價值的一張圖：

```
   規劃覆蓋率  vs  實際覆蓋率
   100.0%          ??%      ← 這個差距量化了執行層的所有損失
                              （定位誤差 + 路點失敗 + move_base 繞路）
```

★ **強烈建議把這個做出來** —— 它直接回答「你的系統實際上有多好」。

## 20.7 ⑤ 設計決策

| 決策 | 選了 | 否決了 | 理由 |
|---|---|---|---|
| 測試工具位置 | `test/`，不掛 launch、不安裝 | 放 `scripts/` | 明確區分「產品」與「工具」 |
| 演算法測試 | 離線 + 合成地圖 | 只做實機測試 | 秒級 vs 半小時、可重現 vs 不可重現 |
| 頻率量測 | 自己寫一隻 | 只用 `rostopic hz` | 報告要留可重現的程序 |
| 有效距離 | **宣告 vs 實測對照** | 只引用規格書 | ★ 對照本身就是論證 |
| 原始地圖檢視 | 獨立的最小版本 | 在主程式加開關 | 最小對照組，二分法定位 |
| RViz 檢視 | 獨立節點，共用演算法核心 | 複製一份演算法 | 避免兩份會走鐘的實作 |

## 20.8 ⚠ 這一層的限制

**① 離線測試的地圖是「完美的」**

合成地圖的牆是精確的直線，沒有 SLAM 的雜訊、鬼影、閉環誤差。
⚠ **真實地圖的邊界更破碎**，第 19 章缺陷 #2（鋸齒碎裂）在實機上可能**更嚴重**。

**改進**：用 `map_recorder.py` 錄下的**真實地圖**跑 `coverage_bench`。
資料已經有了（`maps/` 底下），只要加一個「讀 PNG 還原成 OccupancyGrid」的函式。

**② 沒有自動化回歸測試**

改了演算法之後，要人工去看 `coverage_bench` 的輸出有沒有變差。

**改進**：把期望值寫成斷言：

```python
assert evaluate('長方形4x2')['cov'] > 0.99
assert evaluate('含柱4x2')['bad_sweep'] == 0     # ★ 掃描線永不穿牆
assert evaluate('L形4x4')['cells'] == 3
```

★ **`bad_sweep == 0` 是最重要的一條** —— 它是第 09 章 v2 修好的性質，
是這個演算法正確性的核心保證。**任何改動都不該破壞它。**

**③ 沒有量測「實際覆蓋率」**

見 20.6 方法 C。

## 20.9 ⑥ 本章重點回顧

1. ★ **三層驗證，由下往上做**：離線演算法測試（秒級）→ ROS 元件量測 → 實機。
   把能在第 1 層抓到的問題留到第 3 層，成本差 500 倍。
2. **`test/` 刻意不掛 launch、不安裝** —— 這本身就是「不是產品的一部分」的宣告。
3. ★ **`test_lidar_range.py` 的「宣告值 vs 實測值」對照，本身就是論證結構**。
   宣告 3.5 m、實測約 3 m 的差距直接影響建圖完整度。
4. **`map_server_raw.py` 是最小對照組**：懷疑處理弄壞地圖時，
   用它做二分法定位。
5. **`boustrophedon.py` 和 `map_server` 共用同一份演算法核心**，
   所以 RViz 和網頁看到的路徑保證一致。
6. ★ **報告裡寫覆蓋率一定要附上定義**：分母是膨脹後的可走格、只算掃描線、
   假設路徑被完美執行 —— 這是「規劃的覆蓋率」而不是「實際的覆蓋率」。
7. ★ **最值得補做的兩件事**：
   ① 用真實地圖（`maps/`）跑離線測試；
   ② 用實際軌跡量「實際覆蓋率」，和規劃覆蓋率對照。

## 20.10 ⑦ 自我檢核題

**Q1. 為什麼要花時間寫 `test_lidar_freq.py`？`rostopic hz /scan` 一行就做到了。**

<details>
<summary>參考答案</summary>

**功能上確實重複，價值在別的地方：**

**① 留下可重現的量測程序**

報告裡寫「我們用 `rostopic hz` 量到 5 Hz」，讀者只能相信你。
附上一段可以直接執行的程式碼，讀者可以**自己跑一次驗證**。
這是實驗可重現性的基本要求。

**② 輸出格式可以自己控制**

```
收到訊息總數: 47 | 總運行時間: 9.42s | 平均頻率: 4.99 Hz
```

包含了「總數」和「總時間」—— 讀者可以自己驗算。
`rostopic hz` 只給一個瞬時平均值。

**③ 可以擴充**

想加「最大間隔」「抖動標準差」「掉幀次數」時，改自己的程式碼就好。

**④ 教學價值**

它是最小的 ROS 訂閱者範例（30 行），
本講義第 01 章就是用它和 `boustrophedon.py` 當 pub/sub 的教材。

★ **但要誠實**：如果只是為了「知道現在幾 Hz」，`rostopic hz` 更快。
自己寫的價值在**留下證據**，不在功能。
</details>

**Q2. 你在報告裡寫「覆蓋率 100%」。口試委員問「這 100% 是怎麼算的？」
你要怎麼回答才不會被抓漏洞？**

<details>
<summary>參考答案</summary>

★ **一定要主動說明定義和限制，不要等被追問。**

> 「這是**離線的規劃覆蓋率**，定義是：
>
> **『膨脹後的可走格中，中心點距離任一條掃描線 ≤ 0.10 公尺的比例』**
>
> 三個要點：
>
> **① 分母是膨脹後的可走格**，不是房間的實際面積。
> 安全邊距吃掉的部分（約 10%）不列入分母。
>
> **② 只計算掃描線，不計算轉場線。**
> 機器人在轉場時也在移動、也在覆蓋，但那不是有計畫的覆蓋，
> 我們保守地不算進去。
>
> **③ 0.10 公尺是機器人的覆蓋半徑**（清掃/感測範圍的一半）。
>
> **這個數字假設路徑被完美執行** —— 沒有定位誤差、沒有路點失敗、
> `move_base` 沒有繞路。所以它是**規劃品質的上界**，不是實際表現。
>
> 實際表現會更低，主要損失來自三個地方：
> 定位誤差、`move_base` 對到不了的路點回傳失敗（我們會跳過），
> 以及 cell 之間的轉場沒有避障規劃導致的繞路。
>
> ★ 要量『實際覆蓋率』的話，我們有記錄實際行走軌跡（每 0.1 m 一點），
> 用同樣的公式套在實際軌跡上就能得到 —— 這是我們接下來要補的實驗。」

★ **這個回答的價值**：你不只給了數字，還給了**數字的邊界**。
主動說出限制比被抓到限制好一百倍。
</details>

**Q3. `map_server_raw.py` 只做 `map_server.py` 的一小部分功能。
為什麼要維護這樣一支「功能較少」的程式？**

<details>
<summary>參考答案</summary>

★ **它是一個「最小對照組」，用途是二分法除錯。**

`map_server.py` 從 `/map` 到網頁上的圖，中間經過：

```
   OccupancyGrid → int16 轉換 → 三種形態學 → 灰階映射
                 → 裁切 (_crop) → 上下翻轉 → PNG 編碼 → HTTP
```

**任何一步都可能出錯**，而症狀都是「網頁上的地圖看起來不對」。

`map_server_raw.py` 把中間全部拿掉：

```
   OccupancyGrid → 灰階 → PNG → HTTP
```

**除錯流程**：

```
   網頁地圖看起來不對
        │
        ├─ 開 map_server_raw.py
        │
        ├─ 原始地圖就不對  → 問題在 SLAM / 感測器 → 用 test_lidar_*.py 往下查
        │
        └─ 原始地圖是對的  → 問題在我們的處理 → 用二分法逐段檢查
                              （先關裁切、再關形態學…）
```

★ **這種「拿掉所有可疑功能的最小版本」是系統除錯的標準武器。**

**類比**：醫生排除診斷、電路的最小可運作系統、
軟體的 minimal reproducible example。

**維護成本很低**（122 行，而且幾乎不會變），
**價值在出問題的那一天**才會顯現 —— 而那一天通常是 demo 前一晚。
</details>

**Q4. 20.6 提到的「方法 C：實機軌跡回放」還沒實作。
如果要你做，具體要寫什麼？會遇到什麼困難？**

<details>
<summary>參考答案</summary>

**要寫的東西（約 30~50 行）：**

```python
# ① 取得實際軌跡（執行完成後，網頁還顯示著）
import requests
d = requests.get('http://<ip>:8080/robot_state').json()
path_px = d['path']                    # ⚠ 這是像素座標，要轉回世界座標

# ② 取得當時的地圖（要能還原成 free 陣列）
# ⚠ 困難點 1：/map.png 是渲染過的灰階圖，不是原始 OccupancyGrid

# ③ 用和 coverage_bench 相同的公式
covered = 每個 free 格離任一軌跡線段 <= 0.10 m
ratio = covered.mean()
```

**三個困難：**

**⚠ 困難 1：`/robot_state` 只回像素座標**

`path` 欄位是 `world_to_px` 轉換過的。要轉回世界座標需要
`origin_x/y`、`resolution`、`r0`、`c0`、`crop_h` —— 而 API 只回 `resolution`。

**解法**：新增一個 `/robot_state?raw=1` 回傳世界座標，或直接在後端算。
★ **在後端算更好**：後端本來就有 `robot_path`（世界座標）和 `map_data`。

**⚠ 困難 2：拿不到原始的 `free` 陣列**

`/map.png` 是渲染過的。要重建 `free` 需要原始的 `OccupancyGrid`。

**解法**：新增一個 `/coverage/report` 路由，在後端直接算完回傳 JSON。

**⚠ 困難 3：軌跡是離散點（每 0.1 m）**

線段之間要內插。但 0.1 m 的間隔遠小於 0.10 m 的覆蓋半徑，
直接把相鄰兩點連成線段就夠了（和 `coverage_bench` 的處理方式一樣）。

**建議的做法**：★ **做成後端的一條路由 `/coverage/report`**

```python
@app.route('/coverage/report')
def coverage_report():
    with cov_lock:   path_plan = list(cov_path); st = dict(cov_status)
    with robot_lock: path_real = list(robot_path)
    with map_lock:   raw = dict(map_data); meta = dict(map_meta)

    free = (raw['data'] == 0) & ~apply_safety_margin(raw['data'], COV_MARGIN, meta['resolution'])
    return jsonify({
        'planned_coverage': coverage_of(free, path_plan, sweep_only=True),
        'actual_coverage':  coverage_of(free, path_real, sweep_only=False),
        'planned_length':   length_of(path_plan),
        'actual_length':    length_of(path_real),
        'skipped':          st.get('skipped', 0),
    })
```

★ **產出的四個數字就是這個專案最有價值的實驗結果**：

```
   規劃覆蓋率 100.0%  vs  實際覆蓋率  ??%
   規劃路徑長  37.5 m  vs  實際路徑長  ?? m   ← 直接量化缺陷 #1
```
</details>

**Q5. 20.8 說「離線測試的地圖是完美的，真實地圖更破碎」。
這對第 22 章的實測結論有什麼影響？**

<details>
<summary>參考答案</summary>

★ **實測結論是「樂觀的下界」—— 真實情況只會更糟，不會更好。**

**具體影響哪些指標：**

| 指標 | 合成地圖 | 真實地圖預期 | 為什麼 |
|---|---|---|---|
| 掃描線穿牆 | 0 | **仍是 0** | 中心線取樣是構造性保證，和地圖品質無關 |
| **cell 數** | 1~5（斜置 30° 例外） | ⚠ **可能更多** | 邊界更破碎 → run 更容易碎裂 |
| **覆蓋率** | 96~100% | ⚠ **更低** | 破碎邊界 + 未知格 |
| 轉場穿牆 | 0~30 | ⚠ **更多** | 更多 cell → 更多轉場 |
| 主軸角度 | 精確 | 略有偏差 | SLAM 的牆面不是完美直線 |

★ **最關鍵的是「鋸齒碎裂」（第 19 章缺陷 #2）會更嚴重**。

合成地圖的邊界是精確的直線光柵化，鋸齒是**規則的**。
真實 SLAM 地圖的邊界有雜訊、鬼影、閉環誤差，鋸齒是**不規則的** ——
掃描帶的中心線更容易在 free / 不 free 之間反覆穿越。

**這代表什麼**：
1. **第 22 章的 cell 數是下界**，實機可能更多
2. **「只有斜置 30° 會碎裂」的結論不能外推到實機** ——
   實機上任何角度都可能碎裂
3. ★ **缺陷 #2 的修復優先度應該提高**

**該補的實驗**：把 `maps/20260627_150914/` 底下錄下來的**真實地圖 PNG**
還原成 `OccupancyGrid`（灰階 → 0/100/-1），餵給 `coverage_bench`。

需要一個 `load_recorded_map(png_path)` 函式，約 15 行。
⚠ 但要注意 PNG 是裁切 + 翻轉過的，還原時要反向處理，
而且原始的 `resolution` / `origin` 沒有存在 PNG 裡 ——
**這暴露了 `map_recorder.py` 的一個缺陷：應該同時存一個 `.yaml` 記錄 metadata。**
</details>
