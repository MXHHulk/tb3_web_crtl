## 22.2 基準組：長方形 4×2

```
   ┌──────────────────────────────────┐
   │ ●━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━● │  10 條掃描線
   │ ●━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━● │  1 個 cell
   │ ●━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━● │  0 個臨界點
   │ ...                              │  覆蓋率 100.0%
   └──────────────────────────────────┘  轉場佔比 4.1%
```

★ **這是「一切正常」長什麼樣的基準**：
- **cell = 1**：沒有障礙物切開掃描線
- **臨界點 = 0**：空間結構沒有變化
- **λ₁/λ₂ = 4.58**：長寬比 2:1 → 主軸非常可信，準確給出 0.0°
- **轉場佔比 4.1%**：只有 9 次換行，每次 0.18 m
- **覆蓋率 100.0%**：`SPACING=0.18 < 覆蓋寬 0.20`，重疊 10%

**判斷其他場地好不好，就是和這一組比。**

## 22.3 障礙物組：含柱、雙柱

### 含柱 4×2 —— ★ 教科書等級的 cell 分解

```
=== 含柱4x2 逐帶診斷 ===
主軸 0.00°   λ比 4.64   帶數 10   run 總數 14
  band 0 b=-0.785 runs= 1 [-1.90,+1.90]
  band 1 b=-0.605 runs= 1 [-1.90,+1.90]
  band 2 b=-0.425 runs= 1 [-1.90,+1.90]
  band 3 b=-0.245 runs= 2 [-1.90,-0.43] [+0.38,+1.90]   ← ★ split
  band 4 b=-0.065 runs= 2 [-1.90,-0.43] [+0.38,+1.90]
  band 5 b=+0.115 runs= 2 [-1.90,-0.43] [+0.38,+1.90]
  band 6 b=+0.295 runs= 2 [-1.90,-0.43] [+0.38,+1.90]
  band 7 b=+0.475 runs= 1 [-1.90,+1.90]                 ← ★ merge
  band 8 b=+0.655 runs= 1 [-1.90,+1.90]
  band 9 b=+0.835 runs= 1 [-1.90,+1.90]
cells=4  臨界點=[(2, 'split'), (11, 'merge')]
cell 內 run 數分布: [3, 3, 4, 4]
```

```
   ┌────────────────────────────────┐
   │          cell（3 runs）         │  band 7~9
   ├──────────────┬──────┬──────────┤  ← merge（run #11）
   │ cell（4 runs）│██████│cell（4）  │  band 3~6
   ├──────────────┴──────┴──────────┤  ← split（run #2）
   │          cell（3 runs）         │  band 0~2
   └────────────────────────────────┘
```

★ **和第 11 章的理論推導完全一致**：
1 個 split + 1 個 merge → 4 個 cell、每個 cell 內每條帶都只有 1 段。

**覆蓋率 100.0%、轉場佔比 7.2%、穿牆 0/0** —— 完美。

> 💡 ★ **這是 demo 和口試最該用的場地**：
> 長方形 + 一個中央柱子。cell 分解看得清清楚楚，
> 而且所有指標都是滿分，沒有需要解釋的異常。

### 雙柱 4×2 —— 轉場開始變貴

| | 含柱 | 雙柱 |
|---|---|---|
| cell | 4 | **5** |
| run | 14 | **22** |
| 轉場長 | 2.7 m | **6.5 m** |
| **轉場佔比** | 7.2% | ⚠ **17.8%** |
| 穿牆轉 | 0 | **2** |

★ **多一個柱子，轉場成本從 7% 跳到 18%** ——
因為 cell 變多，cell 之間的跳躍距離也變長。

**覆蓋率 98.4%**：損失來自兩個柱子之間的窄縫，
被 `min_len` 濾掉了一些短 run。

## 22.4 ★★ 非凸組：L 形、U 形

### L 形 4×4 —— **可以跑，但不漂亮**

★ **這是本講義最重要的一組數據，直接回答「能不能跑 L 形房間」。**

```
=== L形4x4 逐帶診斷 ===
主軸 -45.00°   λ比 2.30   帶數 22   run 總數 30
  band  0 b=-2.093 runs= 1 [-0.12,+0.12]    ← 只有 0.24 m！
  band  1 b=-1.913 runs= 1 [-0.30,+0.30]
  band  2 b=-1.733 runs= 1 [-0.48,+0.48]
  ...（長度逐漸增加）
  band 13 b=+0.247 runs= 1 [-2.46,+2.46]    ← 4.92 m
  band 14 b=+0.427 runs= 2 [-2.64,-0.11] [+0.10,+2.64]   ← ★ split
  band 15 b=+0.607 runs= 2 [-2.62,-0.28] [+0.28,+2.62]
  ...
cells=3  臨界點=[(?, 'split')]
```

**結論：能跑，覆蓋率 100.0%，cell 分解正確切成 3 塊，掃描線 0 條穿牆。**

⚠ **但主軸是 −45°（對角線）**：

```
        ┌─────────┐
        │ ╲ ╲ ╲ ╲ │        PCA 給的主軸是對角線
        │  ╲ ╲ ╲ ╲│        橫支和豎支都差 45°
        │   ╲ ╲ ╲ ├────────┐
        │    ╲ ╲ ╲ ╲ ╲ ╲ ╲ │
        │     ╲ ╲ ╲ ╲ ╲ ╲ ╲│
        └──────╲─╲─╲─╲─╲─╲─┘
```

**為什麼是 −45°**：對稱的 L 形（4×4 挖掉右上 2×2）在對角線方向上是對稱的，
共變異數矩陣的特徵向量必定沿著對角線。★ **PCA 給的是數學上正確的答案** ——
那確實是這堆點最分散的方向。

### ⚠ 代價：效率

| | L 形 4×4 | 同面積長方形（推算） |
|---|---|---|
| 面積 | 10.6 m² | 10.6 m² |
| 掃描長 | **58.8 m** | ~53 m（10.6 ÷ 0.20） |
| 轉場長 | **9.1 m** | ~2 m |
| **總長** | **67.9 m** | **~55 m** |
| 轉場佔比 | 13.4% | ~4% |

★ **多走約 23%**，主要是轉場成本（9.1 m vs ~2 m）。

**還有一個從診斷表才看得出來的問題**：

```
   band 0：[-0.12, +0.12]  → 只有 0.24 m
   band 1：[-0.30, +0.30]  → 0.60 m
   band 2：[-0.48, +0.48]  → 0.96 m
```

★ **對角線掃描讓角落附近出現一堆極短的掃描線。**
機器人要為了 0.24 m 的一小段跑一趟（前後各要轉向、加減速），
**時間成本遠高於路徑長度所反映的**。

### L 形扁平（5×3 挖掉右上）—— 主軸有救

| | L 形 4×4（對稱） | L 形扁平（不對稱） |
|---|---|---|
| 主軸 | ⚠ **−45.0°** | **−20.1°** |
| λ₁/λ₂ | 2.30 | **4.60** |
| 覆蓋率 | 100.0% | 99.2% |
| 轉場佔比 | 13.4% | 15.9% |

★ **不對稱的 L 形，主軸就不會落在對角線上**（−20.1°，比較靠近橫支）。
λ₁/λ₂ 也高得多（4.60 vs 2.30），代表主軸更可信。

> 💡 **實務建議**：如果一定要用 L 形場地，**讓兩支的長度明顯不同**。
> 對稱的 L 形是 PCA 最差的情況。

### U 形 —— 分解非常乾淨

```
=== U形 逐帶診斷 ===
主軸 0.43°   λ比 2.48   帶數 16   run 總數 26
  band  0~4  runs= 1 [-1.92,+1.90]              ← 底部，整條
  band  5~14 runs= 2 [-1.92,-0.94] [+0.87,+1.90] ← 兩支
  band 15    runs= 1 [-1.92,-0.93]              ← 左支頂端
cells=3  臨界點=[(4, 'split')]
cell 內 run 數分布: [5, 10, 11]
```

★ **U 形的主軸是 0.43°（幾乎水平）—— 非常正確！**

因為 U 形的底部是一整條水平的長條，主導了 PCA。
分解結果是「底部 + 左支 + 右支」三個 cell，**完全符合直覺**。

⚠ **注意只有 1 個臨界點（split），沒有 merge**：
因為兩支到頂就結束了，沒有再合併回去。
（band 15 只有左支，它的前驅只有 band 14 的左段 → 一對一 → 不算 merge。）

★ **U 形比 L 形好，因為它有一條「主導方向」明確的底部。**

## 22.5 ★★ 斜置組：最重要的發現

### 三個角度的對照

| | 斜置 15° | **斜置 30°** | 斜置 45° |
|---|---|---|---|
| 主軸 | 15.0° ✓ | 30.1° ✓ | 45.0° ✓ |
| λ₁/λ₂ | 4.57 | 4.66 | 4.59 |
| **cell** | **1** | ⚠ **23** | **1** |
| **run** | 10 | ⚠ **31** | 9 |
| 覆蓋率 | 100.0% | 100.0% | ⚠ 95.9% |
| **穿牆轉** | ⚠ 8 | ⚠ **30** | 3 |

★ **三個場地是完全相同的 4×2 長方形，只是轉了不同的角度。**
PCA 每次都準確算出角度（15.0 / 30.1 / 45.0），
**但 cell 數從 1 爆成 23 又回到 1。**

### 診斷：斜置 30° 到底發生了什麼

```
=== 斜置30度 逐帶診斷 ===
主軸 30.05°   λ比 4.66   帶數 10   run 總數 31
  band 0 b=-0.775 runs= 1 [-1.86,+1.87]
  band 1 b=-0.595 runs= 1 [-1.86,+1.87]
  band 2 b=-0.415 runs= 1 [-1.86,+1.86]
  band 3 b=-0.235 runs= 1 [-1.84,+1.86]
  band 4 b=-0.055 runs= 1 [-1.85,+1.84]
  band 5 b=+0.125 runs= 1 [-1.86,+1.83]
  band 6 b=+0.305 runs= 1 [-1.86,+1.87]
  band 7 b=+0.485 runs= 1 [-1.86,+1.87]
  band 8 b=+0.665 runs= 1 [-1.84,+1.86]
  band 9 b=+0.845 runs=22  ⚠ 碎裂
     [-1.79,-1.71] [-1.68,-1.51] [-1.50,-1.41] [-1.39,-1.11]
     [-1.09,-1.01] [-0.98,-0.71] … 共 22 段
cells=23  臨界點=[(8, 'split')]
cell 內 run 數分布: [1, 1, 1, ... （22 個 1）..., 9]
```

★ **前 9 條帶完全正常（各 1 條 run），只有最後一條（band 9）碎成 22 段。**

### 根因

`b_centers` 的最後一項是 `b = +0.845`，而 `proj_b` 的最大值大約是 **+0.9**。

★ **這條中心線離可走區的邊界只有 0.055 m（約 1 格）—— 它正好貼著光柵化後的鋸齒邊界走。**

```
   斜 30° 的房間邊界，光柵化之後是階梯狀：

        ┌─┐
      ┌─┘ └─┐
    ┌─┘     └─┐          ← 邊界
   ─┴───────────┴─
   ●●●○○●●●○○●●●○○      ← band 9 的中心線取樣
      ↑  ↑  ↑
   在階梯上進進出出 → free / 不 free 交替
```

**每隔幾公分就 free / 不 free 交替一次** → `_true_runs` 切出 22 段。

而 `min_len = res`（0.05 m）**擋不住這些碎片** ——
它們的長度是 **7~28 cm**，全部通過了門檻。

### 後果

```
   22 段短 run
     ↓ 每一段的 pred / succ 都是空的（band 8 是唯一的前驅，但它 succ 有 22 個）
   22 個「只有 1 條 run」的獨立 cell
     ↓ 貪婪走訪順序要在這 22 個 cell 之間跳來跳去
   30 段轉場穿牆
```

★ **實際跑起來會怎樣**：機器人走完前 9 條正常的掃描線之後，
會在房間邊緣做 **22 趟毫無意義的短程來回**，
每一趟之間 `move_base` 都要繞路。

**規劃器報「轉場長 2.2 m」，但實際可能要繞好幾十公尺。**

### ★★ 這是「刀鋒條件」，不是「30 度的問題」

| 角度 | 最後一帶的位置 | 結果 |
|---|---|---|
| 15° | `b=+0.833`，明顯在**裡面** | 1 條 run，正常 |
| **30°** | `b=+0.845`，**正好貼在邊界上** | ⚠ 碎成 22 段 |
| 45° | `b=+0.861`，明顯在**外面** | 0 條 run，覆蓋率 95.9% |

★ **最後一帶落在哪，是 `b_min`、`b_max`、`spacing` 三個量相除取餘數決定的
—— 本質上是準隨機的。**

**任何角度、任何房間尺寸、任何 `spacing` 都可能觸發。**

⚠ **而且合成地圖的邊界是規則的階梯。真實 SLAM 地圖的邊界有雜訊、鬼影、
閉環誤差，鋸齒是不規則的 —— 實機上會更容易發作。**

### 為什麼 15° 也有 8 段轉場穿牆（明明只有 1 個 cell）？

因為 **cell 內部的換行接駁**也會穿牆：

```
   斜置的房間，掃描線的端點在鋸齒邊界上：

   ●━━━━━━━━━━━━━━━━━━━●
                       ╲      ← 從這條的右端，到下一條的右端
   ●━━━━━━━━━━━━━━━━━━━━●        中間切過房間外的一角
```

軸對齊的房間不會發生（端點都在同一條垂直線上），
**斜置的房間，相鄰兩條掃描線的端點會錯開，接駁線就會切出去。**

★ 這是缺陷 #1 的另一種表現形式，而且是**斜置場地特有的**。

## 22.6 極端組：細長、正方形、窄通道

### 細長 6×1.5 —— λ 最高，但覆蓋率最低

| 指標 | 值 |
|---|---|
| λ₁/λ₂ | **18.80** ← 全場最高，主軸極度可信 |
| cell | 1 |
| **覆蓋率** | ⚠ **96.3%** ← 全場第二低 |
| 轉場佔比 | 2.6% ← 全場最低 |

```
=== 細長6x1.5 逐帶診斷 ===
主軸 0.00°   λ比 18.80   帶數 8   run 總數 7
  band 0~6 runs= 1 [-2.90,+2.91]
  band 7   runs= 0                    ← ⚠ 最後一條帶落在可走區外
```

★ **8 條帶只產生 7 條 run** —— 最後一條完全落空。

損失的面積 ≈ 那一條帶的寬度（最多 0.18 m）× 長度（5.8 m）≈ **0.3~0.5 m²**，
佔 7.9 m² 的 4~6% —— 和實測的 3.7% 損失吻合。

★ **這是缺陷 #2 的「A 型」發作（落空），對照斜置 30° 的「B 型」（碎裂）。**

### 正方形 3×3 —— ★ PCA 完全退化

| 指標 | 值 |
|---|---|
| **λ₁/λ₂** | ⚠ **1.00** ← 完全退化 |
| 主軸 | 0.0°（**但這個數字沒有意義**） |
| cell | 1 |
| 覆蓋率 | 98.2% |

★ **λ₁/λ₂ = 1.00 代表點集在所有方向上一樣分散。**

兩個特徵值相等時，**任何方向都是特徵向量** ——
`np.linalg.eigh` 回傳 0.0° 純粹是實作細節（它對退化情況會回傳軸對齊的基底）。

⚠ **不影響覆蓋率**（98.2%，只比 100% 低一點），
**但「PCA 自動對齊主軸」這個賣點在正方形上完全沒有作用。**

> ★ **這證實了「場地必須是長方形」這條經驗**：
> 不是因為演算法會壞，而是因為**正方形場地無法展示 PCA 的價值**。
> 口試時如果用正方形場地，被問「你怎麼證明 PCA 有用」會答不出來。
>
> **建議：展示場地的長寬比至少 2:1（λ₁/λ₂ > 4）。**

### 窄通道 0.5 m —— 通過

```
   ┌──────┐                    ┌──────┐
   │ 房間 │────── 0.5 m ──────│ 房間 │
   │  A   │      走廊          │  B   │
   └──────┘                    └──────┘
```

| 指標 | 值 |
|---|---|
| cell | 5 |
| **覆蓋率** | **100.0%** ✓ |
| 穿牆掃 | **0** ✓ |

★ **0.5 m 的走廊，`MARGIN = 0.10` 之後剩 0.30 m，機器人（直徑 ~0.20 m）通得過。**

（第 18 章 18.3 的 `MARGIN` 掃描顯示，走廊中段的可走格數
從 147（`MARGIN=0.10`）降到 21（`MARGIN=0.25`）—— 那時只剩 1 格寬。）

### 雙房間走廊 —— 臨界點的教學範例

```
=== 雙房間走廊 逐帶診斷 ===
主軸 0.00°   λ比 12.57   帶數 10   run 總數 18
  band 0~3 runs= 2 [-2.66,-0.89] [+0.82,+2.65]   ← 兩個房間各自
  band 4   runs= 1 [-2.66,+2.65]                 ← ★ merge（走廊高度）
  band 5   runs= 1 [-2.66,+2.65]
  band 6~9 runs= 2 [-2.66,-0.89] [+0.82,+2.65]   ← ★ split（走廊上方）
cells=5  臨界點=[(8, 'merge'), (9, 'split')]
cell 內 run 數分布: [2, 4, 4, 4, 4]
```

★ **這是「merge 在前、split 在後」的少見案例。**

一般的障礙物是「先 split 後 merge」（掃描線先被切開、再合併）。
這裡是**兩個房間先各自存在（2 段），在走廊的高度合併成 1 段，過了走廊又分開**。

```
   ┌──────┐              ┌──────┐
   │  4   │              │  4   │      band 6~9：兩段
   ├──────┴──────────────┴──────┤      ← split
   │            2                │      band 4~5：一段（穿過走廊）
   ├──────┬──────────────┬──────┤      ← merge
   │  4   │              │  4   │      band 0~3：兩段
   └──────┘              └──────┘
```

**5 個 cell、覆蓋率 98.9%、轉場佔比 14.6%。**

## 22.7 ★★ 未探索 4×2 —— 量化「假完成」

場地是完整的 4×2 房間，但**右側 1.2 m 被設成未知（`-1`）**，
模擬「SLAM 還沒看到那一塊」。

| | 完整地圖 | **未探索版本** |
|---|---|---|
| 可走面積 | 6.9 m² | ⚠ **4.9 m²**（−29%） |
| cell | 1 | 1 |
| λ₁/λ₂ | 4.58 | 2.25 |
| **回報的覆蓋率** | 100.0% | ⚠ **100.0%** |
| **對真實房間的覆蓋率** | **100%** | ⚠ **71%** |
| 掃描長 | 38.0 m | 26.6 m |

★★ **演算法回報 100%，實際只走了 71%。**

**為什麼**：覆蓋率的分母是「膨脹後的**已知**可走格」。
未知格根本不進規劃，所以它們**不在分母裡，也不在分子裡** ——
從演算法的角度看，那塊區域「不存在」。

```python
# scripts/map_server.py:469
free = (raw['data'] == 0) & ~safe
#                     ↑ 只有 0，-1 完全被排除
```

★ **而且從輸出完全看不出異常**：cell = 1、覆蓋率 100%、穿牆 0 ——
所有指標都是滿分。

**唯一的線索是「可走面積」和「掃描長」偏小**，
但如果你不知道房間應該多大，這兩個數字也看不出問題。

### 這對實機的意義

第 02 章 2.2 講過，LDS-01 的實測有效距離只有約 **3 公尺**。
房間比 3 m 寬時，機器人**必須走到中間**才看得到對面的牆。

⚠ **如果建圖時只推著繞了一圈牆邊，房間中央會是一大片未知**
—— 然後演算法會回報「完成」，而中央從來沒被掃過。

★ **這是實機上最容易遇到的「假完成」**（第 19 章成因一）。

**建議的改進**（第 19 章）：
`/coverage/start` 回傳「未知格佔已知邊界內的比例」，超過 5% 就在網頁上警告。

## 22.9 ⑦ 自我檢核題

**Q1. 口試委員問：「你的演算法能不能跑 L 形的房間？」請完整回答。**

<details>
<summary>參考答案</summary>

★ **「能跑，覆蓋率 100%，但效率有明顯代價，而且我們知道原因。」**

> 「可以。我們用合成地圖實測過一個 4×4 挖掉右上角 2×2 的 L 形房間：
>
> **正確性方面：**
> - **覆蓋率 100.0%**
> - **30 條掃描線，沒有任何一條穿過障礙物**
> - cell 分解正確地把空間切成 **3 塊**，臨界點偵測正常
>
> **效率方面有明顯代價：**
> - PCA 算出的主軸是 **−45°（對角線）**，橫支和豎支**都沒有對齊**
> - 總路徑長 **67.9 公尺**，而同樣 10.6 m² 面積的長方形只要約 **55 公尺**，多了 23%
> - 轉場佔比 13.4%（長方形只有 4.1%）
> - ⚠ 而且逐帶診斷顯示，角落附近有一堆極短的掃描線（最短只有 **0.24 公尺**），
>   機器人要為了這一小段跑一趟並轉向兩次，**時間成本比路徑長度反映的更高**
>
> **為什麼會這樣**：對稱的 L 形在對角線方向上是對稱的，
> 共變異數矩陣的特徵向量必定沿對角線 —— **PCA 給的是數學上正確的答案**，
> 那確實是這堆點最分散的方向。問題在於「最分散的方向」不等於「最好掃的方向」。
>
> **驗證這個解釋**：我們另外測了一個**不對稱**的 L 形（5×3 挖掉右上），
> 主軸變成 **−20.1°**、λ₁/λ₂ 從 2.30 升到 **4.60** —— 明顯好得多。
> 這證實了問題出在對稱性。
>
> ★ **改進方向**：不是『各 cell 各自求 PCA』（我們實測過，
> 效益只有 5.8%，而且會破壞 cell 的定義性質，26% 的帶會分裂）。
> 正確的方向是『**先幾何分區、再對每區跑完整流程**』——
> 用凸分解把 L 形切成兩個矩形，各自求軸。這屬於另一個演算法。」
</details>

**Q2. 斜置 30° 產生 23 個 cell，但 15° 和 45° 都只有 1 個。
這是不是代表「30 度附近的場地不能用」？**

<details>
<summary>參考答案</summary>

**不是。這個現象和「30 度」本身沒有關係。**

★ **根因是「最後一條掃描帶落在哪」**，而那由三個量決定：

```python
n_bands = int(np.floor((b_max - b_min) / spacing)) + 1
最後一帶 b = b_min + spacing/2 + spacing × (n_bands − 1)
```

這個值和 `b_max` 的關係，本質上是 `(b_max − b_min) / spacing` 的**餘數**——
準隨機的。

**三種落點：**

| 角度 | 最後一帶 | 結果 |
|---|---|---|
| 15° | `+0.833`，明顯在裡面 | 1 條 run，正常 |
| **30°** | `+0.845`，**正好貼在鋸齒邊界** | ⚠ 碎成 22 段 |
| 45° | `+0.861`，明顯在外面 | 0 條 run，覆蓋率 95.9% |

★ **換一個房間尺寸、換一個 `spacing`、地圖多一格少一格，發作的角度就完全不同。**

所以正確的說法是：
> **「任何角度都可能觸發，30° 只是我們的測試中剛好撞上的那一個。」**

⚠ **而且合成地圖的邊界是規則的階梯，真實 SLAM 地圖的邊界有雜訊，
鋸齒是不規則的 —— 實機上更容易發作。**

**這也是為什麼修法要處理根因**（讓 `b_centers` 均勻分布在
`[b_min + spacing/2, b_max − spacing/2]` 之內，第 19 章 19.4），
而不是「避開某些角度」或「調 `min_len`」—— 那些只是換一顆骰子。
</details>

**Q3. 「未探索 4×2」的覆蓋率是 100.0%，但實際只走了房間的 71%。
為什麼演算法看不出這件事？要怎麼改？**

<details>
<summary>參考答案</summary>

★ **因為未知格（`-1`）根本不在演算法的世界裡。**

```python
free = (raw['data'] == 0) & ~safe
```

只有 `data == 0`（確定自由）才進入 `free`。
`-1`（未探索）既**不在分母**（可走格總數），也**不在分子**（被覆蓋的格數）。

從 `plan()` 的角度看，那塊區域**不存在** —— 它完美地覆蓋了「它知道的世界」。

**而且所有指標都是滿分**：cell = 1、覆蓋率 100%、穿牆 0。
唯一的線索是「可走面積 4.9 m²」和「掃描長 26.6 m」偏小，
但如果你不知道房間應該多大，這兩個數字也看不出問題。

**怎麼改（由簡到繁）：**

**① 回報未知格比例**（最簡單，~10 行）

```python
known_free = (data == 0).sum()
unknown    = (data == -1).sum()
# 但要限制在「已知區域的凸包/邊界內」，否則地圖外的大片 -1 會讓數字沒意義
```

在 `/coverage/start` 的回應裡加 `unknown_ratio`，
前端在超過 5% 時顯示警告：「⚠ 地圖有 12% 未探索，建議先繼續建圖」。

**② 把 frontier 納入規劃**（中等）

Frontier = 「已知自由格」和「未知格」的邊界。
先規劃一趟去這些邊界，讓 SLAM 補完地圖，再規劃覆蓋。

**③ 兩階段任務**（完整）

`探索模式` → 地圖穩定（frontier 消失）→ `覆蓋模式`。

★ **短期一定要做 ①**：它成本極低，而且直接把
「我不知道我不知道什麼」變成「我知道我不知道多少」。
</details>

**Q4. 為什麼「斜置 15°」只有 1 個 cell，卻仍然有 8 段轉場穿牆？**

<details>
<summary>參考答案</summary>

★ **因為 cell 內部的「換行接駁」也算轉場，而斜置的房間換行接駁會切出去。**

**軸對齊的房間**：

```
   ●━━━━━━━━━━━━━━━●    掃描線的端點都在同一條垂直線上
                    │    換行接駁是垂直的短線段，完全在房間內
   ●━━━━━━━━━━━━━━━●
```

**斜置的房間**：

```
        ╱━━━━━━━━━━●        掃描線的端點沿著斜牆錯開
       ╱          ╱ ╲       接駁線從一個端點連到下一個端點
      ╱━━━━━━━━━━●   ╲ ← 中間切過房間外的一角
     ╱          ╱
    ╱━━━━━━━━━━●
```

★ **因為 `b_centers` 的兩端點是取「整個可走區沿長軸的極值」**
（`_slice_runs` 的 `a_range` 參數），
每條帶的實際端點會落在斜牆上不同的 `a` 位置。
相鄰兩條的端點錯開之後，直線接駁就會切到牆外的三角區。

**10 條掃描線 → 9 個接駁 → 其中 8 個穿牆**，比例極高。

★ **這證明缺陷 #1（轉場沒有避障規劃）在斜置場地上是常態，不是例外**
—— 而**真實場地幾乎一定是斜的**（SLAM 的座標軸由開機朝向決定）。

**實際影響**：機器人每換一條掃描線，`move_base` 都要繞一小段路。
單次可能只多幾十公分，但 9 次累積起來就是好幾公尺，
而規劃器報的「轉場長 1.6 m」完全反映不出來。
</details>

**Q5. 從這 14 組數據，你會怎麼挑選展示（demo / 口試）用的場地？為什麼？**

<details>
<summary>參考答案</summary>

★ **首選：長方形 4×2 + 一根中央柱子（「含柱 4×2」）**

| 指標 | 值 | 為什麼好 |
|---|---|---|
| cell | **4** | ★ cell 分解看得清清楚楚（網頁上四種顏色 + A/B/C/D 標籤） |
| 臨界點 | **2** | 一個 split、一個 merge，教科書等級的示範 |
| λ₁/λ₂ | **4.64** | 主軸非常可信，能展示 PCA 的價值 |
| 覆蓋率 | **100.0%** | 沒有需要解釋的異常 |
| 穿牆 | **0 / 0** | ★ 連轉場都是 0，最乾淨 |
| 轉場佔比 | 7.2% | 正常範圍 |

**★ 關鍵是「穿牆轉 = 0」** —— 這是唯一一個含障礙物、
而且**連轉場都不穿牆**的場地。demo 時不會被問「為什麼機器人繞路」。

★ **要避免的場地：**

| 場地 | 為什麼避免 |
|---|---|
| **正方形** | ⚠ λ₁/λ₂ = 1.00，PCA 完全退化，無法展示核心賣點 |
| **對稱 L 形** | 主軸 −45°，路徑長 23%，角落一堆極短線 |
| **斜置場地** | ⚠ 可能踩到鋸齒碎裂（不可預測），而且轉場穿牆多 |
| 細長比例過大 | 覆蓋率 96.3%（最後一帶落空） |

★ **但如果要展示「演算法的極限」（例如報告的討論章節），
就應該主動秀出 L 形和斜置 30°** ——
把限制講清楚比藏起來有力得多（第 19 章）。

**建議的展示流程**：
1. **長方形**（基準，一切正常）
2. **含柱**（cell 分解，主要展示）
3. **斜置的長方形**（PCA 的價值 —— 讓機器人斜著擺就有了）
4. **討論時提及** L 形和鋸齒碎裂的限制與改進方向
</details>
