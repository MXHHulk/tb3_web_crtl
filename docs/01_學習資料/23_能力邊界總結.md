## 23.1 ★★ 一句話總結

> **在一個已建好完整地圖的長方形空間裡（可含障礙物、可任意角度擺放），

## 23.5 ★ 三個最該修的地方（優先順序）

### ① 連通性檢查 —— < 10 行，消滅 F3

```python
from scipy.ndimage import label

lab, n = label(free, structure=np.ones((3, 3), bool))
if n > 1 and start is not None:
    sr = int(round((start[1] - oy) / res))
    sc = int(round((start[0] - ox) / res))
    if 0 <= sr < free.shape[0] and 0 <= sc < free.shape[1] and lab[sr, sc] > 0:
        comp = lab[sr, sc]
        unreachable = int((lab > 0).sum() - (lab == comp).sum())
        free = (lab == comp)          # 只規劃機器人到得了的部分
```

**效益**：
- 不再規劃到不了的區域 → 路點全部有效
- 可以回報 `unreachable_area` → 網頁上顯示「2.3 m² 因通道過窄無法到達」
- ★ **把「靜默失敗」變成「明確的可行動訊息」**

**成本**：< 10 行、< 1 ms、風險極低（`start` 為 `None` 時退回原行為）。

### ② `b_centers` 均勻分布 —— ~3 行，消滅 F4 和 F5

```python
# 現在
n_bands   = int(np.floor((b_max - b_min) / spacing)) + 1
b_centers = b_min + spacing / 2 + spacing * np.arange(max(1, n_bands))

# 改成
n_bands = max(1, int(np.round((b_max - b_min) / spacing)))
b_centers = np.linspace(b_min + spacing / 2, b_max - spacing / 2, n_bands)
```

★ **保證每條帶都落在 `[b_min + spacing/2, b_max − spacing/2]` 之內**：
- 不會落空（F4 消失）
- 不會貼在邊界上（F5 大幅減輕）
- 實際間距 ≤ `spacing`（所以**不會漏掃**，只會稍微多重疊）

⚠ **要驗證的副作用**：`n_bands` 的計算從 `floor(...) + 1` 改成 `round(...)`，
帶數可能少一條。要跑一次 `coverage_bench` 確認覆蓋率沒有下降。

### ③ `skipped` 計數 —— ~5 行，減輕 F1/F2/F3 的誤導

```python
# run_coverage 裡
skipped = 0
...
if client.get_state() != GoalStatus.SUCCEEDED:
    skipped += 1
    with cov_lock:
        cov_status['skipped'] = skipped
        cov_status['msg'] = f'路點 {i+1}/{n} 跳過（無法到達）'
...
with cov_lock:
    if cov_status['state'] == 'running':
        cov_status.update(state='done', done=n, skipped=skipped)
```

前端顯示：`完成 ✓　共 300 個路點（跳過 17 個）`

★ **讓數字誠實**。跳過 17 個和跳過 0 個，是完全不同的兩件事。

## 23.7 ★ 論文 / 口試的誠實敘述模板

**❌ 不要這樣寫**：

> 「本系統可完整覆蓋任意形狀之室內空間，覆蓋率達 100%。」

⚠ 這句話有三個問題：「任意形狀」不成立（正方形退化、L 形效率差）、
「100%」的分母沒說清楚、沒有提到「地圖必須先建完整」這個前提。

**✅ 建議這樣寫**：

> 「本系統採用 PCA 對齊之牛耕式單元分解（BCD）演算法。
> 以 14 組合成場地離線驗證，**在已知且完整的地圖上**，
> 掃描線覆蓋率為 **95.9% ~ 100%**（中位數 100%），
> **234 條掃描線中無任何一條穿越障礙物**。
>
> 覆蓋率之定義為：安全邊距膨脹後之可行走格中，
> 格心距任一掃描線段 ≤ 0.10 m（機器人覆蓋半徑）之比例；
> 不計入單元間之轉場路徑，且假設路徑被完美執行。
>
> **已知限制**：
> (a) 未探索格（`-1`）不納入規劃，地圖不完整時系統仍回報完成
>     —— 實測一組右側 29% 未探索之場地，回報覆蓋率 100%，
>     對真實空間之覆蓋率實為 71%；
> (b) 單元間之轉場採直線連接，未做避障規劃，
>     故規劃路徑長度為實際行走長度之下界；
> (c) 於正方形空間中，主成分分析之兩特徵值比為 1.00，主軸方向退化；
> (d) 最外側掃描帶之落點取決於幾何餘數，
>     可能落於可行走區之外（覆蓋率損失 3~4%）
>     或貼合光柵化邊界而碎裂（單元數由 1 增至 23）。」

★ **這段敘述的價值**：
1. **給了定義**（覆蓋率怎麼算）
2. **給了前提**（已知且完整的地圖）
3. **給了範圍**（95.9~100%，不是只報最好的）
4. **主動列出四項限制，而且每一項都附數據**

⚠ **口試委員最喜歡問的就是你藏起來的東西。主動說出來，
就變成「你很清楚自己的系統」而不是「你被抓到漏洞」。**

## 23.8 ⑥ 全書總結

### 這個專案做對的五件事

1. ★ **`coverage_planner.py` 零 ROS 依賴**（第 05 章）
   → 讓第 21~23 章的 14 組實測成為可能。**這是整個專案最有價值的一個決定。**

2. ★ **「所見即所算」**（第 07 章）
   → 網頁上的安全邊距圖層呼叫的就是演算法用的那個函式，不會走鐘。

3. ★ **讓演算法可觀察**（第 05 章）
   → `plan()` 回傳 cell 數、臨界點、主軸角度、λ₁/λ₂，
   除錯時一眼看出問題在哪。

4. ★ **中心線取樣的構造性保證**（第 09、10 章）
   → 掃描線不穿牆不是靠檢查，是數學上不可能。**234 條線 0 例外。**

5. ★ **把設計決策和被否決的方案寫進註解**（第 09 章）
   → `res/8` 為什麼不是 `res/2`、為什麼不用「四鄰格全可走」，
   都寫在程式碼裡。三個月後的自己會感謝。

### 這個專案的三個教訓

1. ⚠ **v1 的回歸**（第 09 章 9.3）
   → 為了新功能改變資料表示方式時，**要檢查舊功能的前提還在不在**。
   v0 已經做對的「逐列多段」，v1 為了支援斜向掃描丟掉了，
   造成有效覆蓋率 0% 的回歸。

2. ⚠ **「更保守」不等於「更好」**（第 09 章 9.5）
   → 「四鄰格全可走」完全杜絕切角，但覆蓋率從 99% 掉到 89%。
   **治好了病，殺死了病人。**

3. ⚠ **「所有指標都是滿分」不代表沒問題**（第 22 章 22.7）
   → 未探索場地回報 100% 覆蓋率、0 條穿牆、1 個 cell ——
   完美的數字，實際只走了 71%。
   **要問的是「我的指標有沒有涵蓋這件事」，不是「我的指標好不好看」。**

## 23.9 ⑦ 自我檢核題（總複習）

**Q1. 用一分鐘向完全不懂的人說明這個專案在做什麼，以及它的核心貢獻是什麼。**

<details>
<summary>參考答案</summary>

> 「這是一台會自己把房間走遍的機器人 —— 想像掃地機器人，但我們寫的是它的『大腦』：
> **決定要怎麼走才能不漏掉任何地方、而且不繞冤枉路**。
>
> 系統分三塊：機器人邊走邊用雷射建地圖（用現成的 SLAM 套件）、
> 我們的演算法算出一條走遍全場的路線（**這是核心貢獻**）、
> 再交給現成的導航套件實際開過去。過程中可以用手機開網頁即時監看。
>
> 演算法的核心叫『**牛耕式覆蓋**』—— 像牛耕田那樣來回蛇行。
> 但有兩個難點：
>
> **① 該往哪個方向掃？** 房間相對於地圖是斜的（因為地圖座標軸是機器人開機朝向決定的）。
> 我們用 **PCA** 從地圖自己算出房間的長邊方向，自動對齊 —— 不需要人工設定。
>
> **② 有障礙物怎麼辦？** 一根柱子會把掃描線切成兩段。
> 如果每換一行都要繞過柱子，會多走很多冤枉路。
> 我們用 **BCD（牛耕式單元分解）** 先把空間切成幾個『內部沒有障礙』的區塊，
> 一塊一塊掃完，只在區塊交界處跨越一次。
>
> **實測**：14 種場地，覆蓋率 95.9~100%，
> **234 條掃描線沒有任何一條穿過障礙物** —— 這是演算法設計上的構造性保證。」
</details>

> 現場可以立刻診斷是哪一種：
>
> **① 打開網頁的『原始地圖』圖層** —— 那塊區域是不是灰色的？
> 如果是，代表 SLAM 從來沒看到那裡，演算法根本沒把它納入規劃。
> ★ 這是最常見的。我們的光達實測有效距離只有約 3 公尺，
> 房間比較大時，建圖如果只繞牆邊走，中央就會是未知。
>
> **② 看終端機有沒有『路點 N 跳過』** —— 有的話是 `move_base` 到不了那個點。
>
> **③ 打開『安全邊距』圖層** —— 通往那塊區域的通道是不是被紅色封死了？
> 如果是，那塊區域變成孤島，我們目前**沒有做連通性檢查**，
> 會照常規劃過去然後每個點都失敗。
>
> **我們量化過第 ① 種**：合成一個右側 29% 未探索的場地，
> 系統回報覆蓋率 100%、cell 數 1、穿牆 0 條 ——
> **所有指標都是滿分**，但對真實空間的覆蓋率只有 71%。
>
> **改進方案已經設計好了**：
> 第 ③ 種用 `scipy.ndimage.label` 做連通元件檢查，不到 10 行；
> 第 ② 種加一個 `skipped` 計數顯示在網頁上，約 5 行；
> 第 ① 種短期回報未知格比例並警告，長期要把 frontier 探索整合進來。」

★ **這個回答把「被抓包」轉成「展示你的分析深度」。**
</details>

**Q3. 委員問：「你的演算法和現成的 CCPP 套件比，好在哪？」**

<details>
<summary>參考答案</summary>

★ **誠實面對：不要宣稱比成熟套件更好，而是說明「為什麼要自己寫」和「我們理解到什麼」。**

> 「以功能完整度來說，成熟的套件（例如 `full_coverage_path_planner`）
> 一定比我們的 270 行完整 —— 它們處理更多邊界情況、有更多優化。
>
> **自己寫的理由是這是專題的核心貢獻**。如果連覆蓋規劃都用現成的，
> 這個專題就只剩下『把幾個套件接起來』，沒有可以深入討論的東西。
> 相對地，SLAM 和導航避障我們就完全用現成的（gmapping、move_base）——
> **界線劃在『這是不是我的貢獻』。**
>
> **自己寫換到的東西**：
>
> **① 我們知道它為什麼會失敗。**
> 用現成套件時，出問題只能調參數猜。
> 我們可以逐帶診斷（`--detail`），
> 例如找出『斜置 30° 的 23 個 cell 是最後一條掃描帶貼著鋸齒邊界造成的』
> 這種需要看到內部狀態才能發現的問題。
>
> **② 可觀察性是設計進去的。**
> `plan()` 回傳 cell 數、臨界點、主軸角度、λ₁/λ₂，
> 網頁上直接看得到。現成套件通常只給你一條路徑。
>
> **③ 零 ROS 依賴讓它可以離線測試。**
> 14 種場地幾秒跑完、完全可重現。
> 這讓我們能做參數掃描（第 18 章掃了 6×5 = 30 種組合），
> 實機做同樣的事要 15 小時。
>
> **④ 我們有完整的演進紀錄。**
> 從 v0（沿地圖軸掃）到 v3（PCA + cell 分解），
> 每一版壞在哪、怎麼修、哪些修法被否決（包括『各 cell 各自求 PCA』
> 這個看似合理但實測撤回的方案）都有數據。
>
> ★ **這些是『理解』的價值，不是『功能』的價值。**」
</details>

**Q4. 如果給你兩週時間繼續做，你會做什麼？**

<details>
<summary>參考答案</summary>

★ **按「消滅錯誤結論」優先，不按「聽起來厲害」優先。**

**第 1 天（20 行程式碼，消滅三個失敗模式）**
1. 連通性檢查（`scipy.ndimage.label`）— 消滅 F3
2. `b_centers` 均勻分布 — 消滅 F4、大幅減輕 F5
3. `skipped` 計數 — 讓數字誠實

跑一次 `coverage_bench` 驗證斜置 30° 的 cell 數有沒有從 23 降下來。

**第 2~3 天：把測試變可信**
4. 加自動化斷言（`assert bad_sweep == 0` 等）
5. `map_recorder.py` 補存 `.yaml`（resolution / origin / crop）
6. 寫 `load_recorded_map()`，用 `maps/` 底下的**真實地圖**跑一次
   → ★ 驗證「合成地圖太完美」這個懷疑，看碎裂是不是更嚴重

**第 4~6 天：量化執行層的損失**
7. `/coverage/report` 路由：用**實際行走軌跡**算實際覆蓋率
   → ★ 產出全專案最有價值的一張對照表：
   ```
   規劃覆蓋率 100.0%  vs  實際覆蓋率  ??%
   規劃路徑長  37.5 m  vs  實際路徑長  ?? m
   ```

**第 7~10 天：A\* 轉場接駁**
8. 在 `free` 上做 A\*，加 `links` 欄位（不破壞現有結構）
9. 重跑 `coverage_bench`，得到**真實的**轉場長度
   → 消滅 F8，讓所有路徑長度數據可信

**第 11~14 天：實機驗證 + 補文件**
10. 用最好的場地（長方形 + 中央柱）跑 3 次完整實機
11. 用第 7 步的工具量實際覆蓋率
12. 更新論文的數據章節

★ **刻意不做的**：
- ❌ 幾何分區（L 形效率）—— 是另一個演算法，兩週做不完而且會做壞
- ❌ 2-opt 走訪順序 —— 效益 ~25%，但在 A\* 轉場修好之前，
  路徑長度數據本身不可信，優化它沒有意義
- ❌ 加認證、加 WebSocket —— 不影響任何結論
</details>

**Q5. 這份講義 24 章讀完，你覺得最重要的三個觀念是什麼？**

<details>
<summary>參考答案</summary>

（沒有標準答案，以下是本講義想傳達的三個。）

**① ★ 依賴方向決定了你能做什麼**（第 05 章）

`coverage_planner.py` 那一行 `import rospy` 沒有寫下去，
換來的是第 21~23 章的整整三章實測、第 18 章的參數掃描、
以及「知道自己的演算法在什麼場地會失敗」這件事。

**一個 import 決定了一個專案能不能被理解。**

**② ★ 構造性保證 > 事後檢查**（第 09、10 章）

「掃描線不穿牆」不是靠檢查每條線然後修掉壞的，
而是靠**改變產生線段的方式**（線段由取樣點本身定義），
讓它在數學上不可能穿牆。

234 條線 0 例外 —— 這種保證是**設計出來的**，不是測試出來的。

★ 對照：v2 之前試過的 `scipy.ndimage.label` 修法，
就是「事後找連通塊再連端點」—— 那只是把問題換個地方。

**③ ★ 所有指標都是滿分，不代表沒問題**（第 22 章 22.7）

未探索場地：覆蓋率 100%、穿牆 0、cell 1 —— 完美的數字。
實際只走了房間的 71%。

**因為指標的分母是「演算法知道的世界」，而不是「真實的世界」。**

要問的不是「我的指標好不好看」，而是
**「我的指標有沒有涵蓋這件事」**、
**「有沒有什麼失敗方式，會讓所有指標看起來都正常」**。

★ 這一條適用於任何工程領域，遠遠超出這個專題的範圍。
</details>
