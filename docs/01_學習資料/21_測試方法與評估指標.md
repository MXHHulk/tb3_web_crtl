## 21.4 合成地圖產生器

```python
# test/coverage_bench.py
RES  = 0.05    # 模擬地圖解析度（與 gmapping 預設一致）
WALL = 0.15    # 合成牆厚（公尺）
PAD  = 0.4     # 地圖邊界外的未知區留白

def build_map(pred, xr, yr):
    """
    pred(X, Y) -> bool 陣列，True = 室內可走
    回傳 (data, ox, oy)：0=自由, 100=障礙(牆), -1=未知(牆外)
    """
    ox, oy = xr[0] - PAD, yr[0] - PAD
    W = int((xr[1] - xr[0] + 2*PAD) / RES)
    H = int((yr[1] - yr[0] + 2*PAD) / RES)
    X, Y = np.meshgrid(ox + RES*np.arange(W), oy + RES*np.arange(H))

    inside = pred(X, Y)                    # ① 室內判定
    data = np.full((H, W), -1, dtype=np.int16)
    data[inside] = 0                       # ② 室內 = 自由

    r = max(1, round(WALL / RES))          # ③ 室內外邊界往外 WALL 畫成牆
    near = binary_dilation(inside, np.ones((2*r+1, 2*r+1), bool))
    data[near & ~inside] = 100
    return data, ox, oy
```

### ★ 「室內判定函式」的設計

場地用一個 **`(X, Y) → bool` 的向量化函式**描述：

```python
SCENES = {
    '長方形4x2':  (lambda X, Y: (0 <= X) & (X <= 4) & (0 <= Y) & (Y <= 2),
                   (0, 4), (0, 2)),
    'L形4x4':     (lambda X, Y: (((0 <= X) & (X <= 4) & (0 <= Y) & (Y <= 4))
                                 & ~((X > 2) & (Y > 2))),        # ← 挖掉右上角
                   (0, 4), (0, 4)),
    '含柱4x2':    (lambda X, Y: ((0 <= X) & (X <= 4) & (0 <= Y) & (Y <= 2)
                                 & ~((1.7 < X) & (X < 2.3) & (0.7 < Y) & (Y < 1.3))),
                   (0, 4), (0, 2)),
    ...
}
```

★ **為什麼用「判定函式」而不是直接畫陣列**：

1. **精確**：房間邊界是**數學上的**直線，不是我手畫的格子
2. **好寫**：L 形就是「大矩形 `& ~` 小矩形」，一行搞定
3. **可任意變換**：斜置場地只要加一個旋轉

```python
def _rot(X, Y, deg):
    """把世界座標旋轉 -deg，用來描述斜置的房間。"""
    t = math.radians(deg)
    c, s = math.cos(t), math.sin(t)
    return X * c + Y * s, -X * s + Y * c

'斜置30度': (lambda X, Y: (lambda A, B: (np.abs(A) <= 2) & (np.abs(B) <= 1))(*_rot(X, Y, 30)),
             (-3, 3), (-2, 2)),
```

### ★ 為什麼要有「牆」而不是直接讓室外都是 `-1`

```python
r = max(1, round(WALL / RES))
near = binary_dilation(inside, np.ones((2*r+1, 2*r+1), bool))
data[near & ~inside] = 100        # 只有貼著室內的一圈是牆（100）
                                   # 更外面維持 -1（未知）
```

★ **因為 `apply_safety_margin` 只膨脹 `data == 100` 的格子**（第 08 章 8.1）。

如果室外全部是 `-1`，**安全邊距就完全不會生效** ——
可走區會一直延伸到房間邊緣，路點貼著牆生成。這就測不出真實行為了。

**這也對應真實情況**：SLAM 的地圖裡，牆是一圈 `100` 的格子，
牆後面（雷射打不到的地方）是 `-1`。

### 特殊場地：未探索區

```python
UNKNOWN_SCENE = ('未探索4x2',
                 lambda X, Y: (0 <= X) & (X <= 4) & (0 <= Y) & (Y <= 2),
                 lambda X, Y: (X > 2.8),          # ★ 這塊維持未知
                 (0, 4), (0, 2))
```


## 21.5 ★★ 六個評估指標

### 指標一：cell 數 / run 數 / 臨界點數

**定義**：直接來自 `plan()` 的回傳值。

```python
cells = len(r['cells'])
runs  = r['n_runs']
crit  = len(r['critical'])
```

**怎麼解讀**：

| 觀察 | 意義 |
|---|---|
| cell 數 = 1 | 空間是簡單的（無障礙、或障礙不切開掃描線） |
| cell 數 = 3~5 | 正常的含障礙場地 |
| ⚠ **cell 數 > 10** | **run 碎裂了**，去跑 `--detail` 查哪一帶 |
| 臨界點 = 0 但有障礙 | 障礙沒有切開任何掃描帶（例如貼著牆的障礙） |
| run 數 ÷ 帶數 ≈ 1 | 每條帶一段，空間簡單 |
| ⚠ **run 數 ÷ 帶數 > 3** | 碎裂 |

### 指標二：主軸角度 與 λ₁/λ₂

```python
axis  = math.degrees(math.atan2(axis_a[1], axis_a[0]))
ratio = float(max(eigvals) / min(eigvals))
```

★ **λ₁/λ₂ 是「主軸可信度」**（第 08 章 8.2）：

| λ₁/λ₂ | 意義 |
|---|---|
| > 4 | 主軸非常可信 |
| 2~4 | 大致可信 |
| **≈ 1** | ⚠ **完全退化**，主軸方向由數值誤差決定 |

**主軸角度要和場地的實際朝向對照**：
斜置 30° 的場地應該得到 30° 左右 —— 對不上就是 PCA 出問題了。

### 指標三：★ 覆蓋率

```python
def coverage_ratio(free, ox, oy, wps):
    """可走格中心離任一「掃描線」<= COV_RADIUS 的比例。轉場線不計入覆蓋。"""
    rows, cols = np.where(free)
    px, py = ox + cols * RES, oy + rows * RES
    covered = np.zeros(len(rows), bool)
    for i in range(0, len(wps) - 1, 2):              # ★ 偶數 index 起 = 掃描線
        a, b = np.asarray(wps[i]), np.asarray(wps[i + 1])
        ab = b - a; L2 = float(ab @ ab)
        if L2 == 0: continue
        t = np.clip(((px - a[0])*ab[0] + (py - a[1])*ab[1]) / L2, 0, 1)   # ★ 投影並夾住
        dx, dy = px - (a[0] + t*ab[0]), py - (a[1] + t*ab[1])
        covered |= (dx*dx + dy*dy) <= COV_RADIUS ** 2
    return float(covered.mean())
```

**★ 完整定義（報告裡一定要寫）**：

> **膨脹後的可走格中，格子中心距離「任一條掃描線段」≤ 0.10 m 的比例。**

**四個要注意的地方：**

**① 分母是「膨脹後的可走格」，不是房間面積**

安全邊距吃掉的約 10% 不列入分母。所以 100% 不代表「整個房間都掃到」。

**② 只算掃描線，不算轉場線**（`range(0, len, 2)`）

機器人在轉場時也在移動、也在覆蓋，但那不是有計畫的覆蓋。
**保守地不計入**，讓數字偏低而不是偏高。

**③ 「點到線段的距離」，不是「點到直線的距離」**

```python
t = np.clip(..., 0, 1)      # ★ 這個 clip 是關鍵
```

`t` 是投影參數。不夾在 `[0,1]` 的話，
線段**延長線**上的點也會被算成覆蓋 —— 覆蓋率會虛高。

```
   線段 A━━━━━B
                    ● P     ← 沒有 clip：算成離 B 很近（沿延長線投影）
                              有 clip：t=1，距離 = |PB|，正確
```

**④ `COV_RADIUS = 0.10` 是機器人的覆蓋半徑**

對應 0.20 m 的覆蓋寬度。這個值決定了 `SPACING` 的懸崖位置（第 18 章 18.2）。

**⚠ 最大的限制**：這是**規劃的覆蓋率**，假設路徑被完美執行 ——
沒有定位誤差、沒有路點失敗、`move_base` 沒有繞路。
**它是實際表現的上界。**

### 指標四：掃描長 / 轉場長 / 轉場佔比

```python
sweep_len = sum(math.dist(wps[i], wps[i+1]) for i in range(0, len(wps)-1, 2))
link_len  = sum(math.dist(wps[i], wps[i+1]) for i in range(1, len(wps)-1, 2))
```

★ **利用第 12 章的路點結構約定**：偶數 index 起 = 掃描線，奇數起 = 轉場。

**轉場佔比 = `link / (sweep + link)`** 是**效率指標**：

| 轉場佔比 | 意義 |
|---|---|
| < 5% | 幾乎沒有空跑，非常有效率 |
| 5~10% | 正常（有障礙的場地） |
| > 13% | ⚠ 空跑偏多，通常代表 cell 之間距離遠 |

⚠ **這個長度是「直線距離」**，實際 `move_base` 可能繞路（第 19 章缺陷 #1）。
**所以轉場長是低估的。**

### 指標五：★★ 穿牆段數（掃描 / 轉場）

```python
def seg_is_free(free, ox, oy, p, q):
    """線段 p→q 是否整條都落在可走格上（沿線以 res/4 取樣檢查）。"""
    d = math.hypot(q[0]-p[0], q[1]-p[1])
    n = max(2, int(d / (RES/4)) + 1)
    for i in range(n + 1):
        t = i / n
        x, y = p[0] + t*(q[0]-p[0]), p[1] + t*(q[1]-p[1])
        c, r = round((x-ox)/RES), round((y-oy)/RES)
        if not (0 <= r < H and 0 <= c < W and free[r, c]):
            return False
    return True
```

★ **`bad_sweep` 必須是 0。**

這是第 09 章 v2 修好的性質，也是這個演算法**正確性的核心保證**：
掃描線是由「連續為 True 的取樣點」定義的，
所以它從構造上就不可能穿牆。

> ⚠ **如果哪天 `bad_sweep > 0`，代表 `_slice_runs` 被改壞了。**
> 這一項應該做成自動化的斷言（第 20 章 20.8）。

★ **`bad_link` 則預期會 > 0** —— 那是第 19 章的缺陷 #1，
規劃器不管轉場能不能走。這個數字**量化了 `move_base` 要繞多少次路**。

★ **注意檢查用的取樣步長是 `res/4`，而 `_slice_runs` 用 `res/8`。**
評估器**故意比演算法寬鬆**：如果用一樣的步長，可能因為浮點誤差
在同一個點上得到相同的判斷，變成「自己檢查自己」。
用不同的步長是一種弱的獨立驗證。

### 指標六：可走面積

```python
area = float(free.sum()) * RES * RES
```

用來看 `MARGIN` 吃掉了多少空間（第 18 章 18.3），
以及「未探索」場地少了多少（第 22 章 22.7）。

## 21.6 ⑤ 設計決策

| 決策 | 選了 | 否決了 | 理由 |
|---|---|---|---|
| 測試層級 | 離線呼叫 `plan()` | 實機 / Gazebo 模擬 | 秒級 vs 小時級；完全可重現 |
| 地圖來源 | 合成（判定函式） | 錄下來的真實地圖 | 精確、可參數化；⚠ 但太完美（第 20 章 20.8） |
| 前處理 | **和 `map_server` 逐字相同** | 自己寫一份簡化版 | 測的是真正在用的路徑 |
| 場地描述 | `(X,Y) → bool` 函式 | 手畫陣列 / 讀圖檔 | 一行寫出 L 形；可任意旋轉 |
| 牆的處理 | 邊界一圈設 100 | 室外全 `-1` | ★ 否則安全邊距完全不生效 |
| 覆蓋率 | 只算掃描線 | 掃描 + 轉場都算 | 保守，寧可低估 |
| 距離 | 點到**線段** | 點到直線 | ★ 沒有 `clip` 會讓覆蓋率虛高 |
| 穿牆檢查步長 | `res/4` | `res/8`（和演算法一樣） | 用不同步長做弱獨立驗證 |

## 21.7 ⚠ 這套方法的限制

| # | 限制 | 影響 |
|---|---|---|
| 1 | **合成地圖太完美**（邊界是精確直線） | ⚠ 真實地圖更破碎，碎裂問題會更嚴重（第 20 章 20.10 Q5） |

## 21.9 ⑦ 自我檢核題

**Q1. 為什麼合成地圖要在室內外邊界畫一圈 `100`（牆），
而不是讓室外全部都是 `-1`（未知）？**

<details>
<summary>參考答案</summary>

★ **因為 `apply_safety_margin` 只膨脹 `data == 100` 的格子。**

```python
# scripts/coverage_planner.py:31
obs = data == 100
```

如果室外全部是 `-1`：
- `obs` 會是**全 False**（沒有任何障礙格）
- `binary_dilation` 的結果也是全 False
- `free = (data == 0) & ~safe` = `(data == 0)` —— **安全邊距完全沒有作用**

**後果**：可走區一直延伸到房間的最外緣，
路點會生在離牆 0 公分的地方 —— 完全測不出真實行為。
所有和 `MARGIN` 有關的實驗（第 18 章 18.3）都會失效。

★ **而且這也不符合真實情況**：SLAM 的地圖裡，
牆是一圈被雷射打到的 `100` 格子，牆**後面**（雷射穿不過去的地方）才是 `-1`。

`WALL = 0.15` 這個厚度是刻意選的：
比 `MARGIN = 0.10` 大，確保膨脹不會「穿透」牆跑到外面去。
</details>

**Q2. `coverage_ratio` 裡的 `t = np.clip(..., 0, 1)` 如果拿掉會怎樣？**

<details>
<summary>參考答案</summary>

**覆蓋率會虛高。**

`t` 是「點 P 投影到線段 AB 上的參數」：
- `t = 0` → 投影在 A
- `t = 1` → 投影在 B
- `0 < t < 1` → 投影在線段中間
- ⚠ `t < 0` 或 `t > 1` → **投影落在線段的延長線上**

不 `clip` 的話，計算的是**點到「無限長直線」的距離**：

```
   A━━━━━━━B
                       ● P

   有 clip：t 被夾成 1 → 距離 = |PB|（正確，很遠）
   沒 clip：t = 1.8    → 距離 = P 到延長線的垂直距離（很近！）
```

**具體後果**：一條掃描線的**延長線**上的所有格子都會被算成「已覆蓋」，
即使那些格子在房間的另一頭、或者根本被障礙物擋住。

★ **對「含柱」場地影響最大**：柱子左側的掃描線延長出去，
會把柱子右側的格子也算成覆蓋 —— 明明還沒走過去。

★ **這是幾何計算裡最經典的坑之一**：
「點到線段的距離」和「點到直線的距離」是兩件事，
差別就在那一行 `clip`。
</details>

**Q3. `seg_is_free` 用 `res/4` 取樣，而 `_slice_runs` 用 `res/8`。
為什麼故意不一樣？**

<details>
<summary>參考答案</summary>

★ **為了避免「自己檢查自己」。**

如果評估器用和演算法**完全相同**的取樣步長和取樣位置，
那麼演算法認定「這 641 個點都是 free」的線段，
評估器會檢查**同樣的 641 個點**，當然也會說 free。

★ **這樣的檢查是套套邏輯，驗證不到任何東西。**

用 `res/4`（比較稀疏）之後：
- 取樣點的位置**不同**（不同的步長 → 不同的浮點座標）
- 雖然更稀疏，但它是**獨立**的一組觀察

★ **這是一種「弱的獨立驗證」**：不是完全獨立（用的是同一套座標轉換），
但至少不會因為「同一個浮點誤差」而同時錯。

**更強的驗證方式**（可以考慮加）：
- 用**完全不同的方法**檢查，例如 Bresenham 直線演算法逐格走訪
  （純整數運算，完全不涉及浮點取樣）
- 用**更密**的步長（`res/16`）—— 如果更密的檢查也說 0 條穿牆，那更有信心

★ **通用原則：測試不該重用被測程式碼的實作方式。**
（同理，`coverage_bench` 的前處理**刻意重用** `apply_safety_margin` ——
因為那不是被測的對象，而是「要複製的環境」。
被測的對象是 `plan()`，所以驗證 `plan()` 的部分才要獨立。）
</details>

**Q4. 為什麼覆蓋率只算掃描線，不算轉場線？機器人在轉場時也在移動、也在覆蓋啊。**

<details>
<summary>參考答案</summary>

**技術上你說得對** —— 機器人在轉場時確實會覆蓋到路徑周圍的區域。

**但刻意不算，有三個理由：**

**① 保守原則：寧可低估**

實驗數據的可信度來自「不會高估」。
如果把轉場也算進去，覆蓋率會虛高，而我們無法保證那些覆蓋是可靠的。

**② ⚠ 轉場線可能穿牆（缺陷 #1）**

第 22 章實測，斜置 30° 有 **30 段轉場穿牆**。
這些線段機器人**根本不會照著走**（`move_base` 會繞路），
把它們算成覆蓋是**錯的**。

★ 這是最關鍵的理由：**如果連線段本身都不可信，就不該用它算覆蓋。**

**③ 語意清楚**

「覆蓋率」應該衡量的是**規劃品質**：
「這套掃描線的安排，能不能覆蓋整個空間」。
轉場是副產品，不是設計的一部分。

如果轉場恰好多覆蓋了一些，那是紅利，不是規劃的功勞。

★ **代價**：報出來的數字比實際保守一點點。
但在報告裡，**一個保守而可辯護的數字，勝過一個樂觀而站不住腳的數字**。
</details>

**Q5. 21.7 說「合成地圖太完美」是最需要改進的限制。
具體要怎麼改？會遇到什麼問題？**

<details>
<summary>參考答案</summary>

**要做的**：用 `maps/` 底下 `map_recorder.py` 錄下的**真實 SLAM 地圖**跑同一套評估。

```python
def load_recorded_map(png_path, resolution, origin_x, origin_y):
    img = np.array(Image.open(png_path).convert('L'))
    img = np.flipud(img)                       # ① 反轉 map_recorder 的 flipud
    data = np.full(img.shape, -1, np.int16)
    data[img > 180] = 0                        # ② 白 → 自由
    data[img < 80]  = 100                      # ③ 黑 → 障礙
    return data, origin_x, origin_y            # 128 灰維持 -1（未知）
```

**三個問題：**

**⚠ 問題 1：PNG 沒有存 metadata**

`resolution`、`origin_x/y` 沒有存進 PNG 裡，而 `world_to_px` 需要它們。
更麻煩的是 `map_recorder.py` 有做**裁切**（`crop_pad`），
所以 PNG 的 (0,0) 不是地圖的 (0,0)。

★ **這暴露了 `map_recorder.py` 的一個設計缺陷**：
應該同時輸出一個 `.yaml`（像 ROS 官方 `map_server` 那樣）記錄
`resolution` / `origin` / `crop` 偏移。**這是應該補的第一件事。**

**臨時解法**：用 `crop_pad:=-1` 錄製（不裁切），
`resolution` 用 gmapping 預設的 0.05，`origin` 設成 0 ——
因為評估指標（覆蓋率、cell 數、穿牆段數）都是**相對量**，
原點設哪裡不影響結果。

**⚠ 問題 2：灰階閾值的還原不是無損的**

`map_recorder` 的轉換是 `255 - data*255//100`，
原始的 0 / 100 / -1 分別變成 255 / 0 / 128。
還原時用閾值判斷是可以的，但如果原始資料有中間值（機率 30、70）就會失真。

**實務上沒問題**：gmapping 只吐 0 / 100 / -1。

**⚠ 問題 3：真實地圖是「某一刻」的快照**

同一個場地的不同時刻，地圖不一樣。所以「真實地圖測試」**仍然不完全可重現**，
只是比實機測試好得多（至少同一張 PNG 每次跑結果相同）。

★ **預期會看到什麼**（第 20 章 20.10 Q5 的推論）：
- `bad_sweep` **仍是 0**（構造性保證，和地圖品質無關）
- **cell 數比合成地圖多**（邊界更破碎）
- **覆蓋率更低**
- 這會證實缺陷 #2 在實機上更嚴重，提高它的修復優先度
</details>
