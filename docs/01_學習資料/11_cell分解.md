# 第 11 章　cell 分解

> **本章目標**：把第 10 章產出的一堆 run，串成幾個「內部沒有障礙」的區塊（cell）。
> 這一步就是 **BCD（Boustrophedon Cellular Decomposition，牛耕式單元分解）** 的本體，
> 也是這個演算法的學名由來。
>
> 兩個函式：`_link_runs()`（12 行）和 `_build_cells()`（30 行）。

---

## 11.1 ① 問題：run 之間怎麼串？

第 10 章結束時我們有一份 run 清單：

```
k=10  ────────────────────────  run #0
k=9   ────────────────────────  run #1
k=8   ────────────────────────  run #2
k=7   ────────────────────────  run #3
k=6   ──────────  ────────────  run #4, #5
k=5   ──────────  ────────────  run #6, #7
k=4   ──────────  ────────────  run #8, #9
k=3   ────────────────────────  run #10
...
```

（注意程式裡 run 是**依帶序號遞增**排列的，上圖為了對應前一章的示意圖倒過來畫。）

**如果只是「照順序、左右交替」把所有 run 串起來會怎樣？**

```
   帶 3 走完（整條，左→右）
   帶 4 右段（右→左）→ 走完後在左端
        然後要跳到帶 4 的左段？還是帶 5？
        不管怎麼跳，都要橫跨整個障礙物
   帶 5 ...又要跨一次
```

★ **每換一條帶就要跨越障礙物一次**，來回空跑，路徑長度暴增。

---

## 11.2 ② 直覺做法：每條帶的多段各自處理

「一條帶有兩段，那就先走左段再走右段嘛」：

```
   帶 4：左段 → 右段
   帶 5：右段 → 左段（交替）
   帶 6：左段 → 右段
```

### ③ 撞牆

```
   ┌────────────────────────────┐
   │  ●━━━━━●  ████  ●━━━━━●    │  帶 6：左→右，跨越 1 次
   │       ╱          ╲         │
   │  ●━━━●    ████    ●━━━━●   │  帶 5：右→左，跨越 1 次
   │       ╲          ╱         │
   │  ●━━━━━●  ████  ●━━━━━●    │  帶 4：左→右，跨越 1 次
   └────────────────────────────┘
             ↑↑↑
        每一帶都跨越一次障礙物
```

如果障礙物寬 1 公尺、有 5 條帶穿過它，光是跨越就多走 **5 公尺**。

**而且這些跨越線都是穿牆的** —— 要靠 `move_base` 繞路，實際走的距離更長。

## 11.3 ④ 現在的做法：先分區，再各自蛇行

### 核心想法

> **與其在障礙物兩側來回跳，不如把左半邊整個走完，再走右半邊。**

```
   ┌───────────────────────────────┐
   │            cell C             │  ← 每條帶只有 1 段
   ├──────────┬──────┬─────────────┤  ← merge 臨界點
   │  cell A  │██████│   cell B    │  ← 各自每條帶 1 段
   ├──────────┴──────┴─────────────┤  ← split 臨界點
   │            cell D             │  ← 每條帶只有 1 段
   └───────────────────────────────┘

   走法：D 全走完 → A 全走完 → B 全走完 → C 全走完
         只在 cell 交界處跨越，總共 3 次
```

### cell 的定義（很重要）

> **cell = 一群 run，滿足「沿掃描方向切片時，每一片都是單一連通區間」。**

換句話說：**cell 內部沒有障礙物把掃描線切開**，所以可以放心蛇行。

### 怎麼找出 cell 的邊界

★ **關鍵觀察（第 10 章結尾）**：

> **run 的數量發生變化的地方，就是空間結構改變的地方。**

```
   帶 3：1 段  ┐
   帶 4：2 段  ┘ ← 1 變 2：split（分裂）

   帶 6：2 段  ┐
   帶 7：1 段  ┘ ← 2 變 1：merge（合併）
```

這兩個位置就是 **臨界點（critical point）**，在這裡把空間切開。

## 11.4 `_link_runs()`：判斷相鄰兩帶的 run 是否相接

```python
# scripts/coverage_planner.py:112-129
def _link_runs(runs):
    """
    相鄰兩條掃描帶之間，沿長軸投影範圍有重疊的區間視為相接。

    這是牛耕式分解的標準連通判準：掃描線掃過時，區間一分為二即為分裂臨界點，
    二合為一即為合併臨界點。
    """
    succ = [set() for _ in runs]     # succ[i] = i 的後繼（下一條帶）
    pred = [set() for _ in runs]     # pred[i] = i 的前驅（上一條帶）
    for i, ri in enumerate(runs):
        for j, rj in enumerate(runs):
            if rj['band'] != ri['band'] + 1:      # ① 只看相鄰帶
                continue
            if ri['a0'] <= rj['a1'] and rj['a0'] <= ri['a1']:   # ② 區間重疊
                succ[i].add(j)
                pred[j].add(i)
    return succ, pred
```

### ② 這個重疊判準是什麼

兩個區間 `[a0, a1]` 和 `[b0, b1]` **重疊**的充要條件：

```
   a0 <= b1  且  b0 <= a1
```

```
   重疊：            不重疊：
   A: ├───────┤      A: ├───┤
   B:    ├───────┤   B:        ├───┤
        └─重疊─┘

   a0 <= b1 ✓        a0 <= b1 ✓
   b0 <= a1 ✓        b0 <= a1 ✗   ← 這個條件擋掉了
```

> 💡 **為什麼「投影重疊」就代表「可以換行過去」？**
>
> 因為兩條相鄰帶的距離只有 `spacing`（0.18 m）。
> 如果它們在長軸方向有重疊，那麼在重疊區間的正上/正下方，
> 就有一條長度 0.18 m 的路可以直接走過去。
>
> ⚠ 這是一個**近似判準**：嚴格來說中間那 0.18 m 也可能有障礙
> （例如一個剛好卡在兩條帶之間的小障礙）。
> 但 0.18 m 比安全邊距（0.10 m 膨脹）小，這種障礙如果存在，
> 早就把兩邊的 run 都切斷了。實務上這個近似是安全的。

### 用具體例子看

回到第 10 章的含柱房間：

```
k=4:  [-2.0 ─────── -0.5]        [+0.5 ─────── +2.0]     ← run #8, #9
                  ↑ 重疊               ↑ 重疊
k=3:  [-2.0 ──────────────────────────────────── +2.0]   ← run #10
```

- run #10 vs run #8：`-2.0 <= -0.5` ✓ 且 `-2.0 <= 2.0` ✓ → **重疊**
- run #10 vs run #9：`-2.0 <= 2.0` ✓ 且 `0.5 <= 2.0` ✓ → **重疊**

所以 `succ[#10] = {#8, #9}`，**有 2 個後繼**。

### ⚠ 效能：O(n²)

```python
for i, ri in enumerate(runs):
    for j, rj in enumerate(runs):
```

雙重迴圈，run 有 n 個就要比較 n² 次。

**目前沒問題**：一般場地的 run 數在 10~30 之間，n² = 100~900 次比較，微秒等級。

**但第 22 章的斜置 30° 場地有 31 個 run**（其中 22 個來自碎裂的最外帶），
n² = 961。如果碎裂更嚴重（例如 200 個 run），就是 40,000 次 —— 開始有感。

**可以改進**：runs 已經依 `band` 排序，可以先建一個 `band → run 索引`的字典，
只比較相鄰兩帶的 run，複雜度降到 O(n × 每帶平均 run 數)。
以目前的規模不值得做（第 19 章列為未來工作）。

## 11.5 `_build_cells()`：串鏈與臨界點偵測

```python
# scripts/coverage_planner.py:131-168
def _build_cells(runs, succ, pred):
    """
    把區間串成 cell：只有「前後一對一」才繼續延伸，一分為多或多合為一即為臨界點。
    """
    # ── 第一段：記錄臨界點 ──
    critical = []
    for i in range(len(runs)):
        if len(succ[i]) > 1:
            critical.append((i, 'split'))
        if len(pred[i]) > 1:
            critical.append((i, 'merge'))

    # ── 第二段：串鏈 ──
    cells, taken = [], [False] * len(runs)
    for i in range(len(runs)):                    # runs 已依帶序號遞增排列
        if taken[i]:
            continue
        # 若自己是某個前段的唯一後繼，代表會被那條鏈接走，不另起新 cell
        if len(pred[i]) == 1:
            p = next(iter(pred[i]))
            if len(succ[p]) == 1:
                continue

        chain, cur = [i], i
        taken[i] = True
        while len(succ[cur]) == 1:
            nxt = next(iter(succ[cur]))
            if len(pred[nxt]) != 1 or taken[nxt]:
                break
            chain.append(nxt)
            taken[nxt] = True
            cur = nxt
        cells.append(chain)

    return cells, critical
```

### 第一段：臨界點

```python
if len(succ[i]) > 1:  critical.append((i, 'split'))    # 後繼變多 = 分裂
if len(pred[i]) > 1:  critical.append((i, 'merge'))    # 前驅變多 = 合併
```

★ **注意 `critical` 只是給網頁顯示用的診斷資訊**，
串鏈的邏輯是獨立的（下面第二段），不依賴這個清單。

```python
# scripts/map_server.py:490
n_critical = len(r['critical']),
```

網頁的「規劃資訊」面板顯示這個數字（`web/index.html:197`）。

### 第二段：串鏈的三個判斷

**判斷 A：「我該不該起一條新鏈？」**

```python
if len(pred[i]) == 1:
    p = next(iter(pred[i]))
    if len(succ[p]) == 1:
        continue          # 我會被 p 那條鏈接走，不用另起爐灶
```

白話：**如果我只有一個前驅 p，而且 p 也只有我這一個後繼，
那我和 p 是「一對一」關係，p 那條鏈延伸過來時就會把我收進去。**

反過來說，**會起一條新鏈的只有兩種 run**：
- **沒有前驅**（第一條帶的 run，或緊接在 split 之後的 run）
- **前驅關係不是一對一**（前驅有多個，或前驅有多個後繼）

**判斷 B：「這條鏈能延伸下去嗎？」**

```python
while len(succ[cur]) == 1:      # 我只有一個後繼
    nxt = next(iter(succ[cur]))
    if len(pred[nxt]) != 1:     # ★ 但它有多個前驅（merge）→ 停
        break
    if taken[nxt]:              # ★ 它已經被別條鏈拿走了 → 停
        break
    chain.append(nxt)
    ...
```

★ **「一對一」必須雙向成立**：我只有一個後繼 **而且** 它只有我一個前驅。

```
   一對一（可以串）：       split（不能串）：      merge（不能串）：
      ●                        ●                    ●    ●
      │                       ╱ ╲                    ╲  ╱
      ●                      ●   ●                     ●
```

**判斷 C：`taken` 標記防止重複**

一個 run 只能屬於一個 cell。`taken` 陣列保證這件事。

### ⚠ `taken` 造成的一個副作用

```python
if len(pred[nxt]) != 1 or taken[nxt]:
    break
```

`taken[nxt]` 這個條件會讓某些鏈**提早斷開**。

想像一個罕見情況：run X 的前驅只有 Y，Y 的後繼只有 X（一對一），
但 Y 因為某種順序上的原因已經被另一條鏈接走了。
此時 X 會另外起一條新 cell，而不是接在後面。

**後果**：cell 數量比理論上的 BCD 稍多。

**但覆蓋不會漏** —— 每個 run 都一定屬於某個 cell（外層迴圈保證掃過所有 run）。

> 💡 這是一個「正確但不最佳」的實作。因為 run 是依 band 遞增排列的，
> 而連結只發生在相鄰帶之間，實務上這個情況幾乎不會發生。
> 真正會產生大量單 run cell 的是**鋸齒碎裂**（第 22 章），那是另一個問題。

## 11.7 ⑤ 設計決策

| 決策 | 選了 | 否決了 | 理由 |
|---|---|---|---|
| 連通判準 | 相鄰帶的 a 投影重疊 | 檢查中間那段是否真的可走 | 兩帶只差 0.18 m，比安全邊距小；多檢查一次划不來 |
| 串鏈條件 | **雙向**一對一 | 只看 `len(succ)==1` | 只看單向會把 merge 前的兩條鏈錯誤合併 |
| 臨界點 | 只記錄不參與串鏈 | 用臨界點來切 | 串鏈的邏輯本身就足夠；臨界點只當診斷資訊 |
| 連結搜尋 | O(n²) 雙重迴圈 | 依 band 建索引 | ⚠ 目前 n < 40 不是瓶頸；碎裂時會變慢 |
| cell 內是否重求主軸 | 否 | 各 cell 各自 PCA | 第 09 章 9.7：實測撤回 |

## 11.8 ⑥ 本章重點回顧

1. ★ **cell 的定義**：一群 run，滿足「沿掃描方向切片時每片都是單一連通區間」
   —— 也就是**內部沒有障礙把掃描線切開**。
2. ★ **臨界點 = run 數量變化的位置**：
   `len(succ) > 1` 是 **split**（分裂），`len(pred) > 1` 是 **merge**（合併）。
3. **連通判準是「相鄰帶的長軸投影重疊」**：`ri.a0 <= rj.a1 and rj.a0 <= ri.a1`。
   這是一個近似（沒檢查中間 0.18 m），但因為比安全邊距大，實務上安全。
4. ★ **串鏈條件是「雙向一對一」**：我只有一個後繼，**而且**它只有我一個前驅。
   只看單向會把 merge 前的兩條鏈錯誤合併。
5. **`taken` 保證每個 run 只屬於一個 cell**；
   ⚠ 副作用是某些鏈可能提早斷開，cell 數比理論值稍多，但**覆蓋不會漏**。
6. **cell 分解的價值不是「覆蓋更完整」（第 10 章就做到了），而是「路徑更短」**
   —— 消掉每條帶都要跨越障礙的空跑。
7. ⚠ `_link_runs` 是 **O(n²)**，run 大量碎裂時（第 22 章的斜置 30°）會變慢。

## 11.9 ⑦ 自我檢核題

**Q1. 為什麼串鏈的條件要「雙向」一對一？只檢查 `len(succ[cur]) == 1` 會怎樣？**

<details>
<summary>參考答案</summary>

會在 **merge（合併）** 的地方出錯。

```
   band 7:        [-2.0 ──────────────── +2.0]   run #10
                    ↑                  ↑
   band 6:  [-2.0 ── -0.5]      [+0.5 ── +2.0]
              run #8              run #9
```

- `succ[#8] = {#10}` —— **只有一個後繼** ✓
- `succ[#9] = {#10}` —— 也只有一個後繼 ✓
- 但 `pred[#10] = {#8, #9}` —— **有兩個前驅**

只檢查 `succ` 的話，柱子左側那條鏈（`#4→#6→#8`）會把 `#10` 接進來，
繼續往上串到 band 10 —— **左側 cell 吃掉了整個上半部**。
然後右側那條鏈（`#5→#7→#9`）走到 `#9` 就沒得接了（`#10` 已被 `taken`）。

**後果**：
- cell 邊界跑掉了，上半部被歸到左側 cell
- 蛇行時會從「柱子左側」直接接到「整條寬的帶」，
  兩條 run 的長度差很多，換行接駁會拉出一條斜線
- 走訪順序的最佳化失去意義（cell 的形狀不再是「乾淨的區塊」）

**正確的語意**：cell 邊界要切在**空間結構改變的地方**，
merge 就是這樣一個地方 —— 它上面是一整塊，下面是兩塊，不該歸在同一個 cell。
</details>

**Q2. `_link_runs` 的判準 `ri['a0'] <= rj['a1'] and rj['a0'] <= ri['a1']`
為什麼能判斷「兩個區間重疊」？舉一個剛好不重疊的例子。**

<details>
<summary>參考答案</summary>

兩個區間 `A = [a0, a1]`、`B = [b0, b1]` **不重疊**只有兩種情況：
A 完全在 B 左邊（`a1 < b0`），或 A 完全在 B 右邊（`b1 < a0`）。

取反（重疊）就是：`a1 >= b0` **且** `b1 >= a0`，
也就是程式裡的 `a0 <= b1 and b0 <= a1`。

**剛好不重疊的例子**：

```
   A = [-2.0, -0.5]     柱子左側
   B = [+0.5, +2.0]     柱子右側

   a0 <= b1 ?   -2.0 <= 2.0   ✓
   b0 <= a1 ?    0.5 <= -0.5  ✗   ← 這裡擋掉了
```

所以柱子左側的 run 和右側的 run **不會被連在一起**，
這正是我們要的 —— 它們屬於不同的 cell。

★ 注意這個判準包含「剛好接觸」的情況（`a1 == b0` 也算重疊）。
對本專案來說這是合理的：兩個區間端點重合代表它們在長軸上剛好接壤，
確實可以從一邊走到另一邊。
</details>

```python
n_critical = len(r['critical']),
```

**Q4. `_link_runs` 是 O(n²)。第 22 章的斜置 30° 場地有 31 個 run，
如果碎裂更嚴重變成 300 個 run，會怎樣？怎麼改進？**

<details>
<summary>參考答案</summary>

**300 個 run → 90,000 次比較**。每次比較是幾個 Python 的比較運算加 set 操作，
粗估會從微秒級變成**幾十毫秒**。加上後面 `_build_cells` 和貪婪排序
（貪婪是 O(cell² × 4)，300 個 cell 就是 360,000 次 `_cell_waypoints` 呼叫）——
**整個規劃可能要好幾秒**。

使用者按下「開始執行」之後，Flask 執行緒會卡住這麼久
（`/coverage/start` 是同步的，`map_server.py:474`），網頁會沒有反應。

**改進方法**：runs 已經**依 band 遞增排列**，而且只有相鄰帶會連結。
先建索引：

```python
from collections import defaultdict
by_band = defaultdict(list)
for i, r in enumerate(runs):
    by_band[r['band']].append(i)

for i, ri in enumerate(runs):
    for j in by_band[ri['band'] + 1]:      # 只比較下一帶的 run
        rj = runs[j]
        if ri['a0'] <= rj['a1'] and rj['a0'] <= ri['a1']:
            succ[i].add(j); pred[j].add(i)
```

複雜度從 O(n²) 降到 **O(n × 每帶平均 run 數)**。

★ **但真正該修的是根因**：300 個 run 本身就不正常，
代表 `_slice_runs` 把邊界碎裂成一堆小段（第 22 章 22.5）。
修好碎裂之後 run 數會回到正常範圍，這個最佳化就不需要了。

**先修根因，再談最佳化。**
</details>

**Q5. 有人說「cell 分解只是為了讓覆蓋更完整」。這個說法對嗎？**

<details>
<summary>參考答案</summary>

**不對。覆蓋的完整性在第 10 章（中心線取樣）就已經解決了。**

第 09 章的實測數據可以直接證明：v2（中心線取樣，還沒有 cell 分解）
就已經做到「穿牆 0 條、路點守住安全邊距」。
所有的 run 都會被走到，覆蓋率不會因為缺少 cell 分解而下降。

**cell 分解真正解決的是「路徑長度」**：

沒有 cell 分解時，每換一條帶都可能要跨越障礙物一次：

```
   帶 6 右段 → 帶 5 左段：跨越
   帶 5 左段 → 帶 4 右段：跨越
   帶 4 右段 → 帶 3：跨越
```

有 cell 分解之後，只在 cell 交界處跨越：

```
   cell A（下半）全走完 → cell B（左）全走完 → cell C（右）→ cell D（上）
   只跨越 3 次
```

第 09 章的實測：v1 → v3，**掃描線從 5 條增加到 11 條，但路徑長度從 8.09 m 縮短到 7.29 m**。

★ **正確的說法**：
- **中心線取樣**（第 10 章）解決「覆蓋的正確性」
- **cell 分解**（本章）解決「覆蓋的效率」

兩者是不同的問題，不能混為一談。
</details>
