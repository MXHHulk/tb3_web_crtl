# 第 07 章　地圖資料處理

> **本章目標**：把 `/map` 這則訊息，變成「網頁看得到的四張圖」和「演算法吃得下的 bool 陣列」。
>
> 本章也會把全專案最容易搞混的東西一次講清楚：**三層座標系**。

---

## 7.1 ① 問題：一則 `OccupancyGrid` 要變成什麼

收到 `/map` 之後，有兩個完全不同的消費者：

```
                    ┌──→ 網頁：要「人看得懂的圖片」
   /map ────────────┤
   OccupancyGrid    └──→ 演算法：要「機器算得動的 bool 陣列」
```

兩者的需求差很多：

| | 網頁要的 | 演算法要的 |
|---|---|---|
| 格式 | PNG 圖片 | numpy bool 陣列 |
| 大小 | 越小越好（要走網路） | 原始大小 |
| 內容 | 好看、能分辨三種狀態 | 只要「能不能走」 |
| 方向 | 圖片座標（y 向下） | 世界座標（y 向上） |
| 範圍 | 裁掉沒用的空白 | 完整（座標才對得上） |

## 7.2 ② 直覺做法：收到就直接轉成圖片丟出去

```python
# ❌ 最直覺的寫法
def map_callback(msg):
    global map_png
    data = np.array(msg.data).reshape((msg.info.height, msg.info.width))
    map_png = to_png(data)

@app.route('/map.png')
def get_map():
    return map_png
```

### ③ 撞牆：五個問題

**① 圖片會非常大而且大部分是空白**

gmapping 預設地圖是 **384×384 格**（19.2 × 19.2 公尺），
但實際房間可能只有 4×2 公尺 = 80×40 格。
**99% 的圖片是「從沒看過」的灰色。**

**② 黑白顛倒**

`OccupancyGrid` 的值越大代表越可能有障礙（100 = 障礙）。
直接當灰階的話，障礙 = 亮白色、空地 = 全黑，跟直覺完全相反。

**③ 上下顛倒**

地圖的 `data[0]` 是**最下面那一列**（世界座標 y 最小），
但圖片的第 0 列是**最上面**。不翻轉的話，畫出來的地圖是鏡像的。

**④ 網頁看不到「演算法眼中的世界」**

演算法會把障礙物膨脹一圈當安全邊距。使用者在網頁上看到「這裡明明有路」，
但機器人就是不去 —— 因為在膨脹後的地圖上那裡已經被封死了。
**看不到就無法除錯。**

**⑤ 資料競爭**

`map_callback` 在 ROS 執行緒寫、Flask 在另一個執行緒讀。
沒有鎖的話會讀到寫了一半的東西。

### 第 1 段：防呆（第 138~140 行）

```python

```

gmapping 剛啟動時可能發一則尺寸為 0 的空地圖。不擋掉的話 `reshape` 會炸。

### 第 2 段：轉成 numpy 並算出三種遮罩（第 142~146 行）

```python
data  = np.array(msg.data, dtype=np.int8).reshape((h, w)).astype(np.int16)
known = data >= 0        # 已知（0 或 100）
obs   = data == 100      # 障礙
free  = data == 0        # 自由
kern  = np.ones((3, 3), dtype=bool)
```

★ `.astype(np.int16)` 的理由見第 02 章 2.5 —— 防止後面 `data * 255` 溢位。

`known` / `obs` / `free` 是三個**布林遮罩**，同樣大小的 True/False 陣列。
numpy 的布林索引讓後面的程式碼可以寫成 `gray[known] = ...`，
意思是「只對 `known` 為 True 的那些格子賦值」，不用寫迴圈。

### 第 3 段：四種圖層（第 148~168 行）★

```python
# 原始地圖灰階
gray = np.full((h, w), 128, dtype=np.uint8)
gray[known] = np.clip(255 - data[known] * 255 // 100, 0, 255).astype(np.uint8)

# 侵蝕地圖（障礙縮小，顯示用）
gray_e = np.full((h, w), 128, dtype=np.uint8)
gray_e[free] = 255
gray_e[binary_erosion(obs, kern, MORPH_ITER)] = 0

# 膨脹地圖（障礙擴大，顯示用）
gray_d = np.full((h, w), 128, dtype=np.uint8)
gray_d[free] = 255
gray_d[binary_dilation(obs, kern, MORPH_ITER)] = 0

# 規劃用安全邊距：直接呼叫演算法本身的函式，確保畫面與規劃完全一致
safe = apply_safety_margin(data, COV_MARGIN, msg.info.resolution)
gray_m = np.full((h, w), 128, dtype=np.uint8)
gray_m[free] = 255
gray_m[safe] = 0
```

**灰階值的約定**（四張圖都一樣）：

```
   128  未知（-1）      中灰
   255  自由（0）       白
     0  障礙（100）     黑
```

`np.full(..., 128)` 先把整張填成「未知」，再把已知的格子蓋上去。

**`255 - data * 255 // 100` 是什麼？**

這是把 `0~100` 的機率值線性映射到 `255~0` 的灰階（**反轉**）：

```
   data =   0（自由）  →  255 - 0    = 255（白）
   data = 100（障礙）  →  255 - 255  =   0（黑）
   data =  50          →  255 - 127  = 128（灰）
```

雖然 gmapping 實際只吐 0 / 100，但這個寫法能正確處理任何中間值。

### ★ 三種形態學處理的差別（最容易搞混的地方）

| 圖層 | 函式 | 參數 | 用途 | **會不會影響機器人走路** |
|---|---|---|---|---|
| `map_eroded` | `binary_erosion` | `3×3` 核，`MORPH_ITER=2` 次 | 顯示：看細節、判斷是不是雜訊 | ❌ **完全不會** |
| `map_dilated` | `binary_dilation` | `3×3` 核，`MORPH_ITER=2` 次 | 顯示：看障礙物大概多大 | ❌ **完全不會** |
| `map_margin` | `apply_safety_margin` | `MARGIN=0.10 m` → 5×5 核，1 次 | ★ **規劃真正用的** | ✅ **會** |

```
   原始         侵蝕（縮小）      膨脹（放大）
   ░░███░░      ░░░█░░░           ░█████░
   ░█████░  →   ░░███░░       →   ███████
   ░░███░░      ░░░█░░░           ░█████░
```

> ★ **這是本章最重要的一個觀念。**
> 前兩張是**顯示用的視覺工具**，參數 `MORPH_ITER = 2` 是隨便挑的、可以任意改，
> 改了只影響網頁好不好看。
>
> 第三張是**演算法真正吃的東西**，參數 `MARGIN = 0.10` 對應機器人半徑，改了會改變機器人的行為。
>
> ⚠ 口試很可能問：「你的膨脹是幾次？」——
> 要反問「你是說顯示的還是規劃的？」，這兩個是不同的東西。

### 第 4 段：裁切（第 170 行 + `_crop`）

```python
r0, r1, c0, c1 = _crop(known, h, w)
```

```python
# scripts/map_server.py:108-119
def _crop(known, h, w):
    """找出已知格子的最小矩形（加邊距）。"""
    r = np.any(known, axis=1)      # 每一列有沒有任何已知格
    c = np.any(known, axis=0)      # 每一欄有沒有任何已知格
    if not r.any():
        return 0, h, 0, w          # 全部未知 → 不裁
    r0 = max(np.argmax(r)          - CROP_PAD, 0)
    r1 = min(h - np.argmax(r[::-1]) + CROP_PAD, h)
    c0 = max(np.argmax(c)          - CROP_PAD, 0)
    c1 = min(w - np.argmax(c[::-1]) + CROP_PAD, w)
    return r0, r1, c0, c1
```

**`np.argmax` 在布林陣列上的妙用**：`argmax` 回傳「最大值第一次出現的索引」，
布林陣列的最大值是 `True`，所以 **`np.argmax(r)` = 第一個 True 的位置**。

```
   r      = [F, F, F, T, T, T, T, F, F]
              ↑        ↑           ↑
   argmax(r) = 3（第一個 True）

   r[::-1] = [F, F, T, T, T, T, F, F, F]
   argmax(r[::-1]) = 2 → 從後面數第 2 個開始是 True
   → 最後一個 True 的位置 = h - 2 - 1
```

`CROP_PAD = 10` 是往外留 10 格（0.5 公尺）的邊距，讓地圖邊緣不要貼著圖片邊。

**效果**：384×384 的地圖裁成大約 100×60，**圖片體積小 20 倍以上**。

⚠ **裁切帶來一個副作用**：圖片的 (0,0) 不再是地圖的 (0,0)。
所以要記住 `r0`、`c0` 這兩個偏移量，否則路徑會畫錯位置 —— 見 7.4。

### `_to_png`：黑白反轉與上下翻轉

```python
# scripts/map_server.py:101-106
def _to_png(arr):
    """地圖處理後轉 PNG bytes（黑白反轉，並上下翻轉）。"""
    buf = io.BytesIO()
    Image.fromarray(np.flipud(arr), 'L').save(buf, format='PNG')
    return buf.getvalue()
```

- **`np.flipud`**：上下翻轉。解決 7.2 的問題 ③（地圖 y 向上、圖片 y 向下）
- **`'L'`**：8-bit 灰階模式
- **`io.BytesIO()`**：存在記憶體裡，不寫檔案

（「黑白反轉」其實是在第 3 段的 `255 - data * 255 // 100` 做的，docstring 說的是整體效果。）

## 7.4 ★★ 三層座標系（全書最容易出錯的地方）

```
   ┌─────────────────────────────────────────────────────────┐
   │ ① 世界座標 (wx, wy)   單位：公尺                        │
   │    ROS 的通用語言。move_base 的目標點、演算法的路點     │
   │    原點在 map 座標系的 (0,0)，y 軸向上 ↑               │
   └───────────────────────┬─────────────────────────────────┘
                           │  wx = ox + col × res
                           │  col = (wx - ox) / res
   ┌───────────────────────┴─────────────────────────────────┐
   │ ② 格子座標 (row, col)  單位：格                         │
   │    OccupancyGrid 的索引。data[row, col]                 │
   │    ⚠ row 對應 y、col 對應 x（寫成 [y, x]）             │
   └───────────────────────┬─────────────────────────────────┘
                           │  減去裁切偏移 (r0, c0)
                           │  y 方向再翻轉
   ┌───────────────────────┴─────────────────────────────────┐
   │ ③ 圖片像素 (px, py)   單位：像素                        │
   │    裁切後 PNG 的座標。前端 Canvas 直接用                │
   │    原點在左上角，y 軸向下 ↓                            │
   └─────────────────────────────────────────────────────────┘
```

### 一次做完兩層轉換的函式

```python
# scripts/map_server.py:352-356
def world_to_px(wx, wy, meta):
    """座標轉換（世界 → 裁切後圖片像素）"""
    px = (wx - meta['origin_x']) / meta['resolution'] - meta['c0']
    py = meta['crop_h'] - ((wy - meta['origin_y']) / meta['resolution'] - meta['r0'])
    return round(px, 1), round(py, 1)
```

**拆開來看：**

```python
# x 方向
(wx - origin_x) / resolution      # 世界 → 格子座標的 col
                        - c0      # 減掉裁切偏移

# y 方向
(wy - origin_y) / resolution      # 世界 → 格子座標的 row
                        - r0      # 減掉裁切偏移
crop_h - (...)                    # ★ 上下翻轉（對應 _to_png 的 np.flipud）
```

★ **`crop_h - (...)` 這個翻轉是最容易漏掉的一步。**
漏掉的症狀是：地圖看起來正常，但路徑和機器人圖示上下顛倒。

★ **`round(..., 1)` 保留一位小數**，不是取整數。
因為機器人位置是連續的，取整會讓圖示一格一格跳。
保留小數點讓 Canvas 畫在「格子中間」，看起來平滑。

### 誰在用這個函式

```python
# scripts/map_server.py:414-415（機器人位置 + 軌跡）
'path': [list(world_to_px(p[0], p[1], meta)) for p in path_w],

# scripts/map_server.py:448（雷射點）
pts.append(list(world_to_px(wx, wy, meta)))

# scripts/map_server.py:520-521（覆蓋路徑 + cell）
st['path_px']  = [list(world_to_px(x, y, meta)) for x, y in path_w]
st['cells_px'] = [[list(world_to_px(x, y, meta)) for x, y in c] for c in cells]
```

★ **所有要畫到畫面上的東西，都在後端轉好才傳出去**（第 05 章 5.4 的設計決策）。
前端 587 行裡沒有任何一行座標數學。

### 演算法那邊用的是另一組轉換

`coverage_planner.py` 完全不知道「圖片像素」的存在，它只在**世界 ↔ 格子**之間換：

## 7.5 ⑤ 設計決策：被否決的方案

| 方案 | 為什麼否決 |
|---|---|
| **前端自己算座標轉換** | 公式要寫兩份、裁切偏移會變動、上下翻轉極易漏掉。見第 05 章 5.4 |
| **不裁切，傳完整地圖** | 384×384 的 PNG 大部分是空白，浪費 20 倍頻寬 |
| **只提供一張地圖** | 看不到演算法眼中的世界，無法除錯「為什麼那裡不去」 |
| **顯示用膨脹直接用 `apply_safety_margin`** | 0.10 m 只有 2 格，視覺上幾乎看不出來；顯示需要更誇張的效果才有用 |
| **在鎖裡面做 PNG 編碼** | Flask 執行緒每次讀圖都要等幾十毫秒 |
| **回呼裡直接做覆蓋規劃** | 規劃要 200 ms，會塞住 `/map` 的接收（第 17 章） |

## 7.6 ⚠ 已知問題

**① 每次 `/map` 都重算四張圖，即使沒人在看**

`map_callback` 每次都做 3 次形態學 + 4 次 PNG 編碼。
如果沒有人開網頁，這些全部是白工。

**改進方向**：改成 lazy —— 只存 `data`，PNG 在路由被呼叫時才算並快取。
代價是路由變慢、要多一層快取失效邏輯。以目前 `/map` 只有幾 Hz 來說不划算。

**② 裁切範圍會跳動**

地圖長大時 `r0`/`c0` 會變，圖片尺寸也跟著變。
前端每次都用 `orig.naturalWidth/Height` 重設 canvas 尺寸（`web/index.html:284-285`），
所以畫面會有輕微的跳動。

**③ 未知格（-1）在四張圖裡都是 128 灰**

但**演算法把它當成不可走**。畫面上看起來「這裡是灰的、不確定」，
實際上等同於牆。第 19 章會講這造成的「假完成」。

## 7.7 ⑥ 本章重點回顧

1. **一則 `/map` 要餵兩種消費者**：網頁要小而好看的 PNG，演算法要完整的 bool 陣列。
2. ★ **三種形態學處理要分清楚**：`eroded`/`dilated` 是**顯示用**（`MORPH_ITER=2`，改了不影響走路）；
   `margin` 是**規劃用**（`MARGIN=0.10 m`，改了會改變行為）。
3. ★ **「所見即所算」**：`map_margin` 呼叫的就是 `coverage_planner` 的
   `apply_safety_margin`，畫面上的紅色層逐格等於演算法認定不能走的地方。
4. **裁切用 `np.argmax` 找布林陣列的第一個 True**，把 384×384 縮到約 100×60，體積小 20 倍。
5. ★ **所有計算在鎖外做完，鎖內只賦值**；四張圖 + meta + data 必須一次換掉。
6. ★★ **三層座標系**：世界（公尺，y↑）→ 格子（`[row, col]` = `[y, x]`）→
   圖片像素（左上原點，y↓）。`world_to_px` 一次做完後兩層，
   其中 `crop_h - (...)` 的**上下翻轉最容易漏**。
7. **座標轉換全部在後端做**，前端零數學。

## 7.8 ⑦ 自我檢核題

**Q1. 網頁上有「膨脹層」和「安全邊距」兩個圖層，它們差在哪？哪一個才是機器人真正遵守的？**

<details>
<summary>參考答案</summary>

| | 膨脹層（`/map_dilated.png`） | 安全邊距（`/map_margin.png`） |
|---|---|---|
| 產生方式 | `binary_dilation(obs, 3×3核, 2 次)` | `apply_safety_margin(data, 0.10, res)` |
| 核大小 | 3×3，做 2 次 → 約 2 格 | `round(0.10/0.05)=2` → 5×5，做 1 次 → 2 格 |
| 參數意義 | 隨便挑的視覺參數 | 對應機器人半徑（物理量） |
| 誰在用 | **只有網頁** | ★ **`plan()` 真正用的** |
| 改了會怎樣 | 網頁圖層變粗變細 | **機器人行為改變** |

**機器人真正遵守的是「安全邊距」那一層。**

⚠ 兩者膨脹出來的格數碰巧接近（都約 2 格），視覺上很像，所以特別容易搞混。
但意義完全不同：一個是「畫給人看的」，一個是「算給機器用的」。

判斷「為什麼機器人不去某個地方」時，**只能看安全邊距那一層**。
</details>

**Q2. `_crop` 裡的 `np.argmax(r[::-1])` 在做什麼？為什麼不直接寫迴圈找最後一個 True？**

<details>
<summary>參考答案</summary>

`r` 是「每一列有沒有任何已知格」的布林陣列。
`r[::-1]` 把它反轉，`np.argmax` 找出反轉後第一個 True 的位置 ——
也就是**原陣列從尾巴數過來第幾個開始是 True**。

```
   r        = [F, F, T, T, T, F, F]     h = 7
   r[::-1]  = [F, F, T, T, T, F, F]
   argmax(r[::-1]) = 2
   → 最後一個 True 之後有 2 個 False
   → r1 = h - 2 = 5（切片上界，不含）
```

**為什麼不寫迴圈**：`np.argmax` 是 C 實作的，一次掃過整個陣列；
Python 迴圈跑 384 次，慢好幾十倍。而且 `map_callback` 每次收到地圖都會執行一次。

這是 numpy 的典型思路：**把「找位置」的問題轉成陣列運算**，
用反轉 + argmax 代替反向迴圈。
</details>

**Q3. 為什麼 `world_to_px` 的 y 方向要寫成 `crop_h - (...)`？如果漏掉這個減法會怎樣？**

<details>
<summary>參考答案</summary>

因為兩個座標系的 y 軸方向相反：

- **世界/格子座標**：y 向上為正（`row` 越大，位置越高）
- **圖片像素**：y 向下為正（`py` 越大，位置越低）

而 `_to_png` 用 `np.flipud(arr)` 把陣列上下翻轉過才存成 PNG，
所以座標也必須跟著翻轉：`py = crop_h - row_in_crop`。

**漏掉的症狀**：
- 地圖圖片本身看起來完全正常（因為 `np.flipud` 有做）
- 但**路徑、機器人圖示、軌跡、雷射點全部上下顛倒**

⚠ 這種 bug 特別惡劣，因為畫面「看起來有東西」，
只是位置在鏡像的地方。如果房間剛好上下對稱，甚至可能一時看不出來。

**驗證方法**：手動遙控機器人往前走，看網頁上的圖示是往哪個方向動。
</details>

**Q4. `map_callback` 把所有計算都放在 `with map_lock` 外面。為什麼？如果放進去會怎樣？**

<details>
<summary>參考答案</summary>

因為 `map_callback` 裡最慢的部分是：
- 3 次形態學運算（`binary_erosion` / `binary_dilation` ×2 / `apply_safety_margin`）
- **4 次 PNG 編碼**（最慢，每次幾毫秒到幾十毫秒）

**放進鎖裡的後果**：Flask 執行緒每次處理 `/map.png` 請求時，
都可能撞上正在編碼的 `map_callback`，被迫等待幾十毫秒。
前端每秒輪詢 4 張圖，就是每秒 4 次可能的卡頓。

更糟的是 `/coverage/start`：它要在 `map_lock` 裡拿 `map_data`，
如果剛好撞上，使用者按下開始按鈕會有明顯的延遲感。

**現在的寫法**：鎖裡面只有 6 個賦值語句，持有時間是**微秒等級**。

★ 這是併發程式的通用原則：**鎖保護的是「共享狀態的一致性」，不是「計算過程」。**
能在鎖外算的，一律在鎖外算完，鎖裡只做最後的交換。

（但四張圖 + meta + data **必須在同一把鎖裡一起換**，
否則會出現「圖是新的、meta 是舊的」的不一致 —— 這才是這把鎖真正在保護的東西。）
</details>

**Q5. 假設你發現網頁上的覆蓋路徑整體往右偏了 20 個像素。可能是哪裡出問題？**

<details>
<summary>參考答案</summary>

x 方向的偏移，嫌疑犯在 `world_to_px` 的這一行：

```python
px = (wx - meta['origin_x']) / meta['resolution'] - meta['c0']
```

三個可能：

1. **`c0` 不同步**：`meta` 是舊的（`c0` 還是上一張圖的），但 PNG 是新的。
   地圖長大時 `c0` 會變小，差 20 像素代表裁切範圍變了。
   → 檢查是不是有地方在 `map_lock` 外面讀 `map_meta`。

2. **`origin_x` 用錯**：例如用了機器人 odom 原點而不是地圖原點。

3. **前端拿到的 `path_px` 和 `map.png` 是不同時刻的**：
   `refresh()` 用 `Promise.allSettled` 同時發四個請求（`web/index.html:558-565`），
   如果地圖剛好在這幾個請求之間更新，圖片是新的、狀態是舊的。
   ⚠ 這是**現有設計的已知弱點**，但因為 `/map` 更新慢（幾 Hz）、
   裁切變化只在建圖初期發生，實務上很少遇到。

**排查順序**：先看 `/coverage/status` 回傳的 `path_px` 數值，
再自己用 `/map.png` 的尺寸和 `origin`/`c0` 手算一次，比對差異。
</details>
