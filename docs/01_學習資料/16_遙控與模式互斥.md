# 第 16 章　遙控與模式互斥

> **本章目標**：講清楚兩件事 ——
> **怎麼從網頁安全地遙控一台機器人**（斷線就停車），
> 以及**怎麼保證兩個控制來源不會打架**（模式互斥）。
>
> 這一章的內容和演算法無關，但它是**安全機制**，出錯的後果比演算法出錯嚴重得多。

---

## 16.1 ① 問題：網頁按方向鍵，機器人要動

需求很單純：

```
   使用者按住「↑」 → 機器人往前
   使用者放開      → 機器人停
```

但機器人和瀏覽器之間隔著 Wi-Fi、HTTP、ROS，
中間任何一環出問題，機器人可能就**收不到「停」這個指令**。

★ **一台以 0.18 m/s 往前開、而且再也收不到指令的機器人，會一路撞到牆為止。**

---

## 16.2 ② 直覺做法：按下送「開始」，放開送「停止」

```javascript
// ❌ 最直覺的寫法
button.onpointerdown = () => fetch('/teleop', {body: JSON.stringify({v: 1, w: 0})});
button.onpointerup   = () => fetch('/teleop', {body: JSON.stringify({v: 0, w: 0})});
```

```python
# ❌ 對應的後端
@app.route('/teleop', methods=['POST'])
def teleop():
    cmd_pub.publish(Twist(linear=..., angular=...))
```

### ③ 撞牆：六種「停不下來」的情況

| 情況 | 為什麼停不下來 |
|---|---|
| **Wi-Fi 斷線** | 「停止」的請求根本送不出去 |
| **關掉瀏覽器分頁** | `onpointerup` 永遠不會觸發 |
| **手機息屏 / 切換 App** | 同上 |
| **拔掉手機電池** | 同上 |
| **「停止」封包遺失** | HTTP 有重送，但 TCP 連線斷了就沒了 |
| **滑鼠拖出按鈕才放開** | `onpointerup` 在按鈕外觸發，事件收不到 |

★ **共同點：都是「停止」訊號遺失。**

**根本問題**：這個設計把「停」當成一個**事件**。
事件會遺失，而遺失的後果是機器人一直跑。

## 16.3 ④ 現在的做法：心跳 + 逾時（Dead Man's Switch）

★ **把設計反過來**：

> **不是「送一次開始、送一次停止」，而是「持續送『我還按著』，
> 一旦停止收到就自動停車」。**

這叫 **dead man's switch（失知開關）** —— 火車司機的手把、電鋸的握把用的都是同一個原理：
**放開就停，而不是按下才停。**

```
   前端：按住期間每 150 ms 送一次速度
        ●───●───●───●───●───│（放開，不再送）
                             │
   後端：每 100 ms 檢查一次   │
        「最後一次收到是多久前？」
                             │←── 0.6 秒 ──→│
                                            ↓
                                         自動送 0
```

**任何一種「訊號中斷」的情況，結果都一樣：後端 0.6 秒後自動停車。**

### 前端：150 ms 續傳

```javascript
// web/index.html:434-461
let holdTimer = null, holdCmd = null;
const speedScale = () => $('speed').value / 100;

async function teleopSend(v, w) {
    try {
        await fetch('/teleop', {
            method: 'POST',
            headers: { 'Content-Type': 'application/json' },
            body: JSON.stringify({ v, w }),
        });
    } catch {}                                  // ★ 失敗也不管，下一拍會再送
}

function teleopHold(v, w) {
    if (!cov.manual) return;                    // ① 執行中直接不送
    holdCmd = [v, w];
    const push = () => { const s = speedScale(); teleopSend(holdCmd[0] * s, holdCmd[1] * s); };
    push();                                     // ② 立刻送一次（不要等 150 ms）
    clearInterval(holdTimer);                   // ③ 清掉舊的計時器
    holdTimer = setInterval(push, 150);         // ④ 續傳，後端 0.6 秒沒收到就自動停車
}

function teleopRelease() {
    clearInterval(holdTimer); holdTimer = null; holdCmd = null;
    teleopSend(0, 0);                           // ⑤ 主動送一次 0（快速停車）
}
```

**五個細節：**

**② `push()` 先跑一次**：`setInterval` 要等第一個 150 ms 才觸發，
不先送一次的話按下去會有 150 ms 的延遲感。

**③ `clearInterval(holdTimer)`**：如果使用者從「↑」滑到「→」，
兩個 `teleopHold` 會呼叫兩次。不清掉舊的就會有**兩個計時器同時在送**不同的指令。

**⑤ `teleopSend(0, 0)`**：放開時**主動送一次停止**。
這是「快速路徑」—— 正常情況下 0 秒就停了，
逾時機制（0.6 秒）只是**網路正常時用不到的保險**。

★ **兩層保護：主動停止（快）+ 逾時停止（可靠）。**

**`catch {}` 為什麼可以吞掉錯誤**：因為 150 ms 後會再送一次。
單次失敗完全不影響 —— 這正是心跳模式的韌性。

### 後端：10 Hz 心跳 + TTL 檢查

```python
# scripts/map_server.py:220-235
def teleop_tick(_evt):
    """10 Hz 送出手動速度指令；指令過期或非手動模式一律送 0。"""
    if cmd_pub is None:
        return
    if not manual_allowed():
        return                                   # ① 覆蓋執行中，/cmd_vel 交給 move_base

    with teleop_lock:
        v, w, t = teleop_cmd['v'], teleop_cmd['w'], teleop_cmd['t']
    if rospy.get_time() - t > TELEOP_TTL:        # ② 網頁沒有續傳 → 自動停車
        v = w = 0.0

    tw = Twist()
    tw.linear.x  = v
    tw.angular.z = w
    cmd_pub.publish(tw)                          # ③ 一律發布，即使是 0
```

```python
# scripts/map_server.py:618
rospy.Timer(rospy.Duration(0.1), teleop_tick)   # 10 Hz 遙控心跳
```

★ **這個 Timer 從節點啟動就一直跑，和有沒有人在遙控無關。**

**HTTP 路由只是「更新一個變數」：**

```python
# scripts/map_server.py:531-548
@app.route('/teleop', methods=['POST'])
def teleop():
    """手動遙控。body: {v: -1..1, w: -1..1}（比例值，後端乘上速度上限）。"""
    if not manual_allowed():
        return jsonify({'ok': False, 'msg': '覆蓋執行中，請先按結束'}), 409   # ★

    body = request.get_json(silent=True) or {}
    try:
        v = float(body.get('v', 0.0))
        w = float(body.get('w', 0.0))
    except (TypeError, ValueError):
        return jsonify({'ok': False, 'msg': '速度格式錯誤'}), 400

    v = max(-1.0, min(1.0, v)) * V_MAX          # ★ 夾住 + 換算
    w = max(-1.0, min(1.0, w)) * W_MAX
    with teleop_lock:
        teleop_cmd.update(v=v, w=w, t=rospy.get_time())   # ★ 只更新變數
    return jsonify({'ok': True, 'v': round(v, 3), 'w': round(w, 3)})
```

★ **路由不發布 `/cmd_vel`**，它只寫 `teleop_cmd`（含**時間戳 `t`**）。
真正的發布由 Timer 統一做。

**為什麼要這樣分離？**

| | 路由直接發布 | 現在（Timer 統一發布） |
|---|---|---|
| 發布頻率 | 跟著 HTTP 請求（不穩定，可能 5 Hz 可能 20 Hz） | **穩定 10 Hz** |
| 網路抖動 | 指令忽快忽慢，機器人一頓一頓 | 不受影響 |
| 逾時停車 | 沒地方做 | ✅ Timer 每次都檢查 |
| 模式切換 | 要在多處檢查 | ✅ 一處檢查 |

### 三個安全參數

```python
# scripts/map_server.py:56-58
V_MAX      = 0.18   # 手動遙控線速度上限（m/s），Burger 規格 0.22
W_MAX      = 1.50   # 手動遙控角速度上限（rad/s），Burger 規格 2.84
TELEOP_TTL = 0.6    # 遙控指令有效期（秒）；逾時未收到新指令就自動停車
```

**① `V_MAX` / `W_MAX` 壓在規格以下**

前端送的是 **−1~1 的比例值**，後端乘上上限。所以：
- 前端**不知道**實際速度是多少（也不需要知道）
- ★ **前端就算被竄改送 `v: 999`，`max(-1, min(1, v))` 也會夾成 1**

**縱深防禦**：前端的滑桿限制在 20~100%，
後端再夾一次比例，最後再乘上保守的上限。

**為什麼比規格慢**：人在網頁上操作有延遲（150 ms 續傳 + 網路 + 渲染），
開太快來不及反應就撞了。0.18 m/s 大約是**慢走**的速度。

**② `TELEOP_TTL = 0.6`**

為什麼是 0.6 而不是 0.3 或 1.0？

```
   前端續傳間隔     150 ms
   TTL              600 ms  = 4 個續傳週期
```

★ **容許連續掉 3 個封包才停車**。

- **太短（例如 0.2 s）**：Wi-Fi 稍微抖一下就停車，操作會一頓一頓
- **太長（例如 2 s）**：斷線後機器人還會往前開 0.36 公尺才停

0.6 秒 × 0.18 m/s = **最多滑行 11 公分**，可以接受。

## 16.4 ★ 模式互斥

### 問題：`/cmd_vel` 有兩個發布者

第 01 章 1.10 講過：

```
   move_base   ────publish───┐
                             ├──→ /cmd_vel ──→ 馬達
   map_server  ──publish─────┘
```

ROS **完全允許**這件事，不會報錯。後果是馬達交替收到兩邊的指令，
機器人一頓一頓、方向亂跳。

### 解法：單一真相來源

```python
# scripts/map_server.py:10-14（檔案 docstring）
模式互斥規則（單一真相來源＝cov_status['state']）：
  state == 'running'  → 覆蓋執行中，手動遙控被拒絕
  其他狀態            → 可手動遙控
按下停止、覆蓋完成、或發生錯誤都會離開 running，自動切回可手動。
```

```python
# scripts/map_server.py:92-95
def manual_allowed():
    """手動遙控是否被允許（覆蓋執行中一律禁止）。"""
    with cov_lock:
        return cov_status['state'] != 'running'
```

### ★ 四道防線

```
   ① 前端 UI：執行中把遙控盤 disabled（web/index.html:520-521）
        ↓ 就算被繞過（開發者工具、直接 curl）
   ② 前端邏輯：teleopHold 開頭 if (!cov.manual) return（web/index.html:450）
        ↓ 就算被繞過
   ③ 後端路由：/teleop 回 HTTP 409（map_server.py:532-534）
        ↓ 就算 teleop_cmd 裡有殘留值
   ④ 後端 Timer：teleop_tick 開頭 if not manual_allowed(): return（map_server.py:224-225）
        ↓
      /cmd_vel 一句話都不會發
```

★ **第 ④ 道是真正的防線**。前三道都是「更早拒絕、更好的使用者體驗」，
但即使全部失效，只要 Timer 不發布，`move_base` 就獨占 `/cmd_vel`。

★ **回 HTTP 409 Conflict 而不是 403 Forbidden**：
409 的語意是「**因為目前的狀態衝突**」，而不是「你沒有權限」。
使用者按「結束」之後就可以了 —— 這正是 409 要表達的意思。

### 模式切換時的收尾

**進入自動模式**（`/coverage/start`）：

```python
# scripts/map_server.py:466
teleop_halt()                                  # 交出 /cmd_vel 控制權前先停車
```

```python
# scripts/map_server.py:238-247
def teleop_halt():
    """立刻把速度歸零（切換模式或重啟 SLAM 前呼叫）。"""
    with teleop_lock:
        teleop_cmd.update(v=0.0, w=0.0, t=-1e9)   # ★ t 設成極小值 = 立刻過期
    if cmd_pub is not None:
        cmd_pub.publish(Twist())                   # ★ 立刻發一次 0
```

★ **`t = -1e9`** 讓這筆指令**永遠是過期的**。
即使之後 `manual_allowed()` 又變成 True，
`teleop_tick` 也會因為 TTL 檢查而送 0，不會拿舊速度繼續跑。

**離開自動模式**（`/coverage/stop`）：

```python
# scripts/map_server.py:505
teleop_halt()
```

★ 停止覆蓋時也要 `teleop_halt()`。為什麼？
因為 `move_base` 被 `cancel_all_goals()` 之後不一定會發最後一個 0，
機器人可能帶著殘餘速度。我們主動補一個 0 上去。

**前端也做了同樣的事**：

```javascript
// web/index.html:527-529
// 剛從手動被鎖住 → 確保沒有殘留的續傳
if (wasManual && !cov.manual) teleopRelease();
wasManual = cov.manual;
```

★ **邊緣觸發**（只在狀態變化的那一刻做，不是每秒做）。
清掉 150 ms 的續傳計時器，避免它繼續對後端送請求（雖然後端會拒絕，但是無謂的流量）。

## 16.5 前端的三種輸入方式

### ① 九宮格按鈕

```html
<!-- web/index.html:174-184 -->
<div class="pad" id="pad">
    <button data-v="0.7"  data-w="0.6"  title="左前">↖</button>
    <button data-v="1"    data-w="0"    title="前進 (W)">↑</button>
    <button data-v="0.7"  data-w="-0.6" title="右前">↗</button>
    <button data-v="0"    data-w="1"    title="左轉 (A)">←</button>
    <button data-v="0"    data-w="0"    title="停止 (空白鍵)" class="stop">■</button>
    <button data-v="0"    data-w="-1"   title="右轉 (D)">→</button>
    <button data-v="-0.7" data-w="0.6"  title="左後">↙</button>
    <button data-v="-1"   data-w="0"    title="後退 (S)">↓</button>
    <button data-v="-0.7" data-w="-0.6" title="右後">↘</button>
</div>
```

★ **速度值寫在 HTML 的 `data-*` 屬性裡**，JS 直接讀：

```javascript
// web/index.html:463-472
for (const b of $('pad').children) {
    const v = parseFloat(b.dataset.v), w = parseFloat(b.dataset.w);
    b.addEventListener('pointerdown', e => {
        e.preventDefault();
        (v === 0 && w === 0) ? teleopRelease() : teleopHold(v, w);
    });
    b.addEventListener('pointerup',     teleopRelease);
    b.addEventListener('pointerleave',  teleopRelease);   // ★ 滑出按鈕也放開
    b.addEventListener('pointercancel', teleopRelease);   // ★ 手勢被系統打斷
}
```

★ **三個放開事件都要接**：
- `pointerup` — 正常放開
- `pointerleave` — **滑鼠按著拖出按鈕範圍**（不接的話機器人會一直跑）
- `pointercancel` — 手機上被系統手勢（下拉通知、返回手勢）打斷

★ **`pointer*` 事件同時支援滑鼠和觸控**，不用分別寫 `mouse*` 和 `touch*`。

★ **斜向的 `0.7 / 0.6`**：斜前進不用滿速，避免轉太急。

### ② 鍵盤

```javascript
// web/index.html:474-494
const KEYS = {
    w: [1, 0], arrowup:    [1, 0],
    s: [-1, 0], arrowdown: [-1, 0],
    a: [0, 1], arrowleft:  [0, 1],
    d: [0, -1], arrowright:[0, -1],
};
let heldKey = null;
addEventListener('keydown', e => {
    if (e.target.tagName === 'INPUT') return;      // ① 在滑桿上打字時不要觸發
    const k = e.key.toLowerCase();
    if (k === ' ') { e.preventDefault(); teleopRelease(); return; }   // ② 空白鍵 = 停
    if (!KEYS[k] || !cov.manual || heldKey === k) return;             // ③ 防重複
    e.preventDefault();                                                // ④ 防捲動
    heldKey = k;
    teleopHold(...KEYS[k]);
});
addEventListener('keyup', e => {
    const k = e.key.toLowerCase();
    if (k === heldKey) { heldKey = null; teleopRelease(); }            // ⑤ 只認同一個鍵
});
addEventListener('blur', () => { heldKey = null; teleopRelease(); });  // ★ 切換視窗
```

★ **③ `heldKey === k` 防重複觸發**：按住不放時瀏覽器會**連續觸發 `keydown`**
（自動重複）。不擋的話每次都會 `clearInterval` + `setInterval`，
計時器一直被重設，`push()` 一直被立即呼叫 —— 變成每秒送 30 次請求。

★ **⑤ `if (k === heldKey)`**：如果使用者按住 W 再按 A 再放開 A，
不該停車（W 還按著）。只有放開「當前記錄的那個鍵」才停。

★ **`blur` 事件**：切換到別的視窗、按 Alt+Tab、手機切 App 時觸發。
不接的話，`keyup` 永遠不會來 → 機器人一直跑。

> 💡 就算 `blur` 也漏了，**後端 0.6 秒的 TTL 還是會停車**。
> 這就是「多層防護」的意義：每一層都可能有漏洞，但同時漏的機率極低。

### ③ 速度滑桿

```javascript
// web/index.html:435-437
const speedScale = () => $('speed').value / 100;
$('speed').oninput = () => { $('speed-val').textContent = $('speed').value + '%'; };
```

```javascript
// web/index.html:452
const push = () => { const s = speedScale(); teleopSend(holdCmd[0] * s, holdCmd[1] * s); };
```

★ **`speedScale()` 在 `push` 裡面每次重新讀取**，
所以**按著方向鍵的同時拖動滑桿，速度會即時改變**。

如果在 `teleopHold` 開頭讀一次存起來，就得放開重按才會生效。

**最終的速度計算鏈**：

```
   按鈕的 data-v  ×  滑桿比例(0.2~1.0)  →  前端送出（−1~1）
                                       →  後端夾住 max(-1, min(1, v))
                                       →  × V_MAX(0.18)
                                       →  Twist.linear.x
```

## 16.6 ⑤ 設計決策

| 決策 | 選了 | 否決了 | 理由 |
|---|---|---|---|
| 遙控協定 | **心跳 + TTL** | 送「開始/停止」事件 | 事件會遺失，遺失 = 機器人不停 |
| 發布 `/cmd_vel` | Timer 統一 10 Hz | 路由直接發布 | 頻率穩定、逾時檢查有地方做 |
| 續傳間隔 | 150 ms | 更長 / 更短 | TTL 的 1/4，容許掉 3 個封包 |
| TTL | 0.6 s | 0.2 s / 2 s | 0.2 太敏感會頓；2 s 會滑行 36 cm |
| 速度上限 | 0.18 / 1.50 | 用規格上限 0.22 / 2.84 | 人有操作延遲，保守一點 |
| 前端送什麼 | **比例值 −1~1** | 實際速度 m/s | 上限只在後端一處定義；前端被竄改也無害 |
| 互斥判斷 | `cov_status['state']` 單一來源 | 另設一個 `mode` 變數 | 兩個變數就會不同步 |
| 拒絕的狀態碼 | **409 Conflict** | 403 Forbidden | 409 = 狀態衝突（按結束就好），403 = 沒權限 |
| 事件監聽 | `pointer*` | `mouse*` + `touch*` | 一套程式碼同時支援滑鼠與觸控 |

## 16.7 ⚠ 已知問題

**① 沒有加速度限制**

從 0 直接跳到 0.18 m/s。TurtleBot3 的驅動有內建平滑，
但如果換成加速更猛的底盤，會很顛。

**改進**：在 `teleop_tick` 裡做速度的一階低通（每次最多變化 0.02 m/s）。

**② 遙控時不看障礙物**

手動模式完全不經過 `move_base`，**沒有任何避障**。
使用者可以直接把機器人開進牆裡。

**這是刻意的** —— 手動模式的用途之一就是「把卡住的機器人救出來」，
如果有避障反而出不來。但要在文件裡講清楚。

**③ 多個使用者同時遙控會互相覆蓋**

兩個人同時開網頁，兩邊的續傳都會寫 `teleop_cmd`，
機器人會收到交替的指令。沒有「誰在控制」的概念。

**④ `teleop_tick` 在非手動模式直接 `return`，不發布 0**

```python
if not manual_allowed():
    return          # ← 沒有 publish
```

★ 這是**正確的**（要把 `/cmd_vel` 完全讓給 `move_base`），
但代表模式切換的那一刻，是靠 `teleop_halt()` 主動送 0 來停車的。
如果哪天有人漏掉 `teleop_halt()`，機器人可能帶著殘餘速度進入自動模式。

---

## 16.8 ⑥ 本章重點回顧

1. ★ **遙控用「心跳 + 逾時」而不是「開始/停止事件」**。
   事件會遺失（斷線、關分頁、息屏），而遺失的後果是機器人不停。
   心跳模式下，**任何訊號中斷的結果都一樣：自動停車**。
2. **前端 150 ms 續傳、後端 0.6 s TTL** —— 容許連續掉 3 個封包，
   最壞滑行 11 公分。
3. ★ **HTTP 路由只更新變數（含時間戳），不發布 `/cmd_vel`**；
   發布由 10 Hz 的 `rospy.Timer` 統一做 → 頻率穩定、逾時檢查有地方做。
4. **前端送比例值（−1~1），後端夾住再乘上限** —— 上限只在一處定義，
   前端被竄改也無害。
5. ★ **模式互斥的單一真相來源是 `cov_status['state']`**，四道防線，
   其中 `teleop_tick` 開頭的檢查是**真正的**那一道。
6. **`teleop_halt()` 把時間戳設成 `-1e9`**，讓舊指令永遠過期。
7. **`pointerleave` / `pointercancel` / `blur` 三個事件都要接** ——
   它們都是「使用者其實已經放開了，但 `pointerup`/`keyup` 不會來」的情況。
8. **回 409 Conflict 不是 403** —— 語意是「狀態衝突」不是「沒權限」。

## 16.9 ⑦ 自我檢核題

**Q1. 如果拿掉後端的 `TELEOP_TTL` 檢查（永遠用最後收到的速度），
使用者關掉瀏覽器分頁會發生什麼？**

<details>
<summary>參考答案</summary>

**機器人會保持最後那個速度，一路開到撞牆為止。**

流程：
1. 使用者按住「↑」，前端每 150 ms 送一次 `{v: 1, w: 0}`
2. `teleop_cmd` 被更新成 `v = 0.18`
3. **使用者直接關掉分頁**（不是放開按鈕）
4. `teleopRelease()` **永遠不會被呼叫**，那個 `(0,0)` 永遠不會送出
5. 沒有 TTL 的話，`teleop_tick` 每 100 ms 讀到的還是 `v = 0.18`
6. **`/cmd_vel` 持續發布 0.18 m/s，永遠不停**

★ **這正是 dead man's switch 要解決的問題。**

有 TTL 之後：
- 最後一次收到是在 T 時刻
- T + 0.6 秒之後，`rospy.get_time() - t > 0.6` 成立
- `v = w = 0.0`，`/cmd_vel` 開始發 0 → 停車
- 最壞滑行 0.6 × 0.18 = **11 公分**

**同樣被這個機制救到的情況**：Wi-Fi 斷線、手機息屏、拔電池、
瀏覽器當掉、封包全部遺失。**全部都是同一個處理方式。**
</details>

**Q2. 為什麼 `/teleop` 路由不直接 `cmd_pub.publish()`，而要交給 `rospy.Timer`？**

<details>
<summary>參考答案</summary>

四個理由：

**① 發布頻率會不穩定**

HTTP 請求的到達時間受網路抖動影響。前端設定 150 ms，
實際可能是 120、200、80、350 ms。直接發布的話，
`/cmd_vel` 的頻率就跟著抖 —— 機器人會一頓一頓。

Timer 用固定的 10 Hz 發布，**不管 HTTP 什麼時候來**。

**② 逾時檢查沒地方做**

TTL 的語意是「**已經多久沒收到新指令了**」。
這件事必須由一個「定期醒來檢查」的東西來做。
如果只有收到請求時才執行程式碼，**沒收到請求時就沒有任何程式在跑** ——
根本沒有機會發現「太久沒收到了」。

**③ 模式檢查集中在一處**

`teleop_tick` 開頭的 `if not manual_allowed(): return`
是**唯一**能保證「執行中絕對不發 `/cmd_vel`」的地方。

**④ 職責分離**

- **路由**：接收使用者意圖（快、無狀態、可能失敗）
- **Timer**：控制輸出（穩定、有狀態、有安全檢查）

★ 這是控制系統的通用模式：**輸入是事件驅動的，輸出是週期驅動的。**
中間用一個「當前期望值 + 時間戳」的狀態把兩者解耦。
</details>

**Q3. `TELEOP_TTL` 為什麼設 0.6 秒？設成 0.2 或 2.0 會怎樣？**

<details>
<summary>參考答案</summary>

**0.6 秒 = 前端續傳間隔（150 ms）的 4 倍**，也就是**容許連續掉 3 個封包**。

**設成 0.2 秒**（≈1.3 個週期）：
- Wi-Fi 稍微抖一下、或瀏覽器忙一下（正在解碼 PNG）導致一次續傳晚了 50 ms
  → 立刻停車 → 下一拍又開始 → **機器人一頓一頓**
- 手機在弱訊號區幾乎沒辦法用

**設成 2.0 秒**：
- 斷線後機器人繼續開 2 秒 = **0.36 公尺**
- 在小房間裡足以撞牆
- 而且使用者會覺得「怎麼放開了還在動」

**0.6 秒的實際後果**：
- 最壞滑行 0.6 × 0.18 = **11 公分**（小於機器人自己的直徑 20 cm）
- 容許 3 個封包遺失，一般 Wi-Fi 環境幾乎不會誤觸發

★ **一般的設計原則**：TTL 應該是**心跳間隔的 3~5 倍**。
太接近 1 倍會誤觸發，太大則失去保護意義。

（如果要更安全，可以把 `V_MAX` 再壓低，滑行距離會等比例縮短。）
</details>

**Q4. 前端送的是 −1~1 的比例值而不是實際速度 m/s。這個設計有什麼好處？**

<details>
<summary>參考答案</summary>

**① 速度上限只在一個地方定義**

```python
V_MAX = 0.18   # scripts/map_server.py:56
```

要調速度只改這一行。如果前端送實際速度，
上限的知識就會散在 HTML 的 `data-v`、JS 的計算、後端的夾取三個地方。

**② 前端被竄改也無害**

```python
v = max(-1.0, min(1.0, v)) * V_MAX
```

有人用開發者工具送 `{v: 999}` → 夾成 `1.0` → `0.18 m/s`。
★ **最壞情況就是全速，不會超過上限。**

如果前端送實際速度，後端要夾的就是 `max(-0.22, min(0.22, v))` ——
語意變成「檢查一個物理量」，而不是「檢查一個比例」，比較容易寫錯。

**③ 換機器人型號不用改前端**

Waffle 的最高速度是 0.26 m/s。改 `V_MAX` 就好，前端一行都不動。

**④ 語意更清楚**

`data-v="0.7"` 的意思是「**七成的力道往前**」，
比 `data-v="0.126"` 直觀得多，而且不用去想那個數字怎麼來的。

★ **通用原則：跨越信任邊界時傳「意圖」不傳「物理量」，
把「意圖 → 物理量」的換算放在有權威的那一側。**
</details>

**Q5. 手動遙控模式完全沒有避障。這是 bug 還是設計？如果要加避障，
會不會有什麼副作用？**

<details>
<summary>參考答案</summary>

**這是設計，不是 bug。**

**理由**：手動模式最重要的用途之一是**把卡住的機器人救出來**。

想像機器人被 `move_base` 開進一個角落，
局部 costmap 上四面都是障礙 —— 這時如果手動模式也有避障，
機器人**任何方向都不肯動**，你只能走過去用手搬。

同樣的情況：
- 安全邊距把窄通道封死（第 08 章 8.1），要手動開過去
- 地圖有錯誤的障礙（雷射反射造成的鬼影），要手動穿過去
- 測試時要把機器人擺到一個貼牆的起點

**如果要加避障，副作用**：

1. **失去救援能力**（上面說的）
2. **要重複實作一次 costmap 邏輯**，或者把指令走 `move_base` 的
   `/cmd_vel` 混合器 —— 那會讓「模式互斥」這個乾淨的設計整個複雜化
3. **延遲增加**：要查 costmap、要判斷方向，遙控的即時感會變差

**折衷方案**（如果真的需要）：
- 只擋「前方 20 cm 內有障礙時的前進指令」，**後退和轉向永遠允許**
  → 保留救援能力，又能防止直直撞牆
- 或者做成一個可切換的選項（預設關閉）

★ **重點是：這件事要寫進文件**。
使用者以為「機器人很聰明不會撞」而放心亂開，才是真正的問題。
</details>
