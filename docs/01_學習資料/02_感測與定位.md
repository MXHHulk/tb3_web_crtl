# 第 02 章　感測與定位

> **本章目標**：搞懂機器人「怎麼知道周圍有什麼」和「怎麼知道自己在哪」。
> 這兩件事是後面所有演算法的輸入 —— 沒有地圖就沒有覆蓋規劃。
>
> 本章要講四個東西：**光達**、**里程計**、**TF 座標樹**、**佔據網格 + SLAM**。

---

## 2.1 先講問題：機器人的「眼睛」和「內耳」

要走遍一個房間，機器人至少得回答兩個問題：

```
Q1  周圍有什麼？  → 需要感測器（本專案：360° 雷射光達）
Q2  我在哪裡？    → 需要定位（本專案：輪子編碼器 + SLAM 修正）
```

這兩件事互相糾纏：**要建地圖，得先知道自己在哪**（不然拼不起來）；
**要知道自己在哪，得先有地圖**（不然沒有參照物）。這個雞生蛋問題正是 SLAM 要解的。

## 2.2 光達（LiDAR）與 `sensor_msgs/LaserScan`

TurtleBot3 Burger 裝的是 **LDS-01** 雷射測距儀，工作方式是：

```
        機器人上方俯視
             90°
              ↑
              │
   180° ←───[ ● ]───→ 0°     感測頭以 300 rpm（5 Hz）旋轉，
              │              每轉一圈量 360 次，得到 360 個距離值
              ↓
             270°
```

### 訊息長什麼樣

```python
msg.angle_min        # 第一束光的角度（弧度），通常是 0.0
msg.angle_max        # 最後一束的角度，通常是 2π
msg.angle_increment  # 每束之間差多少角度 = 2π/360 ≈ 0.01745 rad = 1°
msg.range_min        # 驅動宣告的最小有效距離，LDS-01 是 0.12 m
msg.range_max        # 驅動宣告的最大有效距離，LDS-01 是 3.5 m
msg.ranges           # ★ 360 個距離值（公尺），這是主體
msg.header.frame_id  # 這些數字是以哪個座標系為準，通常是 'base_scan'
```

**`ranges` 是相對於感測器的極座標。** 第 `i` 個值代表「往
`angle_min + i × angle_increment` 這個方向看過去，最近的障礙物在幾公尺外」。

### ⚠ 陷阱一：無效值是 `inf`，不是 0

超出量測範圍（太近、太遠、或打到黑色吸光材質）時，回傳的是 `inf`（無限大）而不是某個數字。
如果你直接拿去算三角函數，會得到 `nan` 汙染整批資料。

本專案的過濾寫在 `scripts/map_server.py:444`：

```python
for r in msg.ranges:
    if rmin <= r <= rmax:          # 同時排除 inf / nan
        ...
```

> 💡 為什麼 `rmin <= r <= rmax` 就能排掉 `nan`？
> 因為 **`nan` 和任何數字比較都回傳 `False`**（IEEE 754 的規定），`inf` 則會被 `<= rmax` 擋掉。
> 一個條件同時擋掉兩種壞值，不需要另外寫 `math.isnan()`。

### ⚠ 陷阱二：宣告值 ≠ 實際值

驅動宣告 `range_max = 3.5`，但實測有效距離大約只有 **3 公尺**。
本專案專門寫了一隻工具驗證這件事：

```python
# test/test_lidar_range.py 的核心思路
# ① 印出驅動宣告的 range_min / range_max（規格書寫的）
# ② 統計實際 ranges[] 裡「量得到的最遠有效值」（真實能力）
# 兩者的差距就是證據
```

搭配的實驗方法（寫在該檔的 docstring 裡）：
**把機器人正對一面牆，逐步把牆往後移，觀察正前方距離何時從有限值跳成 `inf`
—— 跳掉的那一刻就是真正的有效上限。**

> 這個 3 m vs 3.5 m 的差距會影響什麼？影響**建圖速度**：
> 房間比 3 m 寬時，機器人得走到中間才看得到對面的牆，
> 所以一開始地圖會有很大一塊是「未知」。這對覆蓋規劃是致命的（見第 19 章）。

### 本專案怎麼用 `/scan`

只用在**網頁上顯示即時掃描圖層**，不參與規劃（規劃用的是 SLAM 整理過的 `/map`）。

```python
# scripts/map_server.py:210-214
def scan_callback(msg):
    """收到 /scan 時僅保存最新一筆，轉換到地圖座標延後到 /scan 路由處理。"""
    global scan_msg
    with scan_lock:
        scan_msg = msg
```

★ 注意這個回呼**什麼事都沒做**，只把訊息存起來。
極座標轉世界座標那 360 次三角函數留到有人開網頁時才算。
這是本專案貫穿全域的設計原則 —— **「回呼只存不算」**，理由在第 17 章。

## 2.3 里程計（Odometry）與 `nav_msgs/Odometry`

### 原理：數輪子轉了幾圈

兩顆馬達各裝一個編碼器，數出各自轉了多少。已知輪徑和輪距，就能推算：

```
   左輪走了 dL，右輪走了 dR
   → 中心前進  d  = (dL + dR) / 2
   → 中心轉了  dθ = (dR - dL) / 輪距
   → 累加起來就是「從開機到現在，我走到了 (x, y)，面朝 θ」
```

這叫 **航位推算（dead reckoning）**。

### ⚠ 致命缺陷：誤差會累積且永不歸零

```
  真實軌跡  ────────────────────────
                                     ↘  誤差
  里程計推算 ──────────────────╲       ↘
                                ╲_______↘
```

輪子打滑、地毯壓縮、輪徑製造公差、地面不平 ——
每一步都有一點誤差，而且是**積分**上去的，走幾分鐘就可能偏差幾十公分。

**所以里程計絕對不能單獨用來定位。** 它的角色是「短時間內很準的相對位移」，
長時間的絕對位置要靠 SLAM 修正（見 2.5）。

### 訊息長什麼樣

```python
msg.pose.pose.position.x       # 位置 x（公尺）
msg.pose.pose.position.y       # 位置 y
msg.pose.pose.orientation      # 朝向，四元數 (x, y, z, w)
msg.twist.twist.linear.x       # 當前線速度
msg.twist.twist.angular.z      # 當前角速度
msg.header.frame_id            # 通常是 'odom'
```

### 為什麼朝向用四元數而不是角度？

平面機器人其實只需要一個角度 θ，但 ROS 統一用 **四元數（quaternion）** 表示 3D 旋轉，
因為它沒有萬向鎖問題、內插平滑。代價是不直觀。

只繞 z 軸轉（平面機器人的情況）時，換算公式很簡單：

```python
# 角度 → 四元數（scripts/map_server.py:282-284）
def _yaw_to_quat(yaw):
    return math.sin(yaw / 2), math.cos(yaw / 2)     # 只有 z 和 w 非零
```

```python
# 四元數 → 角度（scripts/map_server.py:437）
yaw = math.atan2(2*(q.w*q.z + q.x*q.y), 1 - 2*(q.y*q.y + q.z*q.z))
```

本專案兩個方向都用到：送目標點給 `move_base` 時要把「面向下一個路點」的角度轉成四元數，
把雷射點轉到地圖座標時要把 TF 的四元數轉回角度。

### 本專案怎麼用 `/odom`

```python
# scripts/map_server.py:188-207
def odom_callback(msg):
    rx = msg.pose.pose.position.x
    ry = msg.pose.pose.position.y

    # 行走軌跡只在覆蓋執行中記錄；手動移動不留痕
    with cov_lock:
        recording = cov_status['state'] == 'running'

    with robot_lock:
        robot_pos.update(x=rx, y=ry)
        if not recording:
            return
        if not robot_path:
            robot_path.append([rx, ry])
        else:
            dx, dy = rx - robot_path[-1][0], ry - robot_path[-1][1]
            if dx*dx + dy*dy >= 0.01:   # ★ 每 0.1 m 才記一點
                robot_path.append([rx, ry])
                if len(robot_path) > 10000:
                    robot_path.pop(0)
```

三個值得注意的細節：

1. **`dx*dx + dy*dy >= 0.01` 是距離門檻**：`0.01 = 0.1²`，也就是「移動超過 10 公分才記一點」。
   不開根號是為了省 `sqrt`（每秒要判斷 30 次）。
   沒有這道門檻的話，機器人靜止時也會塞進成千上萬個重複點。
2. **`len(robot_path) > 10000` 是上限保護**：跑一個小時也不會把記憶體吃爆。
3. **軌跡只在 `running` 時記錄**：手動遙控不留痕跡，而且執行結束後保留該次結果供檢視
   （所以停止後畫面上的軌跡不會消失）。

## 2.4 ★ TF：座標系轉換樹

這是 ROS 最重要也最容易搞混的機制。

### 為什麼需要它

雷射量到「正前方 2 公尺有東西」。這個「正前方」是**相對於雷射感測器**的。
但你想在地圖上畫出這個障礙物，需要知道它在**地圖座標**的哪裡。這中間隔了好幾層：

```
   雷射點在感測器上的位置
        ↓ 感測器裝在機器人上，往上 20 公分、往前 3 公分
   雷射點在機器人本體的位置
        ↓ 機器人現在在 odom 座標的 (1.2, 3.4)，面朝 45°
   雷射點在 odom 座標的位置
        ↓ odom 累積了 15 公分的漂移，SLAM 算出修正量
   雷射點在 map 座標的位置        ← 這才是我們要的
```

**TF（Transform）就是幫你自動做完這串轉換的系統。**

### 本專案的 TF 樹

```
        map                 ← 全域固定座標系（地圖原點）
         │
         │  ← 由 gmapping 發布，內容是「odom 漂移了多少」，會隨時間跳動修正
         ↓
        odom                ← 里程計起點座標系（開機時的位置）
         │
         │  ← 由 turtlebot3_bringup 發布，內容是里程計推算的位移，連續平滑
         ↓
   base_footprint           ← 機器人在地面的投影點
         │
         ↓
      base_link             ← 機器人本體中心
         │
         ↓
      base_scan             ← 雷射感測器的位置（固定偏移）
```

### ★ 為什麼要 map 和 odom 兩層？不能只有一個？

這是 ROS 導航最漂亮的設計之一，口試很可能被問：

| | `odom → base_footprint` | `map → odom` |
|---|---|---|
| 誰發布 | 硬體驅動（里程計） | SLAM（gmapping） |
| 更新頻率 | 高（30 Hz） | 低（幾 Hz） |
| 性質 | **連續、平滑**，但會漂移 | **會跳動**，但長期正確 |
| 用途 | 局部避障需要平滑的位置 | 全域規劃需要正確的位置 |

如果只有一層，SLAM 每次修正定位都會讓機器人的位置「瞬間跳一下」，
局部路徑規劃器（DWA）看到位置突然跳 15 公分，會以為機器人瘋狂加速，控制直接爆掉。

分成兩層之後：
- **`odom → base` 永遠平滑**，DWA 用這個算速度，很穩定
- **`map → odom` 承受所有跳動**，全域規劃用 `map → base`（兩段相乘），長期位置正確

> 💡 一句話記法：**odom 短期準、map 長期準，兩者相乘才是真正的位置。**

### 程式怎麼用 TF

```python
# scripts/map_server.py:603-604（初始化，只做一次）
tf_buffer = tf2_ros.Buffer()             # 建一個緩衝區
tf2_ros.TransformListener(tf_buffer)     # 開一個背景執行緒，持續訂閱 /tf 填進緩衝區
```

`TransformListener` 建立後就不用管了，它會在背景一直收 `/tf` 和 `/tf_static`，
把整棵樹的關係存進 `tf_buffer`。要用的時候查詢：

```python
# scripts/map_server.py:429-434
frame = msg.header.frame_id or 'base_scan'
try:
    tf = tf_buffer.lookup_transform('map', frame, rospy.Time(0), rospy.Duration(0.05))
    #                                └─①   └─②    └─③            └─④
except (tf2_ros.LookupException, tf2_ros.ConnectivityException,
        tf2_ros.ExtrapolationException):
    return jsonify({'points': []})       # ⑤ 查不到就回空清單，不讓網頁掛掉
```

| | 意思 |
|---|---|
| ① `'map'` | 目標座標系（我要把東西轉成 map 座標） |
| ② `frame` | 來源座標系（東西現在是 `base_scan` 座標） |
| ③ `rospy.Time(0)` | **時間點。`0` 是特殊值，代表「給我最新的」** |
| ④ `rospy.Duration(0.05)` | 最多等 50 毫秒。TF 資料可能還沒到，等一下下 |
| ⑤ 三種例外 | 查不到（樹沒建好）、不連通（中間斷一節）、時間外插失敗 |

★ **這三個例外一定要接**。TF 在系統剛啟動、SLAM 重啟後的幾秒鐘一定查不到，
沒接的話 Flask 路由會噴 500 錯誤，網頁整頁壞掉。
本專案的做法是「查不到就回空清單」——網頁只是暫時沒有雷射圖層，其他照常顯示。

### 轉換的實際計算

拿到 `tf` 之後，本專案沒有用 `tf2_geometry_msgs` 的通用轉換函式，而是自己算：

```python
# scripts/map_server.py:436-448
t, q = tf.transform.translation, tf.transform.rotation
yaw  = math.atan2(2*(q.w*q.z + q.x*q.y), 1 - 2*(q.y*q.y + q.z*q.z))   # 四元數 → 角度
cos_y, sin_y = math.cos(yaw), math.sin(yaw)                           # 三角函數只算一次

for r in msg.ranges:
    if rmin <= r <= rmax:
        lx, ly = r * math.cos(ang), r * math.sin(ang)   # 極座標 → 感測器直角座標
        wx = t.x + cos_y * lx - sin_y * ly              # 2D 旋轉 + 平移
        wy = t.y + sin_y * lx + cos_y * ly
        pts.append(list(world_to_px(wx, wy, meta)))
    ang += inc
```

> 💡 **為什麼不用現成的轉換函式？** 因為要轉 360 個點，通用函式每個點都要建一個
> `PointStamped` 訊息物件、查一次 TF，開銷是這個寫法的幾十倍。
> 這裡把四元數轉角度只做**一次**，之後 360 個點共用同一組 `cos_y`/`sin_y`，只有加減乘。

## 2.5 佔據網格 `nav_msgs/OccupancyGrid`

這是本專案演算法的**唯一輸入**，一定要徹底搞懂。

### 概念：把世界切成一格一格的棋盤

```
   每格 5 公分 × 5 公分（resolution = 0.05）

   ┌──┬──┬──┬──┬──┬──┬──┐
   │██│██│██│██│██│██│██│   ██ = 100  障礙（有東西）
   ├──┼──┼──┼──┼──┼──┼──┤
   │██│  │  │  │  │  │██│      = 0    自由（確定沒東西，可以走）
   ├──┼──┼──┼──┼──┼──┼──┤
   │██│  │  │▒▒│▒▒│  │██│   ▒▒ = -1   未知（還沒看過，不知道）
   ├──┼──┼──┼──┼──┼──┼──┤
   │██│██│██│██│██│██│██│
   └──┴──┴──┴──┴──┴──┴──┘
```

### 訊息欄位

```python
msg.info.resolution        # 每格幾公尺，gmapping 預設 0.05
msg.info.width             # 幾欄（column）
msg.info.height            # 幾列（row）
msg.info.origin.position.x # ★ 第 [0][0] 格的左下角在世界座標的哪裡
msg.info.origin.position.y
msg.data                   # ★ 一維陣列，長度 = width × height
msg.header.frame_id        # 通常是 'map'
```

### ★ `data` 的三種值

| 值 | 意思 | 本專案怎麼看待 |
|---|---|---|
| `0` | **自由**：雷射穿過這裡，確定沒東西 | 可以走 → 覆蓋規劃的候選 |
| `100` | **障礙**：雷射打到這裡停住 | 不能走，還要往外膨脹安全邊距 |
| `-1` | **未知**：從來沒被看過 | ⚠ **當成不能走**，不會被覆蓋 |

⚠ **`-1` 被排除是一個重要限制。** 房間如果沒探索完，
未探索的部分就不會出現在覆蓋路徑裡，機器人會「走完了」但實際還有一大塊沒去。
這是第 19 章「假完成」現象的原因之一。

（ROS 規格上 `data` 是 0~100 的機率值，但 gmapping 實際只吐 0 / 100 / -1 三種。）

### ★ 一維陣列怎麼變二維

```python
# scripts/map_server.py:142
data = np.array(msg.data, dtype=np.int8).reshape((h, w)).astype(np.int16)
```

`msg.data` 是一維的，用 **row-major（列優先）** 排列：

```
   一維索引:  0   1   2   3   4   5   6   7   8  ...
              ↓
   二維 (w=3):
              [0][0]=0  [0][1]=1  [0][2]=2      ← 第 0 列
              [1][0]=3  [1][1]=4  [1][2]=5      ← 第 1 列
              [2][0]=6  [2][1]=7  [2][2]=8      ← 第 2 列

   換算： index = row × width + col
```

`reshape((h, w))` 就是幫你做這件事。之後就能用 `data[row, col]` 存取。

> ⚠ **為什麼要 `.astype(np.int16)`？**
> 原本是 `int8`（範圍 −128~127）。後面 `map_server.py:150` 要算
> `255 - data[known] * 255 // 100`，`data * 255` 會直接溢位。
> 轉成 `int16` 就有足夠空間。這是很容易漏掉的坑。

### ★ 格子座標 ↔ 世界座標

```
   世界座標（公尺，原點在地圖 origin）
        ↕  wx = ox + col × res
           wy = oy + row × res
   格子座標（整數索引 row, col）
```

反過來：

```python
col = round((wx - ox) / res)
row = round((wy - oy) / res)
```

這組換算在專案裡到處出現，例如 `coverage_planner.py:97-98`（取樣點查表）
和 `map_server.py:352-356`（`world_to_px`，多一層裁切偏移）。第 07 章會完整整理三層座標系。

### ⚠ 陷阱：row 對應 y，col 對應 x

`data[row, col]` 的第一維是 **row（對應 y 方向）**，第二維是 **col（對應 x 方向）**。
寫成 `data[y, x]` 而不是直覺的 `data[x, y]`。這個順序寫反是最常見的 bug，
症狀是地圖看起來被轉了 90 度。

## 2.6 SLAM 與 gmapping

### 要解的問題

前面說過的雞生蛋：

```
   要建地圖 → 需要知道自己在哪 → 需要地圖當參照 → 要建地圖 → ...
```

**SLAM（Simultaneous Localization And Mapping）= 同時解決兩件事。**

### gmapping 的做法（粒子濾波，概念版）

```
① 撒出 N 個「粒子」，每個粒子代表一個「機器人可能在的位置 + 它眼中的地圖」

② 機器人移動時，每個粒子依照里程計 + 一點隨機雜訊往前推
      粒子 A ──→
      粒子 B ───→        （彼此稍微不同，模擬里程計誤差）
      粒子 C ─→

③ 收到新的雷射資料時，問每個粒子：
      「照你的位置和你的地圖，這圈雷射該長什麼樣？」
      跟實際量到的比對，越像的粒子權重越高

④ 重新採樣：權重高的粒子多複製幾份，權重低的淘汰

⑤ 權重最高的粒子的地圖 → 發布成 /map
   它的位置和里程計的差 → 發布成 map→odom 的 TF
```

**關鍵理解**：gmapping 並不是「修正里程計」，而是**額外發布一個修正量**。
里程計自己還是繼續漂移（`odom → base` 不變），
SLAM 把「漂了多少」包在 `map → odom` 裡。這就是 2.4 講的兩層設計。

### gmapping 產出什麼

```
   gmapping 節點
      ├── 發布 /map          （OccupancyGrid，幾 Hz 更新一次）
      └── 發布 map→odom TF   （定位修正）
```

**兩者都是本專案的命脈**：
- `/map` 給覆蓋規劃當輸入，也給網頁顯示
- `map→odom` 給 `move_base` 定位用（沒有它 `move_base` 根本不知道機器人在哪）

這也是為什麼 `launch/start.launch:14` 的註解特別強調
「gmapping 同時發布 `/map` 與 `map→odom` TF，供 `move_base` 定位用」——
少了 SLAM，導航整組失效，不是只有地圖沒了。

### 本專案的特殊安排：SLAM 由 `map_server` 管

一般專案會在 launch 檔裡 `<include>` SLAM。本專案刻意**不這麼做**：

```xml
<!-- launch/start.launch:16-18 -->
注意：SLAM 不在這裡啟動，改由 map_server 以子行程管理（見下方第 4 節）。
這樣網頁上的「重啟 SLAM」才能收掉舊的 gmapping、重新開一個乾淨的地圖，
不必整包 roslaunch 重跑。
```

理由是**需求驅動**的：想在網頁上按一個鈕就重新建圖。
如果 SLAM 由 launch 啟動，就只能整包 `roslaunch` 重來（連機器人驅動、`move_base` 都要重開，要等三十秒）。
完整實作在第 06 章。

## 2.7 三個感測資料在本專案的定位

```
   /scan（LaserScan）
      ├──→ gmapping ────→ /map ──★──→ 覆蓋規劃（第 08~12 章）
      │                      └───────→ 網頁地圖圖層
      ├──→ move_base ───────────────→ 局部避障（第 03 章）
      └──→ map_server ──────────────→ 網頁即時雷射圖層（純顯示）

   /odom（Odometry）
      ├──→ gmapping ────→ 粒子推進
      ├──→ move_base ───→ 速度回授
      └──→ map_server ──→ 網頁上的機器人位置 + 行走軌跡

   TF 樹
      ├──→ move_base ───→ 定位
      └──→ map_server ──→ 把雷射點轉到地圖座標
```

★ **注意最上面那條**：覆蓋規劃用的是 **`/map`**，不是 `/scan`。
演算法拿到的是 SLAM 整理好的靜態網格，不需要處理原始感測雜訊 ——
這是為什麼 `coverage_planner.py` 可以做到零 ROS 依賴、可以離線測試。

## 2.8 本章重點回顧

1. **光達給的是極座標距離陣列**，無效值是 `inf`，用 `range_min <= r <= range_max`
   一次擋掉 `inf` 和 `nan`。宣告 3.5 m，實測約 3 m。
2. **里程計短期準、長期漂移**，絕對不能單獨用來定位。
3. ★ **TF 樹分成 `map → odom → base` 兩層**：
   `odom→base` 連續平滑給局部規劃用，`map→odom` 承受所有跳動給全域規劃用。
4. **`OccupancyGrid` 的 `data` 是一維 row-major 陣列**，值只有 `0`（自由）、
   `100`（障礙）、`-1`（未知）三種；⚠ 本專案把 `-1` 當成不能走。
5. `data[row, col]` 的順序是 **`[y, x]`**，寫反會讓地圖轉 90 度。
6. **gmapping 不修正里程計，而是額外發布一個修正量** 包在 `map→odom` 裡。
7. ★ **覆蓋演算法的輸入是 `/map` 不是 `/scan`**，所以演算法模組能做到零 ROS 依賴。

## 2.9 自我檢核題

**Q1. `msg.ranges[90]` 代表什麼？如果它的值是 `inf`，代表什麼？**

<details>
<summary>參考答案</summary>

代表「往 `angle_min + 90 × angle_increment` 這個方向看過去，最近的障礙物有多遠」。
LDS-01 的 `angle_increment` 是 1°、`angle_min` 是 0，所以是**機器人左方 90 度**的距離。

值是 `inf` 代表**這個方向在有效範圍內沒量到東西**，可能是：
- 太遠（超過約 3 m）
- 太近（小於 0.12 m）
- 打到黑色/鏡面/透明材質，光沒反射回來

⚠ 它**不代表**「那個方向是空的」。可能只是看不到而已 ——
這正是 `OccupancyGrid` 需要 `-1`（未知）這個值的原因：
「沒量到」和「確定沒東西」是兩回事。
</details>

**Q2. 為什麼 TF 樹要分 `map → odom` 和 `odom → base` 兩層？只用一個 `map → base` 不行嗎？**

<details>
<summary>參考答案</summary>

因為兩種使用者對「位置」的要求互相衝突：

- **局部路徑規劃（DWA）** 需要**連續平滑**的位置。位置突然跳動，它會誤判成機器人瘋狂加速，控制輸出會爆掉。
- **全域路徑規劃** 需要**長期正確**的位置，容許偶爾跳一下修正。

只有一層的話，SLAM 每次修正就會讓位置瞬間跳幾十公分，第一個需求直接崩潰。

兩層設計把矛盾分開：
- `odom → base` 由里程計發布，**永遠連續平滑**（但會慢慢漂）
- `map → odom` 由 SLAM 發布，**承受所有跳動**（但讓總和長期正確）

要真正的位置就把兩段相乘（`map → base`）；要平滑的位置就只用 `odom → base`。
</details>

**Q3. `data = np.array(msg.data, dtype=np.int8).reshape((h, w)).astype(np.int16)`
最後為什麼要轉成 `int16`？不轉會怎樣？**

<details>
<summary>參考答案</summary>

因為後面 `map_server.py:150` 要計算：

```python
gray[known] = np.clip(255 - data[known] * 255 // 100, 0, 255)
```

`data` 的值最大是 100，`100 * 255 = 25500`。
`int8` 的範圍只有 **−128 ~ 127**，這個乘法會直接溢位，算出完全錯誤的灰階值
（numpy 對整數溢位是靜默 wrap-around，**不會報錯**，這才是可怕的地方）。

轉成 `int16`（範圍 −32768 ~ 32767）就足夠容納。

這類「先用小型別省記憶體、算之前要記得放大」是 numpy 常見陷阱。
</details>

**Q4. `tf_buffer.lookup_transform('map', frame, rospy.Time(0), rospy.Duration(0.05))`
的三個例外為什麼一定要接？如果不接會怎樣？**

<details>
<summary>參考答案</summary>

三個例外分別是：
- `LookupException` — 查詢的座標系根本不存在（樹還沒建好）
- `ConnectivityException` — 兩個座標系存在但中間斷了一節，接不起來
- `ExtrapolationException` — 座標系存在，但在要求的時間點上沒有資料

**在下列時刻一定會發生**：系統剛啟動的前幾秒、按下「重啟 SLAM」之後的幾秒
（gmapping 死了，`map → odom` 消失）、SLAM 當掉時。

不接的話，Flask 路由會拋出未處理的例外 → 回傳 HTTP 500 → 前端的
`fetch('/scan')` 失敗。本專案前端用 `Promise.allSettled` 有做保護，
但畫面上的雷射圖層會整個消失且沒有解釋。

本專案的做法是 **`return jsonify({'points': []})`** —— 回一個空清單。
語意是「這一刻沒有雷射點可以畫」，網頁其他部分完全不受影響，
等 TF 恢復後下一次輪詢就自動好了。這叫**優雅降級（graceful degradation）**。
</details>

**Q5. 覆蓋演算法的輸入是 `/map` 而不是 `/scan`。這個選擇帶來什麼好處和什麼限制？**

<details>
<summary>參考答案</summary>

**好處：**
1. `/map` 是 SLAM 整理過的**靜態、去雜訊、全域一致**的網格，不需要處理原始感測雜訊、
   不需要自己做座標轉換、不需要自己拼接多幀資料。
2. 演算法的輸入退化成「一個 numpy bool 陣列 + 解析度 + 原點」這麼單純的東西，
   所以 `coverage_planner.py` 能做到**零 ROS 依賴**，可以離線用合成地圖測試
   （第 21~23 章的所有數據就是這樣來的）。

**限制：**
1. **必須先建好圖才能規劃**。開機當下 `/map` 幾乎全是 `-1`，規劃出來會是空的或很小一塊。
2. **未知格 `-1` 一律不覆蓋**。房間沒探索完就按開始，機器人會「走完」但漏掉一大塊
   —— 第 19 章的「假完成」現象。
3. **規劃是一次性的靜態快照**。按下開始的那一刻算好整條路徑，
   之後 SLAM 就算發現新空間也不會重新規劃。
</details>
