# 第 12 章　路徑生成與排序

> **本章目標**：把 cell 變成一串真正的路點。兩件事：
> **cell 內部怎麼蛇行**（`_cell_waypoints`）、**cell 之間走訪什麼順序**（貪婪最近鄰）。
> 最後把 `plan()` 從頭到尾串一遍。

---

## 12.1 ① 問題：從 cell 到路點清單

第 11 章結束時我們有：

```python
cells = [[0, 1, 2, 3],      # cell A：run 0~3
         [4, 6, 8],         # cell B：柱子左側
         [5, 7, 9],         # cell C：柱子右側
         [10, 11, 12, 13]]  # cell D
```

要變成 `move_base` 吃得下的東西：

```python
waypoints = [(0.15, 0.20), (3.80, 0.20), (3.80, 0.38), (0.15, 0.38), ...]
```

兩個子問題：

```
   ① cell 內：這幾條 run 要用什麼順序、什麼方向走？
   ② cell 間：四個 cell 要用什麼順序走？從哪一端進入？
```

## 12.2 ② 直覺做法與撞牆

### 子問題 ①：每條 run 都從左邊走到右邊

```python
# ❌ 最直覺的寫法
for i in chain:
    wps += [runs[i]['p0'], runs[i]['p1']]
```

**撞牆**：

```
   ●──────────────→●      走完第 1 條，人在右端
   ●──────────────→●      但第 2 條要從左端開始 → 空跑一整條的長度
   ●──────────────→●
   ↑
   每條都要跑回左邊
```

一條 4 公尺的線、10 條帶，光是回頭就多走 **36 公尺**（路徑總長直接翻倍）。

**修法**：交替方向（這就是「牛耕」的本意）。

### 子問題 ②：cell 照編號順序走

```python
# ❌ 最直覺的寫法
for cell in cells:
    waypoints += cell_waypoints(cell)
```

**撞牆**：cell 的編號是 `_build_cells` 的迴圈順序決定的，**和空間位置無關**。
可能出現「走完最左邊的 cell → 跳到最右邊 → 又跳回中間」。

## 12.3 ④ 現在的做法（一）：cell 內蛇行

```python
# scripts/coverage_planner.py:170-186
def _cell_waypoints(chain, runs, reverse, flip):
    """
    產生單一 cell 的蛇行路點。

    reverse : 帶的走訪方向反過來（從最後一條帶往回掃）
    flip    : 第一條掃描線從哪一側開始
    交替旗標每產生一條線就翻轉，確保是蛇行而不是每條都從同一側重新開始。
    """
    order = chain[::-1] if reverse else chain
    wps, l2r = [], not flip
    for i in order:
        r = runs[i]
        p0, p1 = (r['p0'], r['p1']) if l2r else (r['p1'], r['p0'])
        wps += [(float(p0[0]), float(p0[1])), (float(p1[0]), float(p1[1]))]
        l2r = not l2r          # ★ 每畫完一條線就翻轉
    return wps
```

### 核心只有一行：`l2r = not l2r`

```
   l2r=True   ●──────────────→●       p0 → p1
   l2r=False  ●←──────────────●       p1 → p0
   l2r=True   ●──────────────→●       p0 → p1
   l2r=False  ●←──────────────●
```

每條 run 貢獻**兩個路點**（兩端），方向交替，形成 ∽ 形。

**路點數量**：`len(waypoints) = 2 × run 數`。

★ **這個「偶數 index 是掃描線起點、奇數 index 是掃描線終點」的結構
在後面很多地方被利用**：

```python
# test/coverage_bench.py：只算掃描線的長度
sweep_len = sum(math.dist(wps[i], wps[i+1]) for i in range(0, len(wps)-1, 2))
#                                                          ↑ 從 0 開始，步長 2
# 轉場（換行接駁）的長度
link_len  = sum(math.dist(wps[i], wps[i+1]) for i in range(1, len(wps)-1, 2))
#                                                          ↑ 從 1 開始
```

```javascript
// web/index.html:320-335：前端用同樣的規則分別畫兩種線
for (let i = 1; i + 1 < wps.length; i += 2) { /* 細虛線＝換行接駁 */ }
for (let i = 0; i + 1 < wps.length; i += 2) { /* 粗實線＝掃描線 */ }
```

### `reverse` 和 `flip`：進入 cell 的四種姿態

| `reverse` | `flip` | 意思 |
|---|---|---|
| `False` | `False` | 從第一條帶開始，第一條線 `p0→p1` |
| `False` | `True` | 從第一條帶開始，第一條線 `p1→p0` |
| `True` | `False` | 從**最後一條帶**開始，第一條線 `p0→p1` |
| `True` | `True` | 從最後一條帶開始，第一條線 `p1→p0` |

```
   reverse=False, flip=False        reverse=True, flip=True
   ┌─────────────────┐              ┌─────────────────┐
   │ ●────────────→● │ band 3       │ ●←────────────● │ band 3  ← 從這裡開始
   │ ●←────────────● │ band 2       │ ●────────────→● │ band 2
   │ ●────────────→● │ band 1       │ ●←────────────● │ band 1
   │ ●←────────────● │ band 0       │ ●────────────→● │ band 0
   └─────────────────┘              └─────────────────┘
     ↑ 從這裡開始（左下）             起點在右上
```

★ **四種姿態的四個進入點分別在 cell 的四個角落。**
所以不管機器人現在在哪，總有一個姿態的起點離它比較近。

## 12.4 ④ 現在的做法（二）：cell 走訪順序

```python
# scripts/coverage_planner.py:236-253
cur = (np.asarray(start, dtype=float) if start is not None
       else pts[np.lexsort((proj_a, proj_b))[0]])

remaining, ordered, waypoints = set(range(len(cells))), [], []
while remaining:
    best, best_d = None, None
    for ci in remaining:                          # 每個還沒走的 cell
        for reverse in (False, True):             # 四種進入姿態
            for flip in (False, True):
                wps = _cell_waypoints(cells[ci], runs, reverse, flip)
                d = float(np.hypot(*(np.asarray(wps[0]) - cur)))
                if best_d is None or d < best_d:
                    best, best_d = (ci, wps), d
    ci, wps = best
    remaining.discard(ci)
    ordered.append(wps)
    waypoints += wps
    cur = np.asarray(wps[-1], dtype=float)        # ★ 更新為這個 cell 的終點
```

### 演算法：貪婪最近鄰（Greedy Nearest Neighbour）

```
   ① 從「目前位置」出發
   ② 對每個還沒走的 cell × 四種姿態，算「目前位置 → 該姿態的第一個路點」的距離
   ③ 選最近的那一組
   ④ 把該 cell 的路點接上，「目前位置」更新為該 cell 的最後一個路點
   ⑤ 回到 ②，直到所有 cell 都走完
```

### 起點怎麼決定

```python
cur = (np.asarray(start, dtype=float) if start is not None
       else pts[np.lexsort((proj_a, proj_b))[0]])
```

- **有給 `start`**：用機器人目前的位置。
  ```python
  # scripts/map_server.py:471-475
  with robot_lock:
      start = (robot_pos['x'], robot_pos['y']) if robot_pos['x'] is not None else None
  r = plan_coverage(free, ..., start=start)
  ```
  ★ 這讓規劃結果**從機器人腳下開始**，不用先跑到房間另一頭。

- **沒給**：用 `np.lexsort((proj_a, proj_b))[0]`。

**`np.lexsort` 是什麼？** 多鍵排序，**最後一個鍵是主鍵**：

```python
np.lexsort((proj_a, proj_b))     # 主鍵 proj_b，次鍵 proj_a
```

意思是「先找 `proj_b` 最小的（短軸最下面），同樣小的裡面再找 `proj_a` 最小的（長軸最左邊）」——
也就是**左下角**。這是一個確定性的起點，保證結果可重現。

### ⚠ 這個貪婪法的三個弱點

**① 只看「到起點的距離」，不看 cell 內部的路徑長度**

```python
d = float(np.hypot(*(np.asarray(wps[0]) - cur)))
#                        └── 只有第一個路點
```

一個「進入點很近但很大」的 cell 會贏過「進入點稍遠但很小」的 cell，
即使走完後者再走前者總長更短。

**② 只看「進入」不看「離開」**

選 cell 時沒有考慮「走完之後我會停在哪裡、離下一個 cell 遠不遠」。

**③ 貪婪本來就不是最佳解**

這是 TSP（旅行推銷員問題）的變形，貪婪最近鄰的典型誤差是最佳解的 **25%** 左右。

> 💡 **為什麼還是用它？**
> - cell 數量通常很少（1~5 個），貪婪和最佳解的差距很小
> - 實作只有 12 行，沒有額外依賴
> - **cell 之間的接駁本來就是直線估算**（見 12.6），
>   路徑長度的估算誤差已經比貪婪的誤差大了 —— 先修那個更划算
>
> **改進方向**：2-opt 局部最佳化（第 19 章列為未來工作）。

### ⚠ 效能

```
   外層 while：      cell 數 次
   內層 for ci：     剩餘 cell 數 次
   × reverse × flip： 4 次
   每次呼叫 _cell_waypoints：O(cell 內 run 數)
```

總複雜度約 **O(cells² × 4 × 平均 run 數)**。

- 正常場地（5 個 cell）：5² × 4 = 100 次呼叫 → 微秒級
- ⚠ **第 22 章的斜置 30°（23 個 cell）**：23² × 4 = 2,116 次 → 仍可接受
- 如果碎裂到 300 個 cell：360,000 次 → **會有感的延遲**

★ 而且 `_cell_waypoints` 每次都**重新算一遍**同樣的四種姿態，
最後只用其中一種。可以快取，但目前不是瓶頸。

## 12.5 `plan()` 從頭到尾

```python
# scripts/coverage_planner.py:188-259
def plan(free, res, ox, oy, spacing=SPACING, start=None):
    empty = {'waypoints': [], 'cells': [], 'axes': None,
             'n_runs': 0, 'critical': []}

    # ── 0. 防呆 ────────────────────────────────
    rows, cols = np.where(free)
    if len(rows) < 3:
        return empty

    pts = np.column_stack([ox + cols.astype(float) * res,
                           oy + rows.astype(float) * res])

    # ── 1. PCA：由環境自己決定掃描方向 ─────────  第 08 章
    center, axis_a, axis_b, eigvals = principal_axes(pts)
    diffs  = pts - center
    proj_a = diffs @ axis_a
    proj_b = diffs @ axis_b

    # ── 2. 切帶並沿中心線取樣 ─────────────────  第 10 章
    b_min, b_max = proj_b.min(), proj_b.max()
    n_bands   = int(np.floor((b_max - b_min) / spacing)) + 1
    b_centers = b_min + spacing / 2 + spacing * np.arange(max(1, n_bands))

    runs = _slice_runs(free, res, ox, oy, center, axis_a, axis_b,
                       (proj_a.min(), proj_a.max()), b_centers, min_len=res)
    if not runs:
        return empty

    # ── 3. 臨界點與 cell 分解 ─────────────────  第 11 章
    succ, pred      = _link_runs(runs)
    cells, critical = _build_cells(runs, succ, pred)

    # ── 4. 蛇行 + 貪婪走訪順序 ────────────────  本章
    ...

    return {'waypoints': waypoints,
            'cells': ordered,
            'axes': (center, axis_a, axis_b, eigvals),
            'n_runs': len(runs),
            'critical': critical}
```

### 資料流全圖

```
   free (H×W bool)
        │
        ├─ np.where ──→ pts (N, 2) 世界座標
        │                  │
        │                  ├─ principal_axes ──→ center, axis_a, axis_b, eigvals
        │                  │                          │
        │                  └─ 投影 ──→ proj_a, proj_b │
        │                                  │          │
        │                                  ↓          │
        │                          b_centers（帶的位置）
        │                                  │          │
        └──────────────────────────────────┴──────────┤
                                                      ↓
                                            _slice_runs
                                                      │
                                              runs [{band, a0, a1, p0, p1}]
                                                      │
                                              _link_runs
                                                      │
                                              succ, pred
                                                      │
                                              _build_cells
                                                      │
                                        cells [[run idx]] + critical
                                                      │
                              ┌───────────────────────┤
                              │   貪婪迴圈             │
                              │     _cell_waypoints ──┤ ×4 姿態
                              │     取最近            │
                              └───────────────────────┤
                                                      ↓
                                    waypoints [(x,y)] + ordered cells
```

### 兩個 `return empty` 的防呆

| 位置 | 條件 | 什麼時候發生 |
|---|---|---|
| 第 194 行 | `len(rows) < 3` | 地圖幾乎全未知、安全邊距把空間封死 |
| 第 228 行 | `not runs` | 有可走格但每一段都短於 `min_len` |

兩者最終都讓 `/coverage/start` 回覆
「無可走路徑，地圖可能不完整」（`map_server.py:476-477`）。

## 12.6 ⚠ 這一章留下的最大問題：轉場是直線

```python
wps += [(p0[0], p0[1]), (p1[0], p1[1])]
```

`_cell_waypoints` 只輸出**每條 run 的兩端**。
兩條 run 之間（換行接駁）、兩個 cell 之間（跨區轉場）的路徑**完全沒有規劃**
—— 只是把兩個路點依序丟給 `move_base`，讓它自己想辦法。

### 這造成兩個後果

**① 轉場線可能穿過障礙物**

第 22 章的實測（**掃描線穿牆 0 條，轉場穿牆則不然**）：

| 場地 | 轉場穿牆段數 |
|---|---|
| 長方形 4×2 | 0 |
| 含柱 4×2 | 0 |
| L 形 4×4 | 1 |
| U 形 | 1 |
| 斜置 15° | **8** |
| **斜置 30°** | **30** |

`move_base` 會繞路，機器人不會撞牆 —— 但…

**② 規劃的路徑長度 ≠ 實際走的路徑長度**

規劃器以為兩點距離 0.5 m，`move_base` 可能要繞 4 m。

★ **這是唯一會影響數據正確性的項目**（開發日志明確標註）。
所有「路徑長度」的比較（v1 vs v3、不同場地之間）都受這個誤差影響。

**改進方向**：cell 之間用 A\* 在 `free` 上規劃接駁路徑，
把中間的轉折點也加進 `waypoints`。第 19 章列為**優先度最高的未來工作**。

## 12.7 ⑤ 設計決策

| 決策 | 選了 | 否決了 | 理由 |
|---|---|---|---|
| cell 內走法 | 交替方向蛇行 | 每條都從同一側 | 回頭空跑會讓路徑長度翻倍 |
| 進入姿態 | 列舉 4 種取最近 | 固定從第一條帶、左側進入 | 4 種的進入點在四個角，總有一個近 |
| cell 順序 | 貪婪最近鄰 | ① 編號順序<br>② 精確 TSP<br>③ 2-opt | ① 和空間無關<br>② cell 少時不值得<br>③ 未來工作 |
| 距離評估 | 只算到第一個路點 | 算完整路徑長 | 簡單；⚠ 但這是貪婪的弱點之一 |
| 預設起點 | `lexsort` 取左下角 | 隨便挑一個 | 確定性，保證可重現 |
| 轉場 | 直線，交給 move_base | A\* 規劃接駁 | ⚠ 已知缺陷，第 19 章優先項 |

## 12.8 ⑥ 本章重點回顧

1. ★ **蛇行的核心只有一行 `l2r = not l2r`**，每畫完一條掃描線就翻轉方向。
   不翻轉的話路徑長度直接翻倍。
2. ★ **路點的結構是「偶數 index = 掃描線起點、奇數 index = 掃描線終點」**，
   前端畫圖和離線評估都靠這個規則區分「掃描線」與「轉場線」。
3. **`reverse` × `flip` 四種姿態的進入點在 cell 的四個角落**，
   所以總有一個離機器人比較近。
4. **貪婪最近鄰**：每次選「進入點離目前位置最近」的 cell + 姿態。
   ⚠ 三個弱點：只看進入點不看 cell 大小、不看離開位置、貪婪本身非最佳（約 +25%）。
5. **`start` 參數讓規劃從機器人腳下開始**；沒給時用 `lexsort` 取左下角（確定性）。
6. ⚠ ★ **最大的已知問題：轉場是直線，完全沒有避障規劃。**
   `move_base` 會繞路所以不會撞，但**規劃路徑長 ≠ 實走路徑長**，
   這是唯一影響數據正確性的項目。第 22 章實測斜置 30° 有 **30 段**轉場穿牆。

## 12.9 ⑦ 自我檢核題

**Q1. `_cell_waypoints` 裡如果拿掉 `l2r = not l2r` 這一行，路徑會變成什麼樣？
長度大約差多少？**

<details>
<summary>參考答案</summary>

會變成「每條掃描線都從同一側開始」：

```
   ●──────────────→●      走完，人在右端
   （空跑回左端）
   ●──────────────→●
   （空跑回左端）
   ●──────────────→●
```

**長度差多少**：假設掃描線長 L、有 n 條帶。

- **有蛇行**：掃描 `n×L` + 換行 `(n-1)×spacing`
- **無蛇行**：掃描 `n×L` + 回頭 `(n-1)×L` + 換行 `(n-1)×spacing`

以第 22 章「長方形 4×2」為例（掃描長 38.0 m、10 條 run、每條約 3.8 m）：

- 有蛇行：38.0 + 1.6 = **39.6 m**
- 無蛇行：38.0 + 9×3.8 + 1.6 = **73.8 m**

**接近 1.9 倍**。而且那 34 公尺的回頭路完全沒有覆蓋價值
（走的是已經掃過的地方）。

★ 這也是「牛耕式（Boustrophedon）」這個名字的由來 ——
古希臘文的「像牛耕田那樣來回」，重點就在「來回」。
</details>

**Q2. 為什麼要列舉 `reverse` × `flip` 四種姿態？固定用一種不行嗎？**

<details>
<summary>參考答案</summary>

**四種姿態的進入點分別在 cell 的四個角落**：

```
   reverse=F, flip=F → 起點在「第一條帶」的 p0 側
   reverse=F, flip=T → 起點在「第一條帶」的 p1 側
   reverse=T, flip=F → 起點在「最後一條帶」的 p0 側
   reverse=T, flip=T → 起點在「最後一條帶」的 p1 側
```

**固定一種的後果**：機器人可能剛好在 cell 的右上角，
但被迫先跑到左下角才能開始掃 —— 白跑一趟對角線。

以一個 4m × 2m 的 cell 來說，最壞情況是白跑 √(4² + 2²) ≈ **4.5 公尺**。
如果有 4 個 cell，最多可能白跑 18 公尺。

**成本**：每次評估要多算 4 倍的 `_cell_waypoints`（正常場地約 100 次呼叫，微秒級）。

★ 這是一個「用很小的計算換很大的路徑節省」的典型取捨。
</details>

**Q3. 貪婪最近鄰只用 `wps[0]`（第一個路點）算距離。
舉一個例子說明這會選錯。**

<details>
<summary>參考答案</summary>

**場景**：機器人在原點，有兩個 cell。

```
   機器人 ●
          │ 0.5 m
          ↓
   cell A 的進入點 ●━━━━━━━━━━━━━━━━━━━━━━━━━━━━━● 走完停在 20 m 外
                                                   │
                                                   │ 20 m
                                                   ↓
   cell B 的進入點 ●━● 走完只有 1 m         （在原點附近 0.8 m 處）
```

**貪婪的選擇**：A 的進入點距離 0.5 m < B 的 0.8 m → **先走 A**。

- 總長 = 0.5（到 A）+ 20（走 A）+ 20（從 A 終點回 B）+ 1（走 B）= **41.5 m**

**更好的選擇**：先走 B。

- 總長 = 0.8（到 B）+ 1（走 B）+ 0.5ish（到 A）+ 20（走 A）= **22.3 m**

★ 差了將近一倍。

**根本原因**：貪婪只看「進入成本」，不看「這個選擇讓我停在哪裡」。
把小的、順路的 cell 留到最後，會逼自己多跑一次長距離折返。

**改進**：把評估函數改成 `進入距離 + w × (離開點到剩餘 cell 的估計距離)`，
或直接做 2-opt 後處理（第 19 章）。
</details>

**Q4. 「規劃的路徑長度 ≠ 實際走的路徑長度」為什麼是「唯一影響數據正確性」的問題？**

<details>
<summary>參考答案</summary>

因為它讓**所有以路徑長度為基礎的比較都失去意義**。

專案報告裡會出現的比較：
- 「v3 比 v1 路徑短 10%」（第 09 章的表）
- 「L 形場地的路徑長 67.9 m，長方形只要 39.6 m」（第 22 章）
- 「改了 `spacing` 之後路徑短了多少」（第 18 章）

★ **這些數字全部是「規劃器以為的長度」**，也就是把路點用直線連起來的總和。

但實際上，只要有一段轉場穿過障礙物，`move_base` 就會繞路 ——
規劃器以為 0.5 m，實際可能走 4 m。

**第 22 章的實測**：斜置 30° 有 **30 段**轉場穿牆。
如果每段平均多繞 2 m，實際路徑就比規劃長 60 m ——
而規劃器報出來的「36.5 m 掃描 + 2.2 m 轉場」完全看不出這件事。

**對比其他已知問題**：
- 貪婪非最佳：會讓路徑變長，但**規劃器知道自己算出來的長度**，數字是誠實的
- 鋸齒碎裂：cell 數異常，但同樣可以從數字上看出來
- 轉場直線：⚠ **規劃器完全不知道自己錯了**，報出來的數字是自信而錯誤的

**這就是為什麼它排在改進清單的第一位。**
</details>

**Q5. 如果要用 A\* 修掉轉場問題，`plan()` 的回傳結構要怎麼改？
會影響哪些下游？**

<details>
<summary>參考答案</summary>

**做法**：在把兩段路點接起來之前，用 A\*（在 `free` 陣列上）
規劃一條從「上一個路點」到「下一個路點」的路徑，把中間的轉折點插進 `waypoints`。

**回傳結構的問題**：現在的結構有一個隱含約定 ——
**「偶數 index = 掃描線起點、奇數 index = 掃描線終點」**。
插入額外的轉折點會**破壞這個約定**。

**受影響的下游**：

1. **`web/index.html:320-335`**：前端靠 `i += 2` 區分掃描線（粗實線）和換行（細虛線）。
   約定一破，畫出來的線型會亂掉。
2. **`test/coverage_bench.py`**：`sweep_len` / `link_len` / `bad_sweep` / `bad_link`
   四個指標全部靠這個約定，**第 22 章的所有數據都會失效**。
3. **`map_server.py:306-320`（`run_coverage`）**：
   「面向下一個路點」的朝向計算不受影響（它只看前後兩點），但
   `total` 路點數會暴增，進度百分比的意義改變。

**建議的改法**：不要破壞 `waypoints` 的結構，**另外加一個欄位**：

```python
return {'waypoints': [...],       # 保持不變：只有掃描線端點
        'links': [[(x,y), ...], ...],   # 新增：每段轉場的完整路徑
        ...}
```

`run_coverage` 送目標時把 `links` 展開，前端和評估腳本則可以選擇要不要用。

★ **這是介面演進的通用原則：加欄位比改結構安全。**
現有的消費者不用改就能繼續運作（第 05 章的依賴方向）。
</details>
