## 9.1 為什麼要讀「失敗的版本」

看最終版程式碼，你只會學到「它做了什麼」。
看演進過程，你才會學到**「為什麼不能用比較簡單的做法」**。

而且口試最常見的問題就是：

> 「你為什麼要用 PCA？」
> 「你的掃描線會不會穿過障礙物？」
> 「為什麼要做 cell 分解？直接蛇行不行嗎？」

**這三個問題的答案，就是 v0→v1、v1→v2、v2→v3 這三次改版的理由。**

## 9.2 v0：沿著地圖的 x 軸來回掃

### 想法

最直覺的牛耕式：**一列一列掃過去，每列找出「連續可走的區段」，兩端當路點。**

```python
# git show daf9225:scripts/boustrophedon.py
LINE_SPACING = 0.3    # 掃描線間距（公尺），通常 = 機器人直徑
ROBOT_RADIUS = 0.15   # 機器人半徑（公尺）

def boustrophedon(free, res, origin_x, origin_y):
    h, w  = free.shape
    step  = max(1, round(LINE_SPACING / res))   # 掃描線格距
    pts   = []
    l2r   = True

    for row in range(step // 2, h, step):
        # 找出這一行的連續可走區段
        segs, start = [], None
        for col in range(w):
            if free[row, col] and start is None:
                start = col
            elif not free[row, col] and start is not None:
                segs.append((start, col - 1))
                start = None
        if start is not None:
            segs.append((start, w - 1))

        if not segs:
            continue

        if not l2r:
            segs = [(e, s) for s, e in reversed(segs)]

        for s, e in segs:
            for col in ([s, e] if s != e else [s]):
                pts.append((origin_x + col * res, origin_y + row * res))

        l2r = not l2r
    return pts
```

### v0 其實做對了一件很重要的事

★ **它有處理「一列被障礙切成好幾段」的情況**（那個 `segs` 迴圈）。

```
   row = 20:  ....████....████....
              └─┬─┘    └─┬─┘  └┬─┘
              seg1     seg2   seg3      ← 三段，各自產生兩個端點
```

所以在軸對齊的房間裡，**v0 的覆蓋是正確的、不會穿牆的**。

### ⚠ v0 的致命問題：方向鎖死在地圖的 x 軸

```
   房間和地圖軸對齊 —— 完美                房間斜 30 度 —— 災難
   ┌──────────────────┐                          ╱────────╲
   │ ───────────────→ │                        ╱ ────────  ╲
   │ ←─────────────── │                      ╱ ─────────    ╲
   │ ───────────────→ │                    ╱ ──────────      ╲
   └──────────────────┘                  ╱ ───────────        ╲
                                        ╱____ ──────  ────────╲
   10 條等長掃描線                        掃描線長短不一
   轉彎 9 次                              條數暴增、轉彎暴增
                                          短線段幾乎沒有覆蓋價值
```

**為什麼房間會斜？** 因為 SLAM 的地圖座標軸是**機器人開機時的朝向**決定的。
你把機器人隨手放在地上按下開機，房間相對於地圖就是斜的。

> 這就是「你為什麼要用 PCA」的答案：
> **不是為了炫技，是因為地圖的座標軸和房間的牆面沒有任何關係。**

## 9.3 v1：加上 PCA 對齊主軸

### 想法

第 08 章講的 PCA：從可走格的分布算出「最分散的方向」，當作掃描方向。

```python
# git show 21a2184:scripts/boustrophedon.py
# PCA：找自由空間的長軸（sweep）與短軸（step）
center           = pts.mean(axis=0)
diffs            = pts - center
eigvals, eigvecs = np.linalg.eigh(np.cov(diffs.T))
axis_a = eigvecs[:, np.argmax(eigvals)]   # sweep 方向（長軸）
axis_b = eigvecs[:, np.argmin(eigvals)]   # step  方向（短軸）

if axis_a[0] < 0: axis_a = -axis_a        # ★ 正負號固定（這一版就有了）
if axis_b[1] < 0: axis_b = -axis_b

proj_a = diffs @ axis_a
proj_b = diffs @ axis_b
```

這部分**一直保留到現在都沒變**（`coverage_planner.py:36-55`）。

### ⚠ 但為了「切帶」，v1 引入了一個致命的簡化

問題來了：v0 是沿著地圖的 `row` 掃，`row` 是整數，可以直接 `free[row, col]` 查表。
**斜的掃描線沒有「整數 row」可以用**，怎麼找出每條線上的可走區段？

v1 的做法是：

```python
# git show 21a2184:scripts/boustrophedon.py
while b <= b_max + step / 2:
    mask = np.abs(proj_b - b) < step / 2       # ① 選出這條帶裡的所有可走格
    if mask.any():
        a_vals  = proj_a[mask]
        p_start = center + a_vals.min() * axis_a + b * axis_b   # ② 取 a 的最小值當一端
        p_end   = center + a_vals.max() * axis_a + b * axis_b   # ③ 取 a 的最大值當另一端
        ...
```

**「一條帶的兩端 = 帶內所有可走格的 `proj_a` 極值」。**

這在**沒有障礙物的空房間裡完全正確**，而且非常快（沒有迴圈，純向量運算）。

### ③ 撞牆：兩個同源的缺陷

當時用一個 200×100 cm 的合成場地（含圓形 + 方形障礙）實測，結果慘不忍睹：

#### 缺陷一：掃描線直接橫跨障礙物

```
   帶內的可走格：  ●●●●●●        ●●●●●●
                   ↑            ████       ↑
                a最小          障礙       a最大

   v1 畫出來的線： ●━━━━━━━━━━━━━━━━━━━━━━●
                              ↑
                        直接穿過障礙物
```

★ **`min` 和 `max` 完全忽略了中間有沒有斷開。**

> **實測數據**：5 條掃描線**全部**橫跨障礙物，
> 最嚴重的一條有 **75% 的長度落在障礙物內**。
> **有效覆蓋率 0%** —— 沒有任何一條線是機器人真的走得完的。

#### 缺陷二：路點違反安全邊距

更隱蔽的問題：`p_start = center + a_vals.min() * axis_a + b * axis_b`

這裡的 `a_vals.min()` 和 `b` **來自不同的格子**：
- `a_vals.min()` 是帶內某一格的 a 座標
- `b` 是這條帶的**中心線** b 座標

那一格的實際 b 座標可能偏離中心線最多 `spacing/2`：

```
   帶的範圍：  ├──────── spacing ────────┤
   中心線：            b
                       │
   實際那格：  ●        │             最多偏 spacing/2 = 9 cm
   還原的點：           ●  ← 被硬拉到中心線上
                        ↑
                  可能已經落在牆裡
```

> **實測數據**：傾斜 25° 時，**10 個路點裡有 8 個落在膨脹帶內**，
> 離障礙物只有 0.05 m，小於 Burger 的外接圓半徑 0.112 m
> —— `move_base` 會直接拒絕這些目標。

### 💡 這個版本教會我們什麼

★ **v1 是一次「修好一個問題，弄壞另一個問題」的典型回歸。**

v0 明明有處理「一列被切成多段」，v1 為了支援斜向掃描把它丟掉了。
**當你為了新功能改變資料的表示方式時，要檢查舊功能的前提還在不在。**

v0 的前提是「row 是整數，可以逐格走訪」；
v1 換成連續的投影座標之後，這個前提消失了，但沒有人補上替代方案。

## 9.4 v1.5：架構重構與參數調校（演算法沒變）

中間有兩次改動不影響演算法核心，但值得記錄：

### `2356673` — 抽出 `coverage_planner` 模組

原本演算法直接寫在 `boustrophedon.py`（一個 ROS 節點）裡。
抽出來變成**零 ROS 依賴的純模組**，讓 `map_server.py` 也能用。

這就是第 05 章講的介面設計 —— **而且它讓後來的離線測試變成可能**。

同一個 commit 還加了 `move_base` 的失敗容錯（第 03 章 3.5 講的「跳過繼續」）。

### `d454f7b` — 參數調校

```diff
-SPACING = 0.25   # 掃描線間距（公尺）；< 機器人直徑以確保重疊覆蓋
-MARGIN  = 0.15   # 障礙物安全邊距（公尺） ≈ 機器人半徑
+SPACING = 0.18   # 掃描線間距（公尺）；覆蓋寬度 ≈ 0.20 m，留 10% 重疊
+MARGIN  = 0.10   # 障礙物安全邊距（公尺） ≈ 機器人半徑（直徑 0.20 m）
```

**參數的完整演變**：

| | v0 | v1 | v1.5 | 現在 |
|---|---|---|---|---|
| 掃描間距 | 0.30 | 0.30 | 0.25 | **0.18** |
| 安全處理 | `binary_erosion`<br>半徑 0.15 | 同左 | `binary_dilation`<br>邊距 0.15 | `binary_dilation`<br>邊距 **0.10** |

兩個變化的理由：

**① 間距 0.30 → 0.18**：0.30 m 等於機器人直徑，等於「剛好不重疊」。
但實際上定位有誤差、路徑會偏，剛好不重疊 = **會漏掃**。
0.18 對覆蓋寬度 0.20 m 留了 **10% 重疊**（`0.20 - 0.18 = 0.02`，約 10%）。

**② 侵蝕 → 膨脹**：v0 用 `binary_erosion(free)`（把自由區縮小），
現在用 `binary_dilation(obs)`（把障礙區放大）。

★ 這兩者**在數學上不完全等價**：
- 侵蝕自由區：`free` 邊緣往內縮，但**未知格（-1）不是 free，所以未知區的邊界也會被縮**
- 膨脹障礙區：只有**真正的障礙（100）**會長大，未知區不會

換成膨脹之後，語意變清楚了：「安全邊距是相對於**實體障礙**的，不是相對於未知區的」。

## 9.5 v2：沿中心線取樣（修掉穿牆）

### 想法

回到 v0 的精神：**要知道一條線上哪裡能走，就得沿著那條線一格一格檢查。**

差別在於斜線沒有整數索引，所以改成**參數化取樣**：

```
   v0（軸對齊）                v2（任意方向）
   for col in range(w):        a from a_min to a_max, step = res/8
       free[row, col]              點 = center + a·axis_a + b·axis_b
                                   查最近的格 free[round(...), round(...)]
```

```python
# scripts/coverage_planner.py:88-105
step = res / 8.0
a_lo, a_hi = a_range
n = int(np.ceil((a_hi - a_lo) / step)) + 1
a_s = a_lo + step * np.arange(n)

for k, b in enumerate(b_centers):
    pl = center + a_s[:, None] * axis_a + b * axis_b     # 整條線的取樣點
    c = np.round((pl[:, 0] - ox) / res).astype(int)
    r = np.round((pl[:, 1] - oy) / res).astype(int)
    inb = (r >= 0) & (r < H) & (c >= 0) & (c < W)
    ok = np.zeros(n, dtype=bool)
    ok[inb] = free[r[inb], c[inb]]

    for i0, i1 in _true_runs(ok):
        ...
```

★ **這一步同時修掉了兩個缺陷**：

1. **不會穿牆**：區間是由「連續為 True 的取樣點」定義的，
   線段整條必定落在可走格上 —— **從構造上保證**，不是靠檢查
2. **不會違反安全邊距**：端點就是取樣點本身，
   它的 `(a, b)` 座標和線的 `(a, b)` 完全一致，不會有 v1 那種 9 cm 的垂直偏差

### ❌ 被否決的修法一：用 `scipy.ndimage.label` 做連通標記

**第一版的修法**是這樣：對每條帶內的格子做 **8-連通標記**，
每個連通塊當一段，取塊的兩端當路點。

**為什麼失敗**：

```
   連通塊在網格上可能是「彎的」（繞過障礙轉角）：

        ●●●●
           ●●        ← 這 8 格是一個 8-連通塊
            ●●
             ●●●●

   但把「頭」和「尾」連直線：

        ●━━━━━━━━━━━━━●
              ↑
        直線從障礙物上切過去
```

★ **教訓**：「這些格子彼此連通」不等於「連接它們兩端的直線是可走的」。
連通性是**圖論性質**，直線可走是**幾何性質**，兩者不能互推。

改成中心線取樣之後，線段**由取樣點本身定義**，才從構造上保證不越界。

### ❌ 被否決的修法二：取樣步長用 `res/2`

第一版取樣步長用 `res / 2`（半格），看起來夠密了。

**實測發現**：斜向掃描線仍會從障礙格的**角落「跨」過去**：

```
   障礙格：      ┌────┐
                 │████│
                 └────┘
   取樣點：   ●        ●        ← 兩個取樣點都在障礙格外
                ╲    ╱
                 ╲  ╱          但它們之間的線段切過了障礙格的角
                  ╲╱
```

> **實測漏掉約 11 mm 的切角。** 改用 `res / 8`（≈6 mm）之後不再發生。

程式碼裡有把這個過程寫進註解：

```python
# scripts/coverage_planner.py:86-92
# 取樣步長取 1/8 格（≈6 mm）。步長接近一格時，斜向掃描線會從障礙格的角落
# 「跨」過去而沒被偵測到；實測 res/2 會漏掉約 11 mm 的切角，res/8 則不會。
```

### ❌ 被否決的修法三：「四個包夾格全可走」的保守判定

還試過更嚴格的判定：取樣點不是查「最近的一格」，
而是要求**周圍四個格子全部可走**才算通過。

**效果**：切角問題**完全杜絕**。

**代價**：

> 平均覆蓋率從 **97% 掉到 89%**，最低 **57%**。

原因是它會把「只有兩格寬的窄通道」整條刪掉 ——
兩格寬的通道，中心線上任何一點的四個鄰格必定有一個是牆。

★ **這是一個典型的「治好了病、殺死了病人」的修法。**
最後選擇 `res/8` + 單格查表：接受極少數 6 mm 以下的切角，
換取窄通道能通過。

```python
# scripts/coverage_planner.py:90-92
# （曾試過「四個包夾格全可走」的保守判定，雖然完全杜絕切角，但會把只有兩格寬
#   的窄通道整條刪掉，平均覆蓋率從 99% 掉到 89%，代價過大，故不採用。）
```

## 9.6 v3：真正的 cell 分解

### v2 之後還剩什麼問題

v2 修好了「線不會穿牆」，但**整張圖仍然被當成一塊在蛇行**：

```
   帶 k+2:  ●────────●        ●────────●     ← 兩段
   帶 k+1:  ●────────●        ●────────●
   帶 k  :  ●─────────────────────────●      ← 一段
              ████████
```

如果只是「照帶的順序、左右交替」把所有 run 串起來，會發生：

```
   走法：  帶 k   左→右（整條）
           帶 k+1 右→左（右段）→ 然後要跳到左段？
                  ↑ 跳過整個障礙物，一趟長距離空跑
           帶 k+2 又要跳回去
```

★ **每換一條帶就要跨過障礙物一次**，來回空跑。

### 想法：先把空間切成「內部沒有障礙的區塊」

這就是 **BCD（Boustrophedon Cellular Decomposition）** 的核心：

> **找出「掃描線的區間數發生變化」的位置，在那裡把空間切開。**
> 切出來的每一塊（cell）內部，每條掃描線都只有一段 —— 可以放心蛇行。

```
   ┌───────────────────────────────┐
   │           cell C              │  每條帶 1 段
   ├──────────┬──────┬─────────────┤  ← merge 臨界點
   │  cell A  │██████│   cell B    │  每條帶 1 段（各自）
   ├──────────┴──────┴─────────────┤  ← split 臨界點
   │           cell D              │  每條帶 1 段
   └───────────────────────────────┘
```

實作分三個函式（第 11 章詳解）：

```python
_link_runs()    # 相鄰兩帶的區間，沿長軸投影有重疊 → 相接
_build_cells()  # 只有「前後一對一」才延伸；一分為多/多合為一 = 臨界點
_cell_waypoints()  # 每個 cell 各自蛇行
```

再加上 cell 之間的走訪順序（貪婪最近鄰，第 12 章）。

### 成果（開發日志記錄的實測數據）

同一組合成地圖，**v1 → v3**：

| 場景 | 掃描線 | 穿障線段 | 壞路點 | 有效覆蓋率 | 路徑長 |
|---|---|---|---|---|---|
| 200×100 平行 | 5 → 11 | 5 → **0** | 2 → **0** | 0% → **100.0%** | 8.09 → 7.29 m |
| 200×100 傾斜 25° | 5 → 9 | 5 → **0** | 8 → **0** | 0% → **99.6%** | 7.48 → 4.57 m |
| 240×120 傾斜 35° | 6 → 11 | 6 → **0** | 6 → **0** | 0% → **99.4%** | 12.82 → 9.58 m |
| 300×150 傾斜 15° | 8 → 21 | 8 → **0** | 11 → **0** | 0% → **99.7%** | 22.11 → 17.74 m |

**全面掃描**（4 種房型 × 9 種傾角，共 437 條掃描線）：
- 撞到真實障礙：**0 條**
- 輕微切到安全邊距帶：7 條，最深 **4.5 mm**（邊距本身有 100 mm 餘裕）
- 平均覆蓋率 **97.4%**，最低 86.0%
- 規劃耗時 **1.3 ms**（300×150 場景）

★ **注意「掃描線數量變多了」（5→11）但「路徑長度變短了」（8.09→7.29 m）。**
因為 v1 的 5 條線裡有大半在障礙物內是「假的」，
v3 的 11 條線都是真的能走的，而且 cell 分解消掉了來回跨越障礙的空跑。

---

## 9.7 ❌ 被否決的修法四：各 cell 各自求 PCA 主軸

這是 v3 完成後**寫進待辦清單、實作測試之後又撤回**的方案，特別值得記錄。

### 想法看起來很合理

全域 PCA 對 L 形房間會算出一個「兩支的折衷方向」（第 22 章實測是 **−45°**），
兩支都沒對齊。那麼：**先做 cell 分解，再對每個 cell 自己求一次 PCA、自己重新掃描**，
不就每個 cell 都對齊自己的形狀了嗎？

### 實測結果：撤回

**① 效益很小**

> 逐 cell 重掃只讓掃描線從 **52 條減到 49 條**（減少 5.8%）。

**② 破壞了 cell 的定義性質**

★ 這是最致命的問題。cell 的定義是：
**「沿著某個固定方向切片時，每一片都是單一連通區間」**。

一旦換了掃描方向，這個性質就不成立了：

> 實測 39 條掃描帶中有 **10 條（26%）分裂成多段**。

也就是說，你得**在 cell 內部再做一次遞迴分解** —— 問題沒有被解決，只是被推遲了。

**③ 它救不了全域主軸的偏差**（L 形房間實測）

```
   全域 PCA 給的主軸：158.4°（離橫支的牆面差 21.6°）
   分解後，橫向 cell 自己的主軸：167.6° / 168.6°
                                  ↑ 仍然離牆面 11~12°
```

★ **原因很根本**：cell 的形狀**本來就是被歪掉的全域軸切出來的**。
用歪的軸切出歪的 cell，再對歪的 cell 求軸，當然還是歪的。
**錯誤在第一步就發生了，後面怎麼補都補不回來。**

### 正確的方向是什麼

> **先依幾何分區、再在每區跑完整的 PCA → 分解 → 掃描。**

也就是分區這一步不能用「全域主軸的掃描帶」來做，
要用別的方法（例如形態學骨架、凸分解、房間偵測）先把 L 形切成兩個矩形，
再各自跑一次完整流程。

⚠ **這是另一個演算法，不是這個演算法的參數調整。** 所以列為未來工作（第 19 章）。

> 💡 **這一段的價值不在於「我們沒做」，而在於「我們試了、量了、知道為什麼不行」。**
> 口試被問「L 形房間效率不好，你怎麼改進？」時，
> 「各 cell 各自求 PCA」是最容易被想到的答案，
> 而你能拿出數據說明它為什麼無效，這比隨口說「未來會改進」有力得多。

## 9.9 ⑥ 本章重點回顧

1. **v0 → v1 的教訓**：為了新功能改變資料表示方式時，
   ⚠ **要檢查舊功能的前提還在不在**。v1 從「整數 row」換成「連續投影座標」，
   丟掉了 v0 已經做對的「逐列多段」處理，造成有效覆蓋率 0% 的回歸。
2. **v1 的兩個缺陷同源**：都來自「用帶內所有點的 `proj_a` 極值當端點」。
   一個造成穿牆，一個造成路點垂直偏移最多 `spacing/2` = 9 cm。
3. ★ **v2 的關鍵洞察**：線段要**由取樣點本身定義**，才能從構造上保證不越界。
   「格子彼此連通」≠「連接兩端的直線可走」。
4. **取樣步長 `res/8` 是實測出來的**：`res/2` 會漏掉 11 mm 切角。
5. ★ **「四鄰格全可走」是治好了病殺死病人的修法**：切角杜絕，但覆蓋率 99%→89%。
   **保守不一定是對的。**
6. **v3 的 cell 分解讓「掃描線變多但路徑變短」**，因為消掉了跨越障礙的空跑。
7. ★ **「各 cell 各自求 PCA」被實測撤回**：效益 5.8%，
   但破壞 cell 定義性質（26% 帶分裂），而且救不了主軸偏差
   —— 因為 cell 本來就是被歪掉的軸切出來的。

## 9.10 ⑦ 自我檢核題

**Q1. v0 明明就會處理「一列被障礙切成多段」，為什麼 v1 反而做不到？**

<details>
<summary>參考答案</summary>

因為**資料的表示方式變了**。

- **v0**：沿地圖的 `row` 掃描。`row` 是整數，可以 `for col in range(w): free[row, col]`
  逐格走訪，自然就能偵測到「連續 True 的區段」。
- **v1**：掃描方向是任意角度，**沒有整數索引可以走訪**。
  v1 改用 `mask = np.abs(proj_b - b) < step/2` 選出「屬於這條帶的所有格子」，
  但這個集合是**無序的點集**，只知道有哪些點，不知道它們沿線的排列順序。

從無序點集能取到的只有 `min` 和 `max`，**中間有沒有斷開這個資訊在取 mask 的那一刻就丟失了**。

**修法的方向因此很明確**：要恢復「順序」這個資訊 ——
v2 的做法是沿線**參數化取樣**（`a` 從小到大），人為造出順序，
就能再次用 `_true_runs` 找連續區段。
</details>

**Q2. 「格子彼此 8-連通」和「連接兩端的直線可走」有什麼不同？舉一個例子。**

<details>
<summary>參考答案</summary>

**連通性是圖論性質**（能不能沿著格子走過去），
**直線可走是幾何性質**（兩點之間的線段是否全在可走區）。

**例子**：L 形的連通塊

```
   ●●●●●●
        ●
        ●
        ●●●●●●
   ↑              ↑
   起點           終點
```

這 15 格是 8-連通的（可以沿著格子從頭走到尾），
但**起點到終點的直線**會從中間的空白處（可能是障礙物）切過去。

在本專案的脈絡裡，這發生在掃描帶「繞過障礙物轉角」的時候：
帶內的可走格繞了個彎連在一起，但頭尾連直線就穿出去了。

★ **這就是為什麼 `scipy.ndimage.label` 的修法失敗**。
正確的做法是讓**線段由取樣點本身定義** ——
既然每個取樣點都在線上、而且每個都驗證過可走，
那整條線段就必定可走（在取樣步長的精度內）。
</details>

**Q3. 「四個包夾格全可走」的判定完全杜絕了切角，為什麼還是被否決？
這給你什麼一般性的啟示？**

<details>
<summary>參考答案</summary>

**被否決的原因**：平均覆蓋率從 **99% 掉到 89%**，最低 **57%**。

**機制**：兩格寬的通道（0.10 m），中心線上任何一點的四個鄰格必定至少有一個是牆
→ 判定不通過 → **整條通道被刪掉** → 通道另一端的整個房間變成孤島，完全不覆蓋。

**一般性啟示**：

★ **「更保守」不等於「更好」。** 保守的判定會同時排除掉「真的危險」和「其實沒問題」的情況，
當後者的比例很高時，代價會遠大於收益。

具體到這裡的取捨：
- **接受的風險**：極少數 6 mm 以下的切角（而安全邊距本身有 100 mm 餘裕，
  也就是切進去 6 mm 之後離真正的牆還有 94 mm）
- **換到的收益**：窄通道能通過，覆蓋率高 10 個百分點

**判準是「風險的實際後果 vs 代價的實際後果」**，不是「哪個聽起來比較安全」。
6 mm 的切角在 100 mm 餘裕面前完全無害；少覆蓋 10% 的空間則是實實在在的失敗。
</details>

**Q4. 為什麼 v3 的掃描線數量增加了（5→11），路徑長度反而變短了（8.09→7.29 m）？**

<details>
<summary>參考答案</summary>

兩個原因：

**① v1 的 5 條線裡大部分是「假的」**

那 5 條線全部橫跨障礙物，最嚴重的一條 75% 的長度在障礙物內。
機器人**根本走不了那條線**（`move_base` 會拒絕或繞遠路）。
v3 的 11 條線每一條都是真的可走的區間 —— 數量變多是因為
「一條穿牆的假線」被拆成了「兩條真實的短線」。

**② cell 分解消掉了跨越障礙的空跑**

v1（或沒有 cell 分解的 v2）每換一條帶，就可能要從障礙物的一側跳到另一側：

```
   帶 k+1 走完右段 → 要跳到帶 k+2 的左段 → 橫跨整個障礙物
   帶 k+2 走完左段 → 又要跳回右邊
```

cell 分解之後，左半邊（cell A）整個走完，再走右半邊（cell B），
**只跨越一次**而不是每條帶跨越一次。

★ **這是 cell 分解最直接的價值**：不是為了「覆蓋得更完整」（v2 就做到了），
而是為了「**用更短的路徑**覆蓋」。
</details>

**Q5. 有人建議「既然 L 形房間的全域主軸是 −45°，那就對每個 cell 各自求 PCA」。
你會怎麼回應？**

<details>
<summary>參考答案</summary>

**這個方案已經實作測試過，結論是無效，理由有三個：**

**① 效益很小**：掃描線 52 → 49 條，只減少 5.8%。

**② 破壞了 cell 的定義性質**：cell 的定義是「沿某個固定方向切片時，
每片都是單一連通區間」。換了掃描方向這個性質就沒了 ——
實測 39 條帶中有 **10 條（26%）分裂成多段**。
等於要在 cell 內部再做一次遞迴分解，問題只是被推遲，沒有被解決。

**③ 最根本的問題：它救不了主軸偏差。**

L 形實測：全域 PCA 給 158.4°（離橫支牆面 21.6°），
分解後橫向 cell 的自身主軸仍是 167.6°/168.6°，**還是差 11~12°**。

★ 原因是 **cell 的形狀本來就是被歪掉的全域軸切出來的**。
用歪的軸切出歪的 cell，再對歪的 cell 求軸，結果當然還是歪的。
**錯誤在第一步就發生了。**

**正確的方向**是「**先幾何分區、後求軸**」：
用形態學骨架、凸分解或房間偵測，先把 L 形切成兩個矩形，
再對每個矩形跑一次完整的 PCA → 分解 → 掃描。

⚠ 但這是**另一個演算法**，不是這個演算法的參數調整，所以列為未來工作。
</details>
