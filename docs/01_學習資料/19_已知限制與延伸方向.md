## 19.2 ★★ 「假完成」的四種成因

網頁顯示「**覆蓋完成 ✓　共 N 個路點**」，但實際上還有一大塊沒走到。
這是使用者最容易遇到、也最容易誤導人的問題。

### 成因一：未知格（`-1`）從不進入規劃 ★ 最常見

```python
# scripts/map_server.py:469
free = (raw['data'] == 0) & ~safe
#                     ↑ 只有 0（確定自由）算可走，-1（未知）不算
```

**第 22 章的實測**（4×2 房間，右側 1.2 m 保持未知）：

| | 完整地圖 | 有未知區 |
|---|---|---|
| 可走面積 | 6.9 m² | **4.9 m²** |
| 規劃出的覆蓋率 | 100.0% | **100.0%** ⚠ |
| **對真實房間的覆蓋率** | 100% | **71%** |

★ **演算法報 100%，實際只走了 71%。**
因為它的分母是「已知的可走格」，而不是「房間的實際面積」。

**為什麼會有未知區**：光達實測有效距離只有約 3 m（第 02 章 2.2），
房間比 3 m 寬時，機器人得走到中間才看得到對面。
如果建圖時偷懶只推著繞了一圈邊緣，中間就會有大片未知。

**改進方向**：
1. **短期**：`/coverage/start` 回傳「未知格佔比」，超過 5% 就在網頁上警告
2. **中期**：把 frontier（已知/未知的邊界）也納入規劃，先去探索再覆蓋
3. **長期**：做成兩階段任務（探索 → 覆蓋）

### 成因二：路點失敗被「跳過繼續」吞掉

```python
# scripts/map_server.py:341-345
if client.get_state() != GoalStatus.SUCCEEDED:
    rospy.logwarn(...)
    cov_status['msg'] = f'路點 {i+1}/{n} 跳過（無法到達）'
    # 沒有 return，繼續下一個
```

⚠ `cov_status['msg']` **只保留最後一則**，前面的會被覆寫。
而且最後狀態仍會變成 `done`。

**改進方向**（很簡單，值得馬上做）：

```python
skipped = 0
...
if client.get_state() != GoalStatus.SUCCEEDED:
    skipped += 1
    cov_status['skipped'] = skipped
...
with cov_lock:
    if cov_status['state'] == 'running':
        cov_status.update(state='done', done=n, skipped=skipped)
```

前端顯示「完成 ✓　共 300 個路點（**跳過 17 個**）」。

### 成因三：安全邊距把區域封死（且無連通性檢查）

`MARGIN` 太大或通道太窄時，某些區域會變成孤島。

⚠ **`plan()` 完全沒有連通性檢查**，它會照常規劃跨區路徑，
然後 `move_base` 對孤島裡的每一個路點都失敗 —— 被成因二吞掉 —— 最後顯示完成。

**改進方向**：在 `plan()` 裡對 `free` 做一次 `scipy.ndimage.label`，
只保留「包含機器人起點的那個連通元件」，其餘回報成「不可達區域，面積 X m²」。

```python
from scipy.ndimage import label
lab, n = label(free, structure=np.ones((3,3), bool))
if n > 1:
    start_component = lab[start_row, start_col]
    unreachable_area = (lab > 0).sum() - (lab == start_component).sum()
    free = (lab == start_component)      # 只規劃可達的部分
```

★ **這個改動不到 10 行，但直接消滅成因三，而且順便解決缺陷 #4。**

### 成因四：最外側掃描帶落空（缺陷 #2）

第 22 章實測，細長 6×1.5 的場地覆蓋率只有 **96.3%**，
損失全部來自最後一條帶落在可走區外。

見 19.4。

## 19.3 🔴 缺陷 #1：轉場沒有避障規劃

### 問題

```python
# scripts/coverage_planner.py:181
wps += [(float(p0[0]), float(p0[1])), (float(p1[0]), float(p1[1]))]
```

`_cell_waypoints` 只輸出每條 run 的**兩端**。
run 之間、cell 之間的路徑**完全沒有規劃**，直接丟給 `move_base`。

### 實測（第 22 章）

| 場地 | 掃描線穿牆 | **轉場穿牆** |
|---|---|---|
| 長方形 4×2 | 0 | 0 |
| 含柱 4×2 | 0 | 0 |
| L 形 4×4 | 0 | **1** |
| U 形 | 0 | **1** |
| 斜置 15° | 0 | **8** |
| 斜置 30° | 0 | **30** |

★ **掃描線一條都不穿牆**（第 10 章的中心線取樣保證了這件事），
**但轉場線會穿**。

### 後果

機器人不會撞牆（`move_base` 會繞），但：

★ **規劃器報出來的路徑長度是「假的」。**

規劃器以為兩點距離 0.5 m（直線），`move_base` 實際可能繞 4 m。
所有以路徑長度為基礎的比較（版本比較、場地比較、參數比較）都受這個誤差影響。

### 改進方向

**用 A\* 在 `free` 上規劃接駁路徑**，把中間的轉折點插進結果。

★ **介面要小心**（第 12 章 12.9 Q5）：現有的 `waypoints` 有一個隱含約定
「偶數 index = 掃描線起點、奇數 = 終點」，前端和評估腳本都靠它。

**建議：加欄位，不改結構。**

```python
return {'waypoints': [...],           # 保持不變
        'links': [[(x,y), ...], ...], # ★ 新增：每段轉場的完整路徑
        'link_length': float,          # ★ 新增：真實的轉場總長
        ...}
```

- `run_coverage` 送目標時把 `links` 展開
- 前端可以選擇畫不畫
- 評估腳本可以用 `link_length` 得到**真實的**路徑長度

**工作量**：A\* 本身約 40 行（在 grid 上，用 heapq），介面調整約 20 行。

## 19.4 🔴 缺陷 #2：最外側掃描帶

### 問題

```python
# scripts/coverage_planner.py:223-224
n_bands   = int(np.floor((b_max - b_min) / spacing)) + 1
b_centers = b_min + spacing / 2 + spacing * np.arange(max(1, n_bands))
```

最後一項 `b_min + spacing/2 + spacing × (n_bands − 1)` **可能超出 `b_max`**。

### 兩種發作方式（第 22 章實測）

**A. 落在可走區外 → 覆蓋率損失**

| 場地 | 覆蓋率 | 最後一帶 |
|---|---|---|
| 細長 6×1.5 | **96.3%** | 8 條帶，第 8 條 0 個 run |
| 斜置 45° | **95.9%** | 10 條帶，第 10 條 0 個 run |

**B. 正好落在光柵化的鋸齒邊界上 → cell 碎裂**

```
   斜置 30°，band 9（b = +0.845）：
   [-1.79,-1.71] [-1.68,-1.51] [-1.50,-1.41] [-1.39,-1.11] ... 共 22 段
```

前 9 條帶都正常（各 1 條 run），**只有最後一條碎成 22 段**
→ 22 個只有 1 條 run 的 cell → 總共 **23 個 cell**、**30 段轉場穿牆**。

★ **關鍵洞察：這是一個「刀鋒條件」。**
斜置 15° 和 45° 都沒事（最後一帶剛好落在外面或裡面），
只有 30° 剛好卡在邊界上。**任何角度都可能觸發，取決於幾何巧合。**

⚠ **軸對齊的場地不會發作**（邊界是整齊的直線），
但**真實 SLAM 地圖的邊界永遠是鋸齒的**。

### 改進方向（三個候選）

**① 讓帶均勻分布在可走區內**（最推薦）

```python
n_bands = max(1, int(np.round((b_max - b_min) / spacing)))
b_centers = np.linspace(b_min + spacing/2, b_max - spacing/2, n_bands)
```

保證每條帶都落在 `[b_min + spacing/2, b_max − spacing/2]` 之內。
實際間距會略微偏離 `spacing`（但一定 ≤ `spacing`，所以不會漏掃）。

**② 提高 `min_len`**

從 `res`（0.05）提高到 `spacing`（0.18），濾掉碎片。
⚠ **副作用**：真實的短通道（門縫、壁龕）也會被誤刪（第 10 章 10.8 Q4）。

**③ 加一個「碎裂偵測」**

如果某條帶的 run 數 > 某個門檻（例如 5），就把它整條丟掉並記錄警告。
治標不治本，但可以避免最壞情況。

★ **建議做 ①，它處理的是根因。** ② 和 ③ 是治標。

## 19.5 🟡 缺陷 #5、#6：PCA 的適用範圍

### #6：正方形完全退化

第 22 章實測，正方形 3×3 的 **λ₁/λ₂ = 1.00**。

★ 兩個特徵值相等時，特徵向量的方向**完全由數值誤差決定**。
「PCA 自動對齊主軸」這個賣點在正方形上等於沒有作用。

**不影響覆蓋率**（實測仍有 98.2%），但**不能拿正方形場地當作 PCA 的證明**。

**改進方向**：
- **短期**：`λ₁/λ₂ < 1.2` 時在網頁上顯示警告「主軸方向不可靠」
- **實務**：把展示場地做成長寬比 ≥ 2:1（λ₁/λ₂ > 4）

### #5：L 形的主軸是「折衷值」

第 22 章實測，對稱 L 形 4×4 的主軸是 **−45°** —— 兩支都沒對齊。

```
   ┌─────┐
   │  ╲  │      PCA 給的主軸是對角線
   │   ╲ │      橫支和豎支都差 45°
   │    ╲├─────┐
   │     ╲     │
   └──────╲────┘
```

**後果**：路徑長 **67.9 m**，而同面積（10.6 m²）的長方形只要約 **40 m** ——
效率差了 **70%**。

⚠ **注意覆蓋率仍是 100%** —— 演算法**能跑**，只是**不漂亮**。

**❌ 已否決的修法**：各 cell 各自求 PCA（第 09 章 9.7，實測撤回）。

**正確的方向**：**先幾何分區，再對每區跑完整流程。**

```
   ① 用凸分解 / 形態學骨架 / 房間偵測，把 L 形切成兩個矩形
   ② 對每個矩形各自跑 PCA → 切帶 → cell 分解 → 蛇行
   ③ 用一個上層的順序規劃決定先走哪一區
```

⚠ **這是另一個演算法**，不是參數調整。工作量大約是現有演算法的一半。

## 19.7 ★ 建議的改進順序

如果只有時間做三件事：

```
   ① 連通性檢查（缺陷 #4，順便消滅假完成成因三）      < 10 行，效益極大
   ② b_centers 均勻分布（缺陷 #2）                     ~3 行，修掉覆蓋率損失與碎裂
   ③ skipped 計數（假完成成因二）                       ~5 行，讓數字誠實
```

★ **這三項加起來不到 20 行程式碼，但消滅了三個會讓結論出錯的問題。**

如果還有時間：

```
   ④ A* 轉場接駁（缺陷 #1）                             ~60 行，讓路徑長度數據可信
   ⑤ 未知格佔比警告（假完成成因一）                     ~10 行
   ⑥ 幾何分區 → 每區完整流程（缺陷 #5）                 大工程，另一個演算法
```

## 19.9 ⑥ 本章重點回顧

1. ★ **缺陷排行的判準是「會不會讓數據或結論出錯」**，不是「修起來難不難」。
2. 🔴 **#1 轉場沒有避障規劃**是唯一會讓**路徑長度數據失真**的問題 ——
   所有版本比較、場地比較、參數比較都受影響。
3. 🔴 **#2 最外側掃描帶**是「刀鋒條件」：落空 → 覆蓋率損失 3~4%；
   貼著鋸齒邊界 → cell 從 1 爆成 23。**任何角度都可能觸發。**
4. ★★ **「假完成」有四種成因**：未知格不覆蓋（最常見）、路點失敗被吞、
   邊距封死無連通檢查、最外帶落空。
5. ★ **連通性檢查（`scipy.ndimage.label`）不到 10 行，CP 值最高** ——
   同時解決缺陷 #4 和假完成成因三。
6. **L 形能跑（覆蓋 100%），但主軸是折衷值，路徑長 70%** ——
   ⚠ 正確解法是「先幾何分區、後求軸」，不是「各 cell 各自求 PCA」（已實測撤回）。
7. **建議的前三項改進加起來不到 20 行**，就能消滅三個讓結論出錯的問題。

## 19.10 ⑦ 自我檢核題

**Q1. 口試委員問：「你的機器人顯示覆蓋完成了，但地上明明還有一塊沒掃到，
這是怎麼回事？」你會怎麼回答？**

<details>
<summary>參考答案</summary>

★ **先承認這是已知問題，然後說明它有四種不同的成因，並指出怎麼區分。**

> 「這個現象我們稱為『假完成』。它的根源是：
> **系統報的『完成』只代表『路點清單跑完了』，不代表『空間被覆蓋了』**。
> 有四種成因，可以用不同的方式區分：
>
> **① 未知格沒被規劃**（最常見）。演算法只覆蓋 `data == 0` 的格子，
> `-1`（未探索）完全不進入規劃。我們的光達實測有效距離只有約 3 公尺，
> 房間比較大時，如果建圖沒走完整，中間會有大片未知。
> **判斷方法**：看網頁上的原始地圖圖層有沒有大片灰色。
>
> **② 路點到不了被跳過**。我們的執行層對失敗的路點是『記錄後繼續』，
> 因為 300 個路點裡有一兩個到不了是正常的。
> **判斷方法**：看終端機有沒有『路點 N 跳過』的警告。
>
> **③ 安全邊距把通道封死**，某塊區域變成孤島。
> 規劃器目前沒有連通性檢查，會照常規劃過去，然後每個路點都失敗。
> **判斷方法**：看網頁的『安全邊距』圖層。
>
> **④ 最外側的掃描帶落在可走區外**。這是我們用合成地圖量到的 bug，
> 細長場地會損失約 3.7% 的覆蓋率。
>
> ★ **改進的優先順序**：③ 只要用 `scipy.ndimage.label` 做一次連通元件標記，
> 不到 10 行就能修掉；② 加一個 `skipped` 計數並顯示在網頁上，約 5 行；
> ① 需要把 frontier 探索納入，是比較大的改動。」

★ **這個回答的價值在於：你不只知道有問題，還知道它有幾種、怎麼區分、
修起來各要多少工。** 這顯示你真的分析過。
</details>

**Q2. 為什麼「轉場沒有避障規劃」被排在缺陷第一位？
它明明不會讓機器人撞牆（`move_base` 會繞路）。**

<details>
<summary>參考答案</summary>

★ **因為它是唯一一個「規劃器對自己的錯誤毫無察覺」的缺陷。**

對照其他缺陷：

| 缺陷 | 規劃器知道嗎 | 數字誠實嗎 |
|---|---|---|
| 貪婪非最佳 | 不知道最佳解，但**它算出來的長度是真的** | ✅ 誠實 |
| cell 碎裂 | 不知道，但 **cell 數異常大是看得出來的** | ✅ 可觀察 |
| 未知格不覆蓋 | 不知道，但 **地圖上的灰色是看得出來的** | ✅ 可觀察 |
| **轉場穿牆** | ⚠ **完全不知道，而且從輸出完全看不出來** | ❌ **自信而錯誤** |

規劃器報「掃描 36.5 m + 轉場 2.2 m」，
但如果那 2.2 m 裡有 30 段穿牆，`move_base` 實際可能走 **60 m 以上**。

**這會污染所有以路徑長度為基礎的結論**：
- 第 09 章「v3 比 v1 短 10%」
- 第 22 章「L 形 67.9 m vs 長方形 39.6 m」
- 第 18 章「`SPACING` 0.18 vs 0.30 的路徑長比較」

★ **一個誠實的爛數字，比一個看起來漂亮但錯誤的數字有用得多。**
其他缺陷會讓系統表現變差，但這個缺陷會讓**你對系統的認知**出錯 ——
你可能因此做出錯誤的優化決定。

（開發日志也是這樣標註的：「這是唯一會影響數據正確性的項目」。）
</details>

**Q3. 「最外側掃描帶」的問題，為什麼說它是「刀鋒條件」？
為什麼斜置 15° 和 45° 沒事，只有 30° 出問題？**

<details>
<summary>參考答案</summary>

因為問題的觸發條件是**「最後一條帶的中心線，剛好落在光柵化後的鋸齒邊界上」**
—— 這完全取決於幾何巧合。

`b_centers` 的最後一項 = `b_min + spacing/2 + spacing × (n_bands − 1)`，
它和 `b_max` 的關係是**三個連續量（`b_min`、`b_max`、`spacing`）相除取整後的餘數**
決定的，本質上是準隨機的。

**三種可能的落點**：

```
   情況 A：明顯落在外面     →  0 個 run，那一整條沒掃
                              （細長 6×1.5、斜置 45°）→ 覆蓋率 96%
   情況 B：明顯落在裡面     →  1 個 run，正常
                              （斜置 15°）→ 覆蓋率 100%
   情況 C：⚠ 正好貼在邊界上 →  中心線在鋸齒上進進出出
                              （斜置 30°）→ 碎成 22 段
```

**為什麼 30° 特別容易**：光柵化的鋸齒週期和掃描線角度有關。
30° 時 `tan(30°) ≈ 0.577`，每走 1 格 x 就上升 0.577 格 y ——
階梯的週期和取樣點的間距形成一種「拍頻」，
讓中心線在障礙/非障礙之間規律地交替。

★ **重點是：這不代表「30 度不能用」。**
換一個尺寸的房間、換一個 `spacing`、地圖多一格少一格，
發作的角度就完全不同。**任何角度都可能觸發。**

**這也是為什麼修法要處理根因**（讓帶均勻分布在可走區內），
而不是「避開 30 度」或「調 `min_len`」—— 那些都只是把骰子換一顆。
</details>

**Q4. 「用 `scipy.ndimage.label` 做連通性檢查」為什麼被列為 CP 值最高的改進？**

<details>
<summary>參考答案</summary>

**因為它用不到 10 行，同時解決兩個問題。**

```python
from scipy.ndimage import label

lab, n = label(free, structure=np.ones((3,3), bool))
if n > 1 and start is not None:
    sr = int(round((start[1] - oy) / res))
    sc = int(round((start[0] - ox) / res))
    comp = lab[sr, sc]
    if comp > 0:
        unreachable = int((lab > 0).sum() - (lab == comp).sum())
        free = (lab == comp)          # 只規劃機器人到得了的部分
```

**解決的問題：**

**① 缺陷 #4（沒有連通性檢查）**
現在如果安全邊距把通道封死，規劃器毫不知情，
照常規劃「先走 A 房間再走 B 房間」的路徑。

**② 假完成成因三**
`move_base` 到了 B 房間的第一個路點就失敗，
然後**每一個路點都失敗**，被「跳過繼續」全部吞掉，最後顯示「完成」。
使用者完全不知道發生了什麼事。

**改完之後的行為：**
- 規劃只涵蓋機器人**真的到得了**的區域 → 路點全部有效
- 可以回報 `unreachable_area`，網頁上顯示「有 2.3 m² 因通道過窄而無法到達」
- ★ **使用者拿到一個可行動的訊息**（把 `MARGIN` 調小，或把走廊加寬）

**成本**：
- 程式碼：< 10 行
- 效能：`label` 對 384×384 是 C 實作，**< 1 ms**
- 風險：極低（`start` 是 `None` 時退回原行為）

★ **對照缺陷 #1（A* 轉場）**：效益更大，但要 60 行 + 介面調整。
先做便宜的。
</details>

**Q5. L 形房間的路徑長 67.9 m，同面積長方形只要約 40 m。
有人建議「乾脆不要用 PCA，直接讓使用者指定掃描方向」。你怎麼看？**

<details>
<summary>參考答案</summary>

**這個建議對 L 形有幫助，但整體是退步。**

**它能解決什麼**：使用者看得出 L 形的橫支是水平的，
可以手動指定 0°，讓橫支對齊。路徑會縮短。

**但它有四個問題：**

**① L 形有兩支，指定一個角度只能對齊一支。**
指定 0° 對齊橫支，豎支就差 90°。**問題只解決一半。**

**② 使用者不見得知道正確的角度。**
SLAM 的地圖座標軸是機器人開機朝向決定的，房間相對於地圖是斜的。
使用者要在網頁上看圖目測角度 —— 目測誤差 5° 就會讓效率明顯下降。

**③ 失去自動化。**
每換一個場地、甚至每次重新建圖（開機朝向不同）都要重新設定。
這是專案的核心賣點之一。

**④ 沒有解決根本問題。**
根本問題是「**非凸空間不該用單一掃描方向**」，
而不是「PCA 算錯了」。PCA 對 L 形給出 −45° 是**數學上正確**的答案 ——
那確實是這堆點最分散的方向。

★ **正確的方向是「先幾何分區、後求軸」**（19.5）：
用凸分解把 L 形切成兩個矩形，每個矩形各自跑完整的 PCA → 分解 → 掃描。
這樣兩支都對齊，而且**完全自動**。

**折衷的短期做法**（如果時間不夠）：
保留 PCA 作為預設，但在網頁上加一個「手動覆寫掃描角度」的選項，
並顯示 λ₁/λ₂ 讓使用者知道什麼時候該覆寫（λ₁/λ₂ < 2 時）。
★ **自動為主、手動為輔**，而不是把自動拿掉。
</details>
