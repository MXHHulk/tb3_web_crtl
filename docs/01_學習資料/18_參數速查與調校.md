## 18.2 ★ `SPACING`：掃描線間距

```python
# scripts/coverage_planner.py:15
SPACING = 0.18   # 掃描線間距（公尺）；覆蓋寬度 ≈ 0.20 m，留 10% 重疊
```

### 實測（含柱 4×2 場地，`MARGIN=0.10`）

| `SPACING` | run 數 | 覆蓋率 | 路徑總長 |
|---|---|---|---|
| 0.10 | 26 | 100.0% | 64.8 m |
| 0.14 | 19 | 99.5% | 49.3 m |
| **0.18** | **14** | **100.0%** | **37.5 m** |
| 0.22 | 12 | **87.8%** ⚠ | 31.7 m |
| 0.26 | 10 | **80.5%** ⚠ | 27.6 m |
| 0.30 | 8 | **72.6%** ⚠ | 25.3 m |

★ **0.18 和 0.22 之間有一道懸崖：覆蓋率從 100% 掉到 87.8%。**

### 為什麼是懸崖而不是斜坡

★ **因為機器人的覆蓋寬度是 0.20 m**（半徑 0.10 m 的清掃/感測範圍）。

```
   spacing = 0.18 < 0.20                  spacing = 0.22 > 0.20
   ┌────────────────┐                     ┌────────────────┐
   ══════════════════  ← 覆蓋帶 0.20      ══════════════════
     ══════════════════                        ← 0.02 的縫隙 ⚠
   ══════════════════                     ══════════════════
     ↑ 重疊 0.02（10%）                        ← 又一個縫隙
```

**只要 `spacing > 覆蓋寬度`，每兩條線之間就會留下一條永遠掃不到的縫。**
縫的寬度是 `spacing − 0.20`，覆蓋率損失大約是 `(spacing − 0.20) / spacing`：

```
   spacing = 0.22 → 損失 0.02/0.22 = 9.1%   （實測 12.2%，多出的來自邊緣）
   spacing = 0.30 → 損失 0.10/0.30 = 33.3%  （實測 27.4%）
```

### 選 0.18 的理由

- **不能 ≥ 0.20**：直接漏掃（上面的懸崖）
- **也不能剛好 0.20**：定位有誤差、路徑會偏、機器人會歪。
  剛好接觸 = 實際上會漏。
- **0.18 留 10% 重疊**（`(0.20−0.18)/0.20 = 10%`），
  可以吸收 ±1 公分的定位誤差
- **更小（0.10）**：覆蓋率一樣是 100%，但**路徑長度變成 1.7 倍**（64.8 vs 37.5 m）
  → 電池撐不了、時間拖長，沒有任何好處

★ **這是一個典型的「有懸崖的參數」**：往上一步就掉下去，往下走則是純粹的浪費。
最佳值就卡在懸崖邊往回退一點的地方。

### 調校建議

| 情境 | 建議值 | 理由 |
|---|---|---|
| 預設 | 0.18 | 10% 重疊 |
| 定位不準（地毯、打滑） | 0.15 | 重疊 25%，容忍更大誤差 |
| 換 Waffle（覆蓋寬 0.28） | 0.25 | 一樣留 10% |
| 只是要看路徑形狀（demo） | 0.25 | 線少、畫面清爽、跑得快 |
| ⚠ 追求速度 | **不要調大** | 覆蓋率是這個專案的本體 |

## 18.3 ★ `MARGIN`：安全邊距

```python
# scripts/coverage_planner.py:16
MARGIN  = 0.10   # 障礙物安全邊距（公尺） ≈ 機器人半徑（直徑 0.20 m）
```

### 實測（`SPACING=0.18`）

**含柱 4×2：**

| `MARGIN` | 可走面積 | cell | 覆蓋率 | 路徑總長 |
|---|---|---|---|---|
| 0.05 | 7.02 m² | 4 | 96.8% | 38.9 m |
| **0.10** | **6.29 m²** | 4 | **100.0%** | 37.5 m |
| 0.15 | 5.57 m² | 4 | 96.6% | 32.6 m |
| 0.20 | 4.84 m² | 4 | 100.0% | 31.3 m |
| 0.25 | 4.12 m² | 4 | 95.7% | 23.7 m |

**窄通道 0.5 m（雙房間 + 0.5 m 走廊）：**

| `MARGIN` | 可走面積 | 走廊中段剩幾格 | cell |
|---|---|---|---|
| 0.05 | 8.04 m² | — | 5 |
| **0.10** | **7.17 m²** | **147** | 5 |
| 0.20 | 5.49 m² | 63 | 5 |
| 0.25 | 4.67 m² | **21** ⚠ | **2** |

### 觀察一：可走面積線性下降

★ 每加 0.05 m 的邊距，**可走面積少約 0.7~0.9 m²**（約 10%）。

因為膨脹是沿著**所有障礙物的邊界**往內吃，
邊界總長越長（房間越多角落、障礙越多），吃掉的面積越多。

### 觀察二：⚠ 覆蓋率在 96%~100% 之間跳動

★ **這個跳動不是 `MARGIN` 造成的，是第 10 章 10.3 講的「最後一條掃描帶」問題。**

`b_centers` 的最後一項可能落在可走區外（那一條帶完全沒掃），
也可能剛好落在裡面。`MARGIN` 改變了可走區的邊界位置，
就等於在「最後一條帶會不會落空」這件事上擲骰子。

★ **這是一個重要的診斷**：如果調參數時覆蓋率的變化沒有規律，
先懷疑是這個 bug 而不是參數本身的效果。（第 22、23 章詳談。）

### 觀察三：★ 窄通道會被吃掉

0.5 m 的走廊在不同 `MARGIN` 下：

```
   MARGIN=0.10   ├─────────── 0.30 m ───────────┤   舒適
   MARGIN=0.20   ├──── 0.10 m ────┤                 勉強
   MARGIN=0.25   ├ 0.05 m ┤                         ⚠ 只剩 1 格寬
```

**通道剩餘寬度 = 原始寬度 − 2 × MARGIN**

```
   0.5 − 2 × 0.25 = 0.00 m
```

理論上剛好歸零。實測還剩 21 格（1 格寬 × 21 長），
是因為 `binary_dilation` 的邊界剛好差一格。**這是在懸崖邊緣**。

★ 而且 `cell` 數從 5 掉到 **2** —— 走廊變成一條細線之後，
split/merge 的結構整個改變了。

> ⚠ **更危險的情況**：如果 `MARGIN` 再大一點，走廊會**完全消失**，
> 兩個房間變成兩個互不相連的區域。
>
> **但演算法不會發現這件事** —— `plan()` 完全沒有連通性檢查，
> 它會照常規劃出「先走 A 房間、再走 B 房間」的路徑，
> 而 `move_base` 到了 B 房間的第一個路點就會失敗，
> 然後**每一個路點都失敗**（第 13 章的「跳過繼續」讓它全部跳完），
> 最後顯示「完成」。
>
> ★ 這是第 19 章「假完成」的第四種成因。

### 選 0.10 的理由

- Burger 的外接圓半徑約 **0.105 m**（機身 138×178 mm）
- 0.10 ≈ 剛好等於半徑：路點放在這裡，機器人中心站上去時**車身邊緣剛好貼牆**
- ⚠ **其實偏緊**。之所以能運作，是因為 `move_base` 的 costmap 有第二道膨脹層

### 調校建議

| 情境 | 建議值 | 理由 |
|---|---|---|
| 預設 | 0.10 | ≈ 機器人半徑 |
| 場地有窄通道（< 0.6 m） | 0.10 或更小 | 大了會封死 |
| 場地空曠、想更安全 | 0.15 | 半徑 + 5 cm 餘裕 |
| 常擦撞牆面 | 0.15 | 但先檢查是不是 `move_base` 的 costmap 設定問題 |
| 換 Waffle（半徑 0.22 m） | **0.22** | ★ 一定要改，不然會撞 |

★ **`MARGIN` 和 `move_base` 的 `inflation_radius` 應該協調**。
如果 costmap 的膨脹比我們大，就會出現「我們覺得可以的路點，`move_base` 拒絕」
（第 03 章 3.7 的縫隙 ①）。

## 18.5 `TELEOP_TTL` 與前端續傳：必須成組調整

```python
TELEOP_TTL = 0.6      # scripts/map_server.py:58
```
```javascript
holdTimer = setInterval(push, 150);    // web/index.html:455
```

★ **這兩個參數有一個必須維持的關係**：

```
   TELEOP_TTL >= 3 × 續傳間隔
   0.6 >= 3 × 0.15 = 0.45   ✓（實際是 4 倍）
```

| `TTL` | 續傳 | 結果 |
|---|---|---|
| 0.6 | 150 ms | ✅ 容許連續掉 3 個封包 |
| **0.2** | 150 ms | ⚠ 只容許掉 0 個 → Wi-Fi 稍抖就一頓一頓 |
| 0.6 | **500 ms** | ⚠ 只容許掉 0 個 → 同上 |
| **2.0** | 150 ms | ⚠ 斷線後滑行 0.36 m（可能撞牆） |

**斷線滑行距離 = `TELEOP_TTL` × `V_MAX`**

```
   0.6 × 0.18 = 0.11 m    ← 現在
   2.0 × 0.18 = 0.36 m    ← 太遠
```

★ **要調就兩個一起調**，維持 3~5 倍的關係（第 16 章 16.9 Q3）。

## 18.6 其他參數的取捨

### `CROP_PAD = 10`（裁切邊距）

10 格 = 0.5 公尺的留白。

- **調小（0）**：地圖貼著圖片邊緣，機器人走到邊界時圖示會被切一半
- **調大（30）**：圖片變大，傳輸變慢，而且大部分是空白

### 軌跡取樣 `0.1 m` 與上限 `10,000` 點

```python
# scripts/map_server.py:204-207
if dx*dx + dy*dy >= 0.01:   # 每 0.1 m 記一點
    robot_path.append([rx, ry])
    if len(robot_path) > 10000:
        robot_path.pop(0)
```

10,000 點 × 0.1 m = **可以記錄 1 公里的軌跡**。
以 0.18 m/s 計算，大約是 **1.5 小時**的行程 —— 遠超過一顆電池的續航。

- **取樣調小（0.02 m）**：軌跡更平滑，但 JSON 變大 5 倍、繪製變慢
- **上限調小（1000）**：記憶體省一點，但長時間任務的早期軌跡會消失

### 停止檢查間隔 `0.5 s`

```python
if client.wait_for_result(rospy.Duration(0.5)):
```

按下停止到機器人真的停下來的**最大延遲**。

- **調小（0.1 s）**：反應更快，但迴圈每秒醒 10 次去搶 `cov_lock`
- **調大（2 s）**：使用者會覺得按鈕沒反應

0.5 秒是「人類感覺得出來但可以接受」的邊界。

### `wait_for_server(5.0)`

`move_base` 從啟動到能接受目標，通常要 3~10 秒（要載入 5 個 yaml、建 costmap）。

⚠ **如果常常看到「move_base 未啟動（等待 5 秒逾時）」**，
先確認 `move_base` 真的有跑（`rosnode list`），
確認有的話就把這個值調到 15 秒 —— 樹莓派上初始化比較慢。

## 18.7 ★ 調參的一般原則

**① 先分清楚「物理參數」和「觀感參數」**

| 類型 | 例子 | 怎麼調 |
|---|---|---|
| **物理參數** | `MARGIN`（機器人半徑）、`SPACING`（覆蓋寬度）、`V_MAX`（規格） | **由硬體決定**，不是喜好問題 |
| **觀感參數** | `MORPH_ITER`、`CROP_PAD`、軌跡漸層 300 點 | 隨便調，看起來順眼就好 |
| **時序參數** | `TELEOP_TTL`、續傳間隔、停止檢查 | 有**相互關係**，要成組調 |

**② 找出參數的「懸崖」**

`SPACING` 在 0.20 有懸崖（覆蓋寬度），`MARGIN` 在「通道寬度/2」有懸崖。
★ **懸崖的位置由物理決定，不是試出來的** —— 先算，再驗證。

**③ 一次只改一個**

`MARGIN` 的實測顯示，覆蓋率會因為「最後一條帶落在哪」而跳動。
如果同時改兩個參數，你會分不清變化是誰造成的。

**④ 用 `test/coverage_bench.py` 驗證**

```bash
python3 test/coverage_bench.py                 # 全部場地
python3 test/coverage_bench.py --detail L形4x4  # 單一場地的逐帶診斷
```

★ 改參數之後**先跑離線測試**，再上實機。
離線測試 12 種場地只要幾秒，實機跑一次要半小時。

## 18.8 ⑥ 本章重點回顧

1. ★ **`SPACING` 有一道懸崖在 0.20 m（= 覆蓋寬度）**：
   實測 0.18 → 100%，0.22 → **87.8%**。往上一步就漏掃，往下只是浪費路程。
2. **`SPACING = 0.18` 留 10% 重疊**，吸收定位誤差。
   調到 0.10 覆蓋率一樣，但路徑變 1.7 倍。
3. ★ **`MARGIN` 每加 0.05 m，可走面積少約 10%**；
   通道剩餘寬度 = 原寬 − 2×`MARGIN`。0.5 m 的走廊在 `MARGIN=0.25` 只剩 1 格寬。
4. ⚠ **`plan()` 沒有連通性檢查**：邊距把通道封死時，
   它仍會規劃跨區路徑，`move_base` 全部失敗，最後仍顯示「完成」。
5. ⚠ **調 `MARGIN` 時覆蓋率會無規律跳動（96%~100%）**，
   那是「最後一條掃描帶落在哪」的 bug，不是參數的效果。
6. **`MORPH_ITER` 只影響顯示**，和機器人行為完全無關 —— 口試常見陷阱。
7. ★ **`TELEOP_TTL` 必須 ≥ 3 × 前端續傳間隔**，兩者要成組調整；
   斷線滑行距離 = `TTL × V_MAX`。
8. **換機器人型號時，`MARGIN` 和 `SPACING` 都必須改**（Waffle 半徑 0.22 m）。

## 18.9 ⑦ 自我檢核題

**Q1. 為什麼 `SPACING` 從 0.18 調到 0.22，覆蓋率會從 100% 掉到 87.8%？
為什麼是「懸崖」而不是逐漸下降？**

<details>
<summary>參考答案</summary>

因為**機器人的覆蓋寬度是固定的 0.20 m**（半徑 0.10 m）。

- `spacing < 0.20`：相鄰兩條覆蓋帶**重疊**，中間沒有縫 → 覆蓋率 100%
- `spacing > 0.20`：相鄰兩條之間留下一條 `spacing − 0.20` 寬的**永遠掃不到的縫**

```
   spacing=0.18       spacing=0.22
   ══════════         ══════════
     ══════════            ⚠ 縫 0.02
   ══════════         ══════════
```

★ **這是一個「臨界值」而不是「連續函數」**：
在 0.20 以下，多的重疊完全沒有額外好處（只是多跑路）；
一超過 0.20，立刻開始漏。所以在 0.20 這一點上，行為**質變**。

損失比例約 `(spacing − 0.20) / spacing`：
- 0.22 → 9.1%（實測 12.2%，多出的來自邊緣效應）
- 0.30 → 33.3%（實測 27.4%）

**推論**：如果換成覆蓋寬度 0.28 m 的 Waffle，懸崖就移到 0.28，
`SPACING` 應該設 0.25。
</details>

**Q2. 你把 `MARGIN` 從 0.10 調到 0.25，發現覆蓋率反而從 100% 掉到 95.7%，
但可走面積也變小了。這代表演算法變差了嗎？**

<details>
<summary>參考答案</summary>

**不一定，要先弄清楚「覆蓋率」的分母是什麼。**

`test/coverage_bench.py` 的覆蓋率定義是：
**「可走格中心離任一掃描線 ≤ 0.10 m 的比例」**——
分母是**膨脹後的可走格**，不是房間的實際面積。

所以 `MARGIN` 變大之後，分母也跟著變小，兩個數字**不能直接比較**。

★ **真正的問題是：95.7% 這個數字本身代表有 4.3% 的可走區沒被掃到。**

而第 22 章的診斷指出，這個損失幾乎都來自**最後一條掃描帶落在可走區外**
（第 10 章 10.3）。`MARGIN` 改變了可走區的邊界位置，
等於在「最後一條帶會不會落空」上擲骰子 —— 所以數字才會在
96.8 → 100.0 → 96.6 → 100.0 → 95.7 這樣**無規律跳動**。

**結論**：
- 覆蓋率的跳動**不是 `MARGIN` 的效果**，是一個已知 bug 的副作用
- 要評估 `MARGIN` 的真實影響，應該看**可走面積**（7.02 → 4.12 m²，掉了 41%）
  和**窄通道是否還通**

★ **這題的重點是：解讀實驗數據前，先確認指標的定義。**
</details>

**Q3. 場地有一條 0.4 m 寬的走廊。你應該把 `MARGIN` 設多少？會有什麼風險？**

<details>
<summary>參考答案</summary>

**通道剩餘寬度 = 0.4 − 2 × MARGIN**

| MARGIN | 剩餘寬度 | 評價 |
|---|---|---|
| 0.10 | 0.20 m | ✅ 可行，但只有 4 格 |
| 0.15 | 0.10 m | ⚠ 只剩 2 格，很勉強 |
| 0.20 | **0.00 m** | ❌ **完全封死** |

**建議：`MARGIN = 0.10`（維持預設）。**

**風險：**

1. **0.4 m 對 Burger 本身就很窄**。機器人直徑約 0.18~0.21 m，
   通道只剩 0.19~0.22 m 的餘裕，左右各不到 10 公分。
   定位誤差 5 公分就可能擦撞。

2. ⚠ **`move_base` 可能過不去**。它的 costmap 用自己的 `inflation_radius`，
   如果比 0.10 大（`turtlebot3_navigation` 的預設通常是 **0.10~0.15**），
   走廊在它眼中可能已經封死 → 每個路點都 `ABORTED`。

   ★ **這是最危險的情況**：我們的規劃器覺得可以，`move_base` 覺得不行。
   結果是「規劃出漂亮的路徑，但機器人一步都走不了」。

3. ⚠ **如果 `MARGIN` 設太大導致封死，演算法不會告訴你**。
   `plan()` 沒有連通性檢查，它會照常規劃跨區路徑，
   然後每個路點都失敗、被「跳過繼續」吞掉，最後顯示「完成」。

**應該做的驗證：**

```bash
# ① 離線：確認走廊還通
python3 test/coverage_bench.py --detail 窄通道0.5m

# ② 線上：看網頁的「安全邊距」圖層，走廊有沒有被紅色封死
http://<ip>:8080/map_margin.png

# ③ 對照 move_base 的設定
rosparam get /move_base/global_costmap/inflation_layer/inflation_radius
```

★ **③ 特別重要** —— 兩邊的膨脹半徑要協調。
</details>

**Q4. 有人說「把 `MORPH_ITER` 調大一點，機器人會離牆更遠更安全」。這個說法對嗎？**

<details>
<summary>參考答案</summary>

**完全不對。`MORPH_ITER` 對機器人的行為毫無影響。**

```python
# scripts/map_server.py:157-165
# 膨脹地圖（障礙擴大，顯示用）        ← 註解就寫了「顯示用」
gray_d[binary_dilation(obs, kern, MORPH_ITER)] = 0

# 規劃用安全邊距：直接呼叫演算法本身的函式
safe = apply_safety_margin(data, COV_MARGIN, msg.info.resolution)
```

`MORPH_ITER` 只用在產生 `/map_eroded.png` 和 `/map_dilated.png` 這**兩張顯示圖層**。

**真正決定機器人離牆多遠的是 `MARGIN`**（`coverage_planner.py:16`），
它產生的是 `/map_margin.png` 那一層，而且是**同一個函式**餵給 `plan()` 的
（第 07 章 7.3 的「所見即所算」）。

★ **為什麼會有這個誤解**：
兩者膨脹出來的格數碰巧接近（都約 2 格），視覺上很像，網頁上又並列在圖層清單裡。

**怎麼避免誤解**：
- 網頁上的圖層名稱已經寫了「安全邊距（膨脹）」vs「膨脹層」，但還不夠明確
- ★ 更好的做法是把顯示圖層改名成「膨脹層（僅顯示）」

**口試回答的正確版本**：
> 「我們有兩套膨脹。顯示用的是 3×3 核做 2 次，只是為了讓人在畫面上看清楚障礙物的範圍；
> 規劃用的是 `MARGIN = 0.10 m`（對應機器人半徑）換算成 5×5 核做 1 次，
> 這一套才會影響路點的位置。而且網頁上的『安全邊距』圖層呼叫的就是規劃用的那個函式，
> 所以畫面上看到的紅色區域，逐格等於演算法認定不能走的地方。」
</details>

**Q5. 你要把這個專案移植到 TurtleBot3 Waffle（半徑 0.22 m、覆蓋寬 0.28 m、
最高速 0.26 m/s）。哪些參數要改？改成多少？**

<details>
<summary>參考答案</summary>

| 參數 | 現值 | 新值 | 理由 |
|---|---|---|---|
| `MARGIN` | 0.10 | **0.22** | ★ 必改。機器人半徑翻倍，不改會撞 |
| `SPACING` | 0.18 | **0.25** | ★ 必改。覆蓋寬 0.28，留 10% 重疊 → 0.28 × 0.9 = 0.252 |
| `V_MAX` | 0.18 | 0.22 | 規格 0.26，一樣壓到 ~85% |
| `W_MAX` | 1.50 | 1.50 | Waffle 角速度規格也是 1.82，可保持 |
| `drawRobot` 的 0.105 | 0.105 | **0.22** | `web/index.html:391`，圖示大小 |
| launch 的 `model` | burger | **waffle** | `roslaunch ... model:=waffle` |

★ **`model:=waffle` 會自動處理的部分**：
`costmap_common_params_waffle.yaml` 和 `dwa_local_planner_params_waffle.yaml`
會被載入（`start.launch:35, 53`），`TURTLEBOT3_MODEL` 環境變數也會設好。
**`move_base` 那一側不用手動改。**

⚠ **要注意的連鎖影響**：

1. **窄通道會大量被封死**。`MARGIN` 從 0.10 變 0.22，
   通道剩餘寬度少 0.24 m。0.5 m 的走廊只剩 **0.06 m** → 幾乎封死。
   **場地可能要重新設計。**
2. **cell 分解結果會改變**（可走區形狀變了）。
3. **覆蓋率可能下降**（更多區域被邊距吃掉）。

**驗證步驟**：
```python
# 在 test/coverage_bench.py 裡改 MARGIN/SPACING 的引數再跑一次
python3 test/coverage_bench.py
```
先看 12 種場地的覆蓋率和 cell 數有沒有異常，再上實機。

★ **更好的做法**：把 `MARGIN` / `SPACING` 改成 ROS 參數
（像 `port` 那樣用 `rospy.get_param`），在 launch 檔裡依 `model` 設定，
就不用改程式碼了。這是值得做的改進。
</details>
