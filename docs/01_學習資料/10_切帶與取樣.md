## 10.1 ① 問題：一條掃描線上，哪些地方能走？

第 08 章結束時，我們手上有：

```python
center, axis_a, axis_b, eigvals = principal_axes(pts)
proj_a = diffs @ axis_a      # 每個可走格沿長軸的座標
proj_b = diffs @ axis_b      # 每個可走格沿短軸的座標
```

接下來要做兩件事：

```
   ① 切帶：決定要掃幾條線、每條線在哪
   ② 取樣：對每條線找出「哪一段到哪一段可以走」
```

## 10.2 ② 直覺做法（就是 v1 的做法）

```python
# ❌ v1 的寫法
mask = np.abs(proj_b - b) < spacing / 2     # 選出這條帶裡的所有可走格
a_vals = proj_a[mask]
p_start = center + a_vals.min() * axis_a + b * axis_b
p_end   = center + a_vals.max() * axis_a + b * axis_b
```

### ③ 撞牆

第 09 章 9.3 詳細講過，這裡快速回顧：

```
   帶內的可走格：  ●●●●●●        ●●●●●●
                              ████
                   ↑         障礙        ↑
                a最小                  a最大

   min/max 畫出來的線： ●━━━━━━━━━━━━━━━●   直接穿過障礙
```

★ **問題的本質**：`mask` 選出來的是一個**無序的點集**。
從無序點集只能取到 `min` 和 `max`，「中間有沒有斷開」這個資訊在取 mask 的那一刻就消失了。

**修法的方向**：**人為造出順序** —— 沿著線從一端走到另一端，逐點檢查。

## 10.3 ④ 現在的做法（一）：切帶

```python
# scripts/coverage_planner.py:222-224
b_min, b_max = proj_b.min(), proj_b.max()
n_bands   = int(np.floor((b_max - b_min) / spacing)) + 1
b_centers = b_min + spacing / 2 + spacing * np.arange(max(1, n_bands))
```

### 用一個具體例子走一遍

假設房間是 4m × 2m 的長方形（軸對齊），重心在 (2, 0)，
PCA 算出 `axis_a = (1,0)`、`axis_b = (0,1)`。為方便，把座標原點移到重心：

```

        ↑
```

- `proj_b` 的範圍：−1.0 ~ +1.0

**算帶數**：

```python
b_centers = -1.0 + 0.09 + 0.18 * [0, 1, 2, ..., 11]
```

### 三個細節

**① 為什麼要 `+ spacing/2`？**

讓第一條線落在**帶的中央**而不是邊緣。
如果從 `b_min` 開始，第一條線會貼著牆走（那裡通常已經被安全邊距吃掉了）。

**② 「帶」其實只用中心線**

雖然叫「掃描帶」，程式從頭到尾**只檢查中心線這一條**，不檢查整條帶的寬度。
「帶」只是一個概念，用來說明「這條線負責覆蓋左右各 `spacing/2` 的範圍」。

**③ ⚠ 最後一條帶可能落在可走區之外**

```python
b_centers 的最後一項 = b_min + spacing/2 + spacing × (n_bands - 1)
```

以上例：`k=11` 的 `b = 1.07`，但 `b_max = 1.0` —— **超出範圍了**。

這條帶取樣後 `ok` 全是 False，不產生任何 run，看起來沒事。

**但第 22 章的實測顯示這是一個真實缺陷**：

- **細長 6×1.5 的場地**：最後一條帶落在可走區外 → 那一整條（最寬 0.18 m）
  完全沒被掃到 → 覆蓋率只有 **96.3%**
- **斜置 30° 的場地**：最後一條帶正好落在**光柵化後的鋸齒邊界上**
  → 碎成 22 條 run → **23 個 cell**、30 段穿牆轉場

（第 22 章 22.5 有完整診斷，第 23 章 23.4 有修法建議。）

## 10.4 ④ 現在的做法（二）：沿中心線取樣

### 全部程式碼

```python
# scripts/coverage_planner.py:83-109
H, W = free.shape
step = res / 8.0                                    # ① 取樣步長 ≈6 mm
a_lo, a_hi = a_range
n = int(np.ceil((a_hi - a_lo) / step)) + 1
a_s = a_lo + step * np.arange(n)                    # ② 一整排 a 值

runs = []
for k, b in enumerate(b_centers):
    pl = center + a_s[:, None] * axis_a + b * axis_b # ③ 整條線的世界座標
    c = np.round((pl[:, 0] - ox) / res).astype(int)  # ④ → 格子 col
    r = np.round((pl[:, 1] - oy) / res).astype(int)  #    → 格子 row
    inb = (r >= 0) & (r < H) & (c >= 0) & (c < W)    # ⑤ 界內防呆
    ok = np.zeros(n, dtype=bool)
    ok[inb] = free[r[inb], c[inb]]                   # ⑥ 查表

    for i0, i1 in _true_runs(ok):                    # ⑦ 切成連續區塊
        if a_s[i1] - a_s[i0] < min_len:              # ⑧ 濾掉碎片
            continue
        runs.append({'band': k, 'a0': a_s[i0], 'a1': a_s[i1],
                     'p0': center + a_s[i0] * axis_a + b * axis_b,
                     'p1': center + a_s[i1] * axis_a + b * axis_b})
```

### ① `step = res / 8.0`

`res = 0.05` → `step = 0.00625 m ≈ 6 mm`。

第 09 章 9.5 講過：`res/2` 會讓斜線從障礙格的**角落**跨過去，漏掉 11 mm 的切角。

```
   障礙格：      ┌────┐
                 │████│
                 └────┘
   res/2 取樣：●        ●     兩點都在障礙外，但線段切過角
                ╲    ╱
                 ╲  ╱
   res/8 取樣：●●●●●●●●●     密到一定會踩到障礙格
```

程式碼裡把這個推導完整寫進註解（`coverage_planner.py:84-87`），
連被否決的「四鄰格全可走」方案和它的代價（覆蓋率 99%→89%）都記錄了。

### ② `a_s`：一整排要檢查的 a 座標

```python
n = int(np.ceil((a_hi - a_lo) / step)) + 1
a_s = a_lo + step * np.arange(n)
```

上例中 a 的範圍是 4 公尺，步長 6.25 mm → `n = 641` 個取樣點。

★ **`np.arange` 一次生出整排**，不是 Python 迴圈。後面所有運算都是向量化的。

### ③ `pl = center + a_s[:, None] * axis_a + b * axis_b`

這一行把 641 個 `(a, b)` 座標一次換成 641 個世界座標 `(x, y)`。

**`a_s[:, None]` 是什麼？** 它把形狀 `(641,)` 的一維陣列變成 `(641, 1)` 的二維：

```
   a_s          形狀 (641,)     [a0, a1, a2, ...]
   a_s[:, None] 形狀 (641, 1)   [[a0], [a1], [a2], ...]
   axis_a       形狀 (2,)       [ax, ay]

   a_s[:, None] * axis_a   →   形狀 (641, 2)
                               [[a0*ax, a0*ay],
                                [a1*ax, a1*ay], ...]
```

這叫 **numpy 廣播（broadcasting）**：形狀不同的陣列自動對齊後逐元素運算。
效果等同於：

```python
# 等價但慢 100 倍的寫法
pl = np.array([center + a * axis_a + b * axis_b for a in a_s])
```

### ④⑤⑥ 查表：世界座標 → 格子 → 能不能走

```python
c = np.round((pl[:, 0] - ox) / res).astype(int)     # 世界 x → col
r = np.round((pl[:, 1] - oy) / res).astype(int)     # 世界 y → row
inb = (r >= 0) & (r < H) & (c >= 0) & (c < W)       # 哪些在地圖範圍內
ok = np.zeros(n, dtype=bool)                        # 預設全部「不能走」
ok[inb] = free[r[inb], c[inb]]                      # 界內的才查表
```

★ **`inb` 防呆為什麼必要**：`a_range` 是**整個可走區**沿長軸的範圍，
而不同的帶在這個範圍上的實際長度不同。
斜置的房間更明顯 —— 靠近角落的帶，中心線大半在房間外面。

如果不擋，`free[r, c]` 會用負數索引（Python 會從尾巴繞回去，**不會報錯**，
但拿到完全錯誤的格子）或直接 `IndexError`。

★ **`ok` 預設 `np.zeros`（全 False）**：界外自動是「不能走」，語意正確。

### ⑦ `_true_runs`：把布林陣列切成連續區塊

```python
# scripts/coverage_planner.py:57-68
def _true_runs(flags):
    """把布林序列切成連續 True 的區塊，回傳 [(起始索引, 結束索引), ...]（含端點）。"""
    out, s = [], None
    for i, v in enumerate(flags):
        if v and s is None:          # False → True：區塊開始
            s = i
        elif not v and s is not None:  # True → False：區塊結束
            out.append((s, i - 1))
            s = None
    if s is not None:                # ★ 收尾：以 True 結束的情況
        out.append((s, len(flags) - 1))
    return out
```

```python
_true_runs([F,F,T,T,T,F,F,T,T]) → [(2, 4), (7, 8)]
                ↑─────↑     ↑─↑
```

★ **最後那個 `if s is not None` 很容易漏**。
如果陣列以 True 結尾（掃描線一路走到房間邊界），沒有這三行的話最後一段會整個消失。

> 💡 這是 Python 迴圈（不是向量化的）。可以用 `np.diff` 向量化，但：
> 1. 每條線只跑一次，總共 12 次，不是效能瓶頸
> 2. 這個寫法一眼就看懂，向量化版本要想三分鐘
>
> **不是所有東西都值得向量化。** 熱點才最佳化。

### ⑧ `min_len` 濾掉碎片

```python
if a_s[i1] - a_s[i0] < min_len:       # 太短的碎片不值得跑一趟
    continue
```

呼叫時傳的是 `min_len=res`（`coverage_planner.py:227`），也就是 **0.05 m**。

意思是「短於一格的區間直接丟掉」—— 專程跑一趟去掃 5 公分不划算，
而且那麼短的區間通常是光柵化的雜訊。

> ⚠ **第 22 章的實測顯示這道門檻太鬆**。
> 斜置 30° 場地的最外側帶碎成 22 段，長度介於 **7~28 cm**，
> 全部通過了 5 cm 的門檻，每一段都變成一個獨立的 cell。
> 修法建議見第 23 章 23.4。

## 10.5 ★ run 是什麼

```python
{'band': 5,                                    # 屬於第幾條掃描帶
 'a0': -2.0, 'a1': -0.5,                       # 沿長軸的起訖座標
 'p0': array([0.0, 2.0]),                      # 起點的世界座標
 'p1': array([1.5, 2.0])}                      # 終點的世界座標
```

> **run 的白話定義：一條掃描線被障礙物切開之後，剩下的其中一段可以連續走完的線段。**

**為什麼同時存 `(a0,a1)` 和 `(p0,p1)`？** 因為兩者用途不同：

| 欄位 | 用在哪 |
|---|---|
| `a0`, `a1` | **判斷連通性**（`_link_runs` 比較投影是否重疊）、算長度 |
| `p0`, `p1` | **產生路點**（`_cell_waypoints` 直接輸出這兩個座標） |

先算好存起來，後面就不用重複做座標轉換。

## 10.6 ⑤ 設計決策

| 決策 | 選了 | 否決了 | 理由 |
|---|---|---|---|
| 怎麼找可走區段 | 沿中心線參數化取樣 | ① 帶內取 `proj_a` 極值<br>② `scipy.ndimage.label` 連通標記 | ① 穿牆（v1）<br>② 連通≠直線可走（第 09 章） |

## 10.7 ⑥ 本章重點回顧

1. **切帶**：`n_bands = floor(範圍/spacing) + 1`，
   `b_centers` 從 `b_min + spacing/2` 開始每 `spacing` 一條。
   ⚠ **最後一條可能落在可走區外**（第 22 章證明這會造成覆蓋率損失與碎裂）。
2. **「帶」其實只用中心線**，程式從不檢查帶的寬度。
3. ★ **v1 的錯在於用「無序點集的 min/max」**，順序資訊在取 mask 時就沒了。
   修法是**沿線參數化取樣，人為造出順序**。
4. **取樣步長 `res/8` ≈ 6 mm** 是實測出來的（`res/2` 漏 11 mm 切角）。
5. **`a_s[:, None] * axis_a` 是 numpy 廣播**，一次把 641 個點換算完，
   比 Python 迴圈快兩個數量級。
6. **`inb` 界外防呆必要**：斜置房間的帶，中心線大半在房間外；
   負索引在 Python 不會報錯但會拿到錯誤的格子。
7. ★ **run = 一條掃描線被切開後的一段可連續走完的線段**，
   同時存 `(a0,a1)`（判連通用）和 `(p0,p1)`（產路點用）。
8. ★ **run 數量的變化位置 = 臨界點**，這是第 11 章的起點。

## 10.8 ⑦ 自我檢核題

**Q1. 為什麼不能用「這條帶裡的所有可走格」直接取 `proj_a` 的最小值和最大值當線段兩端？**

<details>
<summary>參考答案</summary>

因為 `mask` 選出來的是一個**無序的點集**，
「這些點沿線排起來中間有沒有斷開」的資訊在取 mask 的那一刻就消失了。

```
   帶內可走格：  ●●●●●●        ●●●●●●
                            ████
   min ────────────────────────────── max
                     ↑ 直線穿過障礙
```

實測（第 09 章）：5 條掃描線**全部**橫跨障礙物，
最嚴重的一條 75% 長度在障礙物內，**有效覆蓋率 0%**。

還有第二個缺陷：`a_vals.min()` 那一格的實際 b 座標可能偏離中心線最多 `spacing/2` = 9 cm，
把它硬拉到中心線上，路點可能就落進牆裡了 —— 傾斜 25° 時 8/10 路點違反安全邊距。

**修法**：沿線參數化取樣，人為造出順序，再用 `_true_runs` 找連續段。
</details>

**Q2. `ok = np.zeros(n, dtype=bool)` 然後 `ok[inb] = free[r[inb], c[inb]]`。
為什麼要先建一個全 False 的陣列，而不是直接 `ok = free[r, c]`？**

<details>
<summary>參考答案</summary>

因為 `r` 和 `c` 裡面**可能有超出地圖範圍的索引**。

`a_range` 是整個可走區沿長軸的範圍，但不同的帶在這個範圍上的實際長度不同。
斜置房間特別明顯：靠近角落的帶，中心線有一大半在房間外，
甚至在地圖陣列的範圍外。

直接 `free[r, c]` 的後果：
- **索引 ≥ H 或 W**：拋 `IndexError`，整個規劃崩潰
- ⚠ **索引為負**：Python **不會報錯**，`free[-3, -5]` 會從陣列尾巴繞回去，
  拿到地圖另一邊某個完全無關的格子 —— 這是最惡劣的情況，
  會產生「憑空出現的掃描線」而且完全沒有錯誤訊息

先建全 False 陣列的語意是：**界外一律視為「不能走」**，這是正確的預設。
只有 `inb` 為 True 的位置才真的去查表。
</details>

**Q3. `_true_runs` 最後的 `if s is not None: out.append((s, len(flags)-1))`
在處理什麼情況？拿掉會怎樣？**

<details>
<summary>參考答案</summary>

處理「**布林陣列以 True 結尾**」的情況。

主迴圈只在遇到 `True → False` 的轉折時才收尾一個區塊。
如果陣列一路 True 到最後一個元素，**永遠不會遇到那個轉折**，`s` 就一直是開著的。

```python
_true_runs([F, F, T, T, T])
#                 └───────┘  這一段沒有結束的 False
```

**拿掉的後果**：這一段整個消失。

**什麼時候會發生**：掃描線一路走到 `a_range` 的邊界都還在可走區內 ——
也就是**掃描線最長的那些帶**。這些正好是最重要的帶。

症狀會是「某些掃描線莫名其妙短了一截，或整條不見」，
而且只在某些角度的房間發生（`a_range` 剛好貼齊可走區的時候），
極難重現。
</details>

**Q4. 假設你把 `min_len` 從 `res`（0.05 m）改成 `spacing`（0.18 m），
第 22 章的「斜置 30°」場地會有什麼變化？有什麼副作用？**

<details>
<summary>參考答案</summary>

**變化**：斜置 30° 最外側那條帶碎出的 22 段長度是 **7~28 cm**。
提高門檻到 0.18 m 之後，長度 < 18 cm 的會被濾掉。
從診斷輸出看，22 段裡大約有 15 段落在 7~17 cm 區間 →
會剩下 7 段左右，cell 數從 **23 降到約 8**，穿牆轉場也會大幅減少。

**副作用（要小心）**：

1. **真實的短通道會被誤刪**。想像一個 15 cm 寬的門縫或壁龕 ——
   它產生的 run 長度可能就是 15 cm，會被一起濾掉，那塊區域完全不覆蓋。
2. **含柱場地的邊緣 run 可能受影響**：障礙物旁邊剩下的窄條也可能短於 0.18 m。
3. **覆蓋率會下降**（濾掉的區域不再被掃）。

**更好的修法**（第 23 章 23.4 討論）：
不是調高全域門檻，而是**針對根因處理** ——
問題出在「最後一條帶貼著鋸齒邊界」，
所以應該讓 `b_centers` 的頭尾帶往內縮，或改用
`n_bands = round((b_max-b_min)/spacing)` 讓帶均勻分布在可走區內。
</details>

**Q5. `a_s[:, None] * axis_a` 和寫成 Python 迴圈
`[a * axis_a for a in a_s]` 效果一樣。為什麼要用前者？**

<details>
<summary>參考答案</summary>

**效能**。

- `a_s` 有 641 個元素，×12 條帶 = **7,692 次**運算
- Python 迴圈每次都要：解譯位元組碼、建立 numpy 純量物件、做函式呼叫
- numpy 廣播是**一次 C 層級的批次運算**，沒有 Python 解譯開銷

實測差距大約 **50~100 倍**。

規劃總耗時是 **1.3 ms**（300×150 場景，開發日志記錄）。
如果全部改成 Python 迴圈，會變成 100 ms 以上 ——
使用者按下「開始執行」會有明顯的延遲感，而且會多佔 Flask 執行緒。

★ **但注意 `_true_runs` 就刻意保留 Python 迴圈**，因為它只跑 12 次（每條帶一次），
不是熱點，可讀性比速度重要。

**判準：先量測，只最佳化熱點。** 這裡的熱點是「每個取樣點都要做的座標轉換」
（7,692 次），不是「每條帶做一次的區段切分」（12 次）。
</details>
