> 本章是整份講義的地圖。讀完你會知道：這個專案在做什麼、講義怎麼編排、
> 依你的目的該從哪一章切入。**建議先完整讀完本章再往下走。**

## 0.1 這個專案一句話

> **讓一台 TurtleBot3 自己把一個未知的房間走遍，過程中即時建圖，
> 而且我可以用手機或筆電開網頁看它現在在哪、規劃了什麼路徑、走到第幾步。**

拆開來看，這句話裡面藏了五件不同層次的事：

| # | 要做的事 | 難在哪 | 對應章節 |
|---|---------|--------|---------|
| 1 | 知道房間長什麼樣子 | 機器人一開始不知道地圖，要邊走邊建 | 第 02 章 |
| 2 | 知道自己在哪 | 輪子會打滑，純靠里程計會漂移 | 第 02 章 |
| 3 | 算出「走遍」的路線 | 這是本專案的演算法核心 | 第 08~12 章 |
| 4 | 真的走過去而且不撞牆 | 路線是理想直線，現實有動態障礙 | 第 03、13 章 |
| 5 | 即時顯示在網頁上 | ROS 在機器人上，瀏覽器在手機上 | 第 14~16 章 |

「走遍一個空間」這個問題在學術上叫 **CCPP（Complete Coverage Path Planning，完全覆蓋路徑規劃）**，
掃地機器人、農用噴藥無人機、船體除鏽機器人做的都是同一件事。

本專案採用的是最經典的 **牛耕式（Boustrophedon）** 解法 —— 名字來自古希臘文
「牛耕田的方式」，也就是來回蛇行：

```
  ────────────────────→
                      │
  ←────────────────────
  │
  ────────────────────→
```

## 0.2 這份講義的定位

**假設讀者是完全新手**：會基本 Python（看得懂 `for`、`def`、list、dict），
但不需要懂 ROS、不需要懂 SLAM、不需要懂 numpy 的向量化寫法。
每個術語第一次出現時都會解釋。

**這不是 API 文件，是「設計思考的重演」。**
市面上大多數專案文件只告訴你「現在的程式長怎樣」，
這份講義要多回答一件事：**「為什麼會長成這樣？」**

所以除了逐段講解程式碼，還有三個專門講設計歷程的章節：

- **第 04 章**：從一句話需求，怎麼推導出要切成哪幾個模組
- **第 05 章**：模組之間的介面怎麼定，哪些設計被否決了、為什麼
- **第 09 章**：覆蓋演算法從 v0 到 v3 的四個版本，每一版壞在哪、怎麼修

---

## 0.3 每章的固定編排（七段式）

除了背景知識章（01~03）之外，每一章都用同樣的七段結構：

```
① 本章要解決什麼問題        ← 先講問題，不要一上來就看程式
② 如果從零開始，你會怎麼寫  ← 最直覺、最笨的做法
③ 直覺做法會撞到什麼牆      ← 具體的失敗現象
④ 現在的做法                ← 程式碼對照（附可點擊行號）+ ASCII 圖解
⑤ 設計決策：為什麼不那樣做  ← 被否決的替代方案與理由
⑥ 本章重點回顧              ← 5 條以內的濃縮
⑦ 自我檢核題                ← 3~5 題問答，附答案
```

背景知識章（01~03）因為講的是外部知識、沒有「我們的設計決策」，
改用比較簡單的四段：概念 → 為什麼需要 → 本專案怎麼用 → 重點回顧 + 檢核題。

## 0.11 自我檢核題

**Q1. 「完全覆蓋路徑規劃」和「一般路徑規劃」差在哪？**

<details>
<summary>參考答案</summary>

一般路徑規劃（例如 A*、Dijkstra）是**點對點**問題：給起點和終點，找一條最短且不撞牆的路。

完全覆蓋路徑規劃是**面**問題：不指定終點，要求機器人的清掃/感測範圍**掃過整個可行走區域**，
而且希望總路徑長度盡量短、重複走過的部分盡量少。

兩者常常搭配使用：本專案用 CCPP 算出一串路點，
再交給 `move_base`（內含點對點規劃）一段一段走過去。
</details>

**Q2. 為什麼這個專案需要 SLAM？如果房間地圖事先就有了呢？**

<details>
<summary>參考答案</summary>

SLAM（Simultaneous Localization And Mapping）同時解決兩件事：**建地圖**和**知道自己在地圖上哪裡**。

即使地圖事先就有，第二件事仍然必要 —— 機器人靠輪子編碼器推算位置（里程計）會隨時間累積誤差，
走個幾分鐘就可能偏差幾十公分，覆蓋路徑會整個歪掉。
所以就算有現成地圖，還是需要定位（此時用 AMCL 之類的純定位模組即可，不需完整 SLAM）。

本專案選擇每次都重新建圖，是因為情境設定為「未知房間」，
而且 gmapping 一次把建圖和定位都解決了，架構最簡單。
</details>

**Q3. 看 0.7 的檔案地圖，`coverage_planner.py` 為什麼要標註「零 ROS 依賴」？這有什麼好處？**

<details>
<summary>參考答案</summary>

因為它 `import` 的東西只有 `numpy` 和 `scipy`，完全沒有 `rospy`。好處有三個：

1. **可測試**：不用啟動 ROS、不用有實體機器人，直接寫個 Python 腳本餵它一個 numpy 陣列就能跑
   —— 第 21~23 章的所有實測數據就是這樣來的。
2. **可重用**：`map_server.py` 和 `test/boustrophedon.py` 兩個地方都用它，不會有兩份會走鐘的複製品。
3. **職責清楚**：演算法只管「給我可走格，還你路點」，不需要知道 ROS、地圖從哪來、路點要給誰。

詳細推導在第 05 章。
</details>

**Q4. 看 0.8 的資料流圖，`/cmd_vel`（速度指令）有幾個可能的來源？這會造成什麼問題？**

<details>
<summary>參考答案</summary>

兩個：**`move_base`**（覆蓋執行時）和 **`map_server.py` 的手動遙控**。

問題是：如果兩者同時發指令，機器人會收到互相矛盾的速度，行為變得不可預測（時走時停、方向亂跳）。

本專案的解法是**模式互斥**——用 `cov_status['state']` 當單一真相來源，
只要狀態是 `running` 就拒絕所有手動遙控請求。詳見第 16 章。
</details>
