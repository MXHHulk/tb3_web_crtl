# 第 17 章　併發與執行緒安全

> **本章目標**：把 `map_server.py` 裡的**六條執行緒**和**五把鎖**講清楚。
>
> 這一章講的問題有一個共同特徵：**出錯時不會有錯誤訊息，只會偶爾行為怪異**。
> 這也是為什麼它值得一整章。

---

## 17.1 ① 問題：一個行程裡有六件事同時在跑

第 04 章決定把地圖處理、HTTP、任務執行、遙控、SLAM 管理全部放在一個節點裡。
代價就是這些東西**真的會同時執行**。

### 六條執行緒

| # | 執行緒 | 誰建立的 | 頻率 | 做什麼 |
|---|---|---|---|---|
| 1 | **主執行緒** | Python | — | `rospy.spin()`，什麼都不做只是不結束 |
| 2 | **ROS 回呼執行緒** | `rospy` | 事件驅動 | `map_callback` / `odom_callback` / `scan_callback` |
| 3 | **ROS Timer** | `rospy.Timer` | **10 Hz** | `teleop_tick` |
| 4 | **TF Listener** | `tf2_ros` | 背景 | 持續收 `/tf` 填進 `tf_buffer` |
| 5 | **Flask 執行緒池** | Flask（`threaded=True`） | 每個請求一條 | 12 條路由 |
| 6 | **`run_coverage`** | `threading.Thread` | 一次性，跑 30 分鐘 | 送 Action 目標 |

```python
# scripts/map_server.py:603-604, 606-610, 618, 626-630
tf_buffer = tf2_ros.Buffer()
tf2_ros.TransformListener(tf_buffer)                      # ← 執行緒 4

cmd_pub = rospy.Publisher('/cmd_vel', Twist, queue_size=1)
rospy.Subscriber('/map',  OccupancyGrid, map_callback,  queue_size=1)   # ← 執行緒 2
rospy.Subscriber('/odom', Odometry,      odom_callback, queue_size=10)
rospy.Subscriber('/scan', LaserScan,     scan_callback, queue_size=1)

rospy.Timer(rospy.Duration(0.1), teleop_tick)             # ← 執行緒 3

threading.Thread(                                          # ← 執行緒 5
    target=lambda: app.run(host='0.0.0.0', port=port, threaded=True, use_reloader=False),
    daemon=True,
).start()
rospy.spin()                                               # ← 執行緒 1
```

```python
# scripts/map_server.py:496
threading.Thread(target=run_coverage, daemon=True).start()  # ← 執行緒 6
```

★ **注意 `app.run` 被丟到背景執行緒，`rospy.spin()` 留在主執行緒。**
第 04 章講過：兩個無限迴圈，一支程式的主執行緒只能給一個。

★ **`threaded=True`** 讓 Flask 每個請求開一條執行緒。
沒有它的話，`/coverage/start`（規劃要 200 ms）會擋住同時進來的 `/map.png`。

## 17.2 ② 直覺做法：全域變數，不加鎖

```python
# ❌
map_png = None

def map_callback(msg):
    global map_png
    map_png = to_png(...)          # 寫

@app.route('/map.png')
def get_map():
    return map_png                  # 讀
```

「Python 有 GIL，應該不會有問題吧？」

### ③ 撞牆：GIL 保護不了你

★ **GIL（全域直譯器鎖）只保證「單一位元組碼指令」是原子的**，
不保證「一段邏輯」是原子的。

**具體會出什麼事：**

**① 讀到不一致的組合**

```python
# 執行緒 A（map_callback）              執行緒 B（/coverage/status）
map_png  = 新圖                    ─→
                                       meta = map_meta      ← 舊的
map_meta = 新的 meta               ─→
                                       png  = map_png       ← 新的
```

結果：**圖是新的（裁切範圍變了），meta 是舊的（`c0`/`r0` 是舊值）**
→ 路徑整體偏移幾十個像素。

**② 讀到寫了一半的清單**

```python
# 執行緒 A                      執行緒 B
robot_path.append(p1)      ─→
                               path = robot_path      # 引用，不是複製
robot_path.append(p2)      ─→
robot_path.pop(0)          ─→
                               for p in path: ...     # ⚠ RuntimeError:
                                                      #   list changed size during iteration
```

**③ 檢查與動作之間被插隊（TOCTOU）**

```python
# ❌ 沒有鎖
if cov_status['state'] != 'running':      # 檢查
    cov_status['state'] = 'running'       # ← 兩個請求可能都通過檢查
    start_thread()                        # → 開出兩個 run_coverage 執行緒
```

★ **最惡劣的是：這些問題可能跑一百次才發生一次**，
而且**重跑就好了**。你在展示的時候遇到一次，回去怎麼查都查不出來。

## 17.3 ④ 現在的做法：五把鎖 + 兩條鐵律

### 五把鎖與它們保護的東西

```python
# scripts/map_server.py:62-90
map_lock = threading.Lock()
map_png = map_eroded = map_dilated = map_margin = None
map_meta = {}   # resolution, origin_x/y, r0, c0, crop_h
map_data = {}   # data(np array), h, w, frame_id  ← 供覆蓋規劃用

robot_lock = threading.Lock()
robot_pos  = {'x': None, 'y': None}   # 世界座標
robot_path = []                       # [[wx, wy], ...] 行走軌跡

cov_lock   = threading.Lock()
cov_status = {'state': 'idle', 'done': 0, 'total': 0, 'msg': ''}
cov_path   = []   # [(wx, wy), ...] 全部路點，世界座標
cov_cells  = []   # [[(wx, wy), ...], ...] 每個 cell 的路點
cov_info   = {}   # n_runs / n_cells / n_critical / axis_deg / ratio

scan_lock = threading.Lock()
scan_msg  = None   # 最新一筆 LaserScan
tf_buffer = None   # tf2 緩衝（map ← 雷射座標查詢用）

teleop_lock = threading.Lock()
teleop_cmd  = {'v': 0.0, 'w': 0.0, 't': -1e9}
cmd_pub     = None

slam_lock = threading.Lock()
slam_proc = None
slam_cfg  = {'manage': True, 'method': 'gmapping'}
```

★ **注意排版**：每把鎖的宣告**緊接著它保護的變數**，中間空一行分組。

> 💡 **這個排版本身就是文件。** 看到 `map_lock` 下面那四個變數，
> 就知道「動這些要拿 `map_lock`」。
> 如果全部鎖宣告在一起、全部變數宣告在一起，就沒有人知道哪把鎖管哪個。

### 完整對照表

| 鎖 | 保護 | 寫入者 | 讀取者 |
|---|---|---|---|
| `map_lock` | 4 張 PNG、`map_meta`、`map_data` | `map_callback`、`slam_restart` | 4 條圖片路由、`/robot_state`、`/scan`、`/coverage/start`、`/coverage/status` |
| `robot_lock` | `robot_pos`、`robot_path` | `odom_callback`、`/coverage/start`、`slam_restart` | `/robot_state`、`/coverage/start` |
| `cov_lock` | `cov_status`、`cov_path`、`cov_cells`、`cov_info` | `/coverage/start\|stop`、`run_coverage`、`slam_restart` | `manual_allowed`、`odom_callback`、`/coverage/status`、`run_coverage` |
| `scan_lock` | `scan_msg` | `scan_callback` | `/scan` |
| `teleop_lock` | `teleop_cmd` | `/teleop`、`teleop_halt` | `teleop_tick` |
| `slam_lock` | `slam_proc` | `slam_restart` | `slam_restart` |

（`tf_buffer` 由 `tf2_ros` 自己保證執行緒安全，不需要我們的鎖。）

### ★ 鐵律一：鎖裡面只做「交換」，不做「計算」

```python
# scripts/map_server.py:142-186（map_callback，簡化）

# ── 鎖外：所有計算 ──────────────────────
data  = np.array(msg.data, ...).reshape((h, w)).astype(np.int16)
gray  = ...                                    # 灰階
gray_e = ...  binary_erosion(...)              # 形態學 ×3
gray_d = ...  binary_dilation(...)
safe   = apply_safety_margin(...)
r0, r1, c0, c1 = _crop(known, h, w)

# ── 鎖內：只有賦值 ──────────────────────
with map_lock:
    map_png     = _to_png(gray[r0:r1, c0:c1])       # PNG 編碼…
    map_eroded  = _to_png(gray_e[r0:r1, c0:c1])
    map_dilated = _to_png(gray_d[r0:r1, c0:c1])
    map_margin  = _to_png(gray_m[r0:r1, c0:c1])
    map_meta = dict(...)
    map_data = dict(...)
```

> ⚠ 嚴格說，`_to_png` 四次編碼**是在鎖裡面**的（`map_server.py:173-176`），
> 那是幾毫秒的工作。更嚴謹的寫法是先編碼到區域變數，再一次賦值。
> 目前這樣的實際影響是：Flask 讀圖時偶爾會等幾毫秒 —— 可接受但不完美。

**為什麼這條鐵律重要**：鎖持有的時間直接決定其他執行緒被阻塞的時間。
形態學 + 裁切大約幾十毫秒，如果放進鎖裡，
前端每秒 4 次圖片請求就會有 4 次幾十毫秒的卡頓。

### ★ 鐵律二：讀取時先「複製」再用

```python
# scripts/map_server.py:423-424
with map_lock:  meta = dict(map_meta)      # ★ dict(...) 是複製
with scan_lock: msg = scan_msg
# 鎖已放開，後面的 360 次三角函數完全不持鎖
```

```python
# scripts/map_server.py:402-403
with map_lock:   meta = dict(map_meta)
with robot_lock: pos  = dict(robot_pos); path_w = list(robot_path)   # ★ list(...) 是複製
```

```python
# scripts/map_server.py:300-302
with cov_lock:
    path = list(cov_path)                   # ★ 複製整條路徑
    fid  = map_data.get('frame_id', 'map')
# 之後 30 分鐘的迴圈用本地的 path，完全不持鎖
```

★ **`dict(x)` 和 `list(x)` 是淺複製**：
- 新的容器物件（別人再怎麼 append/pop 都不影響我）
- 但裡面的元素還是同一批物件

對本專案來說夠了，因為裡面裝的是**不可變物件**（float、str、tuple、bytes）。

⚠ **唯一的例外是 `map_data['data']`（numpy 陣列，可變）**：

```python
# scripts/map_server.py:460-461
with map_lock:
    meta = dict(map_meta)
    raw  = dict(map_data)          # ← raw['data'] 和原本是同一個 numpy 陣列
```

這裡是安全的，因為 `map_callback` **每次都建一個新陣列**再重新綁定 `map_data`
（`map_server.py:181-185`），從不原地修改舊陣列。
但這是一個**隱含的約定**（第 13 章 13.9 Q5 討論過）。

### ★ 鐵律三：不要巢狀持鎖（避免死鎖）

```python
# ✅ 現在的寫法（map_server.py:402-403）
with map_lock:   meta = dict(map_meta)
with robot_lock: pos  = dict(robot_pos)

# ❌ 危險的寫法
with map_lock:
    with robot_lock:      # ← 如果別處是 robot_lock → map_lock 的順序，就會死鎖
        ...
```

**死鎖的機制**：

```
   執行緒 A: 拿到 map_lock，等 robot_lock
   執行緒 B: 拿到 robot_lock，等 map_lock
   → 兩邊永遠等下去，整個節點凍結（而且不會有任何錯誤訊息）
```

**代價**：`meta` 和 `pos` 可能來自不同時刻（第 14 章 14.7 ①）。
實務上因為 `/map` 更新慢，看不出差別。

**唯一的例外**：

```python
# scripts/map_server.py:565-579（slam_restart）
with slam_lock:
    slam_kill()
    with map_lock:   ...
    with robot_lock: ...
    with cov_lock:   ...
```

★ 這裡是巢狀的，但**安全**，因為：
1. `slam_lock` 只被 `slam_restart` 一個地方使用
2. 內層三把鎖是**依序取得再放開**，不是同時持有
3. 沒有任何地方會「先拿 map_lock 再拿 slam_lock」

## 17.4 ★★ 核心設計：「回呼只存不算」

```python
# scripts/map_server.py:210-214
def scan_callback(msg):
    """收到 /scan 時僅保存最新一筆，轉換到地圖座標延後到 /scan 路由處理。"""
    global scan_msg
    with scan_lock:
        scan_msg = msg
```

### 為什麼回呼不能做重運算

```
   /scan 以 5 Hz 進來 ──→ [ROS 佇列 queue_size=1] ──→ scan_callback
```

★ **ROS 的回呼是「序列化」執行的**（同一個訂閱者的回呼不會並行）。
如果 `scan_callback` 要跑 300 毫秒：

```
   T=0.0  訊息 1 到達，開始處理
   T=0.2  訊息 2 到達 → 進佇列
   T=0.3  訊息 1 處理完，開始處理訊息 2
   T=0.4  訊息 3 到達 → 佇列滿（queue_size=1）→ ⚠ 訊息 2 被擠掉？不，訊息 3 擠掉訊息 2
   ...
```

**後果**：
1. **一直處理過期的資料**（永遠落後一拍以上）
2. **大量訊息被丟棄**
3. ⚠ **更嚴重的是：如果回呼裡持有鎖，會拖累所有讀取者**

### 三個回呼的「算」與「不算」

| 回呼 | 算不算 | 為什麼 |
|---|---|---|
| `scan_callback` | ❌ **完全不算** | 消費頻率（0~1 Hz）< 產生頻率（5 Hz）→ 在路由算（第 14 章 14.5） |
| `odom_callback` | ⚠ **算一點點** | 只有一個平方距離比較（`dx*dx+dy*dy >= 0.01`），微秒級 |
| `map_callback` | ✅ **算很多** | 3 次形態學 + 4 次 PNG。因為結果**被 4 個路由共用**，在回呼算才划算 |

★ **`map_callback` 是刻意的例外**，判準還是「消費頻率 vs 產生頻率」：
`/map` 只有幾 Hz，而它的產物被四張圖片路由 + 兩個 JSON 路由消費。

```python
# scripts/map_server.py:203-207（odom_callback 的輕量計算）
dx, dy = rx - robot_path[-1][0], ry - robot_path[-1][1]
if dx*dx + dy*dy >= 0.01:   # 每 0.1 m 記一點
```

★ **不開根號**是刻意的：`sqrt` 比乘法慢，而且比較 `d² >= 0.1²` 和
比較 `d >= 0.1` 完全等價。`/odom` 是 30 Hz，每秒省 30 次 `sqrt`。

## 17.5 幾個關鍵的併發模式

### 模式一：檢查與動作在同一把鎖裡

```python
# ✅ scripts/map_server.py:455-457
with cov_lock:
    if cov_status['state'] == 'running':
        return jsonify({'ok': False, 'msg': '已在執行中'})
```

★ 檢查和「不執行」在同一個臨界區。

⚠ **但注意**：`coverage_start` 的檢查（455 行）和真正設定 `running`（494 行）
**不在同一把鎖裡**（中間有 200 ms 的規劃）。

理論上兩個並發的 `/coverage/start` 都可能通過檢查 → 開出兩個執行緒。

**實務上為什麼沒事**：
1. 前端按下按鈕後立刻 `disabled = true`（`web/index.html:403`）
2. 兩個請求要在 200 ms 內同時進來才會撞上
3. 就算撞上，兩個 `run_coverage` 會搶同一個 `cov_status`，
   第二個會在第一次停止檢查時看到狀態不對而退出

★ **這是一個真實存在但影響很小的競態**。要修的話，
把 `state` 先設成一個中間狀態（例如 `planning`）再去規劃就好。

### 模式二：協作式取消

```python
# 呼叫方（Flask 執行緒）
with cov_lock:
    cov_status['state'] = 'stopped'

# 執行方（run_coverage 執行緒）
with cov_lock:
    if cov_status['state'] != 'running':
        client.cancel_all_goals()
        return
```

第 13 章 13.9 Q1 詳細講過：Python 沒有安全的殺執行緒方法，
必須讓執行緒**自己在安全的點檢查並退出**。

### 模式三：邊緣觸發

```javascript
// web/index.html:527-529
if (wasManual && !cov.manual) teleopRelease();
wasManual = cov.manual;
```

只在**狀態變化的那一刻**做動作，不是每次輪詢都做。

### 模式四：不可變物件天然安全

```python
with map_lock: d = map_png      # bytes 是不可變的
return _serve_png(d)            # 鎖外使用完全安全
```

★ `bytes`、`str`、`int`、`float`、`tuple` 都是不可變的。
拿到引用之後，**別人再怎麼重新綁定全域變數，我手上這份都不會變**。

這就是為什麼四條圖片路由的鎖裡只需要一行賦值。

## 17.6 ⑤ 設計決策

| 決策 | 選了 | 否決了 | 理由 |
|---|---|---|---|
| 併發模型 | 多執行緒 + 共享記憶體 | 多行程 + 訊息傳遞 | 正好需要共享狀態（第 04 章） |
| 鎖的粒度 | **五把細鎖**（按資料分組） | 一把大鎖 | 一把大鎖會讓地圖處理擋住遙控 |
| 鎖的宣告位置 | 緊接被保護的變數 | 集中宣告 | ★ 排版本身就是文件 |
| 臨界區 | 只做交換 | 連計算一起包 | 鎖持有時間直接等於別人的延遲 |
| 讀取 | 先複製再用 | 直接用引用 | 避免迭代中被修改、避免隱含依賴 |
| 多鎖 | 依序取得、不巢狀 | 巢狀持有 | 巢狀 = 死鎖風險 |
| 回呼 | ★ **只存不算**（`map_callback` 例外） | 都在回呼算 | 回呼是序列化的，算太久會塞住訂閱 |
| 取消 | 協作式（設旗標） | `thread.kill()` | Python 沒有安全的殺執行緒方法 |

## 17.7 ⚠ 已知的競態與風險

| # | 問題 | 影響 | 嚴重度 |
|---|---|---|---|
| 1 | `coverage_start` 的檢查與設定不在同一把鎖 | 極端情況可能開出兩個執行緒 | 低（前端已鎖按鈕） |
| 2 | `meta` 和 `robot_pos` 分開取，可能不同時刻 | 座標偏移幾像素 | 極低 |
| 3 | `_to_png` 在鎖裡（幾毫秒） | 圖片路由偶爾多等幾毫秒 | 極低 |
| 4 | `raw['data']` 是共用的 numpy 陣列 | 目前安全，但依賴「回呼不原地修改」的隱含約定 | ⚠ 中（未來改動會踩到） |
| 5 | `run_coverage` 是 `daemon=True` | 程式結束時不會 `cancel_all_goals()` | 低 |
| 6 | 多個使用者同時遙控 | 指令互相覆蓋 | 低（設計上未考慮多使用者） |

★ **第 4 項最值得注意**，因為它是「現在沒事，但未來改動會爆」的類型。
建議在 `map_callback` 加一行註解說明「這裡必須重新建立陣列，不可原地修改」。

## 17.8 ⑥ 本章重點回顧

1. **六條執行緒**：主（`rospy.spin`）、ROS 回呼、10 Hz Timer、TF Listener、
   Flask 執行緒池、`run_coverage`。
2. ★ **GIL 不保護你**：它只保證單一位元組碼原子，不保證一段邏輯原子。
   三種典型錯誤：讀到不一致的組合、迭代中被修改、檢查與動作被插隊。
3. ★ **五把細鎖，宣告位置緊接被保護的變數** —— 排版本身就是文件。
4. ★ **鐵律一：鎖裡只做交換，不做計算。** 鎖持有時間 = 別人的延遲。
5. ★ **鐵律二：讀取時先 `dict()` / `list()` 複製再用。**
   ⚠ 淺複製對可變元素（numpy 陣列）不夠，本專案靠「回呼永遠重建而非原地改」的約定。
6. ★ **鐵律三：不要巢狀持鎖。** 依序取得再放開，代價是資料可能來自不同時刻。
7. ★★ **「回呼只存不算」**：回呼是序列化執行的，算太久會塞住訂閱、丟訊息。
   `map_callback` 是刻意的例外（結果被 6 個路由共用）。
8. **`odom_callback` 用 `dx²+dy² >= 0.01` 不開根號** —— 30 Hz 下省下的 `sqrt`。

## 17.9 ⑦ 自我檢核題

**Q1. Python 有 GIL，為什麼還需要鎖？**

<details>
<summary>參考答案</summary>

**GIL 只保證「單一位元組碼指令」是原子的，不保證「一段邏輯」是原子的。**

執行緒可以在**任意兩個位元組碼指令之間**被切換走。

**例子一：讀到不一致的組合**

```python
map_png  = 新圖         # ← 執行緒可能在這裡被切走
map_meta = 新 meta
```

另一個執行緒此時讀到「新圖 + 舊 meta」→ 裁切偏移對不上 → 路徑畫錯位。

**例子二：檢查與動作之間被插隊**

```python
if cov_status['state'] != 'running':   # A 通過檢查，被切走
                                        # B 也通過檢查
    cov_status['state'] = 'running'     # A 設定
    start_thread()                      # B 也設定 → 兩個執行緒
```

**例子三：迭代中被修改**

```python
for p in robot_path:        # 另一個執行緒同時 append/pop
    ...                     # → RuntimeError: list changed size during iteration
```

★ **GIL 真正保證的只有「不會出現半個物件」這種記憶體層級的損壞** ——
它讓 Python 不會 segfault，但完全不保證**邏輯上的一致性**。

而且 GIL 是 CPython 的實作細節，不是語言規範。
</details>

**Q2. 為什麼 `scan_callback` 什麼都不做，而 `map_callback` 做了一大堆計算？
判準是什麼？**

<details>
<summary>參考答案</summary>

★ **判準是「消費頻率 vs 產生頻率」以及「結果會不會被共用」。**

| | `/scan` | `/map` |
|---|---|---|
| 產生頻率 | **5 Hz** | ~3 Hz |
| 消費者 | **1 個路由**（而且圖層已移除，實際 0） | **6 個路由**（4 圖片 + 2 JSON） |
| 消費頻率 | 0~1 Hz | 1 Hz × 6 |
| 決定 | **在路由算**（lazy） | **在回呼算**（eager） |

**`scan_callback` 如果在回呼算**：每秒白做 5 次 × 360 個點的三角函數 + TF 查詢，
而且沒人看的時候也一直做。更糟的是會拖慢 `/scan` 回呼 ——
`move_base` 和 gmapping 也訂閱 `/scan`，但它們是**不同節點**，不受影響；
影響的是我們自己的訂閱會開始丟訊息。

**`map_callback` 如果在路由算**：4 張圖片路由各自做一次形態學 + PNG，
等於做 4 遍同樣的事，而且**四張圖會來自不同時刻**，疊圖會對不上（第 14 章 14.9 Q1）。

★ **一般原則**：
- 結果**被多人共用** → 在產生端算一次（eager）
- 結果**只有一個消費者，而且消費比產生慢** → 在消費端算（lazy）
</details>

**Q3. 為什麼 `/robot_state` 要寫成兩個並列的 `with`，而不是巢狀？**

<details>
<summary>參考答案</summary>

```python
# ✅ 現在
with map_lock:   meta = dict(map_meta)
with robot_lock: pos  = dict(robot_pos); path_w = list(robot_path)

# ❌ 巢狀
with map_lock:
    with robot_lock:
        ...
```

**巢狀會製造死鎖的可能。**

如果專案裡有另一個地方寫成 `with robot_lock: with map_lock:`（相反順序），
就可能出現：

```
   執行緒 A: 拿到 map_lock，等 robot_lock
   執行緒 B: 拿到 robot_lock，等 map_lock
   → 永遠互等
```

⚠ **死鎖的症狀特別惡劣**：整個節點凍結，**沒有任何錯誤訊息、沒有 traceback**，
網頁完全沒反應，只能 kill 掉重來。而且可能跑一千次才發生一次。

**避免死鎖的兩種標準做法**：
1. **全域統一的取鎖順序**（永遠 map → robot → cov …）—— 要靠紀律維持
2. ★ **根本不要同時持有兩把鎖**（本專案的做法）—— 靠結構保證

第 2 種更安全，因為它不依賴任何人記得規則。

**代價**：`meta` 和 `pos` 可能來自不同時刻。
但 `/map` 只有幾 Hz、裁切偏移只在建圖初期變動，
座標最多差幾個像素，肉眼看不出來。**用一點精度換掉一整類 bug。**
</details>

**Q4. `with map_lock: d = map_png` 之後就放鎖了，後面用 `d` 完全不加鎖。
這樣安全嗎？如果 `map_png` 是一個 numpy 陣列呢？**

<details>
<summary>參考答案</summary>

**`map_png` 是 `bytes` → 完全安全。**

`bytes` 是**不可變物件**。拿到引用之後，就算 `map_callback` 立刻把全域變數
`map_png` 重新綁定到一張新圖，**我手上的 `d` 還是指向舊的那份 bytes，
而且那份 bytes 的內容永遠不會改變**。

★ 不可變物件天然執行緒安全 —— 這就是為什麼四條圖片路由的鎖裡只有一行賦值。

**如果是 numpy 陣列就不一定安全。**

numpy 陣列是**可變**的。分兩種情況：

1. **寫入者每次重建新陣列再重新綁定**（本專案的做法）：
   ```python
   map_data = dict(data=np.array(...), ...)   # 建新的，綁定新的
   ```
   → 安全。我手上的舊陣列不會被動到。

2. ⚠ **寫入者原地修改**：
   ```python
   map_data['data'][:] = 新資料               # 原地改
   ```
   → **不安全**。我正在讀的陣列被改到一半，會拿到新舊混合的資料。

`/coverage/start` 的 `raw = dict(map_data)` 落在情況 1，**目前是安全的**。
但這是一個**隱含的約定**（第 17.7 的風險 #4）——
如果哪天有人把 `map_callback` 改成原地更新（為了省記憶體），
就會出現「規劃時偶爾拿到半新半舊的地圖」的詭異 bug。

★ **建議**：在 `map_callback` 加一行註解說明「必須重建陣列，不可原地修改」，
或在 `coverage_start` 做 `raw['data'].copy()`（多一次記憶體複製，但徹底安全）。
</details>

**Q5. 假設你在展示時遇到一次「網頁上的覆蓋路徑整體偏移了」，重新整理就正常了。
你會怎麼查？**

<details>
<summary>參考答案</summary>

★ **「重跑就好」是併發問題的典型指紋。** 先假設它是競態，而不是邏輯錯誤。

**第一步：確認嫌疑範圍**

「路徑偏移」代表 `path_px` 的座標算錯了。它只依賴兩樣東西：
- `cov_path`（世界座標的路點）
- `meta`（`origin_x/y`、`resolution`、`r0`、`c0`、`crop_h`）

路點在執行期間不會變，所以**嫌疑集中在 `meta`**。

**第二步：找 `meta` 可能不一致的地方**

```python
# scripts/map_server.py:509-521
with cov_lock:
    st = dict(cov_status); path_w = list(cov_path); ...
with map_lock:
    meta = dict(map_meta)              # ← 這裡的 meta
...
st['path_px'] = [world_to_px(x, y, meta) for x, y in path_w]
```

★ **兩把鎖是分開取的**（第 17.3 鐵律三）。
在 `cov_lock` 放開之後、`map_lock` 拿到之前，`map_callback` 可能更新了地圖。

**但這其實不是問題** —— `path_w` 是世界座標，和 `meta` 新舊無關，
用新 `meta` 換算反而是對的（因為前端拿到的圖片也是新的）。

**第三步：找真正的嫌疑犯 —— 圖片和 meta 的不同步**

```javascript
// web/index.html:558-565
const [, robotRes, covRes] = await Promise.allSettled([
    Promise.all([...抓圖片...]),        // ← 請求 A
    fetch('/robot_state'),               // ← 請求 B
    fetch('/coverage/status'),           // ← 請求 C
]);
```

★ **三組請求是並行發出的，中間可能間隔幾十毫秒。**
如果地圖剛好在 A 和 C 之間更新（裁切範圍變了）：
- 圖片是**新的**（`c0` 變小了，圖變寬）
- `path_px` 用的也是**新的** meta

★ 兩邊都是新的，其實對得上。但如果反過來（C 先回、A 後回），
就是「舊 meta 算的座標 + 新圖片」→ **偏移**。

**第四步：驗證**

在 `/coverage/status` 和 `/map.png` 都加一個 `map_version` 計數器
（`map_callback` 每次 +1），前端比對；不一致就記錄下來。
跑十分鐘看有沒有觸發。

**修法**：讓 `/coverage/status` 一併回傳 `map_version`，
前端只在 version 一致時才畫路徑，否則沿用上一幀。

（這就是第 14 章 14.7 ① 記錄的已知問題。）
</details>
