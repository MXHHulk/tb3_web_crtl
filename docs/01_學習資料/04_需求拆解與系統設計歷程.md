# 第 04 章　需求拆解與系統設計歷程

> **本章是全書樞紐。** 前三章講的是「外面已經有什麼」，從這章開始講「我們自己做了什麼決定」。
>
> 本章要回答一個問題：**從一句話需求，怎麼一步步推導出現在這四個檔案的架構？**
> 不是講「架構長怎樣」（那是第 0 章的圖），是講**推導過程**——
> 每一步面對什麼選擇、為什麼選這個。

---

## 4.1 ① 出發點：一句話需求

```
讓一台 TurtleBot3 自己把一個未知的房間走遍，過程中即時建圖，
而且我可以用手機或筆電開網頁看它現在在哪、規劃了什麼路徑、走到第幾步。
```

### 第一步：把「一句話」翻譯成「可驗證的功能」

需求裡的每個詞都要逼問一次：

| 原文 | 逼問 | 得到的具體功能 |
|---|---|---|
| 「未知的房間」 | 未知到什麼程度？ | 開機時沒有任何地圖，要邊走邊建 → **需要 SLAM** |
| 「走遍」 | 什麼叫走遍？ | 機器人的清掃寬度掃過每一格可走區域 → **需要 CCPP 演算法** |
| 「自己」 | 完全自動？ | 按一個鈕就自己跑完，但要能中途叫停 → **需要任務狀態機** |
| 「即時建圖」 | 多即時？ | 網頁上看得到地圖在長大 → **地圖要能持續更新並輸出** |
| 「用手機開網頁」 | 誰跑網頁？ | 機器人自己當伺服器，手機只要瀏覽器 → **機器人上要有 HTTP server** |
| 「它現在在哪」 | 位置怎麼來？ | 訂閱里程計 + SLAM 定位 |
| 「規劃了什麼路徑」 | 要看到什麼？ | 路徑、cell 分解結果、演算法診斷數字 |
| 「走到第幾步」 | 進度怎麼算？ | 路點索引 / 總路點數 |

### 得到的功能清單

```
F1  建圖與定位（未知環境）
F2  覆蓋路徑規劃（核心貢獻）
F3  路徑執行 + 避障
F4  任務控制（開始 / 停止 / 進度 / 錯誤）
F5  網頁即時顯示（地圖、位置、路徑、cell）
F6  手動遙控（測試與救援用）★ 需求裡沒寫，但實際做起來一定需要
F7  重新建圖（換場地時用）★ 同上
```

> 💡 F6、F7 是**需求裡沒有、但實作時一定會發現需要**的功能。
> F6：機器人卡在角落時要能手動推出來；測試時要能把它擺到指定起點。
> F7：改變場地擺設後，舊地圖是髒的，總不能每次都整包重開。
>
> **這種「需求裡沒寫但一定要有」的功能，通常在做到一半才會浮現。**
> 本專案的開發日志（`docs/05_開發日志/CHANGELOG.md`）記錄了它們是後來才加的。

## 4.2 ② 直覺做法：全部寫在一支 Python 裡

最直覺的想法是這樣：

```python
# mega_robot.py —— 一支搞定
import rospy, flask, numpy

def main():
    rospy.init_node('robot')
    rospy.Subscriber('/scan', LaserScan, on_scan)
    rospy.Subscriber('/odom', Odometry, on_odom)

    while True:
        update_slam()          # 建圖 + 定位
        if need_replan:
            path = plan_coverage()
        v, w = follow_path(path)
        avoid_obstacles(v, w)
        publish_cmd_vel(v, w)
        serve_web_requests()   # 順便處理網頁請求
```

看起來很乾淨。**但它不可能運作。**

## 4.3 ③ 撞牆：四個致命問題

### 問題一：頻率根本對不上

把每個功能的時間需求列出來：

```
   功能              需要的頻率        單次耗時
   ─────────────────────────────────────────────
   讀光達            5 Hz（被動）      —
   讀里程計          30 Hz（被動）     —
   SLAM 更新         5 Hz              ~50 ms
   局部避障輸出速度   20 Hz  ★         ~5 ms
   覆蓋路徑規劃      一次性            ~200 ms ★
   網頁請求          隨機（1 Hz）      ~10 ms
```

★ 兩個矛盾：**避障必須每 50 ms 輸出一次**，而**覆蓋規劃一算就是 200 ms**。

單迴圈的話，規劃跑的那 200 毫秒裡，避障輸出直接斷四拍。
機器人正在移動，收不到新速度指令會怎樣？TurtleBot3 的驅動有安全機制會停車，
但實際表現就是「一頓一頓」；更糟的情況是它保持舊速度繼續衝。

### 問題二：Flask 和 ROS 都想要主迴圈

```python
rospy.spin()          # 這一行不會返回
app.run()             # 這一行也不會返回
```

兩個都是「卡在這裡永遠不出來」的無限迴圈。**一支程式的主執行緒只能給一個。**

### 問題三：現成套件不是這個形狀

gmapping、move_base 都是**獨立的 ROS 節點**（而且是 C++ 寫的）。
你沒辦法把它們 `import` 進你的 Python 迴圈裡呼叫。
唯一的用法就是「讓它們自己當一個行程跑，透過話題溝通」。

**這一點直接否決了單行程架構** —— 除非你要自己重寫 SLAM 和導航，那是好幾個月的工程。

### 問題四：一個爆全部爆

覆蓋規劃如果吃到一張奇怪的地圖，`numpy` 丟了個例外出來，整支程式死掉 ——
連帶把 SLAM、避障、網頁全部帶走。機器人變成一塊磚。

## 4.4 ④ 推導架構：三個步驟

### 步驟 1：哪些東西「必須」是獨立行程？

由問題三直接決定：

```
   必須獨立         理由
   ─────────────────────────────────────────
   硬體驅動         現成套件（turtlebot3_bringup）
   SLAM             現成套件（gmapping），C++ 節點
   導航避障         現成套件（move_base），C++ 節點
```

這三個不用想，直接用 ROS 節點的形式跑。**專案的三分之二在這裡就解決了。**

### 步驟 2：現成 vs 自己寫的界線劃在哪？

這是**專題最重要的一個決定**。判準只有一個問題：

> **這件事是不是我的核心貢獻？**

| 功能 | 是核心貢獻嗎 | 決定 |
|---|---|---|
| SLAM 建圖定位 | ❌ 成熟領域，重寫沒有學術價值 | 用 gmapping |
| 點對點導航避障 | ❌ 同上 | 用 move_base + DWA |
| **覆蓋路徑規劃** | ✅ **這就是專題本身** | **自己寫** |
| 網頁監控介面 | ❌ 但沒有現成的能直接接我們的資料 | 自己寫（簡單版） |
| 任務執行與狀態管理 | ❌ 但是黏合層，必須自己寫 | 自己寫 |

> 💡 **設計決策：不要重造輪子，但要清楚知道自己的輪子是哪一個。**
> 如果連 SLAM 都自己寫，時間全部花在讓機器人「不撞牆」上，
> 真正的貢獻（覆蓋演算法）反而做不深。
> 反過來，如果連覆蓋規劃都用現成套件（例如 `full_coverage_path_planner`），
> 那這個專題就沒有東西可以講了。

### 步驟 3：剩下自己寫的部分，怎麼切？

自己要寫的東西剩下這些：

```
   A  地圖資料處理（OccupancyGrid → 可走格 / 圖片）
   B  覆蓋路徑規劃演算法          ★ 核心
   C  任務執行（把路點餵給 move_base、追進度、可停止）
   D  HTTP 伺服器（提供圖片與 JSON）
   E  手動遙控
   F  SLAM 生命週期管理
```

**候選架構一：每個功能一個 ROS 節點（最「ROS 風格」）**

```
   ┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐
   │ 地圖   │→ │ 規劃   │→ │ 執行   │  │ 網頁   │
   │ 節點   │  │ 節點   │  │ 節點   │  │ 節點   │
   └────────┘  └────────┘  └────────┘  └────────┘
```

看起來很漂亮，但推敲一下就發現問題：

- **網頁節點要顯示的東西橫跨所有節點**：地圖圖片在地圖節點、cell 分解在規劃節點、
  進度在執行節點。網頁節點得訂閱三個自訂話題，還要自己定義三種訊息型別。
- **「按下開始」這個動作要跨節點**：網頁收到 POST → 要通知規劃節點算 →
  算完通知執行節點跑。中間要用 Service 或 Action 串，**還要處理「規劃到一半使用者按停止」**。
- **狀態分散在四個地方**，「現在到底是不是執行中」沒有單一答案。

⚠ **這個架構的成本，全部花在「把資料搬來搬去」上，而不是花在演算法上。**

**候選架構二：全部一個節點（回到 4.2 的老路）**

已經被 4.3 否決 —— Flask 和 ROS 搶主迴圈、規劃阻塞避障。

**候選架構三（★ 本專案採用）：一個「胖樞紐」+ 一個「純演算法模組」**

```
   ┌──────────────────────────────────────────────┐
   │  map_server.py（一個 ROS 節點）              │
   │                                              │
   │   A 地圖處理   C 任務執行   D HTTP           │
   │   E 手動遙控   F SLAM 管理                   │
   │                                              │
   │   ↓ 直接函式呼叫（不經過 ROS）               │
   │  ┌────────────────────────────────────────┐  │
   │  │ coverage_planner.py                    │  │
   │  │   B 覆蓋演算法（純函式，零 ROS 依賴）  │  │
   │  └────────────────────────────────────────┘  │
   └──────────────────────────────────────────────┘
```

**為什麼這樣切？**

1. **A、C、D、E、F 全部需要共享狀態**（地圖、機器人位置、任務進度、模式）。
   放在同一個行程裡，就是幾個全域變數 + 幾把鎖的事；
   拆成不同行程，就要設計訊息型別、處理同步、處理節點掛掉。
   **共享狀態密集的東西，放在一起最便宜。**

2. **B 完全不需要共享狀態**。它是純函式：給我一個 bool 陣列，還你一串座標。
   沒有任何理由讓它知道 ROS 的存在。

3. **主迴圈衝突用「執行緒」解決，不用「行程」**：
   ```python
   # scripts/map_server.py:626-630
   threading.Thread(
       target=lambda: app.run(host='0.0.0.0', port=port, threaded=True, use_reloader=False),
       daemon=True,
   ).start()
   rospy.spin()
   ```
   Flask 丟到背景執行緒，主執行緒留給 `rospy.spin()`。兩個無限迴圈各得其所。

4. **規劃阻塞避障的問題自動消失**：避障是 `move_base` 這個**獨立行程**在做，
   我們的規劃跑 200 ms 完全不影響它。

> ★ **關鍵洞察：「一個節點 = 一件事」是 ROS 的建議，不是鐵律。**
> 真正的判準是**共享狀態的密度**。
> A/C/D/E/F 之間狀態糾纏很深，強行拆開只會製造大量搬運程式碼；
> B 完全獨立，就該徹底切出去。

## 4.5 分工的最終樣貌

```
 ┌─────────────────────────────────────────────────────────────┐
 │ 現成套件（三個獨立行程）                                    │
 │                                                             │
 │  turtlebot3_bringup ── /scan /odom ──→                      │
 │  gmapping ─────────── /map, map→odom TF ──→                 │
 │  move_base ────────── 收 Action 目標，發 /cmd_vel           │
 └──────────────────────────┬──────────────────────────────────┘
                            │ ROS 話題 / Action
 ┌──────────────────────────┴──────────────────────────────────┐
 │ map_server.py（一個節點，多執行緒）                          │
 │                                                             │
 │  ROS 回呼執行緒 ×3  ──→ 共享狀態（+ 5 把鎖）                │
 │  Flask 執行緒       ──→ 讀共享狀態，回 PNG / JSON           │
 │  run_coverage 執行緒 ──→ 送 Action 目標，更新進度           │
 │  rospy.Timer 10 Hz  ──→ 手動遙控心跳                        │
 │  subprocess          ──→ SLAM 生命週期                      │
 │                                                             │
 │            ↓ import + 直接呼叫                              │
 │  ┌───────────────────────────────────────────────────────┐  │
 │  │ coverage_planner.py                                   │  │
 │  │   plan(free, res, ox, oy, spacing, start) → dict      │  │
 │  │   純 numpy / scipy，零 ROS 依賴，可離線測試           │  │
 │  └───────────────────────────────────────────────────────┘  │
 └──────────────────────────┬──────────────────────────────────┘
                            │ HTTP（PNG + JSON）
 ┌──────────────────────────┴──────────────────────────────────┐
 │ web/index.html（瀏覽器，單檔）                               │
 │  每秒輪詢一次，Canvas 疊圖                                   │
 └─────────────────────────────────────────────────────────────┘
```

**自己寫的程式碼分量**：

| 檔案 | 行數 | 佔比 |
|---|---|---|
| `map_server.py` | 634 | 黏合層 + 網頁後端 |
| `coverage_planner.py` | 270 | ★ 核心演算法 |
| `web/index.html` | 587 | 前端 |
| `start.launch` | 78 | 組裝 |

⚠ 注意：**核心演算法只佔 270 行，不到四分之一。**
這是很正常的比例 —— 一個能跑的系統，大部分程式碼都是黏合、顯示、錯誤處理。
但答辯時要清楚指出「哪 270 行是我的貢獻」。

## 4.6 ⑤ 設計決策總表（被否決的方案）

| 決策點 | 選了什麼 | 否決了什麼 | 為什麼 |
|---|---|---|---|
| SLAM | gmapping | 自己寫 | 不是核心貢獻，成熟方案品質遠高於自己寫的 |
| 導航避障 | move_base + DWA | 自己寫 goto | 同上；而且避障做不好會毀掉整個 demo |
| 覆蓋規劃 | **自己寫** | 現成 CCPP 套件 | **這是專題本身，用現成的就沒東西可講** |
| 自寫程式的切分 | 一個胖節點 + 一個純模組 | 四個小節點 | 共享狀態密集，拆開的成本全花在搬資料 |
| 主迴圈衝突 | 執行緒（Flask 在背景） | 多行程 | 執行緒共享記憶體，正好符合共享狀態的需求 |
| 前端通訊 | HTTP 輪詢 | rosbridge + WebSocket | 見第 05 章 |
| SLAM 啟動 | `map_server` 子行程管理 | launch 檔 `<include>` | 要支援網頁「重新建圖」，見第 05 章 |

## 4.7 ⚠ 這個架構的代價

沒有免費的午餐。這個架構換來三個問題：

**① `map_server.py` 是個 634 行的胖檔案**

它同時是地圖處理器、HTTP 伺服器、任務執行器、遙控器、行程管理器。
違反「單一職責」原則，改動時要小心互相影響。

**緩解方式**：用註解分隔線把檔案切成清楚的區塊
（`# ════ 地圖處理 ════`、`# ════ 手動遙控 ════`…），
共享狀態集中宣告在檔案開頭並註明每把鎖保護什麼（第 17 章）。

**② 多執行緒 = 資料競爭風險**

五個執行緒讀寫同一批全域變數。忘記加鎖就會出現「偶爾才發生」的怪 bug。

**緩解方式**：五把鎖 + 一條鐵律「回呼只存不算」（第 17 章詳談）。

**③ 單點失效**

`map_server` 掛了，網頁、遙控、任務全部一起死。

**緩解方式**：所有 Flask 路由都做防禦性處理（地圖沒好回 503、TF 查不到回空陣列），
不讓單一功能的失敗擴散成整個節點崩潰。

## 4.8 ⑥ 本章重點回顧

1. **需求逼問**：把「一句話」裡的每個詞都追問一次，得到可驗證的功能清單。
   ⚠ 實作中一定會浮現需求裡沒寫的功能（本專案是手動遙控與重新建圖）。
2. **單行程架構被四件事否決**：頻率衝突（規劃 200 ms 會餓死 20 Hz 的避障）、
   Flask 與 ROS 搶主迴圈、現成套件是獨立行程、單點崩潰。
3. ★ **現成 vs 自寫的判準只有一個：這是不是我的核心貢獻。**
   SLAM 和導航用現成的，覆蓋規劃自己寫。
4. ★ **模組切分的判準是「共享狀態的密度」**，不是「一個節點一件事」。
   A/C/D/E/F 狀態糾纏 → 放一起；B 完全獨立 → 徹底切出去。
5. **主迴圈衝突用執行緒解，不用行程解** —— 因為我們正好需要共享記憶體。
6. **核心演算法只佔 270 行（不到 25%）**，其餘都是黏合層。這很正常，但要說得清楚。

## 4.9 ⑦ 自我檢核題

**Q1. 為什麼不把覆蓋規劃做成一個獨立的 ROS 節點，透過話題把路點傳給執行節點？
（`test/boustrophedon.py` 就是這樣寫的）**

<details>
<summary>參考答案</summary>

技術上完全可行 —— `test/boustrophedon.py` 正是這個做法（訂閱 `/map`，發布 `/coverage_path`）。
但它被降級成**測試工具**，不在執行路徑上。原因：

1. **狀態要跨節點同步**：按下「開始」時，網頁要知道規劃結果（cell 數、主軸角度）、
   執行進度、目前模式。這些狀態如果散在兩個節點，網頁後端得訂閱一堆自訂話題，
   還要自己定義訊息型別（`CoverageInfo.msg` 之類）。

2. **時序問題**：「規劃 → 執行」必須嚴格串接。話題是非同步的，
   執行節點怎麼知道收到的是「這次按下開始要跑的路徑」而不是上一次的殘留？
   要另外設計序號或用 Action 串。

3. **停止語意變複雜**：使用者按停止時，如果規劃節點正在算，要不要取消？
   單行程裡這只是一個布林變數。

4. **規劃本來就是一次性的**：不是持續串流的資料，用話題的模型本身就不對味。

`test/boustrophedon.py` 保留下來的價值是**在 RViz 裡檢視規劃結果**，
而且它和 `map_server.py` **共用同一份 `coverage_planner.py`**，
所以兩邊看到的路徑保證一致，不會有兩份會走鐘的複製品。
</details>

**Q2. 如果指導教授要求「你必須自己實作 SLAM」，這個架構要怎麼改？**

<details>
<summary>參考答案</summary>

**架構幾乎不用改，這正是分層的好處。**

自己寫的 SLAM 只要做到：訂閱 `/scan` 和 `/odom`，發布 `/map`（`OccupancyGrid`）
和 `map → odom` 的 TF。介面對上了，就可以直接把 gmapping 換掉：

```xml
<!-- 原本 -->
<include file="$(find turtlebot3_slam)/launch/turtlebot3_slam.launch" />
<!-- 換成 -->
<node pkg="turtlebot3_ccpp" type="my_slam.py" name="my_slam" />
```

`map_server.py`、`coverage_planner.py`、`web/index.html` **一行都不用動** ——
它們只認 `/map` 這個話題，不在乎是誰發的。

（`map_server.py` 的 SLAM 生命週期管理要改一下 `slam_launch()` 裡的指令字串，
`map_server.py:252-253`。這是唯一的耦合點。）

這就是第 01 章講的「話題完全解耦」的實際價值。
</details>

**Q3. 4.4 說「模組切分的判準是共享狀態的密度」。用這個判準檢查：
手動遙控（E）為什麼放在 `map_server` 裡，而不是拆成獨立節點？**

<details>
<summary>參考答案</summary>

因為遙控和任務執行**共用一個關鍵狀態：誰有權發 `/cmd_vel`**。

```python
# scripts/map_server.py:92
def manual_allowed():
    with cov_lock:
        return cov_status['state'] != 'running'
```

遙控要不要送速度，取決於覆蓋任務的狀態。這兩件事**在邏輯上就是綁在一起的**
（第 01 章 1.10 講的多寫入者問題）。

如果拆成獨立的遙控節點，它必須：
- 訂閱一個「目前模式」話題（要另外定義訊息型別）
- 處理「訊息還沒到就已經在發速度」的競態
- 處理「模式節點掛了怎麼辦」（fail-safe 該是允許還是禁止遙控？）

放在同一個行程裡，這些全部退化成 `cov_lock` 保護的一個字串比較。
**成本從「設計一套分散式協定」降到「一行 if」。**

反過來看第 21~23 章：`coverage_planner` 完全不碰任何共享狀態，
所以它切出去的成本是零，收益（可離線測試）是巨大的。
</details>

**Q4. 這個架構的三個代價（4.7）裡，你覺得哪一個最危險？為什麼？**

<details>
<summary>參考答案</summary>

**多執行緒的資料競爭最危險**，因為它是唯一會產生「偶發、無法重現」的問題。

- **胖檔案**：只是難維護，症狀是「改 A 弄壞 B」，但一定會在測試時被發現。
- **單點失效**：症狀很明顯（整個網頁掛掉），一看就知道要修哪裡。
- **資料競爭**：可能跑 100 次都正常，第 101 次在展示的時候出現一次莫名其妙的
  「地圖畫到一半」或「進度倒退」。而且**你重跑一次它就好了**，根本無從查起。

典型場景：`map_callback` 正在寫 `map_png`，Flask 執行緒同時在讀它，
讀到一半的 bytes → 網頁顯示破圖。或者 `world_to_px` 用的 `meta` 是舊的、
`map_png` 是新的，路徑就會整個偏掉。

本專案的防線是「**每一個共享變數都明確歸屬某一把鎖**」，
而且**讀的時候先整個複製出來再用**：

```python
# scripts/map_server.py:423-424
with map_lock:  meta = dict(map_meta)     # 複製，不是引用
with scan_lock: msg = scan_msg
```

這樣鎖只持有極短的時間，後面的計算完全不需要鎖。第 17 章詳談。
</details>
