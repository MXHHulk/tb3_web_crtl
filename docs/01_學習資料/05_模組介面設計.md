# 第 05 章　模組介面設計

> 第 04 章決定了「切成哪幾塊」，本章決定「塊與塊之間怎麼講話」。
>
> 介面設計比模組切分更重要 —— **切錯了還能重切，介面訂錯了整個系統會慢慢腐爛。**
> 本章的主軸是四個**被否決的設計**，每一個都講清楚：它看起來為什麼合理、
> 實際上會出什麼事、我們改用什麼。

---

## 5.1 ① 問題：介面該訂什麼

模組之間有三件事要談清楚：

```
   ① 資料格式    我傳什麼給你？型別是什麼？
   ② 依賴方向    誰認識誰？（★ 最重要）
   ③ 失敗語意    出事的時候回什麼？
```

第 ② 點最容易被忽略，但它決定了系統能不能演進。

**依賴方向的鐵律：**

> **底層不可以認識上層。**
> 演算法不該知道 ROS 存在；ROS 節點不該知道網頁存在；網頁不該知道 `move_base` 存在。

違反了會怎樣？舉例：如果 `coverage_planner.py` 裡有一行 `import rospy`，
那你就永遠不能離線測試它 —— 第 21~23 章的所有數據都不可能拿到。

---

## 5.2 ★ 核心介面：`plan()` 的簽名

整個專案最重要的一條介面線，是 `map_server` 和 `coverage_planner` 之間這一行：

```python
# scripts/coverage_planner.py:188
def plan(free, res, ox, oy, spacing=SPACING, start=None):
```

### 輸入：四個基本型別，零 ROS

| 參數 | 型別 | 意思 |
|---|---|---|
| `free` | `np.ndarray[bool]` (H×W) | `True` = 可行走 |
| `res` | `float` | 每格幾公尺 |
| `ox`, `oy` | `float` | 地圖原點的世界座標 |
| `spacing` | `float` | 掃描線間距 |
| `start` | `(float, float)` 或 `None` | 機器人起點 |

★ **注意 `free` 是「已經處理好的」bool 陣列，不是原始的 `OccupancyGrid`。**
「怎麼從 `OccupancyGrid` 變成 `free`」這件事被刻意留在呼叫方：

```python
# scripts/map_server.py:468-469
safe = apply_safety_margin(raw['data'], COV_MARGIN, meta['resolution'])
free = (raw['data'] == 0) & ~safe
```

這是一個關鍵決定。如果 `plan()` 直接吃 `OccupancyGrid`：
- 它就得 `import nav_msgs` → **不再是零 ROS 依賴**
- 測試時得偽造一個 `OccupancyGrid` 物件，而不是隨手做一個 numpy 陣列
- 「未知格算不算可走」這個政策就被鎖死在演算法裡，呼叫方無法調整

### 輸出：一個 dict，而不是只有路點

```python
# scripts/coverage_planner.py:206-213（docstring）
return {'waypoints': [...],   # [(x, y), ...] 依序走訪的路點
        'cells':     [...],   # [[(x, y), ...], ...] 各 cell 的路點
        'axes':      (center, axis_a, axis_b, eigvals),
        'n_runs':    int,     # 連通區間總數
        'critical':  [...]}   # [(run 序號, 'split'/'merge'), ...]
```

只回傳 `waypoints` 就夠機器人走了，但網頁要顯示 cell 分解、主軸角度、λ 比值。

> 💡 **設計取捨**：回傳「診斷資訊」讓演算法的介面變胖了，
> 但它換來一個巨大的好處 —— **演算法變成可觀察的**。
> 網頁上直接看得到「這次分解出幾個 cell、主軸幾度、λ₁/λ₂ 多少」，
> 出問題時一眼就知道是 PCA 歪了還是分解爆了。
>
> 一個看不見內部狀態的演算法，除錯只能靠瞎猜。

### 還有一個向後相容的薄包裝

```python
# scripts/coverage_planner.py:262-270
def boustrophedon(free, res, ox, oy, spacing=SPACING, start=None):
    return plan(free, res, ox, oy, spacing=spacing, start=start)['waypoints']
```

`test/boustrophedon.py` 只需要路點，用這個簽名比較乾淨。
**兩個呼叫者、同一份實作**，不會有走鐘的複製品。

## 5.3 ❌ 被否決的設計一：讓 `coverage_planner` 自己訂閱 `/map`

### 這個想法看起來為什麼合理

「規劃需要地圖，那就讓它自己去拿啊。」

```python
# ❌ 假想的寫法
class CoveragePlanner:
    def __init__(self):
        rospy.Subscriber('/map', OccupancyGrid, self.on_map)
    def on_map(self, msg):
        self.free = ...
    def plan(self):
        ...
```

呼叫方變得更簡單：`planner.plan()`，連參數都不用傳。

### 為什麼否決

| 問題 | 後果 |
|---|---|
| **不能離線測試** | 要測一個 L 形房間，得先啟動 roscore、寫一個假的 `/map` 發布者、等它收到 |
| **不能重現** | 每次測試拿到的地圖不一樣（SLAM 一直在更新），數據沒有可比性 |
| **時序不確定** | `plan()` 被呼叫時，`self.free` 是哪一刻的地圖？沒人說得準 |
| **兩個呼叫者會打架** | `map_server` 和 `test/boustrophedon.py` 各自建一個實例，各訂閱一次 `/map` |
| **政策被鎖死** | 「未知格算不算可走」「安全邊距多大」變成模組內部決定，外面改不了 |

### 實際的代價有多大

**第 21~23 章的整整三章，如果選了這個設計就寫不出來。**

現在的做法可以直接這樣測：

```python
# test/coverage_bench.py 的核心
free = (data == 0) & ~safe        # 自己合成一張地圖
r = plan(free, RES, ox, oy)       # 直接呼叫，不需要 ROS
```

12 種場地、瞬間跑完、結果完全可重現。這就是「零 ROS 依賴」的實際價值。

> ★ **通用原則：把「取得資料」和「處理資料」分開。**
> 一個函式如果既要去拿資料又要處理資料，它就沒辦法被單獨測試。

## 5.4 ❌ 被否決的設計二：用 rosbridge + roslibjs 做前端

### 這個想法看起來為什麼合理

ROS 生態有現成的 **rosbridge_suite**：它開一個 WebSocket 伺服器，
把 ROS 話題原封不動地轉成 JSON 丟給瀏覽器。前端用 **roslibjs** 就能直接訂閱：

```javascript
// ❌ 假想的寫法
const ros = new ROSLIB.Ros({ url: 'ws://robot:9090' });
new ROSLIB.Topic({ ros, name: '/map', messageType: 'nav_msgs/OccupancyGrid' })
    .subscribe(msg => drawMap(msg));
```

看起來又乾淨又「正統」，而且是**推播**不是輪詢，即時性更好。

### 為什麼否決

**① 資料量的問題最致命**

`/map` 的 `data` 是一維陣列，長度 = width × height。
一張 400×400 的地圖就是 **160,000 個數字**。
rosbridge 把它轉成 JSON 文字：

```json
{"data": [-1, -1, -1, 0, 0, 100, 0, ... 再 159993 個]}
```

粗估 **300~600 KB 的純文字**，而且瀏覽器還要 `JSON.parse` 它。
每秒一次的話，手機用 Wi-Fi 連過來會很吃力。

對照本專案的做法：後端直接把地圖壓成 **PNG**。同一張圖大約 **3~10 KB**
（灰階 PNG 對這種大片相同顏色的圖壓縮率極高），而且瀏覽器解碼 PNG 是原生的、硬體加速的。

**資料量差了兩個數量級。**

**② 前端要重做一次後端的工作**

如果前端拿到的是原始 `OccupancyGrid`，那「膨脹安全邊距」「產生侵蝕/膨脹圖層」
這些事就得在 JavaScript 裡再實作一次。

⚠ 更嚴重的是：**前端的實作和後端規劃用的實作可能不一致**，
畫面上顯示的安全邊距和演算法實際用的不是同一個東西 —— 這種 bug 極難發現。

本專案刻意避開這件事：

```python
# scripts/map_server.py:394-398
@app.route('/map_margin.png')
def get_map_margin():
    """規劃用安全邊距膨脹（與 coverage_planner 使用的完全相同）。"""
```

```python
# scripts/map_server.py:163（產生這張圖時）
# 規劃用安全邊距：直接呼叫演算法本身的函式，確保畫面與規劃完全一致
safe = apply_safety_margin(data, COV_MARGIN, msg.info.resolution)
```

★ **畫面上看到的紅色膨脹層，就是演算法真正用的那一份**，
因為它們呼叫的是**同一個函式**。這是「所見即所算」。

**③ 多一個必須安裝、必須啟動、可能掛掉的元件**

rosbridge 是另一個節點。它掛了網頁就死了，而且它的錯誤訊息在另一個終端機裡。

**④ 雙向控制反而更麻煩**

「按下開始 → 執行覆蓋」這個動作，用 rosbridge 得包成 ROS Service 或 Action。
用 HTTP 就是一行 `fetch('/coverage/start', {method:'POST'})`。

### 改用什麼：PNG + JSON + 1 Hz 輪詢

```
   後端                                    前端
   ─────────────────────────────────────────────────────
   /map.png          PNG（~5 KB）    ──→  <img> 直接畫
   /map_margin.png   PNG            ──→  colorize() 上色疊圖
   /robot_state      JSON（小）      ──→  位置 + 軌跡
   /coverage/status  JSON（中）      ──→  進度 + cell + 診斷
   /scan             JSON（~360 點） ──→  即時雷射圖層
```

★ **關鍵設計：座標轉換在後端做完。**

```python
# scripts/map_server.py:520-522
st['path_px']  = [list(world_to_px(x, y, meta)) for x, y in path_w]
st['cells_px'] = [[list(world_to_px(x, y, meta)) for x, y in c] for c in cells]
```

前端拿到的是**已經換算成圖片像素**的座標，
直接 `ctx.moveTo(p[0], p[1])` 就能畫，完全不需要知道世界座標、解析度、原點、裁切偏移。

**前端因此變得極度單純**：它只做「畫圖」和「送指令」，一行座標數學都沒有。

> 💡 **代價**：1 Hz 輪詢的即時性不如 WebSocket 推播。
> 但監控一台最高 0.22 m/s 的機器人，1 秒延遲完全可以接受
> —— 機器人一秒最多移動 22 公分。
> **需求決定技術，不是技術決定需求。**

## 5.5 ❌ 被否決的設計三：SLAM 由 launch 檔啟動

### 這個想法看起來為什麼合理

這是**教科書標準做法**，99% 的 ROS 專案都這樣寫：

```xml
<!-- ❌ 標準但不夠用的寫法 -->
<include file="$(find turtlebot3_slam)/launch/turtlebot3_slam.launch">
    <arg name="slam_methods" value="gmapping" />
</include>
```

一行搞定，而且 `roslaunch` 會幫你管理它的生命週期。

### 為什麼否決：一個需求打死它

**F7：換場地擺設後要能重新建圖。**

如果 SLAM 由 launch 啟動，「重新建圖」的唯一辦法是：

```
   Ctrl+C 停掉整個 roslaunch
   → 硬體驅動、move_base、我們的 map_server 全部一起死
   → 重新 roslaunch
   → 等三十秒讓所有東西重新初始化
   → 網頁連線斷掉，要重新整理
```

⚠ **只是想清空一張地圖，卻要把整個系統重開。**

### 改用什麼：`map_server` 用子行程管理 SLAM

```python
# scripts/map_server.py:249-255
def slam_launch():
    """以子行程啟動 SLAM（獨立行程群組，方便整組收掉）。"""
    global slam_proc
    cmd = ['roslaunch', 'turtlebot3_slam', 'turtlebot3_slam.launch',
           f"slam_methods:={slam_cfg['method']}", 'open_rviz:=false']
    rospy.loginfo('[slam] 啟動：%s', ' '.join(cmd))
    slam_proc = subprocess.Popen(cmd, preexec_fn=os.setsid)
```

★ **`preexec_fn=os.setsid` 是這一行的靈魂。**

`roslaunch` 自己會再開好幾個子行程（`slam_gmapping`、`robot_state_publisher`…）。
如果只 kill `roslaunch` 本身，那些孫行程會變成孤兒繼續跑，
下次啟動就會有兩個 gmapping 在搶著發 `/map`。

`os.setsid` 讓子行程成為**新的行程群組組長**，
之後就能用 `os.killpg` 一次收掉整棵樹：

```python
# scripts/map_server.py:258-276
def slam_kill(timeout=10.0):
    """對整個行程群組送 SIGINT，讓 roslaunch 正常收尾。"""
    try:
        os.killpg(os.getpgid(slam_proc.pid), signal.SIGINT)   # ① 先禮
        slam_proc.wait(timeout=timeout)
    except subprocess.TimeoutExpired:
        rospy.logwarn('[slam] SIGINT 逾時，改送 SIGKILL')
        os.killpg(os.getpgid(slam_proc.pid), signal.SIGKILL)  # ② 後兵
        slam_proc.wait(timeout=5.0)
    finally:
        slam_proc = None
```

**先 SIGINT 後 SIGKILL** 是標準的收行程禮儀：
SIGINT 等同 Ctrl+C，讓 `roslaunch` 有機會正常關閉它的孩子；
10 秒還不死才動用 SIGKILL 強制終結。

### 留了一個後路

```xml
<!-- launch/start.launch:60-63 -->
<param name="manage_slam"  value="true" />
```

```python
# scripts/map_server.py:612-616
if slam_cfg['manage']:
    rospy.on_shutdown(slam_kill)     # ★ 節點結束時記得收掉 SLAM
    slam_launch()
else:
    rospy.loginfo('[slam] manage_slam=false，SLAM 由外部負責，/slam/restart 停用')
```

設成 `false` 就退回教科書做法（此時 launch 檔裡被註解掉的那段
`launch/start.launch:20-24` 要取消註解）。**保留退路，不把路走死。**

> ⚠ `rospy.on_shutdown(slam_kill)` 很重要：如果沒有這一行，
> 你 Ctrl+C 停掉 `map_server` 之後，gmapping 會變成孤兒繼續在背景跑。

## 5.6 ❌ 被否決的設計四：用 ROS Service 取代 HTTP 路由

### 這個想法看起來為什麼合理

「開始覆蓋」「停止」「重啟 SLAM」在語意上就是**一問一答的遠端呼叫**，
這正是 ROS Service 的用途：

```python
# ❌ 假想的寫法
rospy.Service('/coverage/start', Trigger, handle_start)
```

好處是可以用 `rosservice call /coverage/start` 從終端機測試，
也可以被別的 ROS 節點呼叫。

### 為什麼否決

**瀏覽器不會講 ROS。** 就這麼簡單。

如果用 Service，網頁還是得透過 HTTP 進來，然後 Flask 路由再去呼叫 Service：

```
   瀏覽器 ──HTTP──→ Flask 路由 ──ROS Service──→ 同一支程式裡的另一個函式
                                  ↑
                          繞了一大圈回到自己
```

**在同一個行程裡，用 Service 呼叫自己是純粹的浪費** ——
序列化、走網路堆疊、反序列化，只為了呼叫隔壁的一個函式。

### 改用什麼：HTTP 路由直接操作共享狀態

```python
# scripts/map_server.py:500-506
@app.route('/coverage/stop', methods=['POST'])
def coverage_stop():
    with cov_lock:
        if cov_status['state'] == 'running':
            cov_status['state'] = 'stopped'
    teleop_halt()
    return jsonify({'ok': True})
```

**停止一個任務 = 改一個字串。** 不需要任何協定。

> 💡 這正是第 04 章「共享狀態密集就放在一起」的紅利。
> 因為 Flask 和任務執行在同一個行程，控制介面退化成最單純的形式。

### 完整的 HTTP 介面（9 條路由）

```
   GET  /                    網頁本體（讀 web/index.html）
   GET  /map.png             原始地圖
   GET  /map_eroded.png      侵蝕（顯示用）
   GET  /map_dilated.png     膨脹（顯示用）
   GET  /map_margin.png      ★ 安全邊距（與規劃完全一致）
   GET  /robot_state         位置 + 軌跡（像素座標）
   GET  /scan                即時雷射點（像素座標）
   POST /coverage/start      規劃 + 開始執行
   POST /coverage/stop       停止
   GET  /coverage/status     進度 + cell + 診斷資訊
   POST /teleop              手動速度
   POST /slam/restart        重啟 SLAM
```

（第 14 章逐條拆解。）

## 5.7 依賴方向總圖

```
        允許的依賴方向（箭頭 = 「認識」）

   web/index.html
        │  只認識 HTTP 端點的網址與 JSON 欄位名
        ↓  ✅ 不知道 ROS、move_base、numpy 存在
   map_server.py
        │  認識 ROS、Flask、move_base、coverage_planner
        ↓
   coverage_planner.py
        │  只認識 numpy 和 scipy
        ↓  ✅ 不知道 ROS、Flask、地圖從哪來、路點要給誰
   numpy / scipy
```

**檢驗方法**：把上層整個刪掉，下層還能不能用？

| 刪掉 | 下層還能用嗎 |
|---|---|
| `web/index.html` | ✅ `map_server` 照常運作，用 `curl` 就能操作 |
| `map_server.py` | ✅ `coverage_planner` 照常運作，`test/coverage_bench.py` 就是證明 |
| ROS 整套 | ✅ `coverage_planner` 完全不受影響 |

反過來，**沒有任何一個下層模組需要上層存在才能運作**。這就是依賴方向乾淨的意思。

## 5.8 ⑥ 本章重點回顧

1. **介面要談三件事**：資料格式、依賴方向、失敗語意。其中 ★ **依賴方向最重要**
   —— 底層不可以認識上層。
2. ★ **`plan()` 的輸入是「已處理好的 bool 陣列」而不是 `OccupancyGrid`**，
   這一個決定換來了零 ROS 依賴、可離線測試、可重現的實驗。
3. **回傳 dict 而不只是路點**，讓演算法變成「可觀察的」——
   網頁上直接看得到 cell 數、主軸角度、λ 比值，除錯不用瞎猜。
4. ❌ **不用 rosbridge**：地圖走 PNG（~5 KB）而不是 JSON（~500 KB），差兩個數量級；
   而且座標轉換在後端做完，前端零數學。
5. ❌ **SLAM 不由 launch 啟動**：為了支援網頁重新建圖，改用 `subprocess` +
   `os.setsid` / `os.killpg` 自管，並保留 `manage_slam=false` 的退路。
6. ❌ **不用 ROS Service 做控制**：在同一行程裡呼叫自己是浪費，
   HTTP 路由直接改共享狀態即可。
7. ★ **「所見即所算」**：網頁上的安全邊距圖層，和演算法用的是**同一個函式**的輸出。

## 5.9 ⑦ 自我檢核題

**Q1. `plan()` 為什麼吃 `free`（bool 陣列）而不是直接吃 `OccupancyGrid`？
列出至少三個好處。**

<details>
<summary>參考答案</summary>

1. **零 ROS 依賴 → 可離線測試**：不用啟動 roscore、不用機器人，
   隨手做一個 numpy 陣列就能跑。`test/coverage_bench.py` 12 種場地瞬間跑完。
2. **可重現**：合成地圖每次都一模一樣，數據可以互相比較；
   真實 SLAM 地圖每一刻都不同，沒有可比性。
3. **政策留在呼叫方**：「未知格 `-1` 算不算可走」「安全邊距多大」
   由 `map_server.py:468-469` 決定，演算法不預設立場。
   想試「把未知格也當成可走」只要改呼叫方一行。
4. **介面更窄 → 更好懂**：函式簽名上看得出它需要的全部資訊，
   不會有「它偷偷從某個話題拿了什麼」的隱藏依賴。
5. **可重用**：`test/boustrophedon.py` 和 `map_server.py` 共用同一份實作。
</details>

**Q2. rosbridge 傳 `OccupancyGrid` 和本專案傳 PNG，資料量差多少？為什麼差這麼多？**

<details>
<summary>參考答案</summary>

一張 400×400 的地圖：

- **rosbridge JSON**：160,000 個數字轉成文字，每個數字加逗號約 2~4 個字元
  → **約 300~600 KB**
- **PNG**：約 **3~10 KB**

**差 50~100 倍。**

原因是 PNG 用了兩層壓縮：
1. 地圖是灰階，每格只要 1 byte（JSON 的 `"-1,"` 就要 3 個字元）
2. 地圖有大片連續相同的值（一整片未知、一整片空地），
   PNG 的 DEFLATE 對這種資料壓縮率極高

而且 **PNG 解碼是瀏覽器原生、硬體加速的**，
`JSON.parse` 一個 160,000 元素的陣列則會讓主執行緒卡頓。

⚠ 代價：PNG 是「已經渲染好的畫面」，前端拿不到原始的格子值。
但本專案的前端本來就不需要 —— 所有計算都在後端做完了。
</details>

**Q3. `subprocess.Popen(cmd, preexec_fn=os.setsid)` 裡的 `os.setsid` 是做什麼的？
拿掉會發生什麼事？**

<details>
<summary>參考答案</summary>

`os.setsid` 讓被啟動的子行程成為**新 session / 新行程群組的組長**，
它之後開的所有孫行程都會屬於這個群組。

**為什麼需要**：`roslaunch turtlebot3_slam ...` 自己還會再開好幾個行程
（`slam_gmapping`、`robot_state_publisher` 等）。

**拿掉的後果**：`slam_kill()` 裡的 `os.killpg(os.getpgid(pid), SIGINT)`
會把訊號送到 `map_server` 自己所在的行程群組 —— **等於自殺**。
就算改成只 kill `roslaunch` 本身（`slam_proc.kill()`），
那些孫行程也會變成**孤兒繼續跑**。

孤兒 gmapping 的症狀特別惡劣：
下次按「重啟 SLAM」會再開一個，變成兩個 gmapping 同時發 `/map`，
畫面上地圖會在兩張之間瘋狂閃爍，而且怎麼查都查不出原因
（`rosnode list` 會看到兩個，但名字被 anonymous 化了不明顯）。
</details>

**Q4. 後端把座標轉換成像素才傳給前端。如果反過來（傳世界座標，前端自己算）會有什麼問題？**

<details>
<summary>參考答案</summary>

前端得知道**四個東西**才算得出來：`resolution`、`origin_x/y`、裁切偏移 `r0/c0`、
裁切後高度 `crop_h`。轉換公式是（`map_server.py:352-356`）：

```python
px = (wx - origin_x) / resolution - c0
py = crop_h - ((wy - origin_y) / resolution - r0)
```

問題有四個：

1. **公式要在 JS 裡再寫一次** → 兩份實作，改了一邊忘了另一邊就錯位。
   特別是那個 `crop_h - (...)` 的**上下翻轉**（因為圖片 y 軸向下、世界 y 軸向上），
   極容易漏掉，症狀是路徑上下顛倒。
2. **裁切範圍會變**：`_crop()` 每次收到新地圖都重算，地圖長大時 `r0`/`c0` 會變。
   前端如果拿到的 `meta` 和圖片不同步（兩個 HTTP 請求之間地圖更新了），
   路徑就會整體偏移。後端在**同一把鎖裡**同時取 `meta` 和資料，沒有這個問題。
3. **多一組 API 欄位**要維護。
4. **前端從此有了數學**，就有了數學 bug 的可能。

現在的設計讓前端只剩兩件事：**畫圖**和**送指令**。
`web/index.html` 587 行裡沒有任何一行座標換算 —— 這不是巧合，是設計出來的。
</details>

**Q5. 5.7 的「刪掉上層，下層還能不能用」是一個檢驗依賴方向的方法。
用它檢驗：如果我想把這個專案的覆蓋演算法搬到一台完全不同的機器人（例如用 ROS 2 的），
要改哪些檔案？**

<details>
<summary>參考答案</summary>

**`coverage_planner.py` 一行都不用改。** 它只依賴 numpy 和 scipy，兩者在 ROS 2 底下一樣能用。

要改的是：

- **`map_server.py`**：`rospy` → `rclpy`，回呼註冊語法不同，
  參數宣告方式不同，`actionlib` → `rclpy.action`。大改。
- **`start.launch`**：ROS 2 用 Python 或 YAML 格式的 launch，要重寫。
- **`package.xml` / `CMakeLists.txt`**：ROS 2 的 Python 套件用 `setup.py` + `ament`。

**`web/index.html` 也一行都不用改** —— 它只認識 HTTP 端點和 JSON 欄位名。

這就是依賴方向乾淨的價值：**改動被侷限在「認識底層框架的那一層」**，
上下兩端都不受影響。如果當初讓 `coverage_planner` 自己訂閱 `/map`（5.3 的方案），
現在連演算法都要跟著改。
</details>
